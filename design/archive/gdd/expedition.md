## Summary

玩家点一次「发布任务」，队伍出村，游戏内若干小时后回来，带回一份材料；材料喂给村庄建造。
表面上是个按钮，实际上背后是性格、作息、结仇、磨洋工的合谋——同一支队伍两次出门能带回
完全不同的数。这套东西存在的理由只有一个：**它是村庄长大的唯一食粮**，所以它必须让玩家
觉得每一趟都跟自己有关，而不是点了就等结果。

> **本文档同时承担修复任务。** 现有实现有三处明确的缺陷（§ Known Defects），本文档给出
> 各自的处理方案，并标明哪些需要开发者拍板。

## Overview

玩家是村长。村庄要长大就要材料，材料不会自己长在村口，只能派人出去拿。玩家做的事是：
从花名册里点几个人凑成一队（最多 4 人），点「发布任务」，系统抽一个任务，队伍出发，
经过一段游戏内时间后回来结算，每个人各按概率带回自己那份，材料入库。

**任务的时长用游戏内小时**，所以一趟近活（北坡采石，3 小时）当天下午就回，一趟远活
（北境旧堡探查，11 小时）要跨过整个白天——玩家会看着村里的人一个个下线，而出去的那几个
还在路上。这是「你在经营一个真的地方」的第一层手感：**等待是有重量的**。

结算不是掷一次骰子就完了，每个人各掷一次。他带回来多少取决于他自己的力、速、性格，
还取决于这队人搭不搭（两个傲在一队会互相别劲），以及他会不会中途撂挑子（傲看不上粗活）
或者私藏一份（贪）。这些都不是随机噪音，是性格的读数——杂谈面板会把它们写成村里人在
说的话，而不是「张三 失败 掉落 0」。

## Player Fantasy

**你是发号施令的那个人，但村庄不是你的玩具。**

你点一次按钮，就有一群人从村口消失，烟囱半天不冒烟。你控制不了他们带回来多少——
你能控制的只有「派谁去」。于是真正的玩法是**看人**：谁今天在线，谁跟谁还没说开，
谁是那种会把石头少背两块回来的人。把最合适的人放进这一队，是你的乐趣；看着他们走回来
时报出不一样的数，是反馈。

三个具体情绪目标：

1. **押注感**。发任务那一刻应该有一点紧张——这队人配得对不对？
2. **等待的重量**。11 小时是实打实的 11 小时，村庄在旁边继续过日子，你什么也做不了。
3. **村里人的口吻**。杂谈里写的是「回来的时候天还没黑，背上 12 份石料，比要的还多」，
   不是「任务成功，获得石料 ×12」。玩家读到的应该是**村里人在讲村里的事**，不是面板在报数。

## Known Defects（本文档要处理的三处现存缺陷）

> 以下三条是实现层面的既有事实，不是设计意图。本节给出处理方案。

### 缺陷 1 — 六种材料只有一个数字

**现状**：`Job` 有 `Res` 字段（石料/泥土/杂物/布匹/木料/铁料），`Chronicle` 也按材料名
填进句子里，但 `Main.cs:35` 只有一个 `private int _mat`。采石和采买往同一个计数器里加数。
**后果**：材料名只活在文案里。村庄升级（`cost = 30 + tier*25`）吃的是一个没有成分的总池，
所以「去挖铁料升级村庄」和「去采石升级村庄」在数值上完全等价——**M3 依赖网建不起来**，
因为没有任何东西会因为缺铁而被卡住。

**处理方案**（Phase A，MVP 必修）：

1. 材料成为独立库存：`Dictionary<MaterialId, int>`，六个 `MaterialId`
   （`StoneSoil/Silt/Scrap/Cloth/Timber/Iron`）。
2. `Job` 声明产出哪种材料，结算时按 `job.MaterialId` 入对应计数器，**不共用**。
3. 升级消耗的仍是**总材料池** `TotalMaterials = Σ 六项`，扣除时按固定顺序
   （石料→泥土→杂物→布匹→木料→铁料）逐项扣，保证 UI 显示的库存和实际扣减永远一致。
   —— 这只是让六个计数器变真，**不给任何一种材料发明新的用途**。
4. `Pocketed` 同样按材料分开计数：说清是「谁在哪一趟、哪种材料」少了几份。
5. UI 与杂谈必须显示**分项**，不能只显示总数——否则玩家还是看不见六种材料的区别。

**需要拍板的部分**：村庄升级、试炼塔、防护罩这些下游到底吃**哪种材料**（见 OQ-1）。
Phase A 只保证库存是真的；「铁料卡住防护罩」这种设计要开发者点头才写。

### 缺陷 2 — 副本不是地方

**现状**：「北境旧堡探查」只是 `Jobs` 数组里的一行 `Job("北境旧堡探查","铁料",38,11h,Glory:true)`。
它有名字、有时长、有材料，**唯独没有位置**。玩家看不到队伍去了哪、走多远、那里有多危险，
`Chronicle.Places` 里那六个地名是随机填的（`PickPlace()`），和任务没有绑定关系。

**处理方案**（分两阶段，边界很重要）：

**Phase A — 让地点成为数据，并且看得见（不改变任何现有数值）**

1. 新增 `Site(Id, Name, TravelHours, Danger, IsDungeon)` 数据表，与六个任务**一一对应**：
   北坡 / 南渠 / 河滩 / 镇上 / 东林 / 北境旧堡（这六个名字已经在 `Chronicle.Places` 里，
   不是新发明的地名）。
2. `Job` 增加 `SiteId` 外键。杂谈里的 `{l}` 槽位改为**填任务绑定的地点**，
   不再随机——玩家从此能看出「他说北坡就是真去了北坡」。
3. `TravelHours` 全部先填 **0**，所以
   `Duration = Site.TravelHours + Job.WorkHours = Job.WorkHours`，
   **六个任务的总时长与今天完全一致**（3/5/4/6/7/11 小时）。这一阶段可以安全合入并验证。
4. `Danger` 与 `IsDungeon` 先**只用于显示**（UI 与杂谈），不进结算公式。
   理由见下方「为什么危险不立刻进公式」。

**Phase B — 危险参与结算（需要开发者先拍板，见 OQ-2）**

`game-brief` 的 M2 写的是「派弱队去危险副本，回来少了人」。但「少了人」属于
系统 #10「死亡与复活」（Vertical Slice，尚未设计），把减员塞进 MVP 会造出一个
没有规则支撑的死亡。**所以本 GDD 只声明接口，不实现减员**：
危险度在 Phase B 作为成功率修正项进入公式，减员作为 `Rule dependency` 指向 #10。

**为什么危险不立刻进公式（设计论证）**：现有的成功率公式已经叠了三层乘数
（基础 + 配合 + 性格）并以 0.95 封顶。再加一层乘数会让高配合高属性的莽小队
在危险副本里也照样 0.95，危险就变成了纯装饰。正确的做法是让危险**压上限**而不是压乘数
（提案见 OQ-2），这样「派精锐去硬骨头」才有意义，而精锐本身已经在上限附近——
两条轴会互相咬合，符合「建筑是网不是等级条」的思路。

**副本与普通营生的界线**：`IsDungeon = true` 当前只有北境旧堡。它同时也是唯一一个
`Glory = true` 的任务。**傲只拒 `Glory = false` 的活**——所以「傲抢着去副本」这条
开发者原话，目前是靠 `Glory` 标记实现的，而不是靠地点本身。地点化之后，
建议把判定改为 `Site.IsDungeon`（或 `Glory` 与 `IsDungeon` 二者取一），
避免出现「这是个副本但它不算有对手的活」这种自相矛盾的配置。此改动见 OQ-3。

### 缺陷 3 — 村长带队没有实现

**现状**：`OnTask()` 只用玩家在花名册上勾选的 `_squad`（上限 4，`SquadMax = 4`）。
村长本人不出现在任何队列里，`HeroAgent` 也没有村长的实例。

**处理方案**：

1. 队伍增加**一个独立的村长位**，与 4 个村民位并存（不占用村民位）。
   开发者说的是「**有时候**也会组织一些人去」——所以是一个显式的开关，不是每趟自动跟随。
2. **村长只去副本**：`Site.IsDungeon = false` 的任务村长不能加入。依据是原话只提到
   「组织一些人来**攻略副本**」，没有说村长去采石。（是否放宽见 OQ-4。）
3. **村长永远在场**：村民受时区作息约束，村长不受——他是玩家，不是被召唤的人。
   任何时候都可以点「我带队」。
4. **村长不计入工地劳力**：与现有规则一致（`TickBuild` 里队伍成员本来就不算工地人力），
   村长出门期间工地照常推进，但少了最多 4 个劳力——这是远行的真实代价，也是设计上的取舍。
5. 村长走**同一个成功率公式**，性格系数固定 `1.00`（他没有性格）。
6. 村长的 `Power` / `Speed` 从哪来是未决的（见 OQ-5）。MVP 建议用与村民同区间
   （10–49）的**固定值**，把接口先跑通；成长曲线交给系统 #13「村长升级线」。
7. 村长在村口面板上要有明确位置，让「我现在不在村」这件事一眼可见。

**注意**：`game-brief` 里这句话有两种读法——「自己带队」（村长是队伍一员）
和「组织人」（村长只是派活的人）。本文档按**前者**实现，因为 brief 原文写的是
「你作为村长，有时候**自己也会带人**去攻副本」——「带人去」意味着他在队伍里。
这个读法需要确认，见 OQ-4。

## Detailed Design

### Core Rules

#### 材料

| MaterialId | 显示名 | 产出任务 |
|---|---|---|
| `StoneSoil` | 石料 | 北坡采石 |
| `Silt` | 泥土 | 南渠挖渠 |
| `Scrap` | 杂物 | 河滩拾荒 |
| `Cloth` | 布匹 | 镇上门市采买 |
| `Timber` | 木料 | 东林伐木 |
| `Iron` | 铁料 | 北境旧堡探查 |

- R1 材料库存是**六个独立计数器**，一个都没有被合并。
- R2 `TotalMaterials` 是六个计数器之和，供村庄建造消耗；**它不替代那六个计数器**。
- R3 结算时材料只进 `job.MaterialId` 指定的那一个计数器。
- R4 私吞（见下）记在**该种材料**的 `PocketedBy[MaterialId]` 下，不影响其他五种。
- R5 开局材料 40（现有实现 `Main.cs:78` `_mat = 40`）在 Phase A 中按 `StoneSoil` 记入
  （首任务为北坡采石），保证开局升级进度不变。

#### 地点

- R6 `Site` 是数据不是字符串。任务通过 `SiteId` 指向地点；杂谈里的 `{l}` 填的是
  **该任务绑定的地点名**，不是随机地名。
- R7 `Duration = Site.TravelHours + Job.WorkHours`。Phase A 中全部 `TravelHours = 0`，
  所以时长与现有实现逐条相等。
- R8 `Danger` 在 Phase A 只显示，不进公式（见缺陷 2 · Phase B）。
- R9 `IsDungeon` 是副本的唯一判据，与任务是否「有对手」保持一致（见 OQ-3）。

#### 队伍与发布

- R10 队伍 = 最多 4 个村民 + 可选的村长。村民位与村长位分开计数。
- R11 只有 `OnDuty` 的人能进队伍：`AbsentDays <= 0`（没病、没打架）且此刻在线
  （作息判定）。点不在的人，杂谈会告诉他原因（「病了」/「18时（东8区）才上线」）。
- R12 **一次只能有一趟远征在外**（现有 `_pendingEnd` 语义）。发布按钮在外征期间禁用。
- R13 **队伍在外征期间冻结**。现有实现 `OnRosterClick` 没有检查 `Expending`，
  而 `ResolveExpedition` 用 `_squad.Where(h => h.Away)` 取人——**远征途中改队伍会改变
  已经出发的那一队的成员**。这是明确的缺陷，必须在 Phase A 一并修掉。
- R14 出发时把队伍成员的 `Away = true`，他们从村庄地图上消失，且不再计入工地人力。
- R15 配合系数在**出发那一刻**算定并锁定（现有行为）。远征途中新结的仇不影响本趟。

#### 傲与贪（性格在远征里的具体行为）

- R16 傲**只拒 `Glory = false` / `IsDungeon = false` 的活**，概率 40%。
  他不是不能干——他真干了，产量照给，只是速度慢（`WorkRate ×0.6`，村庄建造侧）。
- R17 拒活在**结算时**判定，现有实现如此：杂谈的顺序是「队伍出发」→「回来时发现傲撂挑子」。
  这在叙事上说得通（半路上嫌跌份），但玩家在出发时看不到谁会走。
  是否改为出发前决定见 OQ-6。
- R18 贪在**成功后**有 45% 概率私吞一份（数量见公式），私吞只影响本次入账，
  不影响他的成功率。杂谈里这件事永远写得含糊（「少多少，从来没人说得准」）。
- R19 「最少带回一个人」是硬保证：全部人失败时，强行把第一个出发的人判为带回。
  这与 brief 的「没有硬失败」一致。现状代码已实现（`good.Count == 0` 的兜底）。

#### 结算顺序（不可交换）

1. 取队伍成员（`Away` 为真者）→ 2. 傲拒活 → 3. 若全拒，兜底第一人 →
4. 逐人掷成功率 → 5. 若全败，兜底第一人 → 6. 逐人算产量 →
7. 贪掷私吞 → 8. 入账到 `job.MaterialId` → 9. 清 `Away` → 10. 写杂谈。

#### States and Transitions

| State | Entry Condition | Exit Condition | Behavior |
|---|---|---|---|
| `Idle` | 初始；或结算完成 | 玩家发布且至少 1 人 `OnDuty` | 发布按钮可用 |
| `Expedition` | `OnTask()` 成功 | `_clock.AbsoluteHour >= _pendingEnd` | 队伍 `Away`；不发新任务；工地照推 |
| `Resolved`（瞬时） | 到达 `_pendingEnd` | 同帧内走完全部结算 | 写杂谈、入账、清 `Away`，回到 `Idle` |

队伍成员个人状态（不影响远征推进，见 Edge Cases）：
`Online` / `Offline` / `Away` / `Absent`（病或打架）/`Slack` / `Restless`。

#### Interactions with Other Systems

| 对方系统 | 方向 | 交接内容 |
|---|---|---|
| 时间与作息 | 依赖 | 只读 `AbsoluteHour` 与 `IsOnlineAt(hour)`；远征自己**不推进**时间 |
| 性格系统 | 依赖 | 只读性格**系数**（1.15 / 1.10 / 1.00）与 `IsDungeon` 拒活规则；不读事件权重 |
| 配队与配合 | 依赖 | 只读配合系数与 `GrudgeWith`；不决定队伍怎么搭 |
| 村庄建造 | 双方 | 我们交出 `TotalMaterials`；对方扣材料时要求**逐项可追溯**（缺陷 1） |
| 杂谈 | 输出 | 每次结算产出 ≤5 条（出发 N 条 + 每人 1~2 条 + 回来 1 条） |
| 死亡与复活 #10 | 预留 | Phase B 的危险减员**尚未实现**，接口预留，MVP 不产出减员 |

## Formulas

> 全部公式与 `src/Main.cs` 的现状**逐条对齐**。Phase A 合入后，所有数值结果应与今天完全一致。

### F1 · 远征时长

```
Duration_hours = Site.TravelHours + Job.WorkHours
End_AbsoluteHour = Clock.AbsoluteHour + Duration_hours
```

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `Site.TravelHours` | float | 0 – 8（Phase A 全为 0） | 数据表 `sites` | 路上花的小时数 |
| `Job.WorkHours` | float | 3 – 11 | 数据表 `jobs` | 干活花的小时数 |
| `Duration_hours` | float | 3 – 19 | 计算 | 本趟远征总时长（游戏内小时） |
| `Clock.AbsoluteHour` | float | ≥ 0，无上限 | `WorldClock` | 绝对小时；跨天安全 |

**输出范围**：Phase A 为 `3 – 11` 小时。Phase B 批准后为 `3 – 19` 小时。
**边界情况**：跨越 `AbsoluteHour` 的 24 小时倍数是安全的，因为用的是绝对小时。
**单位换算**：`WorldClock.DayLength = 75s` 一天，即 **1 游戏内小时 = 3.125 真实秒**。

**算例**：Day 1，村庄时钟 14:00 → `AbsoluteHour = 23`。发布「北境旧堡探查」
（`WorkHours = 11`，`Site.TravelHours = 0`）→ `End = 23 + 11 = 34`
= Day 2 的 10:00。真实耗时 `11 × 3.125 = 34.4 秒`。

### F2 · 个人成功率

```
chance = (0.52 + (Power + Speed) / 300) × Cohesion × PersonalityMult
chance = Min(0.95, chance)
成功  ⟺  Random() < chance
```

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `Power` | int | 10 – 49 | `HeroFactory`（`10 + rng.Next(40)`） | 力 |
| `Speed` | int | 10 – 49 | `HeroFactory`（`10 + rng.Next(40)`） | 速 |
| `Cohesion` | float | 0.50 – 1.15 | F2a 查表 | 队伍配合系数 |
| `PersonalityMult` | float | 1.00 / 1.10 / 1.15 | 性格 | 莽 1.15 · 傲 1.10 · 贪 1.00 |
| `chance` | float | 0.2649 – **0.95**（封顶） | 计算 | 该人带回材料的概率 |

**输出范围推导**：
- 基础项 `0.52 + (20..98)/300` = **0.5867 – 0.8467**
- 最坏：`0.5867 × 0.50（有仇）× 1.00 = 0.2933`
- 最好：`0.8467 × 1.15（三人合拍）× 1.15（莽）= 1.1197` → **被 0.95 封顶**
- 所以实际范围是 **0.2933 – 0.95**

**边界情况**：
- 上限 0.95 是必要的——不封顶的话最优小队有 11.2% 概率「超额成功」，
  而这个系统里没有第二层判定来消费它。
- **下限 0.2933 意味着「一次都不成」是有可能的**，这是设计意图（brief：村里有敌人）。
  但 R19 的兜底保证本趟至少带回一个人的材料。
- 贪的系数是 `1.00`——贪的强项不是成功率，是产量和私吞（他的采集加成在 `WorkRate`
  那一侧，见村庄建造）。**不要因为「贪没有加成」就给他加一个**，那会破坏性格分工。

**算例**（三人队：莽 / 贪 / 傲 → 触发「边吵边干」`Cohesion = 0.88`）：

| 人 | Power+Speed | 基础 | ×0.88 | ×性格 | 结果 |
|---|---|---|---|---|---|
| 莽 | 30+25 = 55 | 0.7033 | 0.6189 | ×1.15 = **0.7118** | 71% |
| 贪 | 20+40 = 60 | 0.7200 | 0.6336 | ×1.00 = **0.6336** | 63% |
| 傲 | 40+35 = 75 | 0.7700 | 0.6776 | ×1.10 = **0.7454** | 75% |

假设实际掷出：莽成、傲成、贪败 → `good_count = 2`。

### F2a · 配合系数（查表，非公式）

按 `CohesionOf()` 的**判定顺序**求值，**第一个命中的分支生效**：

| 顺序 | 条件 | `Cohesion` | 杂谈 |
|---|---|---|---|
| 0 | 队内有人 `GrudgeWith` 队内另一人 | **0.50** | 「有仇」 |
| 1 | `memberCount == 0` | 1.00 | 「没人在村里」（此路不会发布） |
| 2 | `memberCount < 2` | 1.00 | 「一个人，没有配合可言」 |
| 3 | 傲 ≥ 2 | **0.55** | 「两个傲的挤在一队里，一路上几乎没说话。」 |
| 4 | 贪 ≥ 2 | **0.85** | 「两个贪的在一处，谁的绳索都不肯先递。」 |
| 5 | 傲 ≥ 1 且 莽 ≥ 1 | **0.88** | 「一个嫌慢一个嫌磨蹭，出工倒是一块出。」 |
| 6 | 傲 ≥ 1 且 贪 ≥ 1 | **0.95** | 「谁也看不上谁」 |
| 7 | 莽 ≥ 2 | **1.10** | 「两个莽的抢着往前冲。活干得快，也差点出事。」 |
| 8 | `memberCount >= 3` | 1.15 | 「还算合拍」 |
| 9 | 兜底（2 人，无以上命中） | 1.05 | 「正常」 |

> **⚠️ 这张表里有两条死分支 —— 实现缺陷，需开发者拍板。**
> 只有 3 种性格值（莽/傲/贪），逐一穷举后：
> - **第 8 行（1.15）永远走不到。** 要走到它，必须 `傲≤1 且 贪≤1 且 莽≤1`，
>   三人队就必然是「一傲一贪一莽」，而那会先命中第 5 行（傲+莽 = 0.88）。
> - **第 9 行（1.05）也走不到。** 两人队若要躲开第 5、6 行，得 `傲=0 且 贪=0`，
>   于是两人都是莽 → 先命中第 7 行（1.10）。
>
> 后果：**五人以下的任何队伍都不可能拿到 ≥1.05 的配合**，除非全是莽（1.10）。
> 配队这一层的天花板被意外压死了。修复方案见 OQ-7（本文档不给擅自决定，因为
> 三种改法对玩家的体感差异很大）。

### F3 · 个人产量

```
Yield_i = Job.Amt / good_count  +  Power_i / 8        （两项均为整数除法，向下取整）
```

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `Job.Amt` | int | 14 – 38 | 数据表 `jobs` | 该任务的总产量 |
| `good_count` | int | 1 – 4 | 结算 | 本趟带回材料的人数 |
| `Power_i` | int | 10 – 49 | `HeroAgent` | 该人的力 |
| `Yield_i` | int | **4 – 44** | 计算 | 该人带回的数量 |

**输出范围推导**：
- 最小：`14 / 4 + 10/8 = 3 + 1 = 4`
- 最大：`38 / 1 + 49/8 = 38 + 6 = 44`
- 队伍入账总计 `VillageTotal = Σ Yield_i`（对 `good` 中的人求和）：
  **最小 4，最大 176**（4 人全成、人人 Power 49、北境旧堡）

**边界情况**：
- **两项都是整数除法，向下取整。** `38 / 3 = 12`，三人分 38 份只分到 36，**2 份蒸发**。
  这是现有实现的行为，本文保持不变（改成分配余数是设计改动，见 OQ-8）。
- `Power / 8` 让「力大的人多拿」——所以**两个莽抢一队同一趟活，队内差距最大**。
  这正是配队的乐趣来源，不要削平。
- `Yield_i` **不乘配合系数**。配合只改成功率（能不能带回），不改带回多少。
- `good_count` 用的是**实际成功人数**，不是队伍人数——有人失败，剩下的人分得更多。
  这让「三个人里只回来一个」反而是大丰收，节奏上是有意为之的。

**算例**（接 F2：`北境旧堡` `Amt=38`，`good_count=2` = 莽 + 傲）：
- 莽：`38/2 + 30/8 = 19 + 3 = ` **22**
- 傲：`38/2 + 40/8 = 19 + 5 = ` **24**
- 队伍入账 `VillageTotal = 46` 铁料

### F4 · 私吞

```
if (personality == "贪" and Random() < 0.45):
    Pocketed_i = Max(1, Yield_i / 4)          // 整数除法
    Yield_i   -= Pocketed_i
    PocketedBy[MaterialId] += Pocketed_i
```

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `Pocket`Chance` | float | 0 – 1 | 常量 0.45 | 贪私吞的概率 |
| `Yield_i` | int | 4 – 44 | F3 | 私吞**前**的数量 |
| `Pocketed_i` | int | **1 – 11** | 计算 | 被私吞的数量 |

**输出范围**：`Yield_i/4` = 1（4/4）… 11（44/4），`Max(1,·)` 使下限恒为 1。
贪私吞比例恒在 **25% ± 取整误差**以内，且**永远不会吞光**——他一定还会交出大部分。

**边界情况**：
- `Max(1, ·)` 保证「Yield 很小也至少吞 1 份」——贪不会因为分到得少就完全不贪，
  这符合性格（他不会空手回来）。
- 私吞**只在成功后发生**。失败的贪不私吞（他没东西可吞）。
- 私吞不影响他的 `Yield` 判定顺序——先算产量，再扣私吞。
- 杂谈**不得写出具体数字**（「少几份」而不是「少 5 份」）——这既是文案规范，
  也是让玩家发现不了精确规则的留白。

**算例**（另一支队伍：`北境旧堡`，`good = 贪 + 傲`）
- 贪：`Yield = 38/2 + 20/8 = 19 + 2 = 21` → 掷中私吞：
  `Pocketed = Max(1, 21/4) = Max(1, 5) = 5` → 上交 `16`，`PocketedBy[Iron] += 5`
- 傲：`Yield = 24`，不私吞
- 入账 `VillageTotal = 16 + 24 = ` **40** 铁料（对比无私吞时的 45）
- 玩家可见的唯一线索：杂谈里一条「清点的时候短了几份铁料」。

### F5 · 傲拒活

```
P(refuse) = 0.40   当 Site.IsDungeon == false 且 personality == "傲"
P(refuse) = 0      当 Site.IsDungeon == true  （他抢着去）
```

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `P(refuse)` | float | 0 – 0.40 | 常量 0.40 | 傲撂挑子的概率 |
| `RefusedCount` | int | ≥ 0 | `HeroAgent` | 累计拒活次数（用于 UI/日志） |

**边界情况**：
- 拒活**不改变他的成功率公式**——他真去了，系数仍是 1.10。brief 明确：
  「撂了挑子也不等于不能干」。
- 若全队拒活，兜底把**第一个出发的人**判为去了（现有实现），避免空跑一趟。
- 判定发生在**结算时**，不在出发时。见 OQ-6。

### F6 · 材料入账

```
Materials[job.MaterialId] += Σ_{i ∈ good, after F4} Yield_i
TotalMaterials            = Σ_{six ids} Materials[id]
```

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `Materials[id]` | int | 0 – 无上限 | 本系统 | 单种材料的库存 |
| `TotalMaterials` | int | 0 – 无上限 | 计算 | 六项之和，供村庄建造消耗 |

**扣除顺序（Phase A 约定，待 OQ-1 确认）**：升级村庄扣 `30 + tier*25` 时，

这样 UI 上的分项数字与实际扣减永远对得上，玩家能自己验算。

## Edge Cases

| # | 场景 | 预期行为 | 理由 |
|---|---|---|---|
| E1 | 队伍里没人 `OnDuty`（全病 / 全离线） | 发布按钮不响应，不产生远征，不写杂谈 | 没有硬失败：村庄只是等一等 |
| E2 | 1 人队 | `Cohesion = 1.00`（"一个人，没有配合可言"）；`good_count ≤ 1` 时该人独吞全部产量 | 单人跑一趟是合法的，只是产量全归他 |
| E3 | 全员掷失败 | **兜底判第一人成功**（现有实现） | brief：「没有硬失败」。村庄不该被一次运气卡死 |
| E4 | 全员拒活（全是傲 + 粗活） | 兜底判第一人去了 | 否则一趟 11 小时白跑，玩家会认为按钮坏了 |
| E5 | **远征途中改队伍** | **Phase A 必须修**：外征期间队伍冻结，`OnRosterClick` 拒绝增减 | 现状 `_squad.Where(h => h.Away)` 会在结算时取到**中途塞进来的人**，而那个人从头到尾没出发——白捡材料 |
| E6 | 远征途中队员**生病 / 打架** | `VillageLife` 只筛 `AbsentDays <= 0`，不筛 `Away`，所以**远征中的人照样会被事件击中**（生病、结仇、磨洋工） | 状态一致。但**已锁定的配合系数不变**（R15）；他回来时若是「病假」状态，缺席天数照扣，不影响本趟入账 |
| E7 | 远征途中全村没人在线 | 不影响远征推进。时间照走，到点照结算 | 远征按绝对小时计时，不依赖在场人数 |
| E8 | 远征跨天 | 跨天照常跑 `VillageLife`（村庄自己过日子），远征照常计时 | 两件事互不阻塞——这是 M0 的地基 |
| E9 | 远征期间村庄升级 | 允许（现有实现 `OnUpgrade` 不检查 `Expending`）。材料照扣照扣 | 但远征回来会追加材料，可能让你刚扣完又够升级一次。不算 bug |
| E10 | `Job.Amt / good_count` 向下取整 | 余数蒸发（三人分 38 只得 36） | 保持现状。见 OQ-8 |
| E11 | 私吞发生在 `Yield = 4` 时 | `Max(1, 1) = 1`，贪上交 3 | 保证贪「不会空手回来」 |
| E12 | 材料加到上限 / 溢出 | 当前 int 无上限；若将来加背包上限，需定义溢出丢弃还是拒绝 | 现在不处理，见 OQ-1 |
| E13 | 村长带队时**全村只有他一人** | 允许。村长不是 `OnDuty` 判定的主体，他没有作息 | 他是玩家 |
| E14 | 村长在 `IsDungeon = false` 的任务里 | **不允许**（Phase A 硬规则） | 开发者原话只提「攻略副本」。见 OQ-4 |
| E15 | 配合表第 8、9 行 | **当前不可达**（见 F2a 说明） | 实现缺陷，需修。见 OQ-7 |
| E16 | 傲在远征中拒活，他人全成 | 正常结算；杂谈单独一条写他撂挑子 | 玩家能看出「傲又没去」 |

## Tuning Knobs

| Parameter | Current | Safe Range | Increase 的效果 | Decrease 的效果 |
|---|---|---|---|---|
| `base_chance` | 0.52 | 0.35 – 0.70 | 全员更稳，副本不再有风险 | 远征变dice roll，村长很快会放弃发任务 |

| `Site.Danger` | 待定 | 0 – 3 | 危险感更强（Phase B） | 副本失去风险 |
| `SquadMax` | 4 | 3 – 5 | 单趟上限高，但配合系数表要重算 | 人手更紧张 |
| `WorldClock.DayLength` | 75s | 45 – 120s | 一天变长（远征等待更有重量） | 一天变短 |

> 否则改哪两个都看不出效果。

## Acceptance Criteria

**测试者不需要仪表，只看屏幕就能判定。**

- [ ] **A1 · 材料是真的分开的**：连续发 3 次任务、命中不同材料任务后，顶栏出现
      **三种不同的数字**，且六个分项之和等于总数。对比现状：现在只会看到一个数字。
- [ ] **A2 · 杂谈里的地名是真的**：发「北坡采石」，杂谈里出现的地名**全部**是「北坡」，
      不会出现「东林」。发「东林伐木」，全部是「东林」。
- [ ] **A3 · 时长未变**：Phase A 合入后，同一队在同一钟点发布「北境旧堡探查」，
      仍在 **11 游戏内小时**后回村（DayLength 75s 时为 34.4 真实秒）。
- [ ] **A4 · 远征途中队伍冻结**：外征期间点击花名册上的**其他人**，队伍**不发生变化**，
      杂谈提示「还没回来」。结算时回来的人**正是出发时那几个人**。
- [ ] **A5 · 绝无系统词**：跑 20 次远征，全屏文本检索
      「成功/失败/获得/消耗/属性/奖励」——**0 命中**。
- [ ] **A6 · 至少带回一人**：连续 30 次远征，**每次**结算的杂谈里都有「{N}份{材料}」，
      没有任何一趟是全员空手。
- [ ] **A7 · 贪的私吞可读不可算**：跑 100 次，至少出现 1 次「清点的时候短了几份{X}」，
      但杂谈**从不给出具体短缺数量**。
- [ ] **A8 · 傲会拒、也会去副本**：连续 30 次发布粗活，至少 1 次傲撂挑子；
      连续 30 次发布「北境旧堡探查」，**傲一次都不拒**。
- [ ] **A9 · 配合表可观察**（修死分支之后）：三种配置各跑一次，
