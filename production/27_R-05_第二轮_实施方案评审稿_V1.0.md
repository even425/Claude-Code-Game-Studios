## 1. 审计结论（摘要）

| # | 结论 | 影响 |
|---|---|---|
| A1 | **单场遭遇胜率是唯一参数**：`PlaceholderCombat.PlaceholderHeroWinRate = 0.5`（`src/Application/PlaceholderCombat.cs:60`），判定在 `:81`。**副本要连赢 3 场**（`DungeonFlow.DeclaredStageCount = 3`，`src/Application/DungeonFlow.cs:181`），失败即止（`DungeonFlow.cs:337` → `DungeonRun.AdvanceStage` 不推进） | 副本成功率 = p³。**p=0.5 → 12.5%**（实测 13.6%）；**p=0.65 → 27.5%** |
| A2 | **战斗与日常共用同一条全局随机流**：`Main.cs:61` 的 `_rng` 同时喂给 `Main.cs:486` 的 `PlaceholderCombat` | 改胜率会**改变日常行为的随机序列**（不是独立开关） |
| A3 | **掉落用的是独立子流**，不插队：`LootPipeline.cs:45` 用 `LootSplit.DeriveSeed(runId)`（FNV-1a，`LootSplit.cs:180`）派生 | 改掉落表**不影响**战斗/日常的随机序列 ✓ |
| A4 | **村抽当前是死规则**：`StallFee.Compute`（`src/Domain/Stall/StallFee.cs:43-58`）用 `villageCut = (totalAmount * 5) / 100` **逐笔 floor**，残差全归卖家（`:56`）。单价 3/5/8 时每笔都 floor 到 0 | 实测 5088 金成交额 → 村抽 **0 金**（`production/qa/econ-collect.jsonl`） |
| A5 | **D-023 原文与实现有一处不符**：D-023 说「摊位费拆分走 `Settlement.ApplyWrites` 同一套 I15 路径」，实际实现是 `StallService.TryBuy` **自带** I15（四步预检 + 提交），**不走 Settlement**。D-027（`07:1245`）已澄清此事，但 D-023 那句没改 | 文档需更正措辞（见 §3.1） |
| A6 | **村金库余额已经持久化**：`Main.cs:3183` 存 `Village.Resources` 快照，`Main.cs:3293-3306` 按差额恢复；`SaveGame.cs:254` 是字典结构，`:734-736` 校验非负 | 新增「零头余数」字段**技术上可行**，但要不要存是**设计选择** |
| A7 | **读档不重放交易**：`ApplySave` 只按差额恢复资源与英雄状态，不重跑任何 `TryBuy` | 零头累计状态**不会**因读档被重复累加 ✓ |
| A8 | **`totalAmount * 5` 存在溢出风险**（`StallFee.cs:55` 裸乘法），且 `totalAmount = stall.UnitPrice * qty`（`StallService.cs:278`）本身也可能溢出 | 这是**已存在的隐患**，任何村抽改动都应顺带封住 |
| A9 | 自主购物**不走业务幂等**：`HeroBehaviorService.cs:282` 调 `BuyFromStall(...)`（内部 requestId 为空串）。日闸门（`HeroBehaviorService.cs:293` 写 `LastShoppingDay`）是唯一防重复的机制 | 零头累计若按「每笔累加」实现，重复交易累加两次是**正确**的（两笔就是两笔）；但幂等键非空的路径（手动购买传 requestId）必须保证**重复被拒时不累加** |

### 3.2 零头累计方案

#### 方案 A（**【已确认采用 · D-052】**）：**累计归村库**（余数延迟入账）

**语义变更（必须显式拍板）**：D-023 的「残差归卖家」改为「残差**累计归村库**，
凑够 1 金时入账」。这是本方案与 D-023 的**唯一实质冲突点**。

**计税基数与扣款方**：**不变** —— 买家付 `totalAmount`（`StallService.cs:285`），
卖家收 `sellerNet`，村库收 `villageCut`，三者关系与 D-023 一致 ✅

**整数运算（全部 long，无浮点）**

```
taxUnits   = totalAmount × 5                 // 单位：1/100 金
accumulated = carry + taxUnits
villageCut  = accumulated / 100               // 整除 → 本次入账的整金
newCarry    = accumulated % 100               // 0..99，留到下次
sellerNet   = totalAmount - villageCut
```

**为什么它是对的**：
- 每笔 `sellerNet + villageCut == totalAmount` —— **钱不生不灭**（沿用 `StallFee.cs:21-23` 的守恒律）
- 累计意义上 `sum(villageCut) + carry == floor(5% × 总成交额)` —— **5% 终将足额收齐**
- 例（单价 5，每笔 taxUnits = 25）：4 笔后 accumulated = 100 → 村库入 1 金，carry 归零。
  20 金成交额收 1 金 = **正好 5%** ✓
- 例（单价 3，taxUnits = 15）：20 笔后 accumulated = 300 → 入 3 金。60 金收 3 金 = **正好 5%** ✓
- 例（单价 8，taxUnits = 40）：5 笔后 accumulated = 200 → 入 2 金。40 金收 2 金 = **正好 5%** ✓

**对卖家的影响**：某笔可能比 D-023 多扣 1 金（余数凑整的那一笔）。
**累计后卖家总收入与 D-023 相同**（因为最终都归村库了），但**单笔的分配变了**。
→ 这正是「保护玩家」与「村库真能收到钱」之间的取舍，**必须由开发者拍板**。

**全有或全无与幂等**

| 环节 | 做法 |
|---|---|
| 计算位置 | 预检段**只算不写**：算出 `newCarry` 与 `villageCut` |
| 提交顺序 | ① `_village.Add(Gold, villageCut)`（**唯一可能抛**，失败则什么都没写）→ ② 写 `carry = newCarry`（纯内存赋值，**不会抛**）→ ③ 其余不可失败赋值 |
| 幂等（requestId 非空） | 重复请求在 `StallService.cs:261-264` 就被拒 → **carry 不会被二次累加** ✅ |
| 幂等（requestId 为空） | 自主购物（`HeroBehaviorService.cs:282`）不幂等 → 两次成交 = carry 累加两次 = **正确**（两笔就是两笔） |
| 读档重放 | `ApplySave`（`Main.cs:3291-3306`）**不重放任何交易** → carry 不会被重复累加 ✅ |

**溢出的封堵（顺带修 A8）**

| 风险点 | 现状 | 建议 |
|---|---|---|
| `totalAmount = stall.UnitPrice * qty`（`StallService.cs:278`） | 裸乘法，可溢出 | 加 `checked` 或先除后乘；溢出 → 拒绝交易、状态不变 |
| `taxUnits = totalAmount × 5`（`StallFee.cs:55`） | 裸乘法，可溢出 | 用不溢出的分解式：`totalAmount/100×500 + totalAmount%100×5`（后半 < 500，必不溢出） |

#### 方案 B：**不累计**，把 D-023 的「残差归卖家」改成「残差归村库」

`villageCut = ceil(totalAmount × 5 / 100)`。改动最小（一行），村库立刻有钱收。
**代价**：单笔多收 1 金，**对卖家更狠**（D-023 明写「保护玩家」），且与 D-023 的
「卖 10 金不收 1 分钱」直接冲突。**未采用**（D-052 选了方案 A）。

#### 方案 C：**不累计，也不改残差归属** —— 现状（村抽在当前价格表下是死规则）

不推荐：R-08 已实测 5088 金成交额抽 0 金，D-023 的「5%」名存实亡。

#### 方案 D：余数**跨日清零**

明确**不推荐**：等于每天把零头扔掉，5% 永远收不齐，且与「累积」直觉相反。

### 3.5 会被推翻的既有测试（**实施时必须同步改**）

> ⚠️ **勘误（2026-10-20）**：本稿初版写的是「给 `Compute` 加一个默认参数，
> 现有 8 条用例**一条都不用改**」—— **那不准确**。
> 返回值要带上 `newCarry`，元组就从 2 元组变成 3 元组，
> 现有用例的 `var (a, b) = StallFee.Compute(x)` **解构不匹配 → 编译失败**。

**三种实现形态（推荐第 ③ 种）**

| 形态 | 做法 | 现有 8 条用例 | 评价 |
|---|---|---|---|
| ① 单一函数 + 3 元组 | `Compute(long totalAmount, long carry = 0) -> (long sellerNet, long villageCut, long newCarry)` | ❌ **解构要改**（`var (a, b, _) = ...`），**断言值不变** | 一个真相源，但改 8 处解构 |
| ② 两个函数 | 保留 `Compute(totalAmount)`（2 元组）+ 新增 `ComputeWithCarry(totalAmount, carry)`（3 元组） | ✅ 完全不改 | ⚠️ `Compute` 在购买路径上变成**死代码**（只有测试在用）—— 两个语义相近的函数是下一次 bug 的配方 |
| ③ **单一函数 + 3 元组 + 旧形状的薄包装** | `Compute(totalAmount, carry = 0) -> 3 元组`；另加 `ComputeSplit(totalAmount) -> 2 元组`（供只需要单笔拆分的调用方） | ✅ 完全不改 | **推荐**：真相源唯一（旧函数退化为包装），测试零改动 |

> **推荐形态 ③ 的取舍**：多一个薄包装函数，但避免了
> 「两个函数语义相近」与「8 条测试全要改解构」两个坑。
> 若实施者选 ①，**必须同步改那 8 处解构**（断言值一个都不该变 ——
> carry=0 时结果与今天逐位相同）。

### 3.6 「残差归卖家」在方案 A 下**什么时候**仍然成立

在 carry = 0 的**第一笔**交易上，方案 A 与 D-023 的分配结果**完全相同**。
差异只出现在 carry ≠ 0 的后续交易：此时那一笔的 `villageCut` 可能比 D-023 多 1 金
（余数凑整的那一笔），而**卖家的单笔实收相应少 1 金**。

**累计到账后，卖家总收入与 D-023 完全相同**（同样的总额，只是分批入账）。
所以方案 A 不是「让村库多拿钱」，而是「**把本来永远归卖家的零头，改成迟早归村库**」。

> 这正是需要开发者拍板的那一点：零头最终归谁。
