## 1. M0 · 审计（实测，四条结论）

### 1.1 长跑稳定性：没问题

| 观测 | 结果 |
|---|---|
| 554 模拟天 / 83 现实秒（`--daylen=0.15` → **6.6 天/秒**） | **零错误、零异常** |
| 杂谈条目 | 554 天稳定在 **9 条**（`ChroniclePresenter.MaxEntries = 40` 上限生效） |
| 内存 | 基线 165 MB，1300 天内基本持平 |

**隐患**：`EventLog._byId/_ordered` 与 `ChronicleFeed._entries/_published` **无上限**（线性增长）。
按每天 ~6 个事件的速率，量级上无碍，但长期无界这点要记账。

### 1.2 正常玩法下，经济是**静止**的 ← 最关键

`src/` 里 `PlaceStall` 只被**摆摊按钮**（`Main.OnStall`）与自检调用；
`ResolveDungeon` 只被**发布任务按钮**（`Main.OnTask`）与自检调用。
「英雄自动开摆」是**从第二阶段 M4 就明确挂账**的 P3/V2 项（`07` D-022 M4 挂账条目）。

> **玩家不点按钮 → 没有副本、没有摊位、没有战利品、没有交易。**
> soak 554 天采到的经济数据是**零**（材料 40→1957 增长 ≠ 经济，那是采集行为）。

### 1.3 现有数据：状态够，**流水不够**

| 要统计的 | 现有 | 在哪 |
|---|---|---|
| 各英雄金币 / 背包 | ✅ | 存档 `HeroSave.CoinAmount` / `Bag` |
| 村庄金库 / 材料 | ✅ | `VillageSave.Resources` |
| 摊位定价 / 库存 | ✅ | `StallSave.UnitPrice` / `Stock` |
| **副本掉了什么** | ❌ | 只有 `AppliedSettlementKeys`（**键**），内容在内存事件里，**不落盘** |
| **成交几笔 / 什么价 / 余额变化** | ❌ | 只有 `AppliedPurchaseKeys`（**键**） |
| 事件流水 | ❌ | `EventLog` / `ChronicleFeed` 纯内存，**读档即重置**（`Main.cs:3121`） |

### 1.4 现成抓手

- `TradeCompleted` 事件的 payload **已经**含 buyer/seller/item/qty/amount/sellerNet/villageCut
  → **落盘即可，不用改事件**。
- **副本掉落原先没有事件**：`EvDungeonFought` / `EvDungeonSettled` / `EvSquadBonded`
  的 payload 里只有 place/won/names，**没有掉落内容**。

## 2. 三个设计决定

### 2.1 事件：新增 `DungeonLooted`，**并复用现有的「整场结论」**

实现中途发现一件重要的事：**已经有一条 `EvDungeonSettled` 事件在带回战利品时发**
（`Main.ResolveDungeon`，进杂谈，文案是「X和Y从北境旧堡带回了战利品：…」）。
语义与新增的 `DungeonLooted` **重叠**。所以最终不是「另起一个事件」，而是：

| 事件 | 何时发 | 落盘行 | 用途 |
|---|---|---|---|
| `DungeonSettled`（**既有**，只补了 `runId` + 参战名单） | **每场副本**（成功失败都发） | `DungeonSettled` | **副本成功率**、参战人数 |
| `DungeonLooted`（**新增**） | 成功**且有战利品** | `DungeonLooted` | 掉落清单、分配结果 |

**为什么必须有「每场一行」**：战利品只在成功时才有 —— 只记掉落的话，
失败场次永远采不到，**副本成功率就无从算起**。而成功率恰恰是 R-05 二轮最需要的数之一。

**落盘判据**：`DungeonSettled` 事件**有 `runId`** 才是副本结算行；
同名的另外几条（队伍归来 / 带回战利品 / 白跑一趟）没有 `runId`，落盘时自然被跳过。

`DungeonLooted` 的 `changed = hero.bag`（真的改了背包，符合反装饰规则），
但**不进杂谈**（渲染委托返回 null，与「日常劳作」同一路）——
37 人每天一两条「某某捡到了石料」会把村庄杂谈淹掉。

### 2.2 落盘：JSONL，只收经济类

| 项 | 决定 |
|---|---|
| 格式 | **JSONL**（一行一个对象）—— 两类行字段集合不同，CSV 要么留一堆空列、要么拆两个文件；JSONL 缺字段就不出现，`jq` / pandas 一把梭 |
| 序列化 | `System.Text.Json`（与 `SavePort` 同一理由：Godot 的 JSON 是 `Variant` 形状的，与强类型对象对不上；也不给这一层引入 Godot 依赖） |
| 范围 | **只收**副本结算 / 副本掉落 / 交易。全事件流里绝大多数是日常劳作与社交（37 人 × 每天几条），与分析经济平衡无关 |
| 写入 | 追加 + **立即 flush** —— 采集要跑很久，中途崩了不能丢已采到的行。与存档的「临时文件 + 替换」原子语义不同：流水是**流式**数据，半行总比没数据强 |
| 载荷缺字段 | **跳过，不写半行** —— 半行 JSON 在分析脚本里变成一条「无法解析」的噪声，还会让行数对不上 |
| 开关 | `--econlog=<路径>` 才有落盘；正常游戏**不写盘** |

**紧凑格式**：事件的 payload 是 `string→string`，放不进嵌套结构。
于是用紧凑串：`石料×2,木料×1`（掉落）、`h-0:石料×2,h-1:木料×1`（分配）、
`h-0,h-1`（参战名单）。**格式与解析器都住在 `EconomyLog` 一处** ——
不会出现「写的和读的不是一套」。

### 2.3 采集器：挂在**日切**上

```csharp
// 每天：副本 → 摆摊（自主购物本来就有每日闸门）
CollectOneDay();
```

**为什么不自己推进时间**：自己推进会跳过「英雄在工地干活」那段状态机 ——
于是每次都挑不出人，副本永远开不了。

> **这是实测踩到的**：第一版采集器自己 `SetSimTime(+1 天)`，结果
> **前 6 天零副本、零摊位、零流水** —— 因为天天都在工地的英雄被筛掉了。
> 改成挂日切、跟着真实游戏循环走之后，副本才开始天天跑。

**副本要走任务流程**（`Mission.Create` → `Start` → `ResolveDungeon`）而不是直接调
`ResolveDungeon`：直接调会跳过领域层的「随队 → 归队」迁移，
英雄的 `Presence` 会卡在 `OnMission`，之后谁都不敢再派他。

## 4. 采到的事实

**数据**：`production/qa/econ-collect.jsonl`（2251 行，740 KB，1000 模拟天）。

> **这份数据不可复现**：采集器用全局随机流，其状态不存档 —— 重跑会得到不同的样本。
> 所以它**必须入库**，否则 R-05 二轮就没有依据了。

| 事实 | 数值 | 含义 |
|---|---|---|
| 副本成功率 | **13.6%**（136 成功 / 864 失败 / 1000 场） | 占位胜率是**每场遭遇 0.5**，副本要**连赢 3 场** → 0.5³ = 12.5% |
| 参战人数 | **1000 场全是 2 人** | 采集器固定取 2 人（不是游戏规则） |
| 掉落分布 | 石料 131 场 / 367 份；木料 94 场 / 126 份；布匹 32 场 / 32 份 | 与配置权重 60/30/10 **吻合**（理论 126 / 89 / 37 场） |
| 成交价 | 木料 3 金、石料 5 金、布匹 8 金，**每笔恒定** | 与 D-021「全球统一价」一致 |
| 成交粒度 | 1115 笔 = 1115 份 | 自主购物**一次只买 1 份**（v1 规则） |
| **村抽合计** | **0 金**（成交额 5088 金） | 5% 摊位费在当前价格表下**从未真正生效**（单价 3/5/8 都 < 20，`floor(total×5/100)` 恒为 0）→ **D-023 的 5% 村抽是一条死规则**，村金库一直是 0 |

### 4.1 两条用数据才发现的问题

**① 副本成功率 13.6%，把产出量压到极低。**
1000 模拟天才出 136 份掉落样本。R-05 二轮要定掉落池与抽取次数，
**必须先定副本成功率**（或至少知道它现在多低），否则掉落数值全是空的。

**② 5% 村抽从来没发生过。**
成交额 5088 金，村抽合计 **0 金** —— 因为单价 3/5/8 都 < 20，
`floor(totalAmount × 5 / 100)` 恒为 0。**D-023 的村金库规则在当前价格表下是死规则。**
这是坐在桌前定概率表**永远不会看到**的一条。

> 两条都印证了那句「先跑起来再定数值」——
> 桌前能定的是「看起来合理的概率」，跑出来的是「**实际发生了什么**」。

## 5. 怎么重跑与分析

```powershell
# 采集 1000 模拟天（--daylen 压缩日长，6.6 天/秒，约 2.5 分钟）
godot --headless --path . --quit-after 60000 -- --daylen=0.15 --collect=1000 `
      --econlog=production/qa/econ-collect.jsonl

# 分析（PowerShell + ConvertFrom-Json，够用）
$rows = Get-Content 'production/qa/econ-collect.jsonl' -Encoding UTF8 | % { $_ | ConvertFrom-Json }
$ds = $rows | ? { $_.Kind -eq 'DungeonSettled' }
$ds | Group-Object { $_.Won } | Format-Table Name, Count        # 副本成功率
$rows | ? { $_.Kind -eq 'DungeonLooted' } | % { $_.Loot } | Group-Object Item | Format-Table Name, Count
$rows | ? { $_.Kind -eq 'TradeCompleted' } | Group-Object Item | Format-Table Name, Count
```

> **读文件必须指定 `-Encoding UTF8`** —— PowerShell 5.1 默认按 ANSI 读，
> 中文会变成「鍖楀鏃у牎」那样的乱码（文件本身是好的）。

## 6. 边界与未做

- **占位配置产出的数据不是正式经济平衡结果**：掉落权重（60/30/10）、抽取次数（3）、
  基础价格（5/3/8）全是**占位**（D-050）。数据文件必须标清楚，避免被当成正式平衡结论。
- 采集器**不改任何规则**，只替玩家按按钮；它**不**模拟玩家的操作节奏
  （玩家不会每天恰好两次副本、也不会每天准时收摊重开）。
- 采集器的参战人数**固定 2 人**（它挑人时最多取 2 个）—— 真实玩法里队伍规模由玩家定。
- R-05 第二轮**数值**仍待定 —— 现在有数据了，可以据此定。
- R-06 独立保留；但**动 UI 时应与 R-07 的行尾标记放在同一次布局评审**（共用 248 像素）。
- 全事件流落盘**不做**（只落经济流水）。
- 「英雄自动开摆」**仍未做** —— 那是 P3/V2 的玩法项，本轮只做采集，不碰玩法。
