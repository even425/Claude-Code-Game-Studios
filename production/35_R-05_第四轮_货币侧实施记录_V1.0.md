### 1.2 三个设计决定（及其理由）

> **① 金币必须并入 `SettlementDelta`，不能另发一次。**
> 副本的**村庄材料**、**英雄战利品**、**英雄金币**是同一笔奖励的三半。
> 分三次发，中间任何一步失败都会留下半笔账 ——
> 与 `Settlement.cs:50-54` 记的「物品为什么也进结算增量」是**同一条理由**。
> 于是三者共用**同一把幂等锁**、在**同一次提交**里落下去。
>
> **② 钱包拒收 → 整笔不应用（沿用 I15 与 R-01 先例）。**
> 任一参战者钱包拒收 → **整笔结算不应用**，幂等键**不落**（可重试）。
> 钱包拒收有三种：容量上限、溢出、英雄不存在。
> **英雄的正式钱包是「容量 0 = 无限」，所以「容量」与「溢出」在正式路径上实际不会触发** ——
> 但**规则已写死**，且第三种（英雄不存在）**真的可达**。
>
> **③ 失败也发金币，是 D-054 引入的**唯一一项**「失败也发」的奖励。**
> 材料与战利品仍遵循 D-010 Q1（失败不发）。`07` 的 **D-010 Q1 原文保留**，已加注说明这一例外。

### 1.3 顺带修掉的一处**真实缺口**：`Wallet.TryAdd` 的溢出

**原状**：`Wallet.TryAdd` 只判容量（`Capacity > 0 && next > Capacity`）。
英雄的钱包容量是 **0 = 无限** → 容量检查**不生效** → `Amount + delta` 溢出会
**绕成负数** → 钱包里出现**负余额**（`I12` 的「不变负」只保护扣减方向）。

**为什么本轮必须修**：阶段 1 的规则是「钱包拒收 → 整笔不应用」。
没有这道判，**溢出会被当成成功** —— 结算就会给英雄记下一个**负钱**的钱包，
而「拒收 → 整笔不应用」变成一句永远走不到的空话。
补上显式溢出判（`delta > long.MaxValue - current` → 拒）后，这条规则**才真的可达**。

> **同类缺口未一并处理**：`Inventory.TryAdd`（物品背包）有**完全相同**的溢出绕负问题。
> 它**不在本阶段范围内**（物品路径没有金额语义），**未改动** → 记进 §4 遗留。

### 2.2 为什么把成本表与扣款**从 Main 抽出来**

升级成本是**规则**，`Main` 是表现层/编排层。留在 `Main` 里就**没法单测** ——
而这恰好是本项最需要守的地方（「金币不足**或**材料不足 → **都不扣**」）。
抽成 `VillageUpgradeService` 后：
- 成本表是**一处可核对的数字**（`AllCosts`）；
- 原子性（I15）能被单测钉住；
- `Main` 只剩「点了要盖哪一级」与「派人去盖」。

> **层级上限的两处数字**：规则的所在地是 `VillageUpgradeService.MaxTier = 5`；
> 视图层 `VillageView.MaxTier = 5` 仍在（`SetTier` 的夹取要用）。
> 两处各写一份迟早分叉 → 加了一条**跨层一致性用例**
> （`MaxTier_MatchesTheViewLayerConstant`）盯着。

### 2.3 原子性（I15）：**预检才是承重的那道**

```csharp
if (!CanUpgrade(tier)) return false;     // ← 承重：两边都够才继续
if (!_village.TrySpend(_gold, cost.Gold)) return false;
if (!_village.TrySpend(_material, cost.Material))
{
    _village.Add(_gold, cost.Gold);       // ← 双保险：理论上走不到
    return false;
}
```

**变异验证揭示的一个事实**（值得留档）：

| 变异 | 结果 |
|---|---|
| 只拆「退还」那一行 | 🟢 **仍全绿** —— 说明**退还走不到**（预检先挡住了），它是**双保险** |
| 同时拆「预检」与「退还」 | 🔴 **1 条变红**（`TryUpgrade_WhenMaterialShort_SpendsNothingAtAll`）→ **预检才是承重的那道** |
| 只拆「层级上限」的一道门（`CostFor` 的越界返回） | 🟢 仍全绿 —— 还有**第二道**（`CanUpgrade` 的 `tier >= MaxTier`）挡着 |
| 两道**同拆** | 🔴 **1 条变红**（`TryUpgrade_AtMaxTier_SpendsNothing`）→ 上限守得住 |

> **教训**：变异测试的价值不只在「抓到 bug」，也在**分辨哪道防线承重、哪道只是冗余**。
> 只拆一道不红，说明有第二道；两道同拆才红，说明**守得住**。
> （第一轮变异时我只改了注释没删代码 → 测试仍绿 → 差点误判「用例无效」。）

### 2.6 升级花掉的金币是**销毁**（不是转移）

### 3.3 固定种子：**能固定「同一批英雄」，但做不到「逐行一致」**

| 层次 | 能不能固定 | 证据 |
|---|---|---|
| 模拟随机流（`Main._rng`） | ✅ | 两次同种子跑：模拟时间与副本实例标识**完全一致** |
| 英雄创建（`HeroFactory._rng`，**另一条随机源**） | ✅（补了 `HeroFactory.Seed` 之后） | 补之前英雄**每次都不同**（名字/世界/性格/属性全变） |
| **逐行一致** | ❌ **做不到** | 两次同种子跑：行数相同、成交笔数**完全相同**（46/46），但**成交金额差 13%**、副本成败不同 |

**为什么做不到**：日界时刻落在**帧内**（`_clock.Tick(dt)` 跨过边界的那一帧），
而帧步长 `dt` 每次都不同 → 日界时刻有**子帧抖动**（实测 0.0037 模拟秒）→
**恰好在边界附近到期的活动**有时完成、有时没完成 → 决策次数变了 →
**随机流消耗次数**随之变 → 流分叉。

> ⇒ **阶段 3 的原验收要求「同一种子两次跑 → 逐行一致」不可满足**（已改）。
> 可达成、且已实测达成的是：**同种子 → 同一批英雄 + 成交笔数相同 + 守恒律逐日成立**。
> 固定种子的价值仍然很大：把「完全不同的英雄」变成「同一批英雄 + 指标接近」。

### 3.4 守恒律的正确形式（**余数不是钱**）

```
货币守恒：Σ英雄钱包金币 + 村库金币 + 累计销毁金币 = 初始金币 + 累计发放金币
税务口径：Σ(villageCut) × 100 + 在途余数 = 成交额 × 5      ← 另一条等式，无 floor
```

**为什么余数不能进守恒律**：`StallFee.Compute` 里 `totalAmount = sellerNet + villageCut` ——
钱在**买家与卖家之间完整转移**，余数只进「下次累计」，**从没从任何钱包里被扣走**。
把它加进左边 = **凭空多算那部分零头**。

**实测**：40 天采集 **40/40 天成立**（例：`345 + 35 + 0 = 300 + 80`）；
300 天采集 **300/300 天成立**。

> **阶段 4 补的一条**：「**待发零头**」同样**不能进守恒律** ——
> 理由不同但结论一样：它是「已挣到、但**还没进任何钱包**」的**应收**。
> 左边是「钱在哪」（它哪都不在），右边是「已经兑现了多少」
> （兑现的那部分才在「累计发放」里）。
> **只把它加在一边 = 凭空多算那部分钱** —— 2026-10-20 的 37 人探针实测
> **差出整整一个零头（3810 vs 3820）**，见 §4.3。
> 它是**独立科目**（跟着存档 0.6 的 `GoldCarry` 走），单独核对自洽性（每英雄 < 100）。

### 3.5 采集结果：**目标 150 金实测不可达**

两个标定点（**300 模拟天 · 同种子 4242 · 3 英雄**）：

| X（每人每次） | 末次流通金 | 成交笔数 | 成交金额 | 每 100 天成交 | 未成·钱不够 | 升级 |
|---|---|---|---|---|---|---|
| **0**（无供给） | **267** | 101 | 666 金 | 55 → 27 → 18 | **66.7%** | 0 |
| **1**（基准候选） | **852** | 154 | 960 金 | 61 → 52 → 41 | 39.6% | 0～1 |
| 0.5 | ⚠️ **未采到**（`--goldreward=0.5` 被静默忽略 → 那轮实际是 X=1；已修，见 §3.2 ③） | | | | | |

**读法**

- **X=0 也不塌缩到 0** —— 池子停在 **267**。而 267 ≈ **货物上限 240 + 金库 27**。
- **X=1 池子单调涨到 852**，成交反而**更稳**（61→52→41，衰减慢于 X=0 的 55→27→18）。
- 两档**守恒律都 300/300 天成立** ✅；税务口径都一致 ✅。

### 3.5.1 🔴 机理解释：**钱只有两个命运，池子有「地板」**

英雄钱包里的钱**只能变成两样东西**：

1. **货**（买来的材料）—— 锁在背包里，**上限 = 5 份/物品 × 3 种 × 单价 = 80 金/人**，
   3 英雄合计 **240 金**。这些钱**花不掉**（背包满了 → D-053 的抽样前过滤把摊全剔了）
   → **永远不会被抽税** → **池子的地板 ≈ 240 金**。
2. **被 5% 抽走的税** —— 每转手一次抽一次。

⇒ **池子的下限 = 货物上限（240 金），上限 = 无界**。
**目标 150 金 < 240 金的地板 → 物理上不可达。**
（X=0 实测停在 267 ≈ 240 + 27，正好落在地板上。）

> **⇒ 真正缺的不是「更多钱」，而是「花掉钱的地方」。**
> 货物的总量有上限（240 金），钱超过这个数就只能囤着；
> 而**唯一会消耗金币的玩法是村庄升级** —— 但它**只有 5 级**、
> 第 1 级就要 50 金（金库税入 ~0.16–0.26 金/天），
> 且**建造本身约 250 模拟天**（`WorkRate` × 0.15 实时秒/天）→ **5 级远超 1000 天**。
>
> **⇒ 决策 ③「金库不做周期性返还」的直接后果被实测确认了**：
> 村库的**唯一出口**（升级）**实际等于没有**。
> 玩家钱唯一的去处是「变成货」，而货有 240 金的地板。

### 3.5.2 为什么我此前那条「阈值 X\* = 0.57」的推导**不成立**

它用的是**收缩轨迹**上测出的 `T(M)` 曲线，**不能外推到增长轨迹**。
现在有实测证据：**单次采集的 `T(M)` 曲线不可跨轨迹外推**（`34` §2.3 记过这条警告，
现在它有了具体后果：按那条推导去选 X，会选到「池子无限涨」的一侧）。

### 4.1 分数报酬：零头**按英雄分别**累计

**为什么需要**：X 必须是分数才能夹住稳态带（§3.5.2），
而金币钱包只收**整金**。X = 0.5 时某英雄两天才够 1 金 —— **中间那 0.5 金得有个地方放**。

**规则（Q2 拍板）**：

| # | 规则 | 理由 |
|---|---|---|
| 1 | 最小单位 = **1/100 金**；`WalletGrantService` 的报酬率用该单位持有 | X 取到 0.01 精度；全程整数算术 |
| 2 | 零头**每个英雄各自一份** | **全局攒**会让**先轮到的英雄**拿走整金、后吃亏 —— 那不是「每人每次 X 金」 |
| 3 | 零头**不销毁**：攒够 100 就发 1 金（可能一次发多金），余下继续攒 | 零头是**已经挣到**的钱，丢掉 = 凭空消失 |
| 4 | 零头**跟着存档走**（存档 0.6 的 `HeroSave.GoldCarry`） | 同上：读档后丢掉 = 凭空少钱（与 D-052 存税额余数同一条理由） |
| 5 | **金额不进结算增量**：`WalletGrant` 只带 `HeroId`，X 住在写入入口 | 金额若进增量，「零头怎么算」就有**两处定义** —— 那是最容易分叉的地方 |

### 4.3 🔴 又一处**被数据抓出来的错误**：待发零头**不进守恒律**

**我怎么搞错的**：阶段 4 加了「待发零头」这个科目后，我**顺手**把它加进了守恒律的右边
（`Σ英雄 + 村库 + 已销毁 = 初始 + 累计发放 + 待发零头`）——
理由是「分数报酬下它也是钱」。

**数据怎么把它抓出来的**：37 人 / 15 天探针，守恒律 **13/13 天成立**，
但税务口径**差出整整 0.2 金**。顺着查下去发现：
`3722 + 38 + 50 = 3810`，而 `3700 + 110 + 10 = 3820` ——
**差额恰好是待发零头（10 金）**。

**我错在哪**：

| 守恒律的左边 | 守恒律的右边 | 含义 |
|---|---|---|
| **钱在哪** | **钱从哪来 + 已经兑现了多少** | 两边都是**已兑现**的量 |

待发零头是「**已挣到、但还没进任何钱包**」的**应收** ——
左边是「钱在哪」（它**哪都不在**），右边是「已经兑现了多少」
（兑现的那部分才在「累计发放」里）。
**只把它加在一边 = 凭空多算那部分钱。**

**正确口径**（实测已核对 1000 天 **1000/1000** 成立）：

```
货币守恒（流通口径）：Σ英雄钱包金币 + 村库金币 + 累计销毁金币 = 初始金币 + 累计发放金币
税务口径：Σ(villageCut) × 100 + 在途余数 = 成交额 × 5      ← 另一条等式，无 floor
待发零头自洽性：每英雄 < 100（1/100 金），合计 < 100 × 人数   ← 独立科目，单独核
```

**处置**：`analyze-econ.py` 的守恒律改回不含待发零头，**另加**一条独立的自洽性核对；
`EconomyLog` / `Main` / `VillageUpgradeService` / `SettlementGoldTests` 的
公式注释**全部改对**（原来三处都写着错公式）。

> **顺带发现并修掉的第二处口径错**：**税务核对的窗口没对齐** ——
> 快照取在「**日界那一刻**」（副本 → 摆摊 → 升级 → 快照 → 之后才是当天的自主购物），
> 所以「第 N 天的快照」里的税额余数只覆盖**到第 N-1 天为止**的成交。
> 拿「全部成交」去配「最后一份快照的余数」，会**恒差最后一天的量**。
> 修法：税务核对只用 `Day ≤ 最后快照日 − 1` 的成交与该快照的余数配对。
> 修前差 0.2 金，修后**一致**（新旧样本都一致）。

#### 4.5.3 三条结论

**① 🔴 「目标流通池 150 金」在 37 英雄规模下**双重失效**。**

- **量级失效**：37 人的**货物地板** = 37 × 80 = **2 960 金**（5 份/物品 × 3 种 × 单价）。
  150 < 2 960 → 比地板还低，**物理上不可达**（与 3 英雄时的「240 金地板」同一条理由，只是放大）。
- **概念失效（更要紧）**：**两档都没有稳态**。X = 1 的话流通金**单调上涨**；
  X = 0.5 的话在第 ~200 天见底后**继续上涨** —— 1000 天时**仍在涨**。
  ⇒ **根本没有一个「稳态 M」可供瞄准**，「目标池 = 某个数」这个提法在此规模下**无从落地**。

**② 村庄升级在 37 人规模下**可达**（3 人规模下不可达）。**

五级升级（合计 750 金 + 400 材料）在**第 ~100 天就全部完成**（day 103 快照已显示 `Upgrades = 5`）。
⇒ §3.5.1 那条「村库的唯一出口实际等于没有」**在 37 人规模下不成立** ——
出口是有的，只是**用完就没了**。

**③ 但钱的主要去处是**永久沉淀在金库**，不是花掉。**

X = 1 时：副本造出 19 920 金，其中 **12 226 金（61%）被 5% 村抽抽走进金库**，
而金库在第 ~100 天升级用完后**再无出口** → 到 day 1000，金库存着 9 782 ~ 11 476 金。
**这不是采集器的采集规则**（税是游戏规则），是**金币只有「变货」与「被抽税」两个出口**的结构性后果。

> **⇒ 这正是 D-054 决策 ③「金库不做周期性返还」的代价，现在有了量级。**
> 3 人规模下金库小（27 金）看不出来；37 人规模下它是**全场最大的一笔钱**，而且**永远花不掉**。
