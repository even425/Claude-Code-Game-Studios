## 2. 分层与模块边界

### 2.1 四层职责

**【已确认】** 沿用基线 §13.2 的四层划分，Godot + C#（基线 §13.1）。

| 层 | 放什么 | 明确不放什么 |
|---|---|---|
| **表现层**（Godot 场景 / Node） | 地图、45° 等距镜头、英雄与建筑的场景节点、动画特效音效、UI、输入采集 | 任何玩法规则；任何对领域状态的直接写入 |
| **应用层** | 玩家指令入口、用例协调、游戏时间与速度控制、场景与会话生命周期 | 规则本身；领域对象的字段 |
| **模拟 / 领域层** | 英雄行为规则、战斗规则、任务与队伍规则、建筑规则、关系（第一阶段仅占位）、领域事件的产生 | Godot 类型、场景树、UI |
| **数据与存档层** | 静态定义、运行时状态的序列化 DTO、存档版本与迁移、加载校验与备份 | 玩法规则 |

**【已确认】** 领域对象**不应全部做成 Godot Node**（基线 §13.3）。场景节点负责呈现与引擎交互，领域对象负责规则与状态。

**【已确认】** 只保留少量真正需要全局访问的服务，**避免巨型 GameManager**（基线 §13.4）。开发计划 M1 的验收项直接引用了这条。

### 2.2 领域对象与 Node 的对应关系

**【建议】** 一条一个领域实体的展示，对应**一个**表现层 Node；Node 由表现层拥有，领域实体由领域层拥有。Node 订阅领域事件来刷新显示，**不反向写回**。

```text
领域实体（普通 C# 类，领域层拥有）
        ▲ 只读查询                    │ 订阅
        │                            ▼
应用层服务 ──发命令──▶ 领域模块 ──发领域事件──▶ 表现层 Node（订阅更新显示）
                         │
                         ▼ 写入
                   存档层（只经序列化 DTO 读写）
```

**【建议】** 领域实体不引用任何 `Node` / `SceneTree` / 引擎类型，因此规则层单元测试可以在没有 Godot 运行时的情况下执行。

### 2.3 领域层内部的模块划分

**【建议】** 领域层按「谁拥有哪份数据」切分，而不是按界面切分。每个模块是**一份数据的唯一写者**。

| 模块 | 第一阶段负责 | 第一阶段**不**负责 |
|---|---|---|
| 模拟时钟与调度 | 推进模拟时间、决定一个模拟步内各模块的执行顺序 | 决定任何英雄做什么 |
| 英雄 | 英雄身份、当前所在活动、持有物引用的归属、当前状态槽位 | 战斗数值、交易定价 |
| 村庄与建筑 | 村庄实例、建筑实例与其在场状态、村庄资源存量 | 建筑功能的具体效果（基线 §12.3 明确未定） |
| 队伍与任务 | 编队合法性、任务生命周期、任务的阶段进度 | 副本内部战斗过程 |
| 副本 | 副本实例、阶段推进与流转、完成条件判定 | 自动战斗规则、战斗结果、村庄资源 |
| 战斗 | 自动战斗执行、产出战斗结果 | 副本阶段流转、奖励内容、村庄资源与英雄持有物 |
| 结算与回流 | 把战斗结果按规则写入村庄 / 英雄 / 事件流，并保证只做一次 | 定义奖励内容 |
| 领域事件与杂谈 | 事件记录、杂谈条目的生成与去重 | 判断事件值不值得记 |

> **V1.0.2 修正：** 原表把「副本与战斗」并为一行，一个模块却由两个唯一写者承担
> （`Dungeon/` 管阶段推进、`Combat/` 管战斗结果），与不变量 I10「跨模块的状态改变只经由拥有该数据的模块」冲突。
> 现拆为 **副本** / **战斗** 两行，各自一个唯一写者，共 **8 个模块**。
> 依据：`04_副本与自动战斗规则` 本身已把「副本生命周期」（§3/§4）与「战斗规则接口」（§5）分章处理，
> `05` §3.6 亦将 `BattleResult` 单列为独立实体。**让模块划分迁就已成型的文档，而不是反过来。**
> 代码侧对应 `src/Domain/` 下 8 个目录，与本表一一对应。

**【已确认】** 事件系统只做触发 / 生命周期 / 协调，不直接承担所有业务细节（基线 §11.4）；同一后果不得因重复加载或重复结算而被应用多次。

### 2.4 跨层通信：命令与领域事件

**【已确认】** 系统通过**明确的命令与领域事件**协作，不互相随意改数据（基线 §13.5、核心玩法循环 §5.2）。

**【建议】** 三条通道，各自有唯一合法用途：

| 方向 | 通道 | 语义 | 允许做什么 |
|---|---|---|---|
| 表现 / 应用 → 领域 | **命令 Command** | 「请系统做这件事」 | 命令是**唯一**能改变领域状态的入口 |
| 领域 → 领域 | **领域事件 DomainEvent** | 「这件事已经发生了」的事实记录 | 其他模块可订阅并据此做**自己的**事 |
| 领域 → 表现 / 应用 | **只读查询 Query / 领域事件** | 读取快照用于显示 | **只读**；禁止拿到领域对象引用后改字段 |

**【建议】** 明确禁止的三件事：

1. 表现层直接写领域字段（如 UI 拖动直接改 `Hero.CurrentState`）。
2. 模块 B 直接改模块 A 的数据（如战斗模块直接把奖励加进村庄资源）。要走命令或事件，让**拥有该数据的模块**写。
3. 事件处理者绕过业务服务改核心数据（基线 §11.6 验收项 V4「事件不越权改数据」）。

**【建议】** 领域事件是**不可变**的事实记录，字段固定为：事件 ID、模拟时间戳、来源实体 ID、参与者 ID 列表、载荷。已发出的事件不改写。

### 2.5 静态定义与运行时状态

**【已确认】** 静态定义描述「这种东西是什么」，运行时状态描述「这个实例当前怎么样」，**运行时变化不得写回静态定义资源**（基线 §13.6）。

**【建议】** 因此每类内容都拆成两份模型：

| 静态定义（Definition） | 运行时状态（State / Instance） |
|---|---|
| 英雄定义、村庄建筑定义、副本定义 | 英雄状态、村庄、建筑实例、副本实例 |
| 编辑期 / 内容期确定 | 运行时可变，且必须能进存档 |
| **不可**被存档写回 | **必须**能被存档完整恢复 |

**【建议】** 第一阶段不引入「属性 / 词条 / 数据驱动数值表」这一层间接。属性字段直接放在定义里，多一层只会让 M1–M7 的读取路径变长。

### 2.6 存档边界

**【已确认】** 存档要求（基线 §13.7）：

- 显式 DTO + 版本号，**不直接序列化整个场景树**
- 临时文件写入后再替换正式存档；保留上一份有效存档
- 加载时先解析 DTO、**校验 ID 和引用**，再恢复运行时状态
- 提供版本迁移入口
- 加载时必须避免：重复发放奖励、重复应用事件后果、装备丢失或重复、建筑坐标冲突、**任务参与者丢失**、已完成事件重新进入进行中

**【建议】** 存档的**边界就是本文 §3 列出的运行时实体**，不多不少：村庄、建筑实例、英雄状态、队伍、任务、副本实例、战斗结果、领域事件、杂谈条目、模拟时钟。「已结算」这类幂等标志必须**显式落盘**，不能靠读档后重新推算。

## 3. 核心实体

> 每一项按四问回答：**持有什么状态 / 由谁创建 / 由谁修改（唯一写者）/ 谁读它**。
> 「唯一写者」一列是本文最重要的一列：它就是 §2.3 的模块边界。

### 3.1 通用约定

**【建议】** 所有运行时实体：

- 持有 `Id`（稳定标识，创建后永不改变、永不复用）。名称不是标识。
- 状态的修改只能通过该实体的拥有模块的公开操作。
- 不持有指向表现层 Node 的引用。

**【建议】** 所有实体之间的引用一律用 **ID**，不用对象引用。理由：存档（§2.6）、校验（§5 不变量 I13）与测试替身都需要。

### 3.2 Hero — 英雄（运行时）

| 项 | 内容 |
|---|---|
| **持有状态** | `Id`；所属村庄；当前状态槽位集合（**具体槽位与取值属【待定】**，基线 §4.4）；当前所在活动（空闲 / 日常活动 / 队伍任务中）；**当前行动实例的剩余时长**（**【建议】**，见 §3.2.1）；持有物引用；首次完成副本的标记（基线 §7.2 点名的杂谈触发条件）；死亡与复活的当前可用性标记 |
| **由谁创建** | 英雄获取流程（第一阶段为最小获取流程；**入口形式属【待定】**，基线 §10.3/§10.6） |
| **由谁修改（唯一写者）** | 英雄模块 |
| **谁读它** | 表现层（显示状态与位置）、队伍与任务模块（是否可被编队）、副本与战斗模块（作为战斗输入）、结算与回流模块、领域事件与杂谈（记录其行为）、存档层 |

#### 3.2.1 「当前行动实例的剩余时长」 **【建议】**

**【建议】** `Hero` 持有当前行动实例的**剩余时长**，作为运行时的第 N 项状态。（依据 `07` **D-009 R-1**，回填自 `03` §4.4 / §10.1 R-1。）

**为什么必须补这个字段：**

- 基线 §13.7 要求**活动任务可恢复**。「可恢复」的最小含义是：一个正在进行的行动，读档后应当**接着做完**，而不是消失或重算。
- 上表的既有字段**无法承载「行动进行中存档」**：「当前所在活动」只能表达「英雄正在做 X」，不能表达「X 已经做了 3/8」。
- 不补的后果是二选一，且**两个都是缺陷**：读档后英雄的当前活动指向一个不存在的行动实例，触发 §4.2 的「引用断了 → 校验失败」；或者行动被从头重算一次（等于白送一次收益 / 白耗一次耗时）。

**【建议】** 取**直接持有剩余时长**，而不是只存一个「行动实例 ID」再由英雄模块解析：直接持有让存档往返只需一次字段比较，间接持有会把解析责任推给模块边界之外。

**【待定】** 该字段的**数值语义**（单位、与模拟时间倍率的换算、跨日时的截断）属 `03` 与 **T-001 / T-002**。本文只要求它**存在且可存档**，不定义它怎么走——与本文 §3.9 对 `SimClock` 的处理同构。

**【建议】** **本字段为【建议】级**：它是 D-009 R-1 批准回填的字段，但确认权仍在开发者。

**【已确认】** 四层建模（人物特质 / 玩法偏好 / 当前状态 / 人际关系）是**正交**的四件事，不合成单一「性格」属性（基线 §4.1、§4.2、§4.3）。

**【已确认】** 玩法偏好**只改变权重与倾向，不改变可行性**（基线 §4.3）：偏好休闲的英雄仍然可以被派去攻略副本。

**【已确认】** 死亡后复活，**不附加任何死亡代价**——没有战力 / 等级损失、没有时间惩罚、没有装备或物品损失、没有关系恶化（基线 §4.6）。因此英雄实体**没有**「永久死亡」「不可用」「装备损毁」这类状态。→ 不变量 I6。

**【已确认】** 「没有关系恶化」**带一条例外**，不得读成「死亡后关系一定不变」：基线 §4.6 的原文是「**没有**（除非 §9 的行为链本身导致，属独立事件）」。即：英雄死在一条 PvP 追杀链里，关系**可以**变——但那是**§9 行为链造成的后果**，不是**死亡造成的后果**，两者必须能区分开。

**【待定】** 人物特质的具体条目与取值（基线 §4.2）；玩法偏好的品类与权重表（基线 §4.3）；当前状态的完整清单与持续时间（基线 §4.4）。

### 3.3 Village / BuildingInstance — 村庄与建筑

| 项 | 内容 |
|---|---|
| **持有状态** | 村庄：`Id`；建筑实例集合；村庄资源存量（**资源种类与数量属【待定】**）。建筑实例：`Id`；所属村庄；建筑定义 ID；是否已建成 / 建造进度；所在坐标 |
| **由谁创建** | 村庄实例由新游戏流程创建为三间土屋（基线 §2.2 已确认起点）。建筑实例由建造流程创建 |
| **由谁修改（唯一写者）** | 村庄与建筑模块 |
| **谁读它** | 表现层（绘制建筑）、副本与战斗模块（作为建筑影响查询的输入，见基线 §8.4）、结算与回流模块（奖励入账）、杂谈（建筑建成 / 升级，基线 §7.2）、存档层 |

**【已确认】** 第一阶段只实现已确认的九种建筑：土屋（起始）、烟囱、井、围栏、铁匠铺、武器店、服装店、试炼塔、防护罩（基线 §12.1）。

**【已确认】** **不得由实现者自行指定每栋建筑的功能**，尤其不得仅凭名称推断它改变战斗或经济数值（基线 §12.3、验收项 B1）。第一阶段若纳入某栋建筑，须先在 `04` 或 `07` 中写明它的用途。

**【待定】** 建筑成本、前置条件、资源种类、建筑效果、解锁规则；建筑之间是否存在相互影响（基线 §12.1、§12.3、待确认清单 #21/#22）。

**【建议】** 第一阶段只要求三间土屋可见可用；其余建筑作为**定义存在但未实现效果**，其效果字段留空而不是填占位数值。

### 3.4 Squad / Mission — 队伍与任务

| 项 | 内容 |
|---|---|
| **持有状态** | 队伍：`Id`；成员英雄 ID 列表；所属任务 ID。任务：`Id`；目标副本定义 ID；状态（未开始 / 进行中 / 已完成 / 已失败）；参与英雄 ID 列表；当前进度阶段 |
| **由谁创建** | 队伍与任务模块，由玩家指令创建（玩家**只能由自己决定队伍组成**，基线 §2.2） |
| **由谁修改（唯一写者）** | 队伍与任务模块 |
| **谁读它** | 副本与战斗模块（队伍成员是战斗输入）、表现层（显示任务进度）、结算与回流模块、杂谈（副本完成的参与者）、存档层 |

**【已确认】** 玩家决定队伍组成，**不等于**直接操纵战斗中的每一步（核心玩法循环 §4.1）。

**【已确认】** 英雄接受任务后，**不能在同一时刻被重复分配到冲突任务**（开发计划 M4）。→ 不变量 I2。

**【已确认】** 编队的**具体**人数上限、职业定位、条件属【待定】（核心玩法循环 §3 阶段 E）。本文因此只记录「成员 ID 列表」，不记录任何人数常量。

### 3.5 DungeonRun — 副本实例（运行时）

| 项 | 内容 |
|---|---|
| **持有状态** | `Id`；副本定义 ID；进入的任务 ID；参与英雄 ID 快照（**进入时快照，不随英雄后续状态变化**）；当前阶段序号；状态（未进入 / 进行中 / 已完成 / 已失败）；**结算是否已应用**标志；关联的战斗结果 ID |
| **由谁创建** | 副本与战斗模块，在任务派遣成功并通过合法性检查后创建 |
| **由谁修改（唯一写者）** | 副本与战斗模块（阶段推进）；结算与回流模块（只写「结算已应用」标志与结果引用） |
| **谁读它** | 结算与回流模块（幂等检查）、表现层（阶段显示）、杂谈（首次完成副本）、存档层（加载时避免「已完成事件重新进入进行中」，基线 §13.7） |

**【已确认】** 副本必须具备：**明确入口、多个遭遇或阶段、最终目标、结算与奖励**；至少两个阶段（单场遭遇不算副本）（基线 §8.2）。第一阶段至少一个副本（开发计划 M5）。

**【建议】** **阶段不单独建实体。** 第一阶段的阶段是副本实例内的一段状态（`当前阶段序号`），不是被别的实体引用的对象。若阶段将来需要被单独引用（如「关卡图鉴」），再升级为独立实体。理由：升级成本远低于提前拆错的成本。

**【建议】** 参与英雄的**ID 快照**是刻意设计：结算与战斗结果必须对应「谁去了」，而不是「读档瞬间谁还在队伍里」，否则读档后重放结算会算出与当时不同的结果。

**【待定】** 副本结构（单场战斗 / 连续房间 / 其他）、阶段数量、失败条件、任务耗时（核心玩法循环 §8 第 12 项；基线 §8.3）。

### 3.6 BattleResult — 战斗结果

| 项 | 内容 |
|---|---|
| **持有状态** | `Id`；所属副本实例 ID；结果（成功 / 失败）；参与英雄 ID 快照；产出清单的**描述**（物品 / 资源种类引用，**数值属【待定】**）；战斗日志（可复现判定依据的记录） |
| **由谁创建** | 副本与战斗模块，在自动战斗结束时创建，且**每个副本实例至多一个** |
| **由谁修改（唯一写者） | **创建后不可修改。** 任何修正通过创建新结果 + 显式替换并记录原因 |
| **谁读它** | 结算与回流模块（唯一的发奖依据）、表现层（战斗可读性展示）、杂谈、存档层 |

**【已确认】** 战斗**全自动**，玩家不直接操控即时攻击；战斗**应在地图上观察**而不是切换到独立战斗场景；战斗必须**可读**——玩家应能看清谁为什么赢、谁为什么输（基线 §8.3）。

**【已确认】** 玩家通过**队伍配置、装备、补给、任务选择**影响结果（基线 §8.3）。

**【已确认】** 战斗日志要能**复现胜负判定所引用的每一个关键事件**（基线 §8.5 验收项 D5）。

**【待定】** 战斗的全部数值规则：伤害、命中、冷却、状态效果、AI 目标选择（基线 §8.3、待确认清单 #13）。本文只定义「战斗结果是一个不可变的事实记录，其内容由 `04` 定义」。

### 3.7 DomainEvent — 领域事件

| 项 | 内容 |
|---|---|
| **持有状态** | 事件 ID；模拟时间戳；类型；来源实体 ID；参与者实体 ID 列表；载荷 |
| **由谁创建** | 各领域模块，在自己完成一次状态变化时创建 |
| **由谁修改（唯一写者）** | **不可修改。** |
| **谁读它** | 杂谈模块（决定是否生成条目）、表现层（触发演出）、存档层 |

**【已确认】** 杂谈**根据已发生的事件生成消息**，而不是每隔几秒随机生成文本（基线 §7.2）。基线点名的触发事件包括：英雄首次完成副本、交易纠纷、关系恶化、获得稀有装备、受伤 / 康复、建筑建成 / 升级、村庄日常、大事件、召唤新英雄、本土剧情进展。

**【建议】** 事件**类型**是一个可扩展的注册表：第一阶段只注册第一阶段会产生的类型。基线 §11.1 要求「新增事件不得要求重写核心世界循环」，同一条要求适用于领域事件类型。

**【已确认】** 杂谈**只是一个功能，一个文字面板**，不是叙事主干（基线 §7.1）。

### 3.8 ChronicleEntry — 杂谈条目

| 项 | 内容 |
|---|---|
| **持有状态** | 条目 ID；来源事件 ID（**必填**）；记录时的模拟时间；参与者；文本 |
| **由谁创建** | 杂谈模块，从领域事件生成 |
| **由谁修改（唯一写者） | **不可修改** |
| **谁读它** | 表现层（文字面板）、存档层 |

**【已确认】** 每条杂谈都能匹配到一个已发生的事件 ID（基线 §7.4 验收项 C1）。**【建议】** 因此「来源事件 ID」是必填字段而非可选元数据。→ 不变量 I5。

### 3.9 SimClock — 模拟时钟

| 项 | 内容 |
|---|---|
| **持有状态** | 当前模拟时间；**日序号**与**日内进度**（**【建议】**，见 §3.9.1）；已处理的模拟步序号；时间倍率设置 |
| **由谁创建** | 会话生命周期（应用层） |
| **由谁修改（唯一写者） | 模拟时钟与调度模块 |
| **谁读它** | 全部领域模块（事件时间戳、行动耗时）、表现层（显示时间） |

#### 3.9.1 「日序号 + 日内进度」 **【建议】**

**【建议】** `SimClock` 在「当前模拟时间」之外，**再持有日序号与日内进度两个字段**，日界为模拟时间的函数。（依据 `07` **D-009 R-2**，回填自 `03` §2.6 方案 (b) / §10.1 R-2。）

**为什么现在加：**

- 「日」是基线 §3.3 已有的**村庄循环单位**，不是本文新造的刻度。基线已经用它描述村庄的一天怎么过。
- 若 `SimClock` 只有连续时间，则任何「一天过去」类语义都只能由显示层用 `Math.Floor` 现算。第二阶段接入玩法时这不是加法，是**破坏性改动**。
- 便宜的改动现在做：两个字段是加法，晚做是重写。

**【待定】** 这两个字段**依赖 T-001**（模拟时间与现实时间的关系、时间倍率）：日界落在模拟时间的哪一点、一日多长，全部由 T-001 决定。本文只要求这两个字段**存在且可存档**，不定义日界的算法——**日序号与日内进度必须保持互为函数**，不允许各自独立演进。

**【建议】** **这两个字段为【建议】级**：D-009 R-2 批准回填，但确认权仍在开发者。

**【待定】** 模拟时间与现实时间的关系、时间倍率、英雄行动频率、是否可暂停 / 加速 / 单步（核心玩法循环 §8 第 1–2 项；开发计划 §2）。本文只要求它**存在且可存档**，不定义它怎么走。

### 4.2 引用表

**每一行的「引用断了会怎样」都是一个必须实现的行为，不是注释。**

| 引用方 | 引用目标 | 引用类型 | 引用断了会怎样 |
|---|---|---|---|
| 村庄 | 建筑实例 | 拥有 | **不允许断。** 加载时发现孤立建筑实例 → 存档校验失败并给出可理解报错（基线 §13.7） |

| 任务 | 参与英雄 | 快照 ID | 派发时校验全部英雄存在且未被冲突占用（不变量 I2）；加载时校验 ID 可解析，解析不到 → 校验失败（基线 §13.7 明列「任务参与者丢失」） |
| 队伍 | 成员英雄 | 快照 ID | 同上。**且不允许通过「读到当前队伍」反推成员**（§3.5 理由） |
| 副本实例 | 参与英雄 | 快照 ID | 同上 |
| 副本实例 | 战斗结果 | 至多一个 | 无战斗结果且状态为已结束 → 校验失败（结束却没有结果） |
| 副本实例 | 「结算已应用」标志 | 内含 | 读档后该标志必须恢复为真，否则会重复发奖（基线 §13.7） |
| 战斗结果 | 参与英雄 / 产出引用 | 快照 / 弱 | 产出引用失效 → 结算时明确报错，**不发一半奖** |
| 结算 | 副本实例 + 战斗结果 | 强 | 见 §5 不变量 I4 |
| 杂谈条目 | 领域事件 ID | 强且必填 | 找不到来源事件的条目 = 伪造事件（核心玩法循环验收项 C9），加载与测试均应判失败 |

| 英雄 | 持有物 / 队伍 / 任务 | 弱或反向 | 英雄被移除时其参与记录不得留下悬空引用；但**第一阶段没有「移除英雄」的操作** |

## 5. 关键不变量

**每条不变量必须能写成一个断言。** 括号内是建议的断言形式；带【待定】的不写断言，等规则确定后再补。

### 5.1 已确认派生

| # | 不变量 | 来源 | 断言形式（建议） |
|---|---|---|---|
| **I1** | 同一时刻，一个英雄 `Id` 对应且只对应一个英雄实体 | 【建议】 | `Distinct(HeroIds).Count == HeroIds.Count` |
| **I2** | 同一英雄同一时刻至多被分配到一个进行中的任务 | 开发计划 M4 | 对每个英雄 `h`，`Count(mission where m.Status==进行中 and h in m.Heroes) <= 1` |
| **I3** | 一个副本实例至多关联一个战斗结果 | 【建议】（基线 §8.2 要求结算明确） | `Count(BattleResults of run) <= 1` |
| **I4** | **已结算的副本不能重复结算**：同一副本实例的结算只能被应用一次 | 【已确认】基线 §13.7「重复发放奖励」；开发计划 M6/M7 | 对同一 `DungeonRun` 连续调用两次结算，断言资源 / 持有物 / 英雄状态的**增量第二次为零**；结算前后存读档再断言一次 |
| **I5** | 每条杂谈条目恰好对应一个已存在的事件 ID；同一事件 ID 至多一条杂谈 | 【建议】（基线 §7.4 C1/C2） | `Every(e => e.SourceEventId 存在)` 且 `GroupBy(SourceEventId).All(g => g.Count() <= 1)` |
| **I6** | 死亡与复活不产生任何持久代价 | 【已确认】基线 §4.6 | 断言：死亡前后英雄的**属性、持有物、可用性完全一致**；**关系的变化必须能追溯到基线 §9 的行为链，且不得由死亡本身直接产生**；不存在表示永久损失的状态字段 |
| **I7** | 运行时状态不得写回静态定义 | 【已确认】基线 §13.6 | 跑完一局后静态定义对象的字段集合与运行前完全相同 |
| **I8** | 关系是有向的二元记录（A→B 与 B→A 分别存储） | 【已确认】基线 §9.3「双向且可不对称」 | 断言存在 `(A→B 恶化) ∧ (B→A 未恶化)` 的状态。**第一阶段只建模方向性存储，不建模关系变化的触发规则**（规则属【待定】） |
| **I9** | 领域层不依赖 Godot 类型 | 【已确认】基线 §13.3 | 领域层程序集可在无 Godot 运行时的条件下编译并运行全部规则层测试 |
| **I10** | 跨模块的状态改变只经由拥有该数据的模块 | 【已确认】基线 §13.5、验收项 V4 | 每个领域的写入点只有一个；通过写入点审计或测试替身计数验证 |
| **I11** | 存档加载先校验 ID 与引用，再恢复状态 | 【已确认】基线 §13.7 | 构造一份引用损坏的存档，断言加载**失败并报出可理解的错误**，而不是部分恢复 |

**【建议】** I6 的断言**不能写成「快照全等」**。那样写会让「英雄死在 PvP 追杀链里、关系因 §9 行为链合法恶化」这一合法行为**测试失败**（详见 §3.2 的例外说明）。建议写成三条断言：

| # | 断言 | 断的是什么 |
|---|---|---|
| 1 | 死亡前后的 `属性` / `持有物` / `可用性` 快照**全等** | 死亡代价。直接比对三个字段 |
| 2 | 死亡后若关系发生变化，则每一条变化都能追溯到**某个基线 §9 的行为链事件 ID** | 「死亡顺带恶化关系」这一伪代价 |
| 3 | **不存在**任何由死亡路径直接写入关系存储的调用点 | 同上，且是静态可查的（写入点审计，同 I10 的验证方式） |

**【建议】** 第 1 条用快照全等即可，**不需要**排除任何东西；第 2、3 条共同承担「例外」这一侧。这样拆开之后，死亡**本身**仍然是无代价的，而 §9 行为链的合法后果不被误判为违约。

**【已确认】** 第一阶段的简化：§7 **不建模 §9 行为链**（开发计划 §6）。因此在第一阶段，断言 2 退化为「**不存在任何关系写入点**」，断言 3 直接成立——两条都**可以现在就写成断言**，不需要等关系规则定案。

### 5.2 建议补入第一阶段的不变量

以下五条把上文的散点串成断言，全部标【建议】：前四条依赖尚未确定的规则，I16 不依赖待定项，它依赖的是 `03` 尚未确认的**占用模型本身**。

| # | 不变量 | 依赖的待定项 | 现在能断言什么 |
|---|---|---|---|
| **I12** | 资源与货币不会变为负数 | 资源种类、数值（核心玩法循环 §8 第 6 项） | 只能断言「扣减前检查充足」这一**流程**成立，不能断言具体数值 |
| **I13** | 模拟时间单调不回退 | 时间倍率与暂停规则（§8 第 1 项） | 只能断言 `SimClock.Now` 的取值序列非递减 |
| **I14** | 已结束的任务不会回到「进行中」 | 失败条件（`04`） | 加载一份已结束任务的存档，断言加载后其状态仍为已结束（基线 §13.7 明列） |
| **I15** | 结算要么完整应用，要么不应用 | 奖励内容（`04`） | 断言结算中途失败时，村庄资源与英雄持有物的**总增量要么全为 0，要么等于结算结果给出的完整增量**，不存在部分入账 |
| **I16** | 同一英雄同一时刻至多处于**一个行动**（日常活动与队伍任务合并计数） | **无待定项**；依赖 `03` §4.2 的占用模型（**【建议】**）。行动频率与耗时属 T-002，但 T-002 **不影响**本断言的成立 | 对每个英雄 `h`，`Count(actions where h is owner) <= 1`。**建议表述为 I2 的上位不变量**：I2 只管「至多被分配到一个**进行中的任务**」，I16 管「至多处于一个**行动**」，同时覆盖日常行动与队伍任务 |

**【建议】** I16 与 I2 **不重复**，两者可同时成立、可同时被违反，互不替代（依据 `07` **D-009 R-2**，回填自 `03` §4.2 / §10.1 R-2）。

**【建议】** I16 的写入侧仍受 I10 约束：`05` §2.3 已定英雄模块是「当前所在活动」的唯一写者，因此占用状态的写入**只能**由英雄模块完成。

## 6. 实体与「一次典型游戏过程」的对应

**【建议】** 用核心玩法循环 §3 的六个阶段检查本文的模型是否覆盖完整：

| 阶段 | 涉及的实体 | 本文是否已定义 |
|---|---|---|
| A 观察村庄 | Village、BuildingInstance、Hero、ChronicleEntry | 是 |
| B 创造生活条件 | 建造命令 → Village / BuildingInstance | 是（规则细节待定） |
| C 英雄自主生活 | Hero 当前状态与所在活动 → DomainEvent | 是（**决策规则不在本文**，属 `03`） |
| D 观察并决定是否干预 | ChronicleEntry、只读查询 | 是（**干预权限边界属【待定】**） |
| E 组队并攻略副本 | Squad → Mission → DungeonRun → BattleResult | 是（**副本与战斗规则属 `04`**） |
| F 结果回流村庄 | Settlement → Village / Hero / DomainEvent | 是（**奖励内容属 `04`**） |

**【已确认】** 副本**不应只是一个与村庄无关的战斗界面**；至少要有一条真实、可验证的结果路径回到英雄生活或村庄经营（核心玩法循环 §3 阶段 F）。本文用 `Settlement`（结算）作为这条路径的唯一执行者，使它在模型上无法被绕过。

## 9. 与既有 `design/registry/entities.yaml` 的关系（需开发者裁决）

**【建议】** 仓库中已存在一份实体注册表 `design/registry/entities.yaml`，其中登记了 `inhabitant`、`bond_pair`、`material_id`、以及常量 `day_length_seconds: 75`、`squad_max: 4`、`building_tier_max: 5` 等条目，并注明来源为 `design/gdd/*.md` 下的若干 GDD。

**这些条目与本文存在直接冲突，本文没有采用它们**，理由如下：

| 注册表条目 | 冲突点 |
|---|---|
| `day_length_seconds: 75`、`work_rate`、`is_online_at`（含 `UtcOffset` / `PlayHours` / `Diligence`） | 这些公式把**疲劳与作息**当作已定机制，而基线 §4.4 明确说疲劳性质**未定**。基线 §0 规定【待定】项不得由实现者填空 |
| `squad_max: 4` | 基线与核心玩法循环均未确认队伍人数（核心玩法循环 §8 第 5 项、§3 阶段 E） |
| `building_tier_max: 5` | 注册表自身注明该「直线层级模型」已被 `functional-buildings.md` 的依赖网取代；而基线 §12.2 又把多维成长整个标为【待定】 |
| `material_id`（六种材料） | 基线未确认材料种类 |
| `bond_pair` 的七字节双向编码、`grudge_with` ×0.50 软惩罚 | 属数值与编码细节；`grudge_with` 条目自身还登记着「硬禁止还是软惩罚」的未决冲突 |

**【建议】** 在开发者裁决之前，注册表中的这些条目应视为**与本基线不一致、暂不生效**，而不是本文与它二选一。裁决方式二选一：

- **(a)** 这些 GDD 与注册表属于另一条设计线，与 V1.2 基线并行存在 → 注册表需要标注为不属于本基线；
- **(b)** 它们是 V1.2 之前的设计产物，已被基线取代 → 相关条目应按注册表自己的规则标 `status: deprecated`，而不是留着让人误当成定案。

**本文不擅自执行 (a) 或 (b)**——修改注册表状态会影响其他文档，需要你决定。
