## 1. 本轮要解决什么

R-05 二轮（`07` **D-052**）的采集暴露了两个**机制级**问题：

1. **成交笔数从 155 笔/百天掉到 50–70 笔/百天**（未归零），当时推断根因是
   「自主购物『买什么』判据里的**背包上限 5 份/物品**」。
2. **5% 村抽是单向货币沉淀**（钱只在英雄之间循环，每笔 5% 永久进村库，没有反向货币来源）。

本轮只处理**问题 1**，并补上它的**测量缺口**：

> ⚠️ **「背包满占未成原因比重」此前从未被直接测过** —— 流水里**只记**副本结算 / 掉落 / 交易，
> **不记未成原因**。所以「背包上限是根因」一直只是**代码推断 + 曲线猜测**。
> 本轮先把这个缺口补上，再谈修法。

**本轮范围（开发者拍板）：** 审计 + 修复 + 重新采集。
**货币沉淀（问题 2）单独立项，本轮不碰。**

## 2. 阶段 0：审计结论 —— 「5 份上限」根本不是一条全局规则

### 2.1 三条硬事实

| 事实 | 证据位置 | 含义 |
|---|---|---|
| 英雄背包的**领域层容量是 0 = 无限** | `src/HeroAgent.cs:234`（`Bag = new Inventory()` → `Inventory.cs:32` 默认 `capacity = 0`）；读档恢复同样不设容量（`src/Main.cs:3371`） | `Inventory.TryAdd` 的容量防线（`src/Domain/Items/Inventory.cs:101`）**从不生效** —— 没有任何路径能因「背包满」而拒收物品 |
| 「5 份」只写在**自主购物决策层** | 原 `src/Application/HeroBehaviorService.cs:262`（内联魔数 `>= 5`） | 战利品入包、摆摊卖货、玩家手动购买（`StallMarketService.BuyAsMuchAsPossible` → `StallMarket.BagRoom` 返回 `Unlimited`）**全都不受它约束** |
| 抽中摊后若背满 → **整笔放弃** | 同上 `:262-269`（`SkipReason.BagFull`） | 当天的购物机会就此浪费：`LastShoppingDay` 不写（明天还有机会），但**今天不会再看第二个摊** —— 村里还有别的摊，英雄根本没去看 |

### 2.2 这条审计改变了什么

- **「取消上限」在当前代码里没有意义**：领域层本来就没有上限。
  开发者拍板的修法（「把判据移到抽样前」「不取消上限」）是**唯一自洽**的：
  它既保住了「每种物品最多 5 份」这条约束，又让它**只管该管的那条路径**。
- **上限被提取为具名常量** `HeroBehaviorService.BagItemLimit = 5`，
  并在注释里写明「它只管自主购物这一条路径，**不是一条全局规则**」——
  避免下一个读代码的人误以为领域层有容量。

### 2.3 顺带发现的一处**采集器**特性（不是游戏规则）

`Main.OpenStallsForCollection`（`src/Main.cs:2316-2323`）遍历 `Bag.Snapshot()`，
**取第一个可售物品**摆摊（`break`）。而 `Snapshot()` 按 `ItemId` 的 **Ordinal** 排序 ——
`布匹(U+5E03) < 木料(U+6728) < 石料(U+77F3)`。

**后果**：只要英雄背包里还有布匹，他**永远只卖布匹**，木料与石料会一直囤在背包里卖不掉。
这解释了本轮采集里「布匹占成交金额 90.9%」的极端结构 ——
**它是采集器摆摊策略的产物，不是游戏规则，也不能外推到真实玩法**（真实玩法里玩家自己决定卖什么）。

## 3. 阶段 1–2：实施（三项 + 一个测量缺口）

### 3.1 修法一：背包上限判据**移到抽样前**（与 R-03 同构）

`src/Application/HeroBehaviorService.cs`：

```
抽样前过滤 = 非自己的摊（R-03 已有） ∧ 背包里该物品未满（D-053 新增）
```

- 抽中的摊**一定**背包装得下 → 「抽到才发现背满 → 整笔放弃」这条路**不存在了**。
- 过滤后**没摊可买**时，原因分两种，**不能混报**：
  - 村里只有自己的摊 → `OnlyOwnStall`（R-03 原语义不变）
  - 有别人的摊但该物品都背满 → **`BagFull`**（保留原枚举值与玩家可见文案）

### 3.2 修法二：一次买**尽可能多**

```
买量 = min(摊位库存, 余额 ÷ 单价, 背包余量)     ← 复用 StallMarket.MaxAffordable
背包余量 = BagItemLimit - 背包里该物品数量        ← 按 5 份上限算
```

**为什么余量按 5 算、而不是按领域容量（无限）算**：
若用无限，「买尽可能多」就等于**取消上限** —— 一次买光整摊、背包无上限囤积，
与「不取消上限」直接冲突。故余量走决策层的 5 份上限 → **单次最多 5 份**。

> `StallMarket.BagRoom` 按**领域容量**算（`Inventory.Capacity`），而领域容量是 0（无限）→ 它永远返回
> `Unlimited`。两者是**不同的尺子**，混用会让「上限」名存实亡。故本轮在
> `HeroBehaviorService` 内另立私有 `BagRoom`（按 `BagItemLimit`），并在注释里写明差别。

### 3.3 补测量缺口：未成原因落进流水

**为什么不能走领域事件**：`DomainEvent` 在**构造期**就拒绝 `ChangedStates` 为空的事件
（`src/Domain/Events/DomainEvent.cs:42-43`：「不改变任何状态的事件按定义就是装饰」）。
未成交**没有任何状态变化**（钱没动、货没动、库存没动、`LastShoppingDay` 也不写）
→ **不得伪造事件**。走 `EconomyLog` 的**专用直写入口**，与 R-07 的每日汇总同一先例（读数不是事件）。

| 改动 | 位置 | 内容 |
|---|---|---|
| 新行类别 | `src/data/EconomyLog.cs` | `ShoppingMissedKind = "ShoppingMissed"`；`EconomyRow.Reason`（存**枚举名**，不存自由文本） |
| 直写入口 | `src/data/EconomyLog.cs` | `AppendShoppingMissed(simTime, hero, reason, seller?, item?)`；没有领域事件 ID → 合成 `missed-{日号}-{序号}`（文件内唯一） |
| 口径唯一 | `src/Application/Stall/ShoppingFeedback.cs` | 新增 `IsWorthShowing(reason)` —— **与 R-07 的玩家可见口径同一份规则** |
| 接线 | `src/Main.cs` | `RecordShoppingMissed(results)`：只记「想买没买成」那四类（钱不够 / 背包满 / 没成交 / 只有自己的摊）；噪音四类**不记** |

> **为什么只记四类**：「今天不想买 / 不在场 / 已经买过 / 村里没摊」**不是**「想买没买成」，
> 记进去会让**分母失真** —— 而「背包满占未成原因多少」这个结论全靠分母。
> 口径与 R-07 的花名册行尾、每日汇总**共用一份规则**（`ShoppingFeedback.IsWorthShowing`），
> 免得两套口径对不上，流水与玩家看到的汇总打架。

### 3.4 明确**不做**的

- **不**把「5 份」提升到领域层（不改 `Inventory` 容量）—— 那会连带改变战利品发放、
  摆摊、玩家手动购买等**本轮范围外**的路径。
- **不**改价格、掉落权重、稀有度、胜率、税率；正式数值仍**【待定】**。
- **不**碰货币沉淀（问题 B）—— 单独立项。
- 存档**版本不变**（仍 0.5）、**无新增存档字段**。

## 5. 阶段 4：重新采集 —— 一次**作废的采集**与它教给我们的东西

### 5.1 第一次采集：跑的是**旧代码**，数据作废

第一次采集（1000 天）产出的数据看起来「很像样」：成交笔数 707 → **1220**（+73%）、
成交金额 3280 → 5942 金。但它**不是新代码跑出来的**。

**根因**：

- Godot headless 运行加载的是 **`.godot/mono/temp/bin/Debug/`** 下的程序集；
  而本轮我只构建了 **Release**（`dotnet build -c Release` / `dotnet test -c Release`），
  **Debug 目录里还是 12:14 的旧程序集**。
- 于是采集跑的是**旧逻辑**（一次只买 1 份、没有未成流水行）。

**怎么发现的**（**靠数据自证**，不是靠猜）：

| 自证点 | 期望（新代码） | 实际（旧代码） |
|---|---|---|
| 成交行的 `Qty` | 应出现 > 1 的单笔份数 | **全部 = 1**（1220 笔全是 1 份） |
| `ShoppingMissed` 行 | 应存在 | **0 条** |
| `--econlog` 逐人明细 | 应出现「买了 X×2/×3」 | 全部「买了 X×1」 |

> ⚠️ **更危险的是**：那轮旧代码采集的成交笔数（1220）比旧基线（707）**高了 73%**，
> 差点被当成「修法生效」的证据写进报告。
> **跨版本对比在这套采集器上极不可靠 —— 种子每次都不同**（见 §5.2）。

**处置**：作废该数据文件（`rm`），**同时把 Debug 与 Release 都重新构建**，再重采。

### 5.2 采集的**不可复现性** —— 跨版本比较必须给区间

`Main.BootSeed = Environment.TickCount * 2654435761 + 1`（`src/Main.cs:65-66`）——
**每次运行的种子都不同**。所以：

- 同一份代码两次跑出的数据**也不同**；
- 单次采集的「成交笔数」差几十个百分点是**噪声**，不是机制差异。

**本轮因此采了多份样本**（每份 1000 模拟天）：

## 6. 阶段 4 的结果：**原假设被实测推翻**

### 6.1 未成原因分布 —— 本轮的核心产出

| 原因 | N1 | N2 | **合并** |
|---|---|---|---|
| **钱不够**（`NotEnoughGold`） | 997（85.0%） | 754（80.6%） | **1751（83.0%）** |
| 只有自己的摊（`OnlyOwnStall`） | 116（9.9%） | 90（9.6%） | 206（9.8%） |
| **背包满**（`BagFull`） | 60（5.1%） | 92（9.8%） | **152（7.2%）** |
| 合计未成行数 | 1173 | 936 | 2109 |

> ### 🔴 结论与原先的推断**相反**
>
> R-05 二轮推断「**背包上限 5 份/物品是成交量的硬顶**」。
> **实测：背包满只占未成原因的 5.1%–9.8%（合并 7.2%）。**
>
> **它是真实存在的约束（60–92 次/1000 天），但不是主因。**
> **真正的主因是「钱不够」—— 83.0%。**
>
> 也就是说：**「背包上限导致成交下滑」这个根因判断是错的**，
> 错在**它把「英雄没钱」误认成了「英雄背满了」** ——
> 而当时的流水里**根本没有未成原因**，两种可能长得一模一样。

**为什么**：初始货币池 = 3 英雄 × 100 金 = **300 金**。

- **旧代码**：每次买 **1** 份 → 钱消耗慢 → 成交虽低迷（10–70 笔/百天），但**能撑到第 ~1000 天**。
- **新代码**：每次买 **2–3** 份 → 钱消耗快 → 1000 天成交额抬到 ~5920 金，
  5% 村抽抬到 ~296 金（≈ 初始池的 **99%**）→ **第 219–261 天钱彻底见底，交易归零**。

> 这不是新引入的缺陷 —— **货币沉淀（问题 B）在旧基线里就存在**
> （O1 抽走 164 金 = 初始池的 55%，O2 抽走 71 金）。
> 本轮只是因为成交额变大，把**慢性收缩**变成了**急性停摆**：
> **成交活跃期从 ~1000 天缩到 ~240 天**。
>
> **必须诚实说明**：本轮修法**加剧**了货币沉淀的显现速度。
> 这与开发者「先做可靠的第一版」的范围约定不冲突（背包上限修法本身是对的，
> 抽样前过滤 + 买尽可能多都是按拍板实施的），
> 但**货币问题必须尽快单独立项** —— 否则修完背包上限，经济反而更早停摆。
>
> ⚠️ 同时也说明：**「买尽可能多」是否保留，最终取决于货币规则怎么定** ——
> 若货币侧补上回流机制，买尽可能多带来的成交额放大是**好事**；
> 若货币侧不动，它就是把停摆提前了。本轮**不**擅自改税率或加金币来源（超出范围）。

### 6.4 成交结构剧变：布匹独占（**采集器产物，未完全解释**）

各样本的成交**金额**结构：

| 样本 | 布匹 | 石料 | 木料 |
|---|---|---|---|
| **N1（新）** | **90.9%** | 7.2% | 1.9% |
| **N2（新）** | **86.8%** | 5.6% | 7.5% |
| O1（旧） | 24.6% | **49.8%** | 25.5% |
| O2（旧） | 11.3% | **64.7%** | 24.1% |

**这是系统性的版本差异**（新代码两份都是布匹 ~87–91%，旧代码两份都是石料 ~50–65%），
**不是**跨样本噪声。

**部分原因见 §2.3**：采集器摆摊取 `Bag.Snapshot()` 里**第一个**可售物品
（Ordinal 序 → 布匹 < 木料 < 石料），所以英雄背包里只要有布匹就**只卖布匹**，
木料与石料会一直囤着卖不掉。布匹是唯一在流转的材料 → 成交额集中在布匹。

> ⚠️ **但这一条没有完全解释**：旧代码两份样本反而是**石料**主导。
> 差额来自背包/金币动态与「买 1 份 vs 买尽可能多」的相互作用，
> 本轮**未做进一步追查**（超出本项范围）。
> **列为遗留**：下次采集前应先决定采集器的摆摊策略是否要改
> （例如「每种可售物品都摆一点」），否则成交结构会被这条采集器规则主导，
> 数据的代表性有限。
>
> **明确边界**：这是**采集器**的产物，**不是游戏规则**，**不能外推到真实玩法**
> （真实玩法里由玩家决定卖什么）。

## 7. 本轮结论

1. ✅ **修法实施到位**：判据移到抽样前；一次买尽可能多；上限仍在（5 份，单次最多 5 份）。
2. ✅ **测量缺口补上**：未成原因进流水（`ShoppingMissed`），口径与 R-07 共用一份。
3. 🔴 **原假设被推翻**：背包满只占未成原因 **7.2%**（合并两样本），
   **钱不够占 83.0%** —— 「背包上限是成交硬顶」的说法**不成立**。
4. ⚠️ **新副作用**：成交额 3280→~5920 金（+80%）→ 村抽 164→~296 金 →
   **成交活跃期从 ~1000 天缩到 ~240 天**（新样本最后一笔在第 219 / 261 天，旧样本在第 990 / 998 天）。
   货币沉淀（问题 B）由**慢性**变**急性**。
5. ⚠️ **方法论**：旧代码的采集方差极大（成交笔数 318–707，成交额 1422–3280，**2 倍以上**）→
   **单次采集不能用于跨版本比较**；本轮因此采了 2+2 份样本，并按区间下结论。
   另：Godot headless 加载 **Debug** 程序集，只构建 Release 会**跑旧代码**（本轮踩过，见 §5.1）。
6. ⏳ **正式数值仍【待定】**：掉落权重 / 基础价格 / 稀有度归类 / 长期供需稳定性 ——
   **本轮不自动定案**（D-053 §4）。
