### 2.1 临时参数的使用纪律 **【已确认】**

开发计划 §二：「为了让原型运行，可以采用明确标注的临时参数，
但临时参数必须集中管理，**不能悄悄变成正式设计规则**。」据此定四条纪律：

| # | 纪律 |
|---|---|
| 1 | 占位值只在本表出现一次，代码里通过**具名常量 + 【待定】标注**引用，**不写裸数字** |
| 2 | 每处占位必须注明它服务于哪个 T 编号，开发者拍板后由该 T 项统一替换 |
| 3 | 占位值**不得**出现在设计文档里冒充定案，也不得被引用为「平衡依据」 |
| 4 | 占位值失效时**允许游戏跑不通**（抛异常或拒绝行动），**不得**用兜底数字掩盖 |

> **第 4 条的理由**：一个填了兜底数字的参数，会让「这个规则还没定」这件事
> 在运行时彻底消失 —— 然后它就变成了事实。

---

### 2.2 为何本次设了占位值 **【建议】**

`VillageLife` 整体删除后，村庄失去每日事件（D-012 记录的功能回归）。
恢复它的正确做法是让 `Domain/Heroes/DecisionFlow` 驱动，而 `DecisionFlow`
需要活动定义集，活动定义集需要 **P-04（耗时）** 与 **P-06（取值范围）**。

**停在回归状态 vs 填占位值继续**：本次选择后者，理由是
「村庄不再过日子」是基线核心幻想的缺失，比一个待校准的数值严重得多。
占位值按上文四条纪律管理，开发者拍板 P-04/P-06 后由 DecisionFlow 统一校准。

### D-004 · 活跃缺陷 C-01 立即单独修复

**日期：** 2026-10-17
**决定人：** 开发者
**状态：** 已完成

**修复内容** `src/Chronicle.cs`

**原缺陷**

`Outcome(..., "refuse")` 的 switch 只认 `over` / `pocket` / `fail`，`"refuse"` 落到 `default => "good"`，于是**拒绝出工的英雄被记成「不但做完了，还在矿洞多待了半日」**——杂谈与领域事实相反。

**修复方式（不是简单加一行 switch）**

1. `kind == "refuse"` 走独立分支，**不再经过会回落 `"good"` 的通用 switch**
2. 该性格没有自己的 `refuse` 模板时，回落到 `RefuseFallback`（傲的拒工文案），**而不是 `"good"`**

### D-015 · 拒绝点前移到构造期，流程侧的死分支已删除 **【已确认】**

**日期：** 2026-10-18　**触发：** M5 验收时发现一个**烧不着的守卫**。

**发生了什么**

`BattleResult.Produce` 在本轮加了两条构造期防线（日志非空、日志含关键事件、
日志条目 ID 互不重复）之后，`DungeonFlow.CiteAndVerify` 里的
`if (!IsVerifiableAgainstLog()) throw` 分支**已经不可能触发**。

逐条推演 `IsVerifiableAgainstLog()` 返回 `false` 的四个理由：

| 理由 | 为何被上游堵死 |
|---|---|
| `DecidingEntryIds` 为空 | `Produce` 已保证日志至少一条 `DecidedOutcome`，此处选出的条目非空 |
| 引用了日志里没有的条目 | 引用的 ID 全部取自 `result.Log` 本身 |
| 同一条被引用多次 | `Produce` 已保证日志条目 ID 互不相同 |
| 引用了非判定条目 | 此处按 `DecidedOutcome` 过滤过 |

**已采取的处理**

1. 删除该死分支，方法改名为 `CiteDecidingEntries`，`stage` 参数随之移除
   （结果标识本身已含阶段信息，见 `BattleResultIdFor`）。
2. `Advance` 的 `<exception>` 文档改正：现在「交不出判定依据」抛的是
   `Produce` 的 `ArgumentException`，不是 `InvalidOperationException`。
3. 相应测试改名为 `..._IsRejectedAtConstruction_...`，
   并新增 `module.Calls == 1` 断言 —— **没有这一条，宽泛的
   `catch (ArgumentException)` 会把「流程在解算之前就抛了别的
   `ArgumentException`」也一并放过，那样的绿灯什么都没证明。**
4. 补 `Advance_WithANullLog_...`：验证「根本没有日志」这条**不同的洞**
   （拒绝点在读胜负结论之前，连 `DidHeroesWin` 都不该被调用）。
   该测试已**看着它红**（拆掉守卫后仅此一条转红）后才算数。

**为什么删而不是留**

> 烧不着的守卫比没有守卫更糟：它让读代码的人相信这里存在一道检查。
> 拒绝这件事**仍然成立**，只是落点前移到了构造期 —— 更早、也更强。

### D-018 · 领域 `Village` 首次被实例化；材料收敛到一个桶 **【已确认】**

> 只打总数的话，「进错桶」这类 bug 在界面上完全看不出来。

**I15 在 `ApplyWrites` 里怎么保证的**

4. **编成没被存档。** 读档时只能「按在场者取前 N 个」重建 —— 那是**猜测**：
   玩家挑好的搭配会悄悄换成另一批人，而游戏不会报错。

### D-038 · R-01 / R-02 暂不接线（阻塞于内容/设计缺失）**【已确认 · 自拍】**

**日期：** 2026-10-19　**触发：** 开发者要求「处理 R-01、R-02 这类已经明确的缺口，决定是否接线」。

**决定**

| 缺口 | 决定 | 理由（实读代码） |
|---|---|---|
| **R-01** `HeroBehaviorService` 未接线 | **暂不接线** | 物品从未进入英雄背包：`HeroAgent.Bag` 默认空；全仓 `TryAddItem/RestoreBag/new Inventory` 只出现在读档与「购买收货」路径，**没有任何产出/掉落/初始配给**。因此 `OnStall` 的「持有可售物品 ≥ 1」永不成立 → 没有 Open 摊位 → `SimulateShopping` 接线后也永远 `Skipped_NoOpenStall`。 |
| **R-02** `AppliedTradeKeys` 未落盘/未使用 | **暂不接线** | `StallService.BuyFromStall` 明确**不走 TradeId/Settlement 幂等**（逐笔直接 I15 提交）；`Settlement.ApplyTrade/ITradeSettler` 是给「英雄 ↔ 英雄」直接交易预留的，而该路径**不存在也未设计**（P2-D08：仅英雄买摊位商品）。现在落盘 `AppliedTradeKeys` 只会得到一份没有生产者的死数据。 |

**共同理由：** 现在接线会产生两段**永远不会执行的代码**，违反 D-015「不养烧不着的守卫」。

**解锁前置**

1. 先定「英雄的物品从哪来」（内容/经济设计决策）——这是 R-01 的真前提；
2. 若要英雄 ↔ 英雄交易，先定 P2-D08 的扩展与 TradeId 接入方式——这是 R-02 的真前提。

**已做（不依赖上述决策的部分）：** R-03 读档丢英雄行动态已修复（见 D-039）。
