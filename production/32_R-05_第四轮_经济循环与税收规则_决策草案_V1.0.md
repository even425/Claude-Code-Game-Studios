## 一、决策背景

根据《货币流入与村庄税专项·审计报告 V1.0》，当前已实现的经济系统存在以下问题：

1. 英雄开局每人获得 100 金，此后没有已实现的常态金币来源。
2. 英雄之间的摊位交易会将成交金额的 5% 转入村庄金库。
3. 村庄金库当前没有已实现的金币支出路径；现有村庄升级消耗的是材料。
4. 英雄金币不足时，自主购物会直接放弃，没有替代收入路径。
5. 工作产出的材料进入村庄材料池，不进入英雄个人背包。

因此，当前经济系统无法形成可持续的金币循环。R-05 第三轮的审计还发现，金币不足占购物未成记录的 83.0%，货币沉淀是需要优先处理的机制问题。

本决策拟先确定经济规则，再根据确认结果制定实施方案。正式掉落权重、掉落次数、基础价格及稀有度映射暂不在本决策中定案。

## 二、核心规则决策

### D-054-01：英雄金币来源

**状态：【建议】**

- 英雄通过副本奖励获得金币。
- 开局每人 100 金的现有规则暂时保留。
- 副本金币奖励应当与副本结算流程关联，不应混同于英雄获得的个人战利品物品或村庄材料奖励。
- 副本失败是否获得金币，需与副本奖励规则统一确定。

**【待定】**

1. 金币奖励是否仅在副本成功时发放。
2. 奖励按副本、关卡、难度还是其他条件计算。
3. 金币奖励是固定值、区间随机值，还是由其他已确认规则决定。
4. 金币奖励发给所有实际参战英雄，还是采用其他分配规则。
5. 副本奖励金币的具体数值。

在上述细节确认前，不确定具体奖励金额，也不将副本金币来源视为已实现功能。

### D-054-02：村庄金库用途

**状态：【建议】**

- 村庄升级同时消耗金币和材料。
- 金币从村庄金库扣除，材料继续按照既有材料消耗规则处理。
- 金库中的金币应当具有明确的用途，不能仅持续累积而没有任何已实现的支出路径。
- 村庄升级的金币成本与材料成本应当分别记录、校验和结算。

**【待定】**

1. 哪些升级需要消耗金币，是否所有升级都需要。
2. 各级升级的金币成本与材料成本。
3. 金库余额不足时的升级失败规则。
4. 金币和材料的扣除顺序，以及失败时如何保证不会发生部分扣款。
5. 是否允许村庄金库用于其他公共建设或服务。

本决策暂不增加其他金库用途；如后续需要，应单独评审。

### D-054-03：村庄税收规则

**状态：【建议】**

- 暂时保留每笔摊位交易 5% 的村庄税率。
- 交易税款进入村庄金库，不直接销毁。
- 允许村庄金库中的金币通过已经明确的规则重新进入可流通经济系统。
- 村庄升级消耗金币是金库的明确支出方向；但这属于金币支出，并不自动等于金币回流英雄钱包。
- 不将“金库有支出”与“经济已经形成完整循环”视为同一结论。

**【待定】**

1. 村庄税款是否仅用于村庄升级，还是允许其他经确认的公共用途。
2. 是否存在金库向英雄返还金币的机制；如存在，返还条件、对象和周期是什么。
3. 金库支出是金币销毁、支付给英雄，还是支付给其他经济参与者。
4. 是否设置金库最低保留金额或其他支出约束。
5. 如何评估 5% 税率在长期运行中的实际影响。

税率暂不修改。任何新增的返还、分红或其他回流机制，均需明确资金流向和结算规则后再实施。

## 三、相关机制规则

### D-054-04：工作材料归属

**状态：【建议】**

- 工作产出的材料继续进入村庄材料池。
- 本轮不将工作产出改为英雄个人背包物品。
- 工作材料归属与英雄金币来源分开处理；本决策选择副本奖励作为金币来源，不以改变工作材料归属来解决货币问题。

**【待定】**

- 工作产出是否存在其他经确认的分配规则。
- 后续是否需要独立设计英雄个人工作报酬；这不属于当前已确认的金币奖励数值。

### D-054-05：「私吞」材料机制

**状态：【建议】**

- 将「私吞」作为独立的灰产机制，后续单独设计。
- 本轮不擅自将私吞材料加入村庄材料池或英雄背包。
- 不把当前 `Pocketed` 计数器直接视为已经实现完整的物品归属与流转机制。

**【待定】**

1. 私吞材料是否实际存在于某个库存中。
2. 私吞行为是否具有可追踪的物品数量和价值。
3. 私吞材料是否可用于交易、隐藏或其他玩法。
4. 是否存在被发现、追责或其他后果。

在单独决策前，不扩展这部分玩法，也不将其纳入本轮经济循环修复。

## 四、采集与验证基础设施

### D-054-06：可选固定随机种子

**状态：【建议】**

- 为经济采集工具增加可选固定随机种子。
- 默认运行行为保持现状，不强制改变日常游戏的随机行为。
- 固定种子用于提高同一代码版本重复采集的可比性。
- 不将固定种子采集结果当作所有随机种子下的普遍结论。

**【待定】**

- 固定种子的命令行参数名称及具体接口。
- 固定种子需要覆盖的随机数来源范围。
- 如何保证不同版本的随机调用顺序变化不会被误解为完全相同的随机过程。

### D-054-07：多商品摆摊采集

**状态：【建议】**

- 采集器支持多种商品参与摆摊和交易。
- 记录各商品的成交笔数、成交份数、成交金额和成交占比。
- 不再仅依据当前单一商品策略推断整体商品经济表现。
- 采集策略与真实游戏的供给规则分开标注；采集器的行为不能自动视为正式游戏机制。

**【待定】**

- 采集器参与交易的商品选择策略。
- 各类商品的供给量、初始库存和补货规则。
- 如何避免商品枚举顺序等实现细节主导采集结果。
- 采集样本数量与重复次数的最终验收标准。

## 五、实施前必须明确的规则

在开始货币侧代码改动前，至少需要确认：

1. 副本金币奖励的触发条件和分配方式。

3. 村庄税款的用途，以及是否存在真正的英雄侧资金回流路径。

上述规则应先写入决策文档，再形成具体实现任务。任何未确认的奖励金额、税款返还比例、升级成本或其他经济数值，继续标记为【待定】。

## 六、实施后的验证要求

以下属于建议的验收标准，具体测试组织方式可在实施方案中细化。

### 6.1 货币守恒

若系统不新增金币，且不销毁金币，则应验证：

`英雄金币合计 + 村庄金库金币 + 税额余数 = 初始金币总额`

若副本奖励创建金币，则应扩展为：

`英雄金币合计 + 村庄金库金币 + 已销毁金币累计 + 税额余数 = 初始金币总额 + 累计新增金币`

该式用于核对金币的创建、持有、转移、销毁与余数结算，不代表货币必须始终停留在英雄钱包中。

> ⚠️ **【2026-10-21 实施中更正 · 上面 §6.1 的式子含一处错误】**
>
> 本节写的两条式子都把 **「税额余数」放进了等式左边**，那是**错的**：
>
> - `英雄金币合计 + 村庄金库金币 + 税额余数 = 初始金币总额`　❌
> - `英雄金币合计 + 村庄金库金币 + 已销毁金币累计 + 税额余数 = 初始金币总额 + 累计新增金币`　❌
>
> **为什么错**：**税额余数不是一笔钱**，它是「5% 税取整后还没凑够 1 金的**记账零头**」。
> `StallFee.Compute` 里 `totalAmount = sellerNet + villageCut` —— 钱在**买家与卖家之间完整转移**，
> 余数只进「下次累计」，**从没从任何人的钱包里被扣走**。
> 把它加进守恒律左边，等于**凭空多算了那部分零头**。
>
> **正确写法**（**§6.1 原文保留，更正如上**）：
>
> ```
> 英雄金币合计 + 村庄金库金币 + 已销毁金币累计 = 初始金币总额 + 累计新增金币
> ```
>
> 余数归**税务口径**管（那是 D-052 已经定过的另一条等式，与货币守恒**不是同一件事**）：
>
> ```
> Σ(villageCut) + 在途余数/100 = floor(5% × 总成交额)
> ```
>
> **实测**（2026-10-21，40 模拟天采集快照）：按**正确**式子 **40/40 天成立**
> （例：末次 `345 + 35 + 0 = 300 + 80`）；按**原**式子只有 **7/40 天成立**
> —— 差的正是那个零头。

### 6.2 交易与税收

- 每笔交易的买家扣款、卖家净收入和村庄税款能够正确对应。
- 税额余数的累计和结转正确。
- 金库支出有明确记录，且不会产生重复扣款。
- 不能把金库支出误认为英雄资金已经回流。

### 6.3 长期经济采集

建议至少记录：

- 副本成功与失败次数、金币奖励总额。
- 英雄金币合计、最低余额及余额分布。
- 村庄金库余额、税收累计和金库支出累计。
- 交易笔数、成交份数、成交金额及商品成交占比。
- 首次交易停摆的时间及停摆原因。
- 固定种子重复运行结果，以及不同种子下的结果区间。

不以“交易必须持续 1,000 天”为硬性目标。应根据最终确认的经济生命周期和金币流向规则判断结果是否符合预期。
