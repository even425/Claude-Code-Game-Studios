## 1. M0 · 现状审计（实测，**两处与草案假设不同**）

草案原文写「以下为预计影响点，需要实施前核对真实调用链」。核对结果：

### 1.1 稀有度在代码里**完全不存在**

`ItemDefinition` 只有 `Id` + `DisplayName`，类注释明写
「稀有度 / 词缀 / 耐久度 / 制作配方——**不做**（计划 §1.3）」。

### 1.2 `ItemDefinition` **全仓无实例化**

13 号审计早就写过「`ItemDefinition` 类存在但全仓无实例化」——
它只在一个测试里被构造过一次（测空 Id 拒绝）。

> **这条改变了实现形状**：稀有度若挂在这个死类上，**仍然是死代码**。
> 所以本轮顺带把它接上 —— 新增 `ItemCatalog` 物品注册表，
> 让「这个 Id 是什么、什么稀有度」有一个**可查、且被掉落表验证器依赖**的地方。

### 1.3 价格链路：与草案的推荐直接冲突

| 事实 | 出处 |
|---|---|
| D-021 / P2-D03 已拍板「固定价格表；**同一物品全球统一价**」，理由是避免「同物不同价 + 套利」 | `07` D-021 |
| `PlaceStall(owner, itemId, qty, simTime)` **没有价格参数**，价从 `_book.PriceOf(itemId)` 取 | `src/Application/StallService.cs:134` |

→ 草案 §5.2 推荐模型 C（英雄自由定价）**被明确不采纳**：它会推翻 D-021，
还要动 `PlaceStall` 签名、`Stall` 校验、摆摊 UI，并重新回答套利问题。
**收益不确定、成本明确 → 保持现状。** 交易链路本轮**一行未动**。

### 1.4 其余核对结果

| 草案假设 | 仓库现实 | 结论 |
|---|---|---|
| 副本阶段可分别掉落 | 现状就是**整场成功后统一掉落**（`ComputeLoot` 在 `ResolveDungeon` 结算时才跑） | ✅ 草案的建议**不用改代码** |
| 掉落配置要验证 | **没有任何验证器可挂**（`SaveValidator` 只管存档） | ⚠️ 需新建 |
| 价格表要版本化 | `SaveGame` **无 Prices 字段** → 价格表**不入档** | ✅ 答案：**不需要版本化** |
| 不可堆叠物品 | `Inventory` 全按 `Id → count` 计数，**所有物品天然可堆叠** | ❌ 首版不做（R-01 的 E06 另开任务） |

| 随机可复现 | `DecisionFlow.SeededRandom`（PCG 风格 LCG），`NextDouble(bound)` 返回 **[0,bound) 的 double** | ✅ 直接复用 |

| 新物品要登记 | `ItemGrantService` 要求物品在 `PriceBook` 中价格 &gt; 0，否则判 `UnknownItem` 拒掉 | ⚠️ R-01 踩过，验证器要把这条守住 |

## 3. 三层结构

```
Domain/Items/     ItemRarity（5 值）
                  ItemDefinition.Rarity（必填）
                  ItemCatalog（Id → 定义 + 稀有度）★ 顺带激活的物品注册表
Domain/Settlement/ LootTable + LootEntry（配置）
                   LootRoller（权重抽取，纯函数）
                   LootTableValidator（错误清单，不抛异常）
Application/       DungeonLootProvider（实现 ILootProvider）
                   DefaultLootTables（占位权重）
```

### 3.1 `ItemDefinition.Rarity` 为什么**没有默认值**

默认值会让「忘了标稀有度」这件事**静默发生** —— 物品悄悄成了"普通"，
直到某天掉落表按稀有度配权重时出了怪事。宁可编译期逼着写。

### 3.2 验证器为什么**返回错误清单而不是抛异常**

掉落表是**策划写出来的配置**。配错了应该由验证器报一条**明确的错**让开发者看见，
而不是让游戏在启动时崩掉 —— 「这个副本今天不掉东西」比「游戏起不来」好对付得多。
这与 `SaveValidator` 的做法一致（它也返回错误清单）。

provider 的降级路径：**配置不合法 → 不发放任何东西 + 把每条错误报给注入的回调**。
回调由 Main 接到 `GD.Print`（`LOOTCONFIG ...`）。

### 3.3 权重**归一化**

表内权重之和可以是任意正数：写 60/30/10 与写 6/3/1 等价。
策划不用凑整 100 —— 凑整 100 的唯一效果是让人以为它有意义。

### 3.4 抽取与分配**共用一条随机子流**

```csharp
var rng = new SeededRandom(LootSplit.DeriveSeed(outcome.Run.Id.Value));
var loot = _lootProvider.LootFor(DungeonName, rng);   // 先抽
return LootSplit.Split(loot, participants, rng);       // 后分
```

- 种子由**副本实例标识**用 FNV-1a 派生 → **同一副本永远得到同一份掉落与分配**，
  读档重放一致。
- 走**独立子流** → 掉落**不插队**进战斗与日常共用的全局随机流
  （一次副本掉落不该改变此后所有战斗与日常的结果）。
- 顺序固定（先抽后分）→ 两条路都不会互相错位。

### 3.5 `ILootProvider` 接口为什么要加随机源入参

原签名 `LootFor(dungeonName, amount)` 是**无随机源的纯查表**。
若 provider 自己 new 一个随机源：
- 每次调用都从同一起点开始 → 「同一副本不同结果」的语义消失；
- 且它的状态不在存档里 → 读档重放得不到同样的掉落。

所以**随机源由调用方递进来**。这是接口必须改的地方，也是 R-05 对既有代码的**唯一破坏性改动**。

### 3.6 占位实现**退役**（删除，不是保留）

`PlaceholderDungeonLootProvider`（R-01 建的）被 `DungeonLootProvider` 取代，**文件已删**。
留着就会有两份「掉落规则」，迟早对不上 —— 而对不上的表现是
「有时掉石料、有时掉布匹、没人知道为什么」。

## 4. 顺带修掉的一处自检**取样时机**错误

`--dungeon` 的「战利品已入档」检查原本在**自检把战利品摆上摊又卖掉之后**才取存档快照：

```csharp
// 旧顺序：开摊 + 卖掉 → 才 BuildSave() → 查「摊主的存档里还有没有这件战利品」
```

卖完之后战利品在**买家**的背包里，摊主的背包已空 —— 查出来自然是「没有」。
**那不是入档失败，是查错了时机。**

R-01 时每次掉落都是 19 份、卖 1 份还剩 18 份，所以这个错误**一直被「数量足够多」掩盖着**。
R-05 的掉落表让每人只分到 1~2 份，它才暴露。

修法：把存档快照与检查**移到战利品刚落地的那一刻**（M4 开摊之前）。

> 这条值得单独记一笔：**一个只在小数值下才暴露的检查错误，会被「数据足够多」长期掩盖。**
> 机制一改（同量级的掉落），它立刻现形。

## 4.5 接缝：抽取与分配**共用一条随机流**

抽取（R-05）与分配（R-01）用的是**同一条子流**，顺序固定为「先抽后分」。
抽取消耗掉的随机次数，决定了分配从流的**哪一段**开始 ——
这是整条链里唯一一处「改了一处、另一处跟着变」的地方。

**所以它必须被测试盯住。** 做法有两条讲究：

### ① 管线要抽成函数，不能在测试里复制一份

```csharp
// src/Domain/Settlement/LootPipeline.cs
public static LootAllocation Run(ILootProvider provider, string dungeonName,
                                  IReadOnlyList<HeroId> participants, string runId)
{
    var rng = new DecisionFlow.SeededRandom(LootSplit.DeriveSeed(runId));
    var loot = provider.LootFor(dungeonName, rng);   // 先抽
    return LootSplit.Split(loot, participants, rng);   // 后分（接着同一条流）
}
```

`Main` 与测试**调的是同一段代码**。若在测试里复制一份管线，
Main 里那两行调换了，测试照样全绿 —— **盯不住接线**。

### ② 表必须**保证有余数**，否则接缝测不到

第一版测试用「抽 3 次 / 3 个参战者」—— 恰好整除，
**分配侧一次随机都没消耗**，接缝根本没被踩到。那个测试因此是**假绿**：
它红不是因为接缝坏，而是因为运气。

改用「抽 2 次 / 3 个参战者」（总数 2 除不尽 3 → 必有余数 → 分配必消耗随机），
并用**固定黄金值**（`h-0|布匹|1; h-1|石料|1`）把「种子怎么派生、抽几次、
抽完分配从哪一段开始」全部钉死。

> **教训**：断言失败时先问「它是因为**该红**而红，还是因为**运气**而红」。
> 这次它红得莫名其妙 —— 顺着查下去才发现接缝压根没被测到。
>
> **机制测试不该被数据调整误伤**：这套测试用**测试自带的表**，不用游戏的默认表 ——
> 二轮调掉落数值时它们照样绿；而机制真变了（顺序、种子派生、随机消耗），它们必红。

## 7. 边界与未做

- **正式数值全部留到二轮**：掉落池、抽取次数、概率、数量区间、基础价格、稀有度归类。
  首版的占位权重（石料 60 / 木料 30 / 布匹 10，抽取 3 次）与 `PriceBook.Default` 的三个占位价同一性质。
- **不采用**「英雄自由定价」；**不设** NPC 回收；**不引入**动态市场、装备词条、保底、经济模拟。
- **不引入**「物品类型」轴与「是否可堆叠」轴（后者要扩 `Inventory` = R-01 的 E06）。
- **掉落表不入档**（静态配置）；已生成的奖励与摊位单价照旧落档，存档版本仍 0.4。
- **稀有度在首版是数据层**，消费方在二轮（价格分档、掉落池分组、界面标记）。
  它**不是死字段** —— 必填、验证器会查。
- 物品**类型**与**是否可交易**本轮不引入；现有物品全部视为可交易（与 R-01/R-02 的行为一致）。
