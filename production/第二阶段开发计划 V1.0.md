## 1. 第二阶段目标

### 1.1 阶段定位

第一阶段已经建立了一个最小可玩闭环，包含：

- 村庄基础场景和模拟时钟；
- 英雄自主行为的基础框架；
- 玩家队伍编成与任务派遣；
- 三阶段副本流程；
- 自动战斗的领域逻辑和战斗日志；
- 副本结果回流；
- 事件记录与村庄杂谈；
- 存档、读档、引用校验及结算幂等保护。

第二阶段不再重复搭建这些基础能力，而是将开发重点转向：

**让英雄在村庄中产生真实的经济活动，让村长通过经营获得收益，并让经济、英雄生活、建筑和冒险逐步形成相互影响的玩法循环。**

第二阶段完成后，村庄不能只是英雄出发和返回的地图。英雄应当能够在村庄里消费、出售物品、进行交易；玩家能够从这些行为中获得经营收益，并观察这些行为对英雄和村庄产生的实际影响。

### 1.2 核心目标

本阶段需要建立以下能力：

1. 基础货币、物品库存与所有权管理。
2. 英雄摆摊、商品出售和交易结算。
3. 村长收取摊位费用。
4. 英雄根据需求自主决定部分生活和经济行为。
5. 村庄建筑与商品、服务之间的基础联系。
6. 交易和生活行为接入现有事件记录与杂谈系统。
7. 经济结果能够保存、加载，并在重复执行或重新加载时保持一致。
8. 经济系统与现有副本、任务、英雄状态建立最小可验证的联系。

### 1.3 本阶段不追求的目标

本阶段不要求一次性完成全部村庄经营玩法。

以下内容暂不纳入本阶段核心交付：

- 完整的英雄召唤、抽卡概率、保底和重复角色处理；
- 复杂欺诈、诈骗识别、纠纷仲裁、PvP 和复仇；
- 完整的城市等级、区域解锁和大型建设系统；
- 完整的市场供需模拟和动态价格经济；
- 大量商品、建筑、英雄和副本内容；
- 完整战斗动画与所有战斗表现优化；
- 全部建筑的建造、升级和维护体系。

如果实现过程中发现某项功能确实是核心闭环的必要依赖，Agent 必须先说明原因、影响范围和替代方案，再决定是否扩展范围，不得自行扩大项目。

## 2. 执行规则与项目保护要求

### 2.1 第一阶段是必须保留的稳定基线

开发开始前，必须检查当前工作区中的代码、文档、测试和版本控制状态。

必须完成：

- 阅读设计基线 V1.2。
- 阅读技术决策记录 D-001 至 D-020。
- 阅读 `production/session-state/active.md`。
- 检查当前 Git 分支、未提交修改和已有技术债记录。
- 运行现有构建与完整测试，记录实际结果。
- 检查第一阶段的八项验收入口和关键领域规则。
- 确认当前实际代码结构与开发总结中的描述一致。

如果当前环境与总结不一致，以实际代码和经确认的权威文档为准，并将差异记录下来。

**禁止在未检查现有代码的情况下直接生成一套新的经济系统。**

### 2.2 不得破坏的技术约束

| 约束 | 执行要求 |
|---|---|
| 技术栈 | 继续使用 Godot 4.7.2、.NET 8、C#；版本是否升级须另行审批 |
| 领域层边界 | Domain 不得引用或依赖 Godot 类型 |
| 架构路线 | 延续 D-001：保留呈现层，改造和扩展领域层 |
| 数据定义 | 不得重新引入已判死的 `entities.yaml` |
| 材料管理 | 延续现有单一材料池设计，不得无理由另建平行库存 |
| 事件系统 | 延续统一事件管道，杂谈不能自行编造事件 |
| 结算机制 | 保留预检、提交、幂等和状态一致性约束 |
| 存档 | 保留引用完整性校验、原子写盘和整份拒绝策略 |
| 随机数 | 延续可保存状态的 `SeededRandom` 方案；不得私自引入不可控随机源 |
| 测试 | 继续运行真实测试命令，不允许以模拟结果或跳过测试制造假绿灯 |

### 2.3 代码变更规则

1. 优先扩展现有领域模型和应用层驱动，不要创建与现有功能重复的管理器。
2. 不要把所有经济规则写进 `Main`、场景脚本或单个大型 `GameManager`。
3. 不允许 UI 直接修改金币、库存或英雄关系。
4. 所有物品和货币变化必须通过明确的领域操作执行。
5. 交易失败时不得出现扣款成功但物品未交付的情况。
6. 不允许为了让测试通过而删除已有有效测试或放宽既有领域约束。
7. 如果必须改变现有接口、存档格式或领域不变量，先记录原因、兼容策略和测试方案。
8. 代码注释使用英文；新增公共类型和复杂业务接口应提供适当的 XML 文档注释。
9. 每完成一个里程碑，都必须运行对应测试和必要的完整回归测试。
10. 新增防线测试时，必须确认测试能够在规则被破坏时失败，而不只是验证正常路径。

## 3. 第二阶段的玩法闭环

### 3.1 目标流程

```text
模拟时间推进
    ↓
英雄根据需求和自身状态选择行为
    ↓
英雄前往摊位、商店或其他已实现的活动地点
    ↓
购买商品、出售物品或进行英雄间交易
    ↓
库存和货币通过交易规则发生变化
    ↓
村长获得已定义的经营收入
    ↓
事件系统记录实际发生的交易和生活行为
    ↓
英雄获得装备、补给或其他已定义物品
    ↓
英雄继续生活或准备下一次冒险
    ↓
冒险结果再次影响英雄物品与村庄经济
```

上图是本阶段的目标流程，不代表所有环节都已经有明确的数值规则。

其中，交易价格、摊位费、英雄购买优先级和具体商品需求均属于待确认规则，必须先确定最小可测试的规则，再进入实现。

### 3.2 最小可玩闭环

本阶段至少必须跑通以下实例：

1. 一名英雄持有一定数量的货币和可出售物品。
2. 该英雄成功开设一个合法摊位。
3. 另一名英雄购买该摊位上的商品。
4. 卖方收到货币，买方获得商品。
5. 双方库存与货币变化符合交易规则。
6. 村长按照已经批准的摊位收费规则获得收入。
7. 交易产生真实事件，并在村庄杂谈中显示有来源的记录。
8. 存档后重新加载，交易结果和收费结果保持不变。
9. 重复处理同一笔已完成交易时，不得再次扣款、发货或收取同一笔费用。
10. 英雄后续行为能够读取更新后的库存和货币状态。

如果缺少第二阶段所需的英雄行为入口、商品定义或库存接口，应先补齐最小依赖，而不是跳过这些依赖直接实现 UI。

## 4. 里程碑安排

建议按照以下顺序实施。每个里程碑的完成情况必须有代码、测试或运行证据支持。

### M0：现状审计与开发基线冻结

**目标：** 在修改代码之前，确认第一阶段现有能力、缺失能力和第二阶段所需的最小变更范围。

任务：

- [ ] 检查现有 Domain、Application、Data、Presentation 结构。
- [ ] 找到英雄、库存、材料、事件、存档和随机数的真实实现位置。
- [ ] 确认目前金币、材料和奖励的存储方式。
- [ ] 确认现有 `DailyLife`、英雄决策流程和模拟时钟的调用入口。
- [ ] 确认现有 Chronicle 事件的合法类型、生成入口和杂谈展示入口。
- [ ] 确认存档 DTO、验证器和迁移策略。
- [ ] 检查现有商品、交易、摊位和建筑是否存在部分实现。
- [ ] 运行构建与完整测试，并记录结果。
- [ ] 建立第二阶段任务清单及设计待定项清单。

**交付物：**

- `production/08_第二阶段开发计划_V1.0.md`
- `production/09_第二阶段现状审计与实施记录.md`
- 更新后的 `production/07_技术决策与待确认事项.md`（仅在确实新增决策时更新）

**验收标准：**

Agent 能明确指出需要复用的类型、需要新增的类型、涉及的存档字段、需要修改的测试，以及仍然缺少开发者决策的规则。

在审计完成前，不开始大规模代码改造。

### M1：基础经济与物品所有权

**目标：** 建立可靠的货币、库存和物品流转基础。

任务：

- [ ] 明确当前已有的材料池、货币和物品模型，优先复用。
- [ ] 区分商品定义与运行时物品数量、持有者等状态。
- [ ] 明确英雄库存和村庄库存之间的边界。
- [ ] 为货币增加统一的读取、扣除和增加操作。
- [ ] 为物品增加统一的添加、移除和转移操作。
- [ ] 对负数量、非法物品 ID、不足余额和库存不足设置防线。
- [ ] 明确操作失败时是否保证所有状态不变。
- [ ] 为经济操作定义清晰的结果类型，避免仅依赖日志判断成功与否。
- [ ] 设计适用于后续交易的交易标识和操作幂等策略。
- [ ] 让现有副本奖励使用同一套库存与物品流转规则，必要时做最小适配。

**重要约束：**

如果现有系统的材料池已覆盖相关物品，不得在没有充分理由的情况下再建立第二套独立库存。

如果当前游戏还没有通用商品模型，可以先定义少量测试商品；不得借此一次性引入完整装备词缀、稀有度、耐久度和制作系统。

**验收标准：**

- 正常增加、扣除和转移货币。
- 正常增加、移除和转移物品。
- 不足余额或库存不足时操作失败，状态保持不变。
- 非法输入不能污染经济状态。
- 交易所需的物品所有权能够被明确判断。
- 已有副本奖励和存档相关测试继续通过。

### M2：交易领域模型与原子结算

**目标：** 在实现摆摊 UI 之前，先完成可独立测试的交易规则。

任务：

- [ ] 定义交易订单或交易请求的最小模型。
- [ ] 定义买方、卖方、商品、数量、价格和交易状态。
- [ ] 定义交易成功、交易拒绝和重复提交的处理方式。
- [ ] 交易执行前预检买方余额、卖方库存和交易合法性。
- [ ] 在同一领域操作中完成付款、收款和物品转移。
- [ ] 确保交易失败时不会出现部分提交。
- [ ] 记录唯一交易标识及其结算状态。
- [ ] 明确交易取消、商品售罄和余额不足时的行为。
- [ ] 对重复提交、重复加载和异常恢复增加测试。

**交易规则的最低要求：**

交易的最终状态必须满足：

- 买方支付金额与卖方收入符合已批准的价格规则。
- 买方获得的物品数量与成交数量一致。
- 卖方失去的物品数量与成交数量一致。
- 同一笔交易不得重复生效。
- 失败的交易不得产生部分经济变更。
- 交易事件必须对应实际成功的交易，不得将请求或失败操作伪装成成交。

**待确认项：**

本阶段不擅自决定交易税、手续费、价格浮动、讨价还价和交易限额。若当前版本只需要固定价格，则应由开发者确认一套最小规则后实现。

### M3：英雄摆摊与村长收费

**目标：** 将基础交易能力转化为玩家可以观察和使用的村庄经营功能。

任务：

- [ ] 为摊位定义最小运行时状态。
- [ ] 关联摊位所属英雄、位置、出售商品及可用状态。
- [ ] 验证摊位是否位于设计基线规定的防护范围内。
- [ ] 允许符合条件的英雄开设摊位。
- [ ] 支持向摊位添加和移除合法商品。
- [ ] 支持买方查看商品并发起购买。
- [ ] 支持商品售罄、摊位关闭和英雄离开时的状态处理。
- [ ] 实现村长收取摊位费的最小机制。
- [ ] 将摊位收费和商品交易区分为不同的业务记录。
- [ ] 为摊位状态、交易状态和收费状态增加必要的存档字段。
- [ ] 为摊位 UI 提供清晰的商品、数量、价格和交易结果展示。

**设计约束：**

- 摊位是英雄经营行为的载体，不应只是 UI 上的一张装饰卡片。
- 商品出售必须影响实际库存。
- 村长收到的费用必须进入明确的村庄资金账户，不能只增加显示数字。
- 村长的收费不能与卖方收到的商品货款混为一谈。
- 摊位收费周期、费率、是否按固定时段收费等规则需要开发者确认。
- 不得在收费规则未确认时，自行决定每小时、每日或每笔交易收取多少费用。

**验收标准：**

可以通过游戏操作或受支持的开发测试入口完成一次摊位创建、商品上架、商品购买和收费结算。相关库存、货币、摊位状态及事件记录相互一致。

### M4：英雄自主经济行为

**目标：** 让英雄能够利用已有的自主决策框架，在村庄中做出有限但真实的经济行为。

任务：

- [ ] 检查现有 `DecisionFlow`、`DailyLife` 和英雄状态模型。
- [ ] 复用现有模拟时钟驱动，不再创建平行时间系统。
- [ ] 为本阶段支持的经济行为定义合法前置条件。
- [ ] 为英雄决策增加经济行为候选项。
- [ ] 根据英雄已有的性格、偏好和当前状态计算行为优先级。
- [ ] 允许英雄在条件满足时选择购物或出售物品。
- [ ] 在没有合适商品、余额不足或需求不成立时提供合理的替代行为。
- [ ] 防止英雄因重复决策而连续执行同一笔交易。
- [ ] 确保行为选择和经济结算分离：选择行为不等于交易成功。
- [ ] 让交易结果反映到英雄后续决策中。

**行为设计要求：**

- 不得把所有英雄的经济行为写成完全相同的固定脚本。
- 不得因为引入经济行为而破坏第一阶段已有的性格权重约束。
- 不得让英雄在没有足够货币、没有库存或商品不合法时完成交易。
- 不得让英雄的自主行为绕过领域规则直接修改货币或物品。
- 不要求本阶段实现完整的人格、情绪和社会关系 AI。

**验收标准：**

在相同的合法初始条件下，英雄能够根据行为条件执行经济活动；在条件不满足时不会产生非法交易。测试能够验证行为选择、实际交易和最终状态之间的关系。

### M5：建筑与经营活动的最小联动

**目标：** 让建筑逐步成为具有真实用途的经营设施，而不是仅提供外观或解锁标记。

任务：

- [ ] 检查现有建筑定义、建筑实例和地图表现。
- [ ] 优先复用当前已有的建筑类型和状态管理。
- [ ] 将摊位的可用位置与防护范围、地图占用规则建立联系。
- [ ] 明确哪些建筑在本阶段真正参与经济活动。
- [ ] 为已经纳入范围的商店提供最小商品展示和购买入口。
- [ ] 为商品供给、库存不足和建筑不可用定义一致的行为。
- [ ] 将武器店和服装店作为不同建筑处理，不得合并为一个通用商店名称来代替设计要求。
- [ ] 只有在已有商品数据和经济规则足够支撑时，才把副本获得的物品接入商店销售流程。

**范围限制：**

本阶段不要求完成所有建筑的建造、升级、损伤、维护、人员分配和完整生产链。

黑smith、武器店、服装店、铁匠铺等名称必须以设计基线中的实际建筑定义为准；不得擅自增加未经确认的设施。

如果当前阶段的最小闭环可以由摊位完成，则不应为了“建筑系统完整”而阻塞经济闭环。其他建筑应根据已有代码和已确认设计逐步接入。

### M6：事件、杂谈与经营结果回流

**目标：** 让玩家能够观察英雄经济活动，并确认记录来自真实状态变化。

任务：

- [ ] 检查当前事件定义与 ChronicleFeed 的约束。
- [ ] 为已成功完成的交易产生合法事件。
- [ ] 为实际发生的摊位开设、关闭和收费定义是否需要记录的规则。
- [ ] 只有在状态真实改变时，才产生对应事件。
- [ ] 交易失败不得生成“交易成功”类记录。
- [ ] 事件中携带必要的英雄、商品、数量或交易引用。
- [ ] 复用已有杂谈展示机制，不另建独立且不一致的日志系统。
- [ ] 检查事件 ID 的唯一性和事件重复处理防线。
- [ ] 验证事件显示与经济状态一致。
- [ ] 为交易、收费和物品变化增加可追踪的来源。

**验收标准：**

玩家能在杂谈中看到真实发生的经济活动；每条记录均能对应合法事件；重复结算不会产生重复的经济变化或重复的成功事件。

不得通过随机生成“英雄买了东西”“英雄赚了钱”等文本来伪装经济系统已经完成。

### M7：存档、读档、UI 整合与回归验收

**目标：** 将第二阶段经济闭环纳入可持续运行的游戏，而不只是一次性测试。

任务：

- [ ] 将新增的货币、库存、摊位、交易和收费状态纳入存档。
- [ ] 按现有机制更新存档版本和必要的迁移逻辑。
- [ ] 为新字段添加读取验证和引用完整性检查。
- [ ] 遵循现有原子写盘和整份拒绝策略。
- [ ] 确认加载后不会重放已完成的交易。
- [ ] 确认加载后不会重复收取已经结算的摊位费。
- [ ] 为玩家提供可用的经营 UI 入口。
- [ ] 验证 UI 展示与领域状态一致。
- [ ] 运行全部既有测试和第二阶段新增测试。
- [ ] 记录构建结果、测试结果和最终验收证据。

**验收标准：**

保存游戏后退出并重新加载，货币、物品、摊位、交易和收费状态保持一致。无效引用按照现有规则拒绝加载；有效存档不会重复结算。

## 5. 领域模型与模块边界

以下是实现方向，不是要求 Agent 必须使用这些精确类名。实际命名必须根据现有代码确定，避免创建重复模型。

| 领域职责 | 应承担的职责 | 不应承担的职责 |
|---|---|---|
| Economy / Wallet | 货币余额、合法的货币变更 | UI 文本、场景节点操作 |
| Inventory / Item ownership | 物品数量、持有者和物品转移 | 自行决定交易价格 |
| Trade | 交易合法性、付款、收款、交付、幂等 | 直接渲染交易界面 |
| Stall | 摊位状态、所属英雄、上架商品 | 绕过 Trade 修改库存 |
| Fee / Treasury | 摊位费规则和村庄资金变更 | 与商品货款混用 |
| Hero decision / DailyLife | 评估并选择自主经济行为 | 直接绕过领域规则改余额 |
| Buildings | 建筑用途、可用状态、位置关联 | 承担全部经济逻辑 |
| Events / Chronicle | 记录真实发生的事件并提供展示 | 自行创造未发生的行为 |
| SaveGame / SaveValidator | 保存、恢复、校验新状态 | 静默丢弃非法经济数据 |
| Presentation / UI | 显示库存、商品和操作结果 | 作为经济状态的唯一来源 |

### 5.1 模块调用原则

建议采用以下调用方向：

```text
Presentation / UI
       ↓
Application use cases
       ↓
Domain rules
       ↓
Domain state changes
       ↓
Domain events / Chronicle
       ↓
Presentation refresh
```

实际项目可以沿用已有调用结构，不要求机械照搬上图。但必须保持领域规则集中、状态变更有明确入口、事件来源可追踪。

### 5.2 交易与存档的关键不变量

新增经济系统至少需要以下不变量：

- 货币余额不得因非法操作变为负数。
- 物品数量不得出现非法负数。
- 物品不得被同一笔交易重复交付。
- 交易双方和商品引用必须有效。
- 同一笔交易只能成功结算一次。
- 收费记录必须对应有效的收费规则和目标。
- 同一笔收费只能结算一次。
- 交易事件不得早于对应的成功状态变更。
- 存档与读档必须保留交易状态及其幂等信息。
- 任何模块不得通过直接改写其他模块内部状态绕过合法入口。

具体不变量应结合现有数据结构转化为可自动执行的测试。

## 6. 必须由开发者确认的规则

以下事项目前不能由 Agent 擅自当作正式设计。

| 编号 | 待确认事项 | 建议处理方式 |
|---|---|---|
| P2-D01 | 货币名称、初始金额及账户划分 | 先检查现有实现，再提交最小方案 |
| P2-D02 | 摆摊收费方式、费率和收费周期 | 提供可比较方案，确认后实现 |
| P2-D03 | 商品价格由固定定价还是其他机制决定 | 第一版优先讨论固定定价方案 |
| P2-D04 | 英雄摆摊所需条件 | 明确位置、商品和英雄状态要求 |
| P2-D05 | 英雄购买商品的需求条件与行为优先级 | 先利用现有性格和状态系统，不新增复杂 AI |
| P2-D06 | 摊位商品库存是否可以无限供货 | 以明确的库存模型为准，不默认为无限 |
| P2-D07 | 建筑是否需要等级、维护费用或解锁条件 | 不属于本阶段默认必做项 |
| P2-D08 | 英雄之间的交易范围 | 本阶段建议限制为合法、可验证的直接交易 |
| P2-D09 | 商店商品来源与补货方式 | 先确定最小数据来源，不建立复杂供应链 |
| P2-D10 | 存档格式的版本号与迁移策略 | 遵循现有机制，明确兼容和拒绝条件 |

**决策流程：**

1. Agent 检查现有实现和设计基线。
2. 对每个必要待定项提交简短的决策建议。
3. 明确标记【建议】和【待定】，不得冒充【已确认】。
4. 开发者确认后，将决策写入 `production/07_技术决策与待确认事项.md`。
5. 实现与测试必须引用对应的决策编号。
6. 如果某项不是当前里程碑的必要条件，可以暂时保留待定，不应为了清空清单而强行定案。

## 7. 测试与质量要求

### 7.1 单元测试

必须覆盖：

- 货币增加、扣除和非法余额。
- 物品增加、移除和转移。
- 余额不足和库存不足。
- 商品与交易引用无效。
- 成功交易的双方状态变化。
- 交易失败时状态不变。
- 重复交易提交。
- 摊位创建、商品上架、售罄和关闭。
- 摊位收费成功、失败和重复结算。
- 英雄自主经济行为的合法前置条件。
- 事件是否对应真实状态变化。
- 存档和读档后经济状态一致。

### 7.2 集成测试

至少覆盖以下完整流程：

**测试 A：英雄交易**

1. 创建两个有效英雄。
2. 为卖方设置合法商品和库存。
3. 为买方设置足够余额。
4. 创建合法摊位并上架商品。
5. 执行购买。
6. 断言双方货币、物品数量和交易状态。
7. 断言生成的事件对应实际交易。

**测试 B：摊位收费**

1. 创建合法摊位。
2. 根据已批准的收费规则触发收费。
3. 检查英雄余额和村庄资金变化。
4. 重复处理同一笔收费。
5. 断言不会重复扣款和入账。

**测试 C：交易失败**

1. 让买方余额不足，或让卖方库存不足。
2. 执行交易。
3. 断言交易失败。
4. 断言双方余额和库存保持不变。
5. 断言没有成功交易事件。

**测试 D：存档与读档**

1. 完成一次交易和一次收费。
2. 保存游戏。
3. 重新加载。
4. 检查余额、库存、摊位和结算记录。
5. 再次处理已经完成的交易和收费。
6. 断言所有结果保持幂等。

**测试 E：自主经济行为**

1. 设置英雄的行为条件和经济状态。
2. 推进模拟时间。
3. 验证英雄能在合法条件下选择经济行为。
4. 验证行为结算通过领域入口执行。
5. 验证余额不足等条件不会产生非法交易。
6. 验证后续决策能读取更新后的状态。

### 7.3 回归测试

第二阶段不能只报告新增测试通过。

每次提交都必须至少记录：

- 构建结果；
- 新增测试通过数和失败数；
- 完整测试通过数和失败数；
- 第一阶段八项验收是否继续通过；
- 两道源码守卫是否继续运行并通过；
- 是否新增技术债或待定设计项；
- 是否修改存档格式、公共接口或已有领域不变量。

第一阶段的 191/191 是本次开发开始时的基线，不应在未实际运行的情况下直接宣称第二阶段仍然通过 191 项测试。

## 9. 第二阶段开发完成后的预期状态

第二阶段完成后，玩家应能观察到：

1. 英雄不再只是地图上的移动角色，而是会参与真实的村庄经济。
2. 摊位不只是场景装饰，而是拥有真实商品、库存和交易结果。
3. 村长的经营收入能够通过明确规则产生，并影响村庄资金。
4. 英雄的经济行为由现有自主决策框架驱动。
5. 经济活动会留下真实事件记录，而不是随机生成的装饰性杂谈。
6. 交易、收费、物品和存档之间具备一致性和幂等保障。
7. 副本冒险与村庄经营开始形成可验证的双向联系。

完成上述内容后，项目才适合进入下一阶段，继续扩展英雄个性、关系变化、复杂社交行为和更完整的村庄成长系统。
