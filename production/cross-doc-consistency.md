## 1. 数值冲突

### 1.1 【最严重】性格对远征成功率有**两套互不相容的系数**

| 文档 | 说了什么 |
|---|---|
| `squad-and-cohesion.md:193` | `person_mult: 莽 1.15 \| 傲 1.10 \| 贪 1.00`，写进 F3 的 `chance` 公式（`:191`） |
| `expedition.md:300` | `PersonalityMult`：莽 1.15 · 傲 1.10 · 贪 1.00，写进 F2 的 `chance` 公式（`:290`） |
| `expedition.md:314` | 明确说「**贪的系数是 1.00**——贪的强项不是成功率，是产量」 |
| `personality.md:200` | 本系统「对外交付的**唯一**速度量」是 `EfficiencyOf(hero, category)`，取值域 `0.60 – 1.30` |
| `personality.md:207` | 效率矩阵**战斗列**：莽 `1.30` · 傲 `1.20` · 贪 `0.70` |
| `personality.md:217` | 「贪 战斗 = 0.70，brief 写『战斗低』」——贪在战斗里是**惩罚**，不是中性 |
| `chief-progression.md:188` / `:396` | 村长「性格系数固定 `1.00`」，来源标注为「`expedition.md` 缺陷 3 第 5 条」，即 #6 那套 |

**为什么会咬人**：远征是唯一同时消费两者的系统。写代码的人问「远征成功率里性格乘什么」，
按 `expedition.md` 查得到 1.15/1.10/1.00，按 `personality.md` 查得到 1.30/1.20/0.70。
两套对**贪**的判断完全相反（1.00 中性 vs 0.70 惩罚），对**莽/傲**差 0.15/0.10。
`personality.md` 声明自己是唯一出口，`expedition.md` 与 `squad-and-cohesion.md` 声明只用 1.15/1.10/1.00 且**不读** `EfficiencyOf`——
两份文档同时在争夺「性格 → 成功率」这个位置的归属权。

**可能的和解方向**（不选）：
- (a) 承认两套共存并划清语义：`PersonalityMult` 管**成功率**、`EfficiencyOf` 管**速度**，两者都进 `chance` 或都只进一处，但必须在两份文档里各写一句「本系统只读 X，不读 Y」；
- (b) 合并为一套：远征成功率先只乘 `EfficiencyOf(战斗)`，`PersonalityMult` 退役（或反过来）；
- (c) 把 `EfficiencyOf` 的战斗列整列拿掉，让矩阵只有「采集/建造/跑腿/经商」四类，成功率侧由 #6 独占。

### 1.2 建造侧的 `P(性格)` 突破了自己上游声明的上限，且是标量而非矩阵

| 文档 | 说了什么 |
|---|---|
| `village-building.md:148` | `WorkRate = base × P(性格) × D(投入度) × S(状态)`，`P(性格)` 写作 **莽 1.35 · 傲 0.60 · 贪 1.00** |
| `village-building.md:159` | 变量表声明 `P(性格)` 取值域 `0.60 – 1.35` |
| `personality.md:206` | 效率矩阵：莽 **战斗 1.30**，非战斗一律 0.90 |
| `personality.md:200` | `EfficiencyOf` 返回值域 **`0.60 – 1.30`** |
| `personality.md:222` | 「数值范围规则：**上限 1.30** / 中性 1.00 / 下限 0.60」 |
| `summoning.md:344` | 引用「`傲` 的效率乘数是最低的那个（×0.60）」——用的是标量口径 |
| `economy-and-stalls.md:226-227` | 反过来把 `EfficiencyOf` 当**按类目**的矩阵用（`莽 经商 = 0.90`「沿用上游原表」） |

**为什么会咬人**：① `1.35` 直接超出 `personality.md` 两处声明的上限 `1.30`，任何「矩阵上界就是 1.30」的验收都会红；
② `village-building` 把性格压成**一个标量**（不分采集/建造），`economy-and-stalls` 与 `personality.md` 用的是**按类目的矩阵**——
同一个字段在两份文档里形状不同，`人物工速 × 经商效率` 到底能不能同时成立取决于实现选了哪一套。
③ 附带：`personality.md:207` 矩阵里**没有「建造」之外的莽战斗格被引用**，若按标量取 1.35，则「莽战斗 1.30」这条推导值永远不生效。

**可能的和解方向**：(a) 把 `1.35` 改成 `1.30` 并在 `personality.md` 同步登记「建造类目沿用 1.30 上限」；
(b) 保留 1.35 但在 `personality.md` 把矩阵上界从 1.30 提到 1.35，并重算 `economy-and-stalls.md:512` 的 `Sales_i` 上界（17 → 17.55 不变，但 `傲` 那格会随 §1.2 的经商店一起变）；
(c) 让 `WorkRate` 也走按类目的 `EfficiencyOf`，删掉标量 `P(性格)`。

### 1.3 一次远征的**材料总量**：一份文档分摊，一份不摊

| 文档 | 说了什么 |
|---|---|
| `expedition.md:362` | `Yield_i = Job.Amt / good_count + Power_i / 8`（每人先分摊） |
| `expedition.md:398` | 私吞 `Pocketed_i = Max(1, Yield_i / 4)`——**依赖「每人自己的 `Yield_i`」** |
| `squad-and-cohesion.md:200` | `material = job.Amt + Σ floor(h.Power / 8)`（**整份加一次**） |
| `squad-and-cohesion.md:203` | 紧跟的注释却写「**`job.Amt` 是按 good 人数分摊的，不是每人一份**」——**与它上一行的公式相反** |
| `squad-and-cohesion.md:226` / `:231` | F4 例算 `E[material] = 14 + 2.48 × 3.75`（未分摊口径） |
| `expedition.md:376` | 队伍入账总计「**最小 4，最大 176**（4 人全成、人人 Power 49）」 |
| `functional-buildings.md:497` | 引用「副本一趟带回 **4 – 176** 材料（#6 F3）」 |

**为什么会咬人**：两条公式的**总量**恰好接近（分摊会蒸发余数），所以自动化测试很难发现它们不同；
但**私吞**只有分摊口径下才能算出来——`Pocketed` 是「他吞自己那份的四分之一」。
按 squad 的公式根本不存在「某人那份」，`expedition.md` F4 无从实现。
另外 `176` 这个上界在自己的公式下算不出来（4 人分 38 时每人是 `38/4+6=15`，全队 60），而它已经被 #7 当作成本推导的锚引用。

**可能的和解方向**：(a) 统一为分摊口径，squad F3 改写为 Σ`Yield_i`（`#6` 已提供 `Yield_i`）；
(b) 统一为不分摊，私吞改为「按队伍总量 × 1/4 × `Power` 加权」，`#6` F4 随之改写；
(c) 保留两段口径但明确分工：`#6` 定义单人 `Yield_i`（分摊），`#4` 只做团队汇总并删掉自己那条公式。

### 1.4 `chance` 的下限在两份文档里写了两个互斥的数

| 文档 | 说了什么 |
|---|---|

## 2. 规则冲突

### 2.1 【最严重】傲的「撂挑子」：性格否决 vs 性格只能改速度

| 文档 | 说了什么 |
|---|---|
| `expedition.md:219` | R16：傲**只拒** `IsDungeon = false` 的活，概率 **40%** |
| `expedition.md:432` | F5：`P(refuse) = 0.40` |
| `squad-and-cohesion.md:438` | Cross-References 把「傲的 **0.40 撂挑子概率**」列为引用 `design/gdd/personality.md` 的元素 |
| `squad-and-cohesion.md:275` | Edge Cases：「全员因傲撂挑子而拒绝 → 强制派出第一个人」 |
| `personality.md:120-124` | **铁律 1**：「唯一能让一个村民『不干活』的，是**状态，不是性格**……任何 `if (personality == X && category == Y) return;` 形式的分支，在本系统中一律视为 **bug**」 |
| `personality.md:379` | Edge Case：「全村只有傲在线，只贴建造活 → **傲接了**」 |
| `personality.md:529-537` | AC B「最后一个人测试」：对 3×5=15 组构造，**每组都必须存在一条通向完成的完整路径** |
| `trade-and-betrayal.md:161` | 引用 `personality.md` 时也承认远征「完全不吃 `Diligence`/`Grit`」 |

**为什么会咬人**：这是**同一个机制，两份文档说它必须不存在**。
`personality.md` 的 AC B-3 是一条可机器执行的断言——对全部 15 组构造，每组都必须有一条成功路径；
`expedition.md` 的 R16 在粗活上给傲 40% 的拒绝率，在一支「1 傲 + 3 非傲」全粗活的队伍里，
全员拒活的概率是 `0.4 × 0.6³ = 8.6%`，而兜底规则（`expedition.md:444`）会让**第一个非傲队员**代他去——
所以 `personality.md` 的「傲接了」那条 AC-B1 断言在远征结算路径上必然失败。

**可能的和解方向**：

- (c) 保留现状但修正归因：把 `squad-and-cohesion.md:438` 的来源改指 `expedition.md`，并在 `personality.md` 的 Cross-References 里补一条「本规则不适用于远征结算（`#6` R16）」的显式例外。

### 2.2 远征途中的队员还会不会挨日常事件

### 3.3 「在场」在三份文档里是三套判定条件

| 文档 | 说了什么 |
|---|---|
| `time-and-schedule.md:75-76` | R7：`Present = ¬Away ∧ Online`；`OnDuty = AbsentDays ≤ 0 ∧ IsOnlineAt(村庄时刻)`——**两个谓词，`OnDuty` 不含 `¬Away`** |
| `time-and-schedule.md:295` | F5：`Present(h) = ¬Away(h) ∧ Online(h)` |

| `village-building.md:196` | 公式 2：`S = { h : h.ToSite ∧ **¬h.Away** ∧ OnDuty(h) }`——三个条件，`Away` 单独成立 |
| `expedition.md:214` | R14：出发时把成员 `Away = true`，他们「**不再计入工地人力**」 |

**为什么会咬人**：`#4` 把 `OnDuty`（不含 `¬Away`）叫作「在场」，于是**正在远征中的人按 `#4` 的定义仍然「在场」**——

而配队面板会把塔里的人算进 `Cohesion`。

**可能的和解方向**：(a) `#4` 的 R2 改用 `#5` 的三条件（含 `¬Away`），并把「在场」这个词让给 `Present`；
(b) 统一术语：`#4` 内部把它的「在场」改名为「可出勤（OnDuty）」，全部 Edge Case 的措辞随之改；
(c) 让 `functional-buildings` 的塔也写 `Away = true`（或新增一个 `InTower` 标志并纳入 `#5` 的三条件），使 `Away` 成为唯一的外出标记。
