# 异世界村庄经营与英雄冒险游戏 — 设计总纲

> **文档状态：** 初步设计基线 / 后续可迭代  
> **目标：** 汇总当前已讨论的核心构想、玩法、系统边界、技术架构、MVP 范围与验收标准，作为项目长期备忘和后续开发依据。  
> **技术基线：** Godot 4 + C#（.NET），Windows 单机，45°等距像素风，32×32 基础图块方向。  
> **说明：** 本文中的数值、目录和接口均属于建议基线；需要通过原型验证的部分会明确标记，不应视为最终定案。

---

## 1. 项目概览

### 1.1 一句话概念

玩家担任异世界新手村村长，从三间土屋起步，通过建造村庄、吸引并培养英雄、发布任务、组织队伍攻略野外区域与副本，逐步把小村庄发展为世界上最繁华、最豪华、最有影响力的超级城市。

### 1.2 游戏定位

- **类型：** 村庄/城市经营 + 英雄生活模拟 + 自动战斗 + 任务冒险。
- **模式：** 单机世界。
- **视角：** 45°等距俯视。
- **美术方向：** 像素风；当前素材制作方向以 32×32 基础图块为参考。
- **战斗：** 全自动战斗。玩家通过队伍、装备、补给、任务和战术配置影响结果，不直接操控英雄进行即时攻击。
- **核心体验：** 玩家既是村长，也是冒险组织者；平时经营城市、观察英雄生活，遇到任务和危机时组织英雄行动，并亲眼看到城市与世界因决策而改变。
- **开发技术：** Godot 4 + C#（.NET）。

### 1.3 核心幻想

1. 从简陋村庄起步，逐渐建立有规模、有特色、有经济活力的城市。
2. 英雄不是静态单位，而是有性格、需求、目标、关系和个人经历的居民。
3. 村庄中的建筑不仅是外观装饰，也会改变生产、交易、训练、冒险和防御能力。
4. 玩家能够观察英雄在村中生活、购物、社交、训练、出发冒险以及与怪物战斗。
5. 玩家可以通过建设、任务安排和队伍配置间接影响英雄，而不是对每个英雄下达每一步指令。
6. 世界原本就有自己的本土居民、势力、文化和历史；玩家并非在一张空白地图上创造整个世界。
7. 游戏长期目标是将村庄发展成极具声望、财富、规模和独特性的世界级城市。

## 2. 设计支柱

### 2.1 城市成长必须可见

城市发展不应只表现为金币、等级或数值增加。应当让玩家直观看到建筑、道路、灯光、人口、商铺和防御设施逐步变化。

例子：

- 初期：三间土屋、篝火、简易储物处。
- 早期：水井、围栏、仓库、简易旅店。
- 中期：铁匠铺、市场、冒险者公会、训练场、诊疗设施。
- 后期：大型商业街、魔法设施、城墙、传送设施、特色地标。
- 终局：形成有鲜明主题和布局风格的繁荣城市。

### 2.2 英雄是居民，不只是战斗数值

英雄应当有基本生活需求和长期倾向。不同性格会影响他们的行为偏好，但不应让行为完全随机。

第一版建议只实现少量性格维度、需求和目标，以验证系统是否有趣。

### 2.3 经营与冒险互相驱动

城市提供冒险所需的装备、补给、治疗、招募和任务信息；冒险带回材料、金币、装备、情报和声望，推动城市升级。

如果冒险不影响经营，或者经营不影响冒险，两个模块就会变成互不相干的小游戏，应避免这种情况。

### 2.4 自动战斗要可读、可理解

玩家虽然不直接操作战斗，但应能看清：

- 英雄为什么选择某个目标；
- 技能何时触发；
- 队伍为什么获胜或失败；
- 装备、阵容、地形和准备工作造成了什么影响；
- 伤势、消耗和战利品如何影响下一次行动。

### 2.5 世界要有自主变化

本土居民、英雄、商店、野外怪物、区域势力和世界事件共同构成动态世界。玩家不是所有行动的唯一发起者，但玩家的决策应当产生可观察的影响。

## 3. 核心游戏循环

### 3.1 主循环

```text
建设村庄
   ↓
吸引英雄与居民
   ↓
英雄生活、训练、购物与成长
   ↓
发布任务 / 组织冒险队伍
   ↓
探索区域、自动战斗、获取资源与情报
   ↓
资源、装备、声望、关系和世界状态发生变化
   ↓
升级建筑、开放新服务与新区域
   ↓
出现更高阶的需求、机会和危机
   └──────────────────→ 继续发展
```

### 3.2 三个子循环

**城市循环**

资源生产与收集 → 建造和升级 → 人口与商业增长 → 新需求与新经济机会。

**英雄循环**

生活需求 → 自主选择行动 → 冒险或工作 → 获得经验、物品与关系变化 → 形成新目标。

**世界循环**

世界状态变化 → 预兆或事件出现 → 玩家与 NPC 做出反应 → 事件结算 → 区域和社会产生后续影响。

### 3.3 关键联动示例

- 建成铁匠铺后，英雄可以买到更好的装备，战斗成功率提高。
- 英雄带回稀有矿石后，城市可以建造高级设施。
- 诊疗设施不足会延长英雄受伤后的恢复时间，影响任务可用人数。
- 声望提高会吸引更强的英雄、商人或本土居民。
- 防御设施和队伍配置会影响兽潮造成的建筑损伤与伤员数量。
- 商贸节可能提升消费和人口流入，但也会增加库存压力或治安事件。
- 英雄间的信任、竞争和纠纷会影响组队、交易与事件结果。

## 4. 玩家角色、动机与长期目标

### 4.1 玩家身份

玩家是村长，负责城市规划、建筑投资、任务发布、英雄招募和危机应对。玩家不是传统意义上直接控制一个战斗角色的冒险者。

### 4.2 穿越/来到异世界的动机

目前可作为剧情待选项，尚未最终定案：

- **方案 A：受托建设。** 本土势力将边境村庄交给玩家，希望其建立能够抵御威胁的城镇。
- **方案 B：异界召唤事故。** 玩家被某种古代设施召唤到异世界，并获得有限的英雄召唤能力。
- **方案 C：城市管理者契约。** 玩家与某个世界系统或守护者达成契约，获得建设权，但必须通过发展城市证明能力。
- **方案 D：继承废弃领地。** 玩家继承一片有历史、居民和潜在资源的旧领地，需要重新建立其繁荣。

建议优先选择能够自然解释“村长身份、有限召唤系统、世界原生居民和城市发展目标”的方案。不要让穿越设定只承担开场解释作用；它最好能与主线目标、召唤机制和世界秘密相连。

### 4.3 长期目标

不要仅把“城市等级达到 100”当作终局。可以组合多个维度：

- **规模：** 城区面积、建筑数量、人口容量。
- **繁荣：** 经济活动、商铺数量、消费和生产能力。
- **声望：** 英雄评价、本土势力认可、区域影响力。
- **安全：** 防御能力、灾害恢复能力、周边区域稳定度。
- **文化与特色：** 独特建筑、节庆、名人、城市风格。
- **世界影响：** 开放新区域、建立贸易关系、解决区域危机。

终局可以采用“达成城市级别要求后解锁最终挑战/城市评选/世界级危机”，而不是强制玩家结束游戏。完成主目标后仍可继续沙盒经营。

## 5. 失败、风险与后果设计

目标是避免一次失误就导致长期存档彻底失败，但仍让选择有分量。

### 5.1 建议的失败层级

1. **轻度后果：** 任务失败、资源损失、装备损坏、声望下降。
2. **中度后果：** 英雄受伤、恢复时间延长、商铺停业、建筑受损。
3. **重度后果：** 英雄被俘或失踪、重要设施被毁、区域关系恶化、危机升级。
4. **极端后果：** 城市短期衰退或某条剧情路线关闭；通常保留恢复方式，不直接永久结束游戏。

### 5.2 恢复机制

- 允许玩家花费资源治疗、修复和重建。
- 失败任务可以产生后续救援、赎回、追踪或补救任务。
- 城市防御不足可以导致损失，但不必直接触发游戏结束。
- 通过保险、储备、避难设施、城墙和应急仓库降低灾害损失。
- 关键角色是否永久死亡需要单独的设计决定；MVP 建议先采用重伤/暂时退出冒险的机制，验证后再决定永久死亡。

### 5.3 风险设计原则

风险应当由玩家能够理解或提前观察的因素决定。大事件应给出预兆和准备窗口；失败后要解释损失来源，并让玩家知道如何改善下一次结果。

## 6. 英雄与居民模拟

### 6.1 英雄的基本组成

英雄至少具有：

- 唯一实例 ID；
- 英雄模板 ID；
- 等级、经验与成长属性；
- 当前生命、疲劳、伤势和状态；
- 背包与装备；
- 性格维度；
- 当前目标、当前活动和行动计划；
- 个人关系；
- 冒险记录、重要事件和历史；
- 声望或其他可选社会属性。

### 6.2 英雄的唯一性

用户希望召唤来的英雄各有独特性。第一版可以通过“基础模板 + 属性差异 + 性格 + 目标 + 初始装备 + 个人经历标签”来构成独特性。

若未来计划商业化，使用现有动漫、影视或游戏 IP 的具体角色可能涉及版权与授权问题。建议先用原创英雄验证玩法，再评估授权或其他合规方式。

### 6.3 性格系统

第一版建议从 4–6 个可调节维度中选取，例如：

- 勇敢 ↔ 谨慎；
- 慷慨 ↔ 逐利；
- 外向 ↔ 内向；
- 纪律性强 ↔ 随性；
- 好奇 ↔ 安稳；
- 竞争心强 ↔ 合作倾向。

这些是连续或分档的行为倾向，不是简单的好人/坏人标签。

性格影响行动评分，例如勇敢者更愿意接高风险任务，逐利者更重视奖励，外向者更常发起社交。但任务承诺、健康状态、个人目标和当前危机应当覆盖单纯性格偏好。

### 6.4 需求与目标

MVP 建议只实现少量需求：

- 休息/疲劳；
- 治疗/伤势；
- 装备与补给；
- 收入或物资需求；
- 社交（可作为较低优先级）。

个人目标第一版可从以下选 2–3 类：

- 提升等级或装备；
- 积累财富；
- 探索未知区域；
- 保护某个角色或群体；
- 提升某种关系；
- 完成特定类型的冒险。

### 6.5 自主行为

建议第一版支持：

- 在村中移动；
- 休息和恢复；
- 购物；
- 训练；
- 社交；
- 接受任务、组成队伍并出发；
- 战斗、返回和领取奖励；
- 受伤后寻求治疗。

英雄 AI 不应直接修改商店库存、城市资源或其他系统的数据。它提出行为意图，由相应系统验证并执行。

### 6.6 AI 决策方式

推荐采用“有限状态机 + 行为评分”，而不是第一版就上复杂规划器。

状态示例：

`Idle`、`Moving`、`Working`、`Shopping`、`Socializing`、`Training`、`Questing`、`Fighting`、`Resting`、`Recovering`。

可将行为评分抽象为：

```text
Score(action) =
    性格匹配权重
  + 当前需求满足程度
  + 对长期目标的贡献
  - 风险成本
  + 小幅随机扰动
```

行为选择还应考虑：

- 已经承诺的任务；
- 当前活动是否可中断；
- 行为冷却；
- 目标是否仍然有效；
- 资源、路线和设施是否可用；
- 低概率随机性，避免所有英雄表现完全一致。

防止 AI 每次更新都切换目标：一旦开始重要行为，设置最短承诺时间或中断条件，只有出现更高优先级情况时才重新规划。

## 7. 村庄、建筑与城市经济

### 7.1 城市成长阶段

| 阶段 | 视觉与功能示例 | 主要玩法 |
|---|---|---|
| 初始村庄 | 三间土屋、篝火、简易储物处 | 收集基础资源、迎接第一批英雄 |
| 初级聚落 | 水井、围栏、仓库、旅店 | 居住、储存、基础交易 |
| 冒险据点 | 铁匠铺、冒险者公会、训练场 | 装备、组队、任务和训练 |
| 繁荣城镇 | 市场、诊疗设施、工坊、防御设施 | 经济循环、伤员恢复、危机准备 |
| 大型城市 | 城墙、商业街、魔法设施、特色地标 | 区域贸易、复杂事件和高级冒险 |
| 世界级城市 | 大型奇观、专属区域、城市特色系统 | 终局目标与持续沙盒经营 |

这只是阶段参考，不要求按表中顺序机械解锁所有建筑。

### 7.2 建筑必须有实际玩法作用

| 建筑示例 | 主要功能 |
|---|---|
| 住宅 | 提供居住容量、影响人口与恢复 |
| 仓库 | 增加资源存储容量 |
| 水井/公共设施 | 满足基础生活需求，提升宜居度 |
| 旅店 | 提供休息、住宿与访客服务 |
| 铁匠铺 | 购买、制造、修理或升级装备 |
| 冒险者公会 | 发布任务、招募队伍、展示委托 |
| 训练场 | 训练英雄、提供训练效率加成 |
| 诊疗设施 | 缩短伤势恢复时间 |
| 市场/商店 | 提供交易与城市经济活动 |
| 防御设施 | 降低怪物袭击和兽潮造成的损失 |
| 魔法防护罩 | 保护指定区域，但需要维护、能量或其他限制 |
| 试炼塔 | 提供阶段挑战、奖励和英雄成长机会 |

### 7.3 建筑状态

建筑实例可以包含：

- 实例 ID 与建筑定义 ID；
- 地图坐标、朝向、占地范围；
- 等级；
- 建造进度；
- 损伤程度；
- 库存与工作状态；
- 工作人员或服务对象；
- 解锁状态及维护成本。

### 7.4 摆摊与交易

后续内容可支持英雄在防护范围内摆摊，玩家收取摊位费，英雄之间进行交易。社会系统可以对交易产生影响：

- 信任度影响交易意愿；
- 声誉影响买家数量；
- 欺诈可能引发纠纷；
- 纠纷可能影响关系、商誉或治安；
- PvP 或冲突可以作为后续扩展，不属于 MVP 必做内容。

第一版应优先建立清晰的库存、金币和交易结算规则，避免多个系统同时修改物品所有权。

## 8. 任务、冒险与副本

### 8.1 任务流程

```text
任务创建
  ↓
等待接取 / 玩家指定队伍
  ↓
队伍检查（人数、装备、状态、任务条件）
  ↓
出发与前往目标
  ↓
探索 / 采集 / 战斗 / 事件处理
  ↓
成功、失败、中止或撤退
  ↓
结算奖励、消耗、伤势、声望与世界影响
  ↓
英雄返回并进入下一项活动
```

### 8.2 第一版任务类型

- 采集木材、石料或其他基础材料；
- 讨伐指定怪物；
- 护送或探索任务可在后续阶段加入；
- 副本和多阶段任务可以等基本任务生命周期稳定后扩展。

### 8.3 任务系统职责

任务系统负责任务状态、目标、队伍、进度和结算；它不应亲自负责所有战斗伤害、库存变更和关系计算，而应调用对应系统。

### 8.4 队伍组织

玩家可以：

- 指定英雄组成队伍；
- 配置装备、补给和目标；
- 查看任务风险与建议战力；
- 在适当情况下选择撤退；
- 任务结束后查看结果和战斗日志。

未来可允许英雄自主报名或邀请同伴，但玩家仍应拥有明确的干预方式。

## 9. 自动战斗系统

### 9.1 战斗原则

- 战斗规则由模拟层计算；
- 角色动画和特效只负责呈现结果；
- 不应由动画播放完成与否决定伤害或胜负；
- 战斗日志要解释关键事件；
- 战前准备应显著影响结果；
- 战斗结束后必须与任务、库存、伤势和英雄成长联动。

### 9.2 MVP 战斗能力

至少包括：

- 生命值、攻击、防御、移动速度等基础属性；
- 普通攻击、攻击范围和冷却；
- 至少一种技能；
- 至少一种状态效果；
- 目标选择、追击和脱离；
- 死亡或重伤状态；
- 胜负判断与撤退；
- 经验、掉落、消耗和伤势结算；
- 可查看的战斗日志。

第一版建议让英雄与怪物在世界地图上进行可观察的战斗，而不是每次都切换到独立战斗场景。若后续发现表现和寻路难以处理，再评估专用战斗场景。

### 9.3 战斗结果影响

- 胜利可带来经验、材料、金币、装备或情报；
- 失败可能造成重伤、装备损坏、资源消耗或任务失败；
- 撤退可以减少进一步损失，但可能无法完成目标；
- 城市中的铁匠铺、诊疗设施、训练场和防御设施应影响战前准备或战后恢复。

---

## 10. 世界地图、怪物与区域

### 10.1 地图表现

- 45°等距俯视；
- 基础地形以 32×32 图块方向作为当前素材制作参考；
- 地面、草地、森林、河流、道路、障碍和建筑；
- 角色、怪物和建筑应遵循统一的地图坐标与遮挡规则；
- 建筑与角色优先采用独立场景或节点实例，而不是把所有动态对象都烘焙进地面瓦片。

具体使用的 Godot TileMapLayer 组织、地图坐标转换、导航和碰撞策略，应在地图原型阶段验证。

### 10.2 区域与怪物

区域可定义：

- 区域 ID 和名称；
- 地形与可通行规则；
- 资源分布；
- 怪物种类和危险等级；
- 任务入口与探索进度；
- 事件影响；
- 区域控制方或本土势力（后续扩展）。

### 10.3 模拟精度分层

为避免英雄和怪物数量增加后性能下降：

- **近景对象：** 完整移动、寻路、动画与较高频率 AI 决策。
- **远景对象：** 降低决策频率，减少表现更新。
- **远离玩家或不在当前地图的活动：** 抽象模拟任务进度、消耗、伤势和结果。
- **关键对象：** 正在执行重要任务或参与大事件的角色，可提高模拟精度。

分层模拟必须保留一致的游戏规则，不能让抽象模拟与地图上的实际模拟产生明显矛盾。

## 11. 世界事件系统

### 11.1 设计目标

大事件不只包括兽潮。系统应允许未来增加商贸节、遗迹开启、瘟疫、区域冲突、贵宾到访、魔法异常等事件，而不需要重写核心世界循环。

### 11.2 通用生命周期

```text
待触发
  ↓
预兆
  ↓
准备
  ↓
进行中
  ↓
结算
  ↓
后续影响
  ↓
结束
```

某些事件可以跳过不适用的阶段，但状态迁移和存档规则要明确。

### 11.3 事件模板与事件实例

- **事件模板：** 触发条件、阶段规则、参与者选择规则、持续时间、结算规则和可能后果。
- **事件实例：** 本次事件的 ID、当前阶段、开始时间、进度、参与者、结果和已应用的后果。

### 11.4 系统边界

事件系统负责触发、生命周期和协调，不直接承担所有业务细节。

例如兽潮事件可以：

- 请求怪物系统生成或调度怪物；
- 请求任务系统提供防御任务；
- 请求战斗系统结算冲突；
- 请求建筑系统计算损伤；
- 请求经济系统扣除消耗；
- 请求关系/声望系统处理结果影响。

事件结束后记录结果，并确保同一后果不会因重复加载或重复结算而被应用多次。

### 11.5 MVP 事件

第一版只需完整实现一个兽潮事件，包含：

1. 预警与准备时间；
2. 怪物来袭；
3. 英雄和防御设施参与；
4. 战斗与损伤结算；
5. 伤员恢复、建筑修复和声望变化；
6. 事件日志与存档恢复。

暂不开发通用事件脚本编辑器。

## 12. 技术基线：Godot 4 + C#

### 12.1 技术选择

- **引擎：** Godot 4 的 .NET 版本；
- **语言：** C#；
- **平台：** Windows 单机优先；
- **画面：** 45°等距像素风；
- **地图：** 使用 Godot 的 TileMapLayer 及场景化动态对象；具体布局经原型验证；
- **配置：** 自定义 C# `Resource` 子类或其他合适的资源配置；
- **存档：** 显式数据模型 + 版本号，优先采用可检查的 JSON 格式；
- **测试：** 核心规则尽量可脱离场景树进行单元测试。

请确保安装与项目匹配的 Godot .NET SDK/编辑器版本，并按所选 Godot 版本的官方要求配置 .NET SDK。具体版本号在项目初始化时锁定，避免团队环境不一致。

### 12.2 分层架构

**表现层（Presentation）**

- 地图和镜头；
- 角色与怪物节点；
- 建筑场景；
- 动画、特效、音效；
- UI 与输入反馈。

**应用层（Application）**

- 玩家指令入口；
- 建造、任务、组队等用例协调；
- 游戏时间与速度控制；
- 场景切换和会话生命周期。

**模拟/领域层（Simulation / Domain）**

- 英雄 AI；
- 战斗规则；
- 经济与库存；
- 任务；
- 建筑规则；
- 关系；
- 世界事件。

**数据与存档层（Data / Save）**

- 静态定义；
- 运行时状态；
- 存档 DTO；
- 版本迁移；
- 加载校验与备份。

### 12.3 C# 与 Godot Node 的职责

不要把所有领域对象都做成 `Node`。

例如：

- `HeroController : Node2D`：负责英雄在地图上的表现、动画和显示位置。
- `HeroState`：保存英雄运行时状态。
- `HeroAIService`：计算下一步行为。
- `CombatService`：计算战斗规则与结果。
- `InventoryService`：负责库存和物品转移。
- `SaveService`：负责保存、读取、校验和迁移。

场景节点负责呈现和与引擎交互；领域对象负责规则和状态。两者通过明确接口、命令、事件或受控引用连接。

### 12.5 Autoload / 全局服务

建议只保留少量真正需要全局访问的服务，例如：

- `GameSession`：当前游戏会话与核心状态入口；
- `WorldClock`：世界模拟时间；
- `SaveService`：存档服务（也可以由应用层持有）。

避免创建一个包含所有业务逻辑的巨型 `GameManager`。全局服务只承担清晰、有限的职责。

### 12.6 模块通信

使用明确的服务接口、命令和领域事件。例如：

**命令示例：**

- `BuildBuildingCommand`
- `AssignQuestCommand`
- `StartAdventureCommand`
- `EquipItemCommand`

**领域事件示例：**

- `BuildingCompleted`
- `QuestCompleted`
- `HeroInjured`
- `ItemPurchased`
- `EventResolved`

命令表达“请求执行某事”，领域事件表达“某事已经发生”。事件处理者可以更新 UI、关系或日志，但不应随意绕过业务服务修改其他模块的核心数据。

MVP 不需要消息队列、微服务或网络后端；普通 C# 类、接口、事件和必要的 Godot 信号即可。

## 13. 模拟时间、性能与调度

### 13.1 模拟与画面分离

- 画面按引擎帧率更新；
- 世界规则使用固定或受控的模拟步长；
- AI 决策以低于渲染帧率的频率运行；
- 暂停、1×、2×、4×等速度控制影响模拟时间推进；
- 不要将所有英雄 AI 放在每帧都执行的 `_Process()` 中。

例如，初期可以测试每 0.25 秒推进一次模拟逻辑；该数值只是起始参数，需通过角色数量、战斗体验和性能测试调整。

### 13.2 调度建议

- 将世界模拟分成明确的 tick；
- 每个 tick 按约定顺序处理移动、需求、AI、任务、战斗和事件，或通过清晰的子系统调度器执行；
- 对耗时或数量较大的对象分批更新；
- 对非关键 AI 加入决策冷却；
- 保存和恢复时记录必要的模拟时间与随机数状态，以提高结果连续性。

### 13.3 性能原则

先建立可测量的基准，再优化。优先减少不必要的全量遍历、每帧重复计算和远景对象的高频更新。只有在性能测试显示确有瓶颈时，才考虑复杂 ECS、Job 系统或更复杂的空间索引方案。

## 14. 数据模型与配置

### 14.1 静态定义与运行时状态分离

静态定义描述“这种东西是什么”；运行时状态描述“这个具体实例当前怎么样”。

例如：

- `HeroDefinition`：基础属性、外观、初始技能和可选标签；
- `HeroState`：具体英雄的等级、当前 HP、装备、关系和行动状态；
- `BuildingDefinition`：建筑成本、占地、功能、升级规则；
- `BuildingState`：地图位置、等级、建造进度和损伤；
- `ItemDefinition`：物品类型、属性、价格和使用规则；
- `ItemStackState` 或相应库存结构：具体持有数量和实例数据。

### 14.2 Godot Resource 配置

可使用继承自 `Godot.Resource` 的 C# 类保存可编辑内容，例如：

- `HeroDefinition`
- `BuildingDefinition`
- `ItemDefinition`
- `MonsterDefinition`
- `QuestDefinition`
- `EventTemplate`

资源配置适合设计师或开发者在 Godot 编辑器中调整。运行时变化不应直接写回静态定义资源，以免一个实例的变化污染所有同类对象。

### 14.3 运行时状态示例

`HeroState` 可包含：

- `InstanceId`
- `DefinitionId`
- `Level`
- `Experience`
- `CurrentHp`
- `Fatigue`
- `InjuryState`
- `Inventory`
- `Equipment`
- `Personality`
- `CurrentGoal`
- `CurrentActivity`
- `Relationships`
- `History`

字段应随实际玩法逐步增加，不要求第一天就设计出所有未来字段。

### 14.4 存档格式

建议采用带版本号的显式 DTO，例如：

- `SaveGameDto`
- `WorldStateDto`
- `HeroStateDto`
- `BuildingStateDto`
- `QuestStateDto`
- `ActiveEventDto`

不要直接序列化整个 Godot 场景树或所有 `Node`。加载时先解析 DTO、校验 ID 和引用，再恢复运行时状态与场景表现。

### 14.5 存档可靠性

第一版就应具备：

- 存档版本号；
- 基本字段与引用校验；
- 临时文件写入后再替换正式存档；
- 备份或至少保留上一份有效存档；
- 读取失败时给出可理解的错误；
- 版本迁移入口；
- 对活动任务、事件和模拟时间的完整恢复。

建议保存必要的随机数状态，避免加载后出现难以解释的模拟跳变；具体可按所使用的随机数实现决定。

## 15. 存档、暂停与模拟一致性

保存时需要覆盖：

- 世界时间与模拟速度相关状态；
- 地图和建筑；
- 英雄属性、需求、装备、背包、目标和活动；
- 怪物与重要对象状态；
- 任务队伍、进度和结算状态；
- 商店、库存和资源；
- 关系与声望；
- 正在进行的世界事件；
- 已经应用过的事件后果或结算标记；
- 必要的随机数状态。

加载时要避免：

- 重复发放任务奖励；
- 重复应用兽潮后果；
- 英雄装备丢失或重复；
- 建筑坐标与占地冲突；
- 活动任务找不到参与者；
- 已完成事件重新进入进行中状态。

## 16. UI 与玩家信息反馈

MVP UI 应支持玩家清楚理解和管理游戏状态：

- **主 HUD：** 时间、暂停、速度、金币和主要资源；
- **建筑建造面板：** 建筑类别、成本、条件、占地与效果；
- **英雄面板：** 属性、性格、需求、装备、目标、关系和活动；
- **任务面板：** 任务要求、奖励、风险、队伍与进度；
- **战斗日志：** 关键攻击、技能、伤势、撤退与结果；
- **事件面板：** 预兆、倒计时、威胁、可采取的准备措施和结算；
- **城市信息：** 人口容量、建筑状态、经济和防御情况。

UI 的重点不是一次展示所有信息，而是在玩家需要做决定时给出足够的信息。特别是自动战斗和大事件，应解释风险与结果，而不只是显示“成功/失败”。

## 19. 关键验收场景

第一版至少要验证以下场景：

1. 玩家从三间土屋起步，收集资源并建成一栋功能建筑。
2. 英雄无需逐个下指令，也能完成多种日常行为。
3. 玩家发布任务后，能够组队并启动冒险。
4. 英雄在地图上遇到怪物后自动战斗。
5. 任务奖励进入正确库存，并可用于建造或购买装备。
6. 英雄会因疲劳、受伤、装备不足或资源不足而改变计划。
7. 铁匠铺或冒险者公会确实改变英雄装备或任务流程。
8. 兽潮中，防御建设和英雄配置会影响结果。
9. 兽潮结束后，建筑损伤、伤员、资源和声望得到正确结算。
10. 保存并重新加载后，英雄、建筑、库存、任务和活动事件恢复正确。
11. 已完成任务和已结算事件在加载后不会重复发奖或重复造成损失。
12. 提高时间倍率后，模拟速度按预期变化，AI 不会因渲染帧率变化而失控。

---

## 20. 测试策略

### 20.1 规则层单元测试

优先覆盖：

- 经济：资源扣除、库存容量、交易和物品转移；
- 建造：成本、占地冲突、条件与升级；
- 英雄 AI：行为评分、承诺优先级、无效目标处理；
- 战斗：伤害、冷却、状态效果、胜负与撤退；
- 任务：状态迁移、队伍条件、奖励只结算一次；
- 事件：阶段迁移、后果只应用一次；
- 存档：序列化、反序列化、版本迁移和无效数据处理。

### 20.2 集成测试

- 任务奖励能正确进入库存；
- 购物会同步更新英雄金币与商店库存；
- 英雄受伤会影响后续任务可用性；
- 建筑功能对经济或冒险结果产生实际影响；
- 兽潮调用战斗、建筑、经济和声望系统后，结果一致；
- 加载存档后任务、事件和库存引用仍然有效。

### 20.3 手工玩法测试

检查玩家能否看懂：

- 英雄为什么选择某个行动；
- 任务风险如何评估；
- 战斗为何胜负；
- 城市建设对冒险的帮助；
- 大事件需要准备什么；
- 失败后如何恢复。

## 21. 风险与待验证事项

### 21.1 需要尽早验证的技术风险

- 等距坐标、网格放置和遮挡排序是否可靠；
- Godot 导航方案是否适合等距地图与动态障碍；
- 地图上多人战斗的表现、寻路和目标选择是否可读；
- 英雄数量增加后 AI 决策成本；
- 固定模拟步长与时间倍率的协调；
- 存档中对象 ID 和跨系统引用的完整性；
- C# Resource 与 JSON 存档之间的边界是否清晰。

### 21.2 需要尽早验证的玩法风险

- 城市经营与冒险是否互相影响；
- 英雄自主行动是否让玩家感到世界鲜活，而不是失去控制；
- 自动战斗是否有足够的战前策略和结果可读性；
- 城市升级是否带来新的玩法，而不仅是更高成本；
- 失败后果是否有分量但不至于让玩家放弃存档；
- 长期目标是否能持续提供新选择。

### 21.3 待定设计问题

- 玩家来到异世界的最终背景；
- 英雄召唤的规则、成本、上限与刷新机制；
- 英雄是否可能永久死亡；
- 世界时间与昼夜、季节的具体规则；
- 城市人口、本土居民与英雄的具体比例；
- 经济价格、资源产出、建筑成本和战斗平衡；
- 终局目标与最终事件；
- 是否采用确定性模拟、固定随机种子或其他重放策略。

这些问题不必一次全部解决。应先完成核心原型，再根据真实玩法测试逐项定案。

## 22. 推荐的第一阶段开发顺序

建议从一个可运行的小切片开始，而不是先搭建所有系统：

1. 创建 Godot 4 .NET 项目，确认 C# 编译、运行和调试正常。
2. 绘制一小块等距地面，确认坐标、排序和碰撞。
3. 放置一栋建筑和一个可移动英雄。
4. 实现资源数量、建造成本和建筑完成。
5. 加入模拟时钟、暂停和时间倍率。
6. 加入一个英雄的状态、需求与简单自主行为。
7. 加入一个任务、一个怪物和最简自动战斗。
8. 实现奖励进入库存并用于下一次建造或装备购买。
9. 加入存档/加载，验证状态恢复。
10. 扩展为 3–5 个英雄、数种建筑和怪物。
11. 最后加入兽潮，验证多个系统协作。

**第一个可玩里程碑：** 玩家能从三间土屋出发，收集资源、建造一栋功能建筑、派遣英雄完成一次冒险、获得奖励并保存进度。这个闭环跑通后，再扩展英雄社会模拟和世界事件。

## 24. 项目原则总结

1. **先完成闭环，再扩展系统。** 不要先把所有未来玩法抽象成庞大框架。
2. **表现和规则分离。** 动画不决定战斗结果，场景树不等于存档数据。
3. **静态定义和运行时状态分离。** 避免实例之间相互污染。
4. **系统通过明确接口协作。** 库存、战斗、任务和事件不能互相随意改数据。
5. **失败要有代价，也要有恢复路径。** 让玩家承担后果，但避免轻易摧毁长期投入。
6. **AI 要可解释、可调试。** 记录行动原因和关键评分，避免行为看起来随机失控。
7. **重要状态必须可保存、可恢复。** 任务和事件尤其要避免重复结算。
8. **性能优化以测量为依据。** 先做可玩的规模，再根据基准优化。
9. **城市成长要改变玩法。** 新建筑、新区域和新阶段都应创造新的选择。
10. **所有未来扩展都以核心循环成立为前提。** 先证明“经营—冒险—回报—扩建”好玩，再扩展更复杂的社会模拟。
