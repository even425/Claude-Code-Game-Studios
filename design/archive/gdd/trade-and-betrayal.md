## 开发者原话（本文档的唯一依据）

> 「玩家间的交易也是有彩蛋的，**比如有些人坏，它会交易一些不好的东西给别人，别人发现了
> 会造成损失，然后就会出现吵架，最后 pvp 等等，上线就追着砍，被砍的只能跑野外升级，
> 变强了再回来报仇**，等等有意思的剧情。**不过这都是后话**」

补充依据来自 `design/game-brief.md`（同属开发者原话整理，非发明）：

> 「有人坏 → 交易不好的东西 → 别人发现 → 损失 → 吵架 → PvP →
> 上线就追着砍 → 被砍的只能跑野外升级 → 变强了回来报仇。
> **这是因果链，不是剧本。** 它需要**物品、交易、谎报品质、PvP、野外地图**——所以属于 M4。」

> 「有些玩家还会在村庄周边，防护罩内**自行摆摊**等，我能收取摆摊费。」
> 「玩家 ↔ 玩家：摆摊，村长抽成。**风险是私下交易让抽成形同虚设**」

> 「傲 ……挑**有对手的、难的**」／村长为傲准备的是：「防护罩、**仲裁**、**PK 规则**」

**开发者自己说了「这都是后话」。** 本文档的优先级因此是 **Alpha**，不是 MVP。
它的首要任务**不是把每一环填满，而是把这条链的形状和接口固定下来**——
让后来的人接上去时，知道每一环凭什么发生。

**本文档没有发明任何机制。** 凡是需要新决策才能接上的环节，一律在
[Open Questions](#open-questions)，正文里不当作已定规则。

## Summary

两个人之间发生了一件事：一方给了另一方一样不该给的东西。剩下的九个环节
——发现、损失、吵架、PvP、追着砍、流放野外、变强、回来报仇——**没有一个是脚本**，
它们全部是从**前一个环节留下的状态**里长出来的。本文做三件事：

1. 把这条链写成一条**状态机**（§ States and Transitions），每一步都有明确的进入条件；
2. 逐环标注**它凭什么发生**——哪些今天就有上游实现，哪些是从原话能推出来的，
   哪些**答不上来**（§ 逐环审计，这是本文档最重要的一张表）；
3. 把答不上来的问题集中到 Open Questions，**不自己接**。

**Alpha 只做前两环**（交易 → 发现），这与 `systems-index.md` 对本系统写的缓解措施
「明确切到 Alpha；**先做前两环**」一致。环 3 起在本文档里**只有接口，没有实现**。

## Overview

村庄是一个真的会出事的地方。两个人私下换了一次东西，其中一样是坏的；收货的人后来发现了，
于是他亏了；于是两个人吵架；吵完架之后有人动了手；动手的人之后一上线就去找对方；
被打的人躲在村外变强；强了以后回来。开发者描述的就是这九步。

本系统**不设计这九步的内容**，它设计的是**这九步之间的接口**。理由很直接：
这九步里，只有「吵架 → 结仇」这一段在今天的代码里已经有真正的实现
（见 `squad-and-cohesion.md` 的 `GrudgeWith`）。其余每一段的强度、范围、触发条件，
开发者都还没说过。**先写内容等于先发明。**

**「结仇」在这条链里的地位，2026-10-17 被开发者改写了。** 原话：「我举例两个玩家可以有仇，
但不代表你就只能有仇啊，你需要扩展。」所以**仇是关系里的一格，不是关系的全部**——
完整的村民关系系统（搭子 / 师徒 / 同乡 / 欠人情 / 嫉妒 / 竞争 / 欠债 …）由
`design/gdd/relations.md` 单独定义。**本文档是它的消费方**，只读其中「敌意」一维，
见 § 本链消费哪些关系量。

所以本系统交付的是一张**可以逐格填的格子纸**：
哪些格子已经有墙（上游实现），哪些格子是空的（等开发者），以及**空格子之间靠什么传递状态**。
后者是本文档唯一真正的产出。

## Player Fantasy

**目标 Aesthetics：Narrative（叙事）+ Discovery（发现）**，辅以 Challenge。

**Discovery 是主感官。** 玩家不应该通过面板知道「张三骗了李四」，他应该是在杂谈里
先看见一句不对劲的话（「那把刀昨天还卷了口」），过两天又看见一句，
然后自己把两件事连起来。**发现是玩家自己完成的，不是系统播报的。**
这是 `personality.md` § UI Requirements 那条决定（不显示效率数值，让玩家从杂谈里推断）
在敌对关系上的同一个用法。

**Narrative 是重量。** 这条链之所以有分量，是因为它的两端都是真的——
李四不是 NPC，他真的少了一批材料，他真的记着。

**Challenge 不是操作挑战，是治理挑战。** 玩家的能力不是「打赢李四」，
是「决定这件事在村里怎么办」。这是本文档里唯一一条真正属于玩家的操作，
也是最重的一条。见 § Player Fantasy · 干预边界。

**反对的读法**：这个系统绝不能读成「一个背叛事件按钮 + 一个复仇任务」。
那样的系统里，玩家点一下坏，弹出「你骗了他」，世界给一段过场。
**那条链上每一环都应该能从别的状态里读出来，而不是从一条时间线上读出来。**

## Detailed Design

### 核心不变量（Invariants）

这九条是本文档唯一被断言为「已定」的内容。**任何实现违反其中一条，就是错的**，
无论数值怎么调。（I1–I7 为初稿七条；**I8 / I9 为 2026-10-17 裁定 ⑫ 与裁定 ⑬ 扩展后新增**。）

| # | 不变量 | 依据 |
|---|---|---|
| **I1** | **链上每一环的进入条件只能是前一环留下的状态。** 不得出现任何按游戏内时间表触发、剧本推进、或「本场战斗结束后自动触发下一场」的写法 | brief 原话：「**这是因果链，不是剧本**」 |
| **I2** | **结仇（`GrudgeWith`）是这条链唯一的承重结构，但它是「关系」这一维里的敌意，不是关系的全部。** 吵架及其后果**复用已实现的机制**，本系统不新建一个平行关系字段；**本系统也不定义、不存储任何其他关系** | `squad-and-cohesion.md` R5/R6、状态表「有仇（Grudge）」；`personality.md` § 8 种日常事件（吵架 → 两人缺席一天 + 结仇）；**裁定 ⑬ 扩展**（见 I9） |
| **I3** | **追砍以「上线」为触发条件，作息是唯一的自由限流器。** 追杀者只能在他自己的作息窗口内行动；目标也只能在自己的作息窗口内被找到。**系统不额外规定他能不能追** | 开发者原话「**上线**就追着砍」+ `time-and-schedule.md` 的时区作息 |
| **I4** | **本系统不产生永久损失。** PvP 的后果走 `死亡与复活`（停机一天）。链上任何一环都不得删除一个村民 | `game-brief.md`「**没有硬失败**」；`死亡与复活`「死亡可以让这个玩家，过一天才能上线」 |
| **I5** | **性格不得成为背叛的硬门槛。** 不得出现 `if (personality == X) betray()`。性格若参与，只能改**概率或效率**，且该取值必须是推导值而非既定事实 | `personality.md` 铁律 1：「唯一能让一个村民『不干活』的，是状态，不是性格」 |
| **I6** | **玩家可见文案零系统词**：成功 / 失败 / 获得 / 消耗 / 属性 / 奖励。链上九环的杂谈句一律不写具体数值——尤其「损失了多少」「差了几件」「还要多久回来」 | `personality.md` § 禁止清单第 5 条；`expedition.md` § 文案禁令；裁定 ⑫「**你看不到他，也无从推测进度**」 |
| **I7** | **本系统的范围以「两个人之间的关系」为单位，不以「村庄」为单位。** 链上任何一环都不得绕过被指的两人直接改村庄全局状态（村长层级的干预是另一个问题，见 OQ-1） | I1 的推论 |
| **I8** | **`OffMap`（离村）与「上线」是两个正交量，谁也不解除谁。** 他**可以已上线而仍在离村状态**；没有任何路径能因为「他上线了」而把 `OffMap` 置回 `false`；**升级计时器不得读 `IsOnlineAt`** | **裁定 ⑫** + `time-and-schedule.md` 的时区作息。详见 § 离村 |
| **I9** | **仇是关系之一，不是关系的全部。** 本系统**只消费敌意一维**，不定义、不存储、不推导搭子 / 师徒 / 同乡 / 欠人情 / 嫉妒 / 竞争 / 欠债中的任何一维，**也不新建平行字段**。完整关系系统归 `design/gdd/relations.md` | 开发者原话：「我举例两个玩家可以有仇，但不代表你就只能有仇啊，你需要扩展」 |

### 链的状态机

链上每一环用 `⟶` 前进，允许**回退**（见 § Edge Cases E2）。每一环的**进入条件**必须有
对应的可读状态字段；**没有进入条件的环节一律不写进代码**。

```
        ┌──────────────────────────────────────────────────────────────┐
        ↓                                                              │
   [1] 已交易 ──→ [2] 已发现 ──→ [3] 已结算 ──→ [4] 已结仇 ──→ [5] 已动手 ──→ [6] 追击中 ──→ [7] 在野外 ──→ [8] 变强 ──→ [9] 已回来
        ↑                                                                                                                    │
        └────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### States and Transitions

| # | 状态 | 进入条件（**必须可从存档字段读出**） | 退出去向 | 开发者依据 |
|---|---|---|---|---|
| 1 | `Traded` | 一次**玩家之间**的物品转移完成，且转移的两方都在场 | `Discovered` / 回 `None` | 「它会交易一些不好的东西给别人」 |
| 2 | `Discovered` | 持有方**察觉**到该物品与交付时不符 | `Settled` / `None` | 「别人发现了」 |
| 3 | `Settled` | 损失**已经落到持有方的账上**（不是将要） | `Grudged` | 「会造成损失」 |
| 4 | `Grudged` | 两人之间的 `GrudgeWith` 被写入 | `Fought` / `None`（搭手可清） | 「然后就会出现吵架」 |
| 5 | `Fought` | 一次 PvP 遭遇**实际交手**（不是「决定要打」） | `Chasing` / `Grudged` | 「最后 pvp」 |
| 6 | `Chasing` | 追杀者在线 ∧ 目标在线（**两个作息窗口的重叠**） | `Exiled` / `Fought` | 「上线就追着砍」 |
| 7 | `Exiled`（**离村**） | **`OffMap == true`**：目标**不在任何地图上**——村庄地图不渲染他，野外地图也不渲染他。⚠️ **谁在何时把它置位，仍未定义**（OQ-5 残余） | `Training` / `Chasing` | 「被砍的只能跑野外升级」+ **裁定 ⑫「离村，不在地图上」** |
| 8 | `Training` | 目标在野外累计满足了某个**尚未定义的**成长条件 | `Returned` | 「变强了」 |
| 9 | `Returned` | 目标**回到村庄**，且仍处于 `Grudged` | 终局判定（**尚未定义**，OQ-6） | 「再回来报仇」 |

#### 离村（`OffMap`）——裁定 ⑫ 落地的状态

**裁定 ⑫（2026-10-17，开发者拍板）**：跑野外升级期间 = **离村，不在地图上**。
开发者原话：「被砍的只能跑野外升级」——升级期间他不在地图上。

这不是一句叙述，本文档把它声明成一个**有名字、有进入条件、能从存档读出**的状态：

```
OffMap : bool      // 离村。true = 他不在任何地图上
```

| 项 | 值 | 说明 |
|---|---|---|
| 进入条件 | 链环 7 `Exiled` 成立，且 `OffMap` 被置为 `true` | **谁置位、何时置位，仍未定义** → OQ-5 残余 (c) |
| 空间断言 | 他**不在任何地图上**：村庄地图不渲染他，**野外地图也不渲染他** | 裁定原文「不在地图上」 |
| 玩家可见后果 | **看不到他，也无从推测进度** | 因此本系统**不产出任何进度 / 剩余时间 / 方向类文案**（I6） |
| 退出条件 | `Training` 达成 → `OffMap = false` → 环 9 | 达成条件未定 → **OQ-9** |
| 对 `Chasing` 的作用 | `OffMap` 为真期间，环 6 **`Chasing` 不成立** | 这正是 OQ-5 原本担心的「在村里 = 追杀可继续 = 循环不闭合」的答案 |

> **旧值 vs 裁定值（修订说明）**：旧接口断言写的是「目标处于野外，且**不在村庄可达范围内**」，
> 并注明「野外地图是否真的与村庄物理隔离，是 `野外地图` 系统要回答的问题」。
> **裁定值**：「**不在任何地图上**」——这个断言**不再依赖几何可达性判定**，
> 因此 `野外地图` 那边答得上来还是答不上来，**都不影响本系统**。旧断言已作废。

#### 三个「不在场」的区别与优先级（本节存在的唯一理由：防止下游混为一谈）

`OffMap`（离村）、`Away`（远征中）、`AbsentDays > 0`（病假）都能让一个人「不在」，
但它们断言的**不是同一件事**。混为一谈会直接写坏「追砍能不能继续」和「工地还有没有人」：

| | **离村 `OffMap`** | **远征中 `Away`** | **病假 `AbsentDays > 0`** |
|---|---|---|---|
| 它断言的是什么 | 他**在哪个空间** | 他**在地图的哪一段路上** | 他**今天能不能干活** |
| 他在地图上吗 | **不在**（任何地图都没有他） | **在**（远征路线本身是地图） | **在**（位置不变，还在村里） |
| 谁能看见他 | **没有人** | 同路的队员、路途上的遭遇 | 所有人——他就在村里，只是不上工 |
| 还能被 `Chasing` 找到吗 | **不能** | 按 `expedition.md` 的远征规则 | 原则上能（他在村里） |
| 谁负责这个状态 | **本系统**（链环 7） | `expedition.md` / `配队与配合` | `time-and-schedule.md`（`RefreshOnline` 递减） |
| 它是**空间**、**位置**还是**出勤能力** | 空间 | 位置 | 出勤能力 |

**优先级：`OffMap` > `Away` > `AbsentDays`**，按此顺序取**第一个成立的**来回答「他在不在场」。

三条必须成立的后果：

1. **`OffMap` 是超集，它一成立，另外两个都不参与判定。** 他不在任何地图上，所以「他在远征路上吗」「他在村里吗」都是无意义的问题。
2. **低优先级状态被 `OffMap` 遮蔽，但不清除。** 进入 `OffMap` 时**不清零** `AbsentDays`、**不置** `Away = false`；退出 `OffMap` 后它们照旧生效。**遮蔽 ≠ 重置。**
3. **`Away` 与 `AbsentDays` 之间没有优先级，因为它们本来就同时成立。** `design/gdd/village-building.md` 公式 2 是 `{ h : h.ToSite ∧ ¬h.Away ∧ OnDuty(h) }`——三项**合取**，不是三选一。本系统**不动那个公式**，只是把 `OffMap` 加在最前面作为**短路条件**。

#### 离线时长由什么决定——OQ-5 更深的那个子问题（已裁定）

> **歧义本身**：他的作息是时区驱动的（`PlayHours` + `UtcOffset`），所以「他在线吗」
> 与「他在哪儿」是两件事。实现者极容易写出「他上线了 ⇒ 他回来了」，或者反过来
> 拿 `IsOnlineAt` 当升级计时器。**本文档把两者的正交关系钉死，下游不必再猜。**

**裁定（2026-10-17）：**

| 量 | 由什么决定 | 与对方的关系 |
|---|---|---|
| `IsOnlineAt(h)`（他上线了吗） | **时区作息**（`time-and-schedule.md`） | 与 `OffMap` **完全正交** |
| `OffMap`（他在哪儿） | **链环 7 的状态**（本系统） | 与 `IsOnlineAt` **完全正交** |

由此得到四条**无歧义**的读法：

1. **他可以「已上线、但仍在离村状态」。** 面板上他在线、杂谈里可能有他（若他产生有后果条目），但**地图上没有他**，`Chasing` 不成立。**「在线」不是「回来」的充分条件。**
2. **他也可以「已回来、但当前不在线」。** `OffMap = false` 之后他回到村庄，但只有在他自己的作息窗口内才在地图上出现。那是作息，不是链的状态。
3. **`IsOnlineAt` 永远不解除 `OffMap`。** 没有任何代码路径可以因为「他上线了」而把 `OffMap` 置回 `false`。**「离线」也不延长它。**
4. **⚠️ 升级计时器不得读 `IsOnlineAt`。** 若有人拿「他在线的累计时长」当升级进度，得到的是「按他的作息攒时长」——**这没有被任何人拍板过**，而且会让升级速度取决于他的时区，从而让同一条链在不同人身上长度不同。**离村时长 = f(变强的达成条件)，与作息无关。** 计时器必须是独立于作息的量。

**所以 OQ-5 的答案是三段式的**：

| 子问题 | 状态 | 答案 |
|---|---|---|

### 关于「坏」的动机（I5 的具体落实）

第 1 环唯一的硬性要求是：**不得写成性格开关。** `personality.md` 的铁律 1
已经把这条路封死了——性格只能改概率和效率。

在此前提下，**推导一个合法的动机接口**（这是接口，不是机制）：

```
BetrayalMotivation(hero, item, counterparty) -> weight ∈ [0, +∞)     # 未定义取值
```

本文档**只声明这个函数存在**，不定义它的取值、不定义它读什么、不定义谁调用它。
任何调用方都必须自己提供依据。

> ⚠️ 特别提醒：`贪` 想要财富、`傲` 想要胜负，都是 `personality.md` 里的**开发者原话**；
> 但**「贪所以会骗人」这一步推不出来**。财富动机到欺骗行为之间没有任何原话。
> 本文档**不假设** `贪` 更容易叛变。若要这么做，必须先过 OQ-2。

### 本链消费哪些关系量（接口声明——**不实现关系系统**）

**开发者原话（2026-10-17）**：「我举例两个玩家可以有仇，但不代表你就只能有仇啊，你需要扩展。」

**完整的村民关系系统由 `design/gdd/relations.md` 单独定义。**
**本文档是它的消费方，不是它的定义方**（I9）。下面这张表是本文档**向 `relations.md` 提出的接口需求**，
本 GDD **只声明它读什么，不声明它怎么算**。

| 本链的哪一步 | 它需要的**关系量** | 方向性 | 对 `relations.md` 的读法要求 |
|---|---|---|---|
| 环 6 `Chasing`「上线就追着砍」 | **单向敌意**：A 想打 B，而 B **不必**想打 A | **单向** | 追砍只需要读 `敌意(A → B)` 一个方向；**不要求互指** |
| 环 5 `Fought` 实际交手 | 双方**可交战** | 双向 | 一次交手之后单向敌意是否变成互指——**写法未定义**，见 **OQ-13** |
| 环 4 `Grudged` 结仇 | `敌意`（当前唯一被实现的字段是 `GrudgeWith`） | 双向（互指） | 今日的 `GrudgeWith` 就是敌意维的**二元子集**；`relations.md` 落地后应改为读写该维 |
| 环 9 `Returned`「回来报仇」 | **双向敌意** 成立，且**未被和解清除** | 双向 | 环 9 的终局判定需要读「敌意是否仍成立」——**它不读好感** |
| 环 9 及之后「带他一起」 | **双向好感** | 双向 | 好友与仇人**可以同时成立**；本链**不假设二者互斥**（裁定 ⑬ 的硬禁止只管同队，不管好感） |

**四条必须成立的推论：**

1. **本文件里的「有仇」只管一格：能不能同队。** 裁定 ⑬ 把它改成**硬禁止 + 可和解**，而**这一格不因其他任何关系而解除**——一个人可以同时是某人的搭子、某人的徒弟、某人的同乡、欠某人一份人情，也仍然是某人的仇人，**同队照样禁止**。**这五格关系彼此独立。**
2. **敌意是「关系」这一维里的一个刻度，不等于「关系差」。** 若 `relations.md` 把关系做成多维（好感 + 敌意 + 亏欠 + 竞争），本链**只读敌意那一维，其余维度一律不读**——包括那些恰好会「降低敌意」的维度（嫉妒、竞争）为什么没被读，理由是**没有依据**，不是被否决了。
3. **本系统不写除敌意以外的任何关系量。** 一次背叛（环 1）会不会改变两人之间的好感、亏欠、同乡感？**没有依据，本文档一个字都不写**（I9 + E8）。
4. **`GrudgeWith` 不是本系统的私有字段。** 复核结论：`chronicle.md` R1 合规表与 `VillageLife` 的吵架 / 干起来了 / 搭手事件**也在写它**。
   ⚠️ **修订说明**：本 GDD 原文两处写「本系统是这条链上**唯一**会写入它的模块」「本系统是该字段**唯一的写入方**」。**该绝对表述已作废**——本系统是**链上**的一个写入方，不是全项目唯一的一个。

### 干预边界（本文档必须提出、不回答的问题）

> 这一节**只陈述张力，不给答案**。完整提问见 OQ-1。

张力来自三处，全部是**已经存在的开发者原话**：

1. `game-brief.md` 的核心一句：**「村民不知道自己活在一个真的世界里。」**
   这不是氛围词，是这个世界的**地基**——它一旦被抽掉，整套「他以为他在打游戏」的
   行为（找 GM、看攻略、互相安利）就没有依据了。
2. `game-brief.md` 的傲行明写：村长为傲准备的是「防护罩、**仲裁**、**PK 规则**」。
   **也就是说，开发者已经许诺了仲裁与 PK 规则这两个设施的存在。**
   所以问题不是「要不要管」，而是「仲裁长什么样」。
3. `死亡与复活` 的既有立场：玩家以为自己被删号了，去找 GM、发帖问怎么注销，
   「而**村长一句也不能解释**」。那是关于**解释**的立场，不是关于**干预**的立场。

把 2 和 1 放在一起，就出现了本文档认为最要紧的一个问题：

> **仲裁是一个 GM 功能。** 如果村长以「村庄的仲裁者」身份处理两个人的争端，
> 他就在做 GM 的事——而村民之所以还能安心地当玩家，前提是他不知道对面坐着的是谁。
> **「提供仲裁」和「不暴露自己」这两件事，在这一环上直接冲突。**
> 开发者的原话同时要求了两者。

本文档**不决定**这一冲突怎么解。它是 OQ-1，是本系统唯一一条我认为
**在实现之前必须由开发者拍板**的问题——因为链上第 6 环（追砍）一旦上线，
它就会自动制造出这个问题，而那时候玩家已经被卷进去了。

## Formulas

### 本节没有公式——这是刻意的

`standard` 档位要求「系统定义了数值规则时才写 Formulas」。
**本系统当前没有定义任何数值规则**，因为链上九环的每一个量级都追溯到一个
尚未做出的决定。写下一组数字，只会给后来的人一个「这些是调过的」的错觉。

以下公式**是需要的**，逐条列出以便拍板后直接填入：

| 待定公式 | 它要回答什么 | 卡在哪 |
|---|---|---|
| `P(betray)` | 谁在什么条件下会去谎报品质 | OQ-2 |
| `P(discover_when)` / 发现延迟 | 「发现」是什么触发、隔多久发生 | OQ-3 |
| `Loss(item, counterparty)` | 损失掉的是什么、多少 | OQ-4 |
| `P(pvp_engages)` | 结仇之后多大概率变成真的动手 | OQ-7 |
| `PvpStrength(a, b)` | **PvP 的强度用什么衡量** | OQ-7 |
| `Cooldown_chase` | 追砍是自动还是有冷却 | OQ-8 |
| `GrowRate(target)` | 变强需要多久 | OQ-9 |
| `OffMapDuration(target)` | **离村多久**。⚠️ 它**必须等于** `Training` 的达成条件，且**必须不读 `IsOnlineAt` / `PlayHours` / `UtcOffset`**（I8） | OQ-9 |

> **一条已经定死、因此不算「待定公式」的**：`OffMap` 期间他**不在任何地图上**，
> `Chasing` **不成立**（裁定 ⑫）。这不是一个量，是一个**布尔断言**——它不需要数值，也不需要调参。

> **一个必须一起定的量（不可拆）**：`Loss` 的量级与 `PvpStrength` 的量级必须一起定。
> 损失小到追不上 inconsequential，损失大到打一场就退坑，两头都是死路。
> 这两个数出自同一个设计决定，**不能分两次拍**。

## Tuning Knobs

**当前无旋钮。** 九环的每一环都还没有数值（理由见 § Formulas）。
下列是拍板之后**必然需要**的旋钮，先登记以免到时候现编：

| Parameter | Current | Safe Range | Category | 调高的效果 | 调低的效果 |
|---|---|---|---|---|---|
| `P(betray)` | **未定义** | 待 OQ-2 | curve | 村庄变成贼窝 | 环 1 几乎不发生，本系统无事可做 |
| `Loss` 相对量 | **未定义** | 待 OQ-4 | curve | 一次背叛毁掉一个人 | 吵不起来 |
| `Cooldown_chase` | **未定义** | 待 OQ-8 | gate | 追杀变成长期折磨 | 上线追着砍变成上线打招呼 |
| `GrowRate` | **未定义** | 待 OQ-9 | curve | 复仇是长期目标 | 复仇在下一场远征后就结束 |
| `OffMapDuration`（离村时长） | **未定义** | 待 OQ-9 | curve | 链走完第 8、9 环需要很长一段不在场 | 他几乎立刻就回来了，`Chasing` 重新成立的机会变多 |
| `UpgradeTimerSource`（升级计时器的数据源） | **不得为 `IsOnlineAt`** | **只有「与作息无关」的量** | **gate** | — | 若允许读 `IsOnlineAt`，升级速度将取决于目标所在时区，**同一条链在不同人身上长度不同**——这不是任何人拍过板的 |
| `GrudgeClearChance` | **未定义** | — | curve | 链能自然收敛 | 村庄积累永久敌人 |

> ⚠️ **`GrudgeClearChance` 是唯一一条可能让整条链「失控」的自由度。**
> `E2` 允许链回退，但**如果和好很容易，环 6 之后的几步永远走不到**；
> **如果和好几乎不可能，村庄会在几十个游戏日内积累出大量不可解的敌对关系**。
> 这个值一旦定错，坏的不是一个数字，是整条链的形状。

## Acceptance Criteria

> Alpha 范围（环 1–2）能验的只有功能项；环 3 之后的项**故意保留为「现在应当失败」**，
> 它们是 OQ 的守门测试——**填上实现之前，它们必须一直是红的**。
> B 组标 **(无依据)** 的是「没人拍过板」；D 组标 **(已裁定)** 的是「拍过板、但代码还没写」——
> **两者当前都应当失败，红的原因不同，实现顺序也不同。**

### A · Alpha 范围（环 1–2）

- [ ] **A1 · 链由状态触发，不由时间触发。** 注入一个只完成环 1 的场景，
      推进 5 个游戏日：杂谈里**不出现**任何与环 3–9 相关的内容。
      （守门 I1）
- [ ] **A2 · 交易需要双方在场。** 一方离线时发起交易，交易**不发生**，不产生任何杂谈条目。
- [ ] **A3 · 「发现」有明确的存档字段。** 环 2 的进入条件可由存档 diff 验证——
      存档里能看出「谁在哪一刻发现了」，而不是只能从杂谈回放。（守门 I1）
- [ ] **A4 · 性格开关不存在。** 对全部 3 种性格 × 全部物品做穷举，
      断言没有任何一条代码路径写成了 `if (personality == …)` 形式的叛变分支。
      静态扫描 + 运行时统计双证。（守门 I5）
- [ ] **A5 · 零系统词。** 对本系统产生的全部玩家可见文本扫描
      `成功 / 失败 / 获得 / 消耗 / 属性 / 奖励`——**0 命中**。（守门 I6）
- [ ] **A6 · 数值不泄漏。** 环 3（若已实现）的杂谈**不得**写出损失的具体数量，
      与 `expedition.md` 对私吞的处理一致（「短了几份」而不是「短了 5 份」）。
- [ ] **A7 · 关系是两人的。** 构造 A→B→C→A 的三角背叛，
      断言**三条独立的链**，且 B 同时持有「受害者」与「加害者」两种状态。
      （守门 E4 / I7）

### D · 已裁定、待实现（当前应当失败，因为代码未写）

> 与 B 组的区别：**这些不需要再拍板，只需要写。** 实现完成后它们应当**转绿**，

- [ ] **D1 · `OffMap` 是一个真实的、可存档读出的状态。** 断言存档里存在 `OffMap` 标志，且环 7 的进入条件可由它读出。（裁定 ⑫）

- [ ] **D5 · 升级计时器不读作息。** ① 静态扫描 + 运行时统计：断言离村时长的计算路径上**不存在**对 `IsOnlineAt` / `PlayHours` / `UtcOffset` 的读取。② 行为测试：构造两个作息窗口完全不同（分处不同时区）的目标，断言在外部条件相同时**离村耗时相同**。（I8 第 4 条）
- [ ] **D6 · 敌意只是关系的一维。** 穷举九环，断言本系统写入的关系量集合 `⊆ {敌意}`：**不写**任何好感 / 师徒 / 同乡 / 亏欠 / 嫉妒 / 竞争 / 欠债 量。（裁定 ⑬ 扩展 / I9）
- [ ] **D7 · 仇人同时是搭子，同队照样禁止。** 构造 A 与 B：`GrudgeWith` 互指，且 `relations.md` 的「搭子」**双向好感**同时为真。断言：**同队仍然被禁止**（裁定 ⑬ 的硬禁止只管这一格，不因其他关系而解除），且 A、B 的好感量**不被本系统改动**。

### C · 体验

- [ ] **C1 · 玩家自己把两件事连起来。** 给试玩者看杂谈，
      5 人中至少 4 人能说出「这两句是同一件事」，**而不是**等系统告诉他。
- [ ] **C2 · 没有人说「他在做任务」。** 链的杂谈读起来必须像村里人在讲村里的事，

- [ ] **C3 · 没有一个测试者说「这些人是 NPC 在演戏」。** 这一条是 OQ-1 的早期信号：
      如果干预边界一条都没定，链跑起来一定会有这个感觉。
