## Summary

杂谈是村庄右侧的一个文字面板，村里发生什么，它就用村里人说话的方式记一行。

它存在的理由是本项目最重要的一条推论：**游戏里 95% 的事情是村民自己做的，玩家控制不了。玩家怎么知道这件事发生了？只有杂谈。** 所以**杂谈写得干，自主性就等于不存在**，不管背后模拟得多复杂——M0 已经验证过这条：工地「0 人、速度 0.0000、进度冻结 9 小时」是真的，玩家能看见它的唯一途径就是杂谈里那一句「村口最后一个人走了」加上第二天他发现柱子没长高。

**它不是日志**（没有时间戳、不能翻页、不能搜索），**它不是交付物**（没有任何东西指向它），**它不解释游戏**（它不告诉你发生了什么，只告诉你村里人看见了什么）。它是**村庄自主行为的唯一读数器**。

> **Quick reference** — Layer: `Presentation` · Priority: `MVP` · Key deps: `时间与作息`、`召唤系统`、`配队与配合`、`村庄建造`、`村庄日常事件`（+ 被以上全部依赖）

## Overview

玩家打开游戏，村庄右边有一栏字。昨天有人病倒了，有人跟人吵了一架，有队出发了、有队回来了，井盖成了。这些字不是系统写给玩家看的报告，是**村里人在转述他们看见的事**：「老李头说，灰九昨天在井边坐了半个下午，谁也没搭理。」「村口来了个生人，没人认得。他站了很久就走了。」

这个面板的全部设计压力来自一件事：**它是唯一读数器。** 别的系统把状态改了，玩家看不见——工地速度掉到四成、某个人明天不能上工、两个仇人不能同队——这些都没有 HUD 提示，只有杂谈里那一行。所以杂谈写坏了，后果不是「文本质量下降」，是**「游戏里的因果变成了随机数」**。

因此这个 GDD 里最重要的一条规则不在文案里，在第 1 条：**事件必须改状态，不能只是写一句话。** 如果一个条目写进杂谈却什么都不影响，它就是装饰。这条已经在 `design/game-brief.md` 立下并且被实现遵守（病倒真的停工、吵架真的结仇、磨洋工真的 ×0.40），本 GDD 的职责是**把它固化成可测试的断言**，并处理它带来的两个后果。

**裁定 ⑮（2026-10-17，开发者拍板）已经处理掉了第二个后果。** 杂谈**分为两个面板**：

| 面板 | 收什么 | 留存 | 一句话 |
|---|---|---|---|
| **杂谈** | **改变了村庄**的事——病倒、吵架、启工、盖成、出征出发 / 归来 | **永久留档** | 「他干了什么」 |
| **近况** | **不改变任何状态**的占位条目——闲逛、陌生人在村口等 | **滚动** | 「村里现在是这样」 |

分类判据见 **R1b**（可测试，不是作者感觉），容量与淘汰见 **R7** / **F4**。
**两个面板互不挤占**——这是这次裁定要解决的问题：远征条目全部有后果，因此全部进留档面板，再也不会吃掉滚动面板的行数（F4b）。

## Player Fantasy

**Aesthetic**：主要是 **Discovery**（次要 Narrative）。

玩家应该感觉到的是「**我不在的时候村里也发生了事，而且那些人对我做的事有反应**」。

**具体到一次游玩**：他昨天把三个人派去东林伐木，今天打开游戏，看见「三个人天没亮就走了。老李头在村口看着他们」，然后隔两行看见「回来一个病了的，躺了一天，屋门口放了一碗粥，放凉了也没人喝」。他不需要任何提示就能自己得出结论：**这次派出去的人选得不好，因为回来的那个已经病了**。这个结论是他自己走出来的——`design/gdd/village-building.md` 的 Feel Acceptance Criteria 写死了同一条：**取舍是被发现的，不是被告知的。**

**Anti-reference（明确不要）**：

- **不要**《缺氧》/《环世界》那种带时间戳、可暂停、可回放的**事件日志**。那条路一旦走上，杂谈就变成调试面板，玩家会开始优化它而不是村庄。
- **不要**带「+12 石料」「任务完成」这类结算行的**任务追踪器**。
- **不要**让杂谈**解释游戏**。「工地停摆是因为没有人在线」这种句子一句都不许有——玩家必须自己从「村口最后一个人走了」+「柱子没长高」把因果拼出来。

**留白是特性，不是缺陷。** village 里的人不知道自己正在被观察，所以杂谈里永远有说不清的话：「多出来那几块，来路没人问。」「少多少，从来没人说得准。」**这不是含混，这是这个面板存在的语气。**

## Detailed Design

### 核心规则

#### R1 — 事件必须改状态，不能只是写一句话

一条杂谈条目**必须**对应一次已经生效的状态改变，否则**删掉**。

**判定标准（三条全满足才算合规）**：

1. 条目被写下时，某个 `HeroAgent` 的字段或村庄的某个量**已经改变**；
2. 这个改变**能被别的系统读到**并产生后果；
3. 后果**玩家能在游戏里看见**，或者**能从杂谈里推断出来**。

**已合规的**（实现已验证）：

| 条目 | 改的状态 | 谁读它 |
|---|---|---|
| 病倒 | `AbsentDays = 1 + rand(2)`，`WorkRate → 0` | 建造、配队、日常事件的候选池 |
| 吵架 | 双方 `GrudgeWith` 互指 | 配队系数 ×0.50；日常事件配对时跳过仇人 |
| 干起来了 | `GrudgeWith` + 双方 `AbsentDays = 1` | 同上 + 明天两人不能出工 |
| 磨洋工 | `SlackDays = 2`，干活率 **×0.40** | `HeroAgent.WorkRate` |
| 想走 | `RestlessDays = 2`，干活率 **×0.30** | 同上 |
| 搭手 | 清 `GrudgeWith`（唯一的解仇途径） | 配队系数 |

**裁定 ⑮（2026-10-17，开发者拍板）已经把这条欠账处理掉了。** `闲逛` / `搭手`（对没有仇的人）/ `陌生人` 三条不改状态，因此按 R1b 被归入**无后果**类，写进**近况**面板（滚动淘汰），不再占用留档空间。

> **修订说明**：本条原文写「它们是本系统唯一允许的装饰」（装饰条目与留档条目混在同一个面板、同样参与淘汰）。**裁定值**：「装饰条目进近况面板，不参与留档」。它们仍然是欠账——`design/game-brief.md` 写明「留给后面的模块变成决策点」——但不再是「留在档里、什么也不改变、还占着行数」的条目。

#### R1b — 「有后果 / 无后果」的判据（裁定 ⑮ 的落地，必须可测试）

裁定 ⑮ 要求把条目分到两个面板。**分类必须由一条机械判据决定，不得由作者觉得这条重不重要、玩家看不看得到、或这句文案的语气决定。**

| 类 | 判据 | 落到哪个面板 |
|---|---|---|
| **有后果** | 条目写入**那一刻**，声明的受监视字段集合中**至少一个值发生变化** | **杂谈**（留档） |
| **无后果** | 条目写入**那一刻**，该集合**逐项相等**，无任何变化 | **近况**（滚动） |

**受监视字段集合 `WatchedFields`（封闭清单，新增字段必须先改这里）**：

| 类别 | 字段 |
|---|---|
| 村民 | `AbsentDays` · `RestlessDays` · `SlackDays` · `GrudgeWith` · 升级 / `Power` 相关字段 · `Away` · `ToSite` · 人口计数 |
| 村庄 | 材料总池 · `VillageCoin` 各分项 · 已建成建筑集合 / `VillageTier` · 在建工地集合 · 防护罩负荷 |

**判定方法（唯一合法方法）**：

```
在条目的写入调用前后各取一次 WatchedFields 的全量快照
有后果  ⇔  snap_after != snap_before
无后果  ⇔  snap_after == snap_before
```

**三条必须成立的推论：**

1. **分类在条目级别，不在模板级别。** `搭手`（`DayHelp`）是**条件条目**：清掉了 `GrudgeWith` → 有后果 → 杂谈；没有仇可清 → 无后果 → 近况。**同一个模板写进两个面板是正确的**，不是 bug。
2. **`Chronicle` 自己不写状态**（R3），所以这个 diff **必须在调用方或测试夹具里取**。面板不能自己判断自己有没有后果。
3. **分类一经写入不再移动。** 村庄状态后来变化、后果后来被别的系统撤销，**都不重新分类**——这是 R10「条目不可变」在分类上的延伸。

**按此判据，当前生产者清单的归类：**

| 类别 | 条目 |
|---|---|
| **有后果 → 杂谈** | 病倒 · 吵架 · 干起来了 · 磨洋工 · 想走 · 召唤 `Arrive`（人口 +1）· 私吞 `pocket`（材料没交足）· 成事 `Outcome good`（材料入账）· 队伍出发 `SquadLeft` / 归来 `SquadBack`（成员 `Away = true`）· 队伍私吞 `SquadGreed` · 开工 `SiteOpened` · 落成 `Building` |
| **条件（写入时判定）** | 搭手 `DayHelp`（清仇→有后果 / 无仇可清→无后果）· 接活 `Took`（**当前无生产者**，见 E12；接上时以它实际写入的字段为准）· 队伍摩擦 `SquadRival` / 成事 `SquadGood` |
| **无后果 → 近况** | 闲逛 `DayIdle` · 陌生人 `DayStranger` · 拒绝 `Refused` · 配合系数脚注 `Note`（读数，不是写入）· 失手 `Outcome fail` · E5 空村一天 · E6 最后一个人走了 |

> ⚠️ **四项归类带设计判断，已登记为 OQ，不得由本文档单方面定死**：配合脚注 `Note`（每次远征 0 或 1 条，是残余的窗口收窄通道，见 F4b）、`Outcome fail`、队伍内部三拍、以及 E5 / E6（如实描述了「没有演员」这件事，但没有任何字段变化）。在 Q10 / Q11 拍板前，本文按上表执行，**不给它们开例外，也不改判据**。

#### R2 — 玩家可见文案禁令

**任何玩家能读到的字符串**（杂谈条目、署名、花名册、按钮）**不得出现**：

> 成功 · 失败 · 获得 · 消耗 · 属性 · 奖励

村民不会那样说话。**注意 `WorkRate` / `IsOnlineAt` / `LoginAt` / `chance` / `Cohesion` 这类内部量名同样禁止**（`design/gdd/time-and-schedule.md` AC-25 已经立了这条）。

**对照写法**：

| ❌ 不写 | ✅ 写 |
|---|---|
| 「灰九任务成功，获得12份石料」 | 「灰九回来的时候天还没黑。背上12份石料，比要的还多。」 |
| 「锈刃偷喝了回魔酒（贪 92%）」 | 「清点的时候短了几份石料。问了一圈，都说没看见。」 |
| 「两人配合度下降 50%，无法进入同一队伍」 | 「……出发前灰九和锈刃在村口吵了一架。到地方还在生闷气。」 |
| 「工地停工：在线劳动力为 0」 | （**什么都不写。** 工地不产条目。） |

#### R3 — 杂谈是纯读数器，不是操纵杆

**杂谈永远不改变游戏状态。** 它不写 `HeroAgent`，不设 `AbsentDays`，不改 `_mat`。所有条目都是**已发生之事的转述**。

这一条是刻意的：如果杂谈能改状态，它就变成了一个可以调参的杠杆，玩家会开始「为了看到某句话而做某件事」，村庄就从模拟退化成刷文本。**杂谈只能被读，不能被写**（除开发者与本 GDD 自己）。

#### R4 — 条目数据结构与署名

```csharp
Entry { Day: int, Text: string, Who: string? }
```

- `Day` 是写入当天。**它只用于排序与截断，不显示给玩家**（见 R7）。
- `Who` 是署名，渲染为 `—— 名字`，字号更小、颜色更暗。

**署名的分配规则（当前实现，且它有意义）**：

| `Who` 非空 | `Who` 为 null |
|---|---|
| 只跟一个人有关的条目：病倒、想走、磨洋工、闲逛、吵架、打架、搭手、召唤、接活、拒绝、出勤结果 | 村子层面的风声：队伍出发/归来、队伍内部摩擦、开工、盖成、陌生人、空村一天、配合系数脚注 |

读法：**有名字 = 有人在被盯着；没名字 = 村里的传言。** 玩家会下意识地觉得「有名字的事跟我有关」。这不是装饰，它让村庄有了**公私之分**。

**槽位表（占位符）**：

|---|---|---|---|
| `{n}` | 名字 | `HeroAgent.Name` | 否 |

| `{t}` | 任务名 | `Jobs[].Name` | 否 |

| `{s}` | 特征短语 | 召唤系统 | **可以是空串** |

#### R6 — 占位符完整性（已知事故的固化）

> **已知事故**：早期版本存在 `{x}` 占位符未被替换、直接印在面板上的情况。

事故本身已经修掉了，但**没有任何东西防止它再次发生**，也没有任何东西防止它的变体。所以本条把它拆成**两条可测试的规则**，两条都必须由**渲染后的字符串**判定，不是由模板源码判定。

**R6a — 无残留分隔符。** 任何条目渲染完成后，**不得包含 `{` 或 `}`**。这条覆盖事故本身，也覆盖「模板里写了 `{zz}` 这种没定义的槽」——未定义的槽不会被 `Fill` 的任何一个 `Replace` 命中，会原样留下。

**R6b — 无空槽。** 每个槽位在**它被调用的那组实参下**都必须有值：

| 情形 | 规则 |
|---|---|
| `qty == 0` | 该次渲染中**不得**使用 `{g}` |
| `other == null` | 该次渲染中**不得**使用 `{y}` |
| `world == ""` | 该次渲染中**不得**使用 `{w}` |
| `trait == ""` | 该次渲染中**不得**使用 `{s}` |

> **这不是假想。当前实现有两处活着的违反，两处潜伏的违反**，逐条列在 Edge Cases E1–E4 与 AC-4。R6b 的存在理由就是它们。

**R6c — 一句话只说一件能被验证的事。** 模板不得写死任何**调用方拿不到**的事实。当前 `Building` 模板里的「前后用了十来天」是写死的（`src/Chronicle.cs`），与实际施工天数无关——它是氛围，不是谎话，但如果将来这个数字变成一个**玩家会拿来对账**的数字，它就是谎话。本条现在把它挡在外面。

#### R7 — 两个面板：容量、淘汰与「留档到底意味着什么」

**代码现状（`src/Main.cs`，⚠️ 尚未按裁定 ⑮ 改动，仅记录）**：

```
_entries.Insert(0, e)              // 最新在最前
while (_entries.Count > 40) RemoveAt(Count-1)     // 容量 40
_chron 渲染 _entries.Take(16)                      // 可见 16，无滚动、无翻页、无按天分组
```

所以今天有 24 条是永远看不到的：它们在内存里，但玩家没有任何路径到达它们。

**裁定 ⑮（2026-10-17，开发者拍板）：杂谈分为两个面板。** 开发者原话：「分两个面板：杂谈（留档）/ 近况（滚动）」。

| 面板 | 收什么（R1b） | 留存方式 | 容量 | 淘汰规则 |
|---|---|---|---|---|
| **杂谈** | **有后果** | **永久留档** | `ArchiveCapacity` = **500** | 仅当超过 500 时丢最旧一条，**静默无提示**。500 条以内，任何条目在物理上不可被淘汰 |
| **近况** | **无后果** | **滚动窗口** | `RecentRows` = **16** | 写入第 17 条时丢最旧一条，**静默无提示** |

**三条规则落点：**

1. **「留得住」的判据不是新机制。** 它就是 R1b 的分类，而 R1b 用的正是 R1 已经存在的那条判断——「这条改了状态吗」。裁定 ⑮ 是 R1 在第二个地方继续跑。落败的私吞、结下的仇、生过的病——这些是玩家明天还要引用的东西，而它们今天恰好最容易被一轮远征挤出去。
2. **两个面板互不挤占。** 一次远征的全部条目（出发、归来、摩擦、出勤）都改了状态 → 全部进留档面板，**不再消耗近况面板的任何一行**。这正是裁定 ⑮ 要解决的问题（F4b 量到：最坏档位 0.8 天 → 4.3 天）。
3. **`ArchiveCapacity = 500` 是内存兜底，不是玩法规则。** 它唯一的用途是防止长期存档无限增长。降到 500 以内会开始「删掉有意义的历史」，因此它的安全区间见 Tuning Knobs。**触顶淘汰仍然是静默的**——本 GDD 不发明「归档回收站」，那会变成第三种去向。

**设计意图：先回答「它不是日志」这件事**（这段保留，它约束两个面板同样成立）：

| | 日志 | 杂谈 / 近况 |
|---|---|---|
| 有时间戳 | 有 | **没有** |
| 可翻页 / 可搜索 | 有 | **没有** |
| 会被别的 UI 引用 | 有 | **没有** |
| 玩家会为了它去做事 | 会 | **不会** |

**一个没有时间戳、不能翻页、不能被引用的东西不要求「滚回去看三天前」。** 那是在拿日志的心智模型要求它。两个面板要回答的问题只有一个：**我不在的时候，村里发生了什么。**

**⚠️ 本条未决的一半：「留档但不可翻页」。**

裁定 ⑮ 给了杂谈一份永久档案，而上表仍然写着「不能翻页」——**一份玩家无法翻阅的档案，在功能上等于没有档案**（那正是本节开头那 24 条的老毛病，只是从 24 条变成了 500 条）。这不是我能替开发者决定的：

- 要么给留档面板一条**到达路径**（滚动 / 分页 / 按天折叠）；
- 要么承认「留档」指的是**存档里的数据留存**，屏幕上的可见行数仍是有限的（可见行数仍归近况那套逻辑管）。

已登记为 **Q10**。**在拍板之前，本条只保证数据层的留存与淘汰规则，不指定屏幕布局**——本 GDD 不会顺手加滚动条，那与 R7 上半部分的定位直接冲突，必须由开发者选一边。

**Q1 已于 2026-10-17 裁定**（见 `production/design-decisions.md` 裁定 ⑮）：原 R7a 建议（「有后果的条目不参与自然淘汰」）**已被采纳并实现为双面板**。原值与裁定值的差异已写在本节表格与 R1b 里。

#### R8 — 语气一致性必须有人看守

**现状是无人看守**，具体到两条：

1. **模板是散落的静态字符串数组**，没有单一数据源、没有校验、没有测试。新增一句模板不需要改任何别的地方，也就没有任何地方会拦住它。
2. **禁用词规则被声明了四次，校验了零次**：

| GDD | 规则编号 |
|---|---|
| `design/gdd/summoning.md` | R9 文案禁令 |
| `design/gdd/squad-and-cohesion.md` | R10 |
| `design/gdd/time-and-schedule.md` | Player-visible 文案约束 / AC-24 |
| `design/gdd/village-building.md` | UI Requirements「玩家可见文案的硬规矩」 |

**四份文档写了同一条规则，没有一处把它变成断言。** 新增模板的人不会去读另外三份 GDD。所以本 GDD 把「新增模板」这件事收口到一个表里（R5），并把校验写成 AC-1 / AC-2 / AC-3 三条 lint。**这条规则的可执行性从「文档里的一句话」变成「PR 过不去的一条测试」，这是它唯一能活下来的方式。**

#### 状态与转换

杂谈自身**无状态**——它是一个写入端（sink）加一个环形缓冲。唯一的转换是缓冲的追加与淘汰：

| 状态 | 进入条件 | 退出条件 | 行为 |
|---|---|---|---|
| 空 | 新开局 | 第一条被写入 | 渲染 0 行 |
| 有条目 | 任一生产者调用写入 | 到达容量上限 | 最新在最前；淘汰最旧 |
| 已淘汰 | 缓冲区满时被挤出 | 不可恢复 | **静默丢弃，无提示** |

**渲染是脏标记驱动的**：`_chronDirty` 为真时才重建节点（每帧重建会拖垮帧率）。这条必须保留在验收里。

#### 与其他系统的交互

| 对方系统 | 方向 | 契约 |
|---|---|---|
| `时间与作息` #1 | **它产出** | 它是唯一主动产出的生产者（E9 空村一天、E10 最后一个人走了）。**本系统不计算时间、不补写离线期间的事** |
| `召唤系统` #2 | **它产出** | 交付 `WorldName` + `Trait` 给 `Arrive` 模板填充；`Nicknames` 表由它持有、本系统每次重掷 |
| `村庄日常事件`（`VillageLife`） | **它产出** | 八类事件各调一次本系统的工厂方法。**本系统不判定事件、不掷权重**——权重在 `VillageLife`，见 F2 |
| `配队与配合` #4 | **它产出** | 交付 `Verdict` 脚注文本；队伍出发/归来/摩擦四拍由本系统写 |
| `村庄建造` #5 | **它产出** | 开工（`SiteOpened`，按在场人数四档）与落成（`Building`）各写一条 |
| `任务与副本` #6 | **它产出** | 接活/拒绝/出勤结果/回村。**结果由那边判定，本系统只转述** |
| UI 层 | 消费本系统 | 渲染 `Entry.Text` + `—— Who` |

**本系统明确不拥有的东西**：事件的触发条件、事件的权重、任何 `HeroAgent` 字段、任何村庄量、任何时间推进。**把生产者搬进本系统是越界**，会让「事件必须改状态」变成「事件由杂谈决定」。

## Formulas

### F1 — 每日村庄日常条数

```
n = 2 + rand_int(0, 3)          // 注意是「加」，所以右端是闭的
```

| 变量 | 类型 | 范围 | 来源 | 说明 |
|---|---|---|---|---|
| `n` | int | **2 – 4** | `VillageLife.RunDay` | 每天村庄自己发生的事件数 |

**期望值** `E[n] = 3`。**注意上界是闭的**（`rand.Next(3)` 返回 0..2，故 `n ∈ {2,3,4}`）——`VillageLife` 里 `4` 是可能的，8 类事件的分布不受影响。

### F2 — 八类事件的权重与概率

权重表按性格分三行，行为 `[闲逛, 吵架, 病倒, 想走, 陌生人, 磨洋工, 搭手, 干起来]`：

| 性格 | 闲逛 | 吵架 | 病倒 | 想走 | 陌生人 | 磨洋工 | 搭手 | 干起来 | **行和** |
|---|---|---|---|---|---|---|---|---|---|
| 莽 | 4 | 1 | 2 | 1 | 1 | 1 | 5 | 2 | **17** |
| 傲 | 2 | 5 | 1 | 6 | 1 | 5 | 1 | 6 | **27** |
| 贪 | 3 | 3 | 2 | 3 | 1 | 6 | 2 | 2 | **22** |

抽取：`r = rand_int(0, 行和)`，从左往右逐个减，第一个使 `r < 0` 的键命中。

**展开后的实际概率：**

| 事件 | 莽 | 傲 | 贪 | 改了什么状态 |
|---|---|---|---|---|
| 闲逛 | 23.5% | 7.4% | 13.6% | — |
| 吵架 | 5.9% | 18.5% | 13.6% | `GrudgeWith` |
| 病倒 | 11.8% | 3.7% | 9.1% | `AbsentDays` 1–2 |
| 想走 | 5.9% | **22.2%** | 13.6% | `RestlessDays = 2`（干活 ×0.30） |
| 陌生人 | 5.9% | 3.7% | 4.5% | — |
| 磨洋工 | 5.9% | 18.5% | **27.3%** | `SlackDays = 2`（干活 ×0.40） |
| 搭手 | **29.4%** | 3.7% | 9.1% | 清 `GrudgeWith` |
| 干起来了 | 11.8% | **22.2%** | 9.1% | `GrudgeWith` + `AbsentDays = 1` ×2 |

**三条可验收的推导结论**（不是设计承诺，是这张表的数学后果）：

1. **`贪` 的头号日常事件是磨洋工（27.3%）。** 超过四分之一的概率，代价是干活率 ×0.40。`贪` 同时是采集效率最高的性格（`WorkRate` ×1.00 但基础项里贪收益最高），所以**村长的主力劳力是最容易自己撂挑子的那一批**。这不是 bug，但它意味着「今天村里为什么盖得慢」的常见答案之一是「有个贪没使劲」。
2. **`搭手` 是全系统唯一能解仇的事件，而它的权重最高的一格是莽（29.4%）。** 也就是说：**两个人吵起来之后能不能和好，取决于这个村子里有没有莽。** 一个全是傲的村庄（傲各 1/27 = 3.7%）会积累**几乎无法化解的仇**，而仇 = 同队 ×0.50。这条是村庄人口构成的一个真实后果，`design/gdd/squad-and-cohesion.md` Q4 讨论「有仇是硬禁止还是软惩罚」时应当一并读。
3. **`傲` 的想走（22.2%）与干起来了（22.2%）并列最高。** 傲是唯一一种「一不高兴就可能直接走人」的性格，而这也正是他挑活的机制在起作用——他不是不干活，他是不干没对手的活。

### F3 — 一次远征产生的条数

```
E = SquadLeft(1) + SquadBack(1) + 每名队员 1 条 + [配合脚注](0 或 1)
  = 2 + |crew| + Note
```

| 变量 | 类型 | 范围 | 说明 |
|---|---|---|---|
| `crew` | int | 1 – 4 | 队伍上限 `SquadMax = 4` |
| `Note` | int | 0 / 1 | 配合系数有脚注时才写一条 |
| **`E`** | int | **3 – 7** | **一次远征最多吃掉 7 条可见空间** |

**边界**：`crew = 0` 时远征不成立（按钮禁用），所以 `E ≥ 3`。

### F4 — 两个面板的窗口（裁定 ⑮ 之后；旧 F4 作废）

> **修订说明**：旧 F4 用**一个** `D` 同时除出「可见天数」和「淘汰天数」，前提是容量 40 与可见 16 共用一个池。
> **裁定值**：两个池互不相干，因此**必须有两个公式**。旧 F4 的两张表保留在下面作为**改版前的对照**，供对照验收使用（AC-10 断言旧值只作历史）。

#### F4a — 杂谈（留档）：没有「几天」的窗口，只有「多少条」

```
ArchiveGrowth = 有后果条数 / 天
可见天数  ≈ ∞（在 ArchiveCapacity 之内）
触顶天数  = ArchiveCapacity / ArchiveGrowth
```

| 玩家行为 | 有后果条数/天 | 触顶 500 条要 | **旧口径：16 条能看** |
|---|---|---|---|
| 纯被动（从不点按钮） | ~2.3 | ~217 天 | ~~5.3 天~~ |
| 每天 1 次远征 | 2.3 + 5 = **7.3** | ~68 天 | ~~2.0 天~~ |
| 每天 3 次远征 + 1 次召唤 | 2.3 + 15 + 1 = **18.3** | ~27 天 | ~~0.8 天~~ |

**推导口径**：村庄日常 `E[n] = 3`（F1），其中无后果约 0.6–0.7 条（F4b 推导），故有后果 ≈ **2.3/天**；一次远征的条目数 `E = 2 + crew + Note`（F3），`crew` 上限 4、`E[crew] = 3`，其中**只有 `Note` 是无后果**，故每次远征有后果 ≈ **5 条**；召唤 `Arrive` = 1 条。

#### F4b — 近况（滚动）：分母里**不含远征**

```
D_recent = 无后果条数 / 天
可见天数 ≈ RecentRows / D_recent          // RecentRows = 16
```

**远征不进入这个分母**——出发、归来、摩擦、出勤、私吞全部改了状态，走留档面板。

| 玩家行为 | 无后果条数/天 | **近况 16 条能看** | 旧口径（同 16 条） | 改善 |
|---|---|---|---|---|
| 纯被动 | **~0.7** | **~23 天** | 5.3 天 | **×4.3** |
| 每天 1 次远征 | ~1.7 | **~9 天** | 2.0 天 | **×4.5** |
| 每天 3 次远征 + 1 次召唤 | ~3.7 | **~4.3 天** | 0.8 天 | **×5.4** |

**推导口径**（三种性格各占 1/3，按 F2 权重表逐行归一）：

| 来源 | 占日常事件比例 | 条数/天 | 说明 |
|---|---|---|---|
| 闲逛 `DayIdle` | (23.5 + 7.4 + 13.6) / 3 = **14.8%** | × 3 = 0.44 | 恒定无后果 |
| 陌生人 `DayStranger` | (5.9 + 3.7 + 4.5) / 3 = **4.7%** | × 3 = 0.14 | 恒定无后果 |
| 搭手 `DayHelp` | (29.4 + 3.7 + 9.1) / 3 = **14.1%** | × 3 = 0.42 | **只有没有仇可清时**计入；纯被动村庄初期几乎没有仇，取上界的一半 ≈ **0.1** |
| 配合脚注 `Note` | — | 0 / 1 / 3 | 每次远征 0 或 1 条（三档行为） |
| **合计** | | **~0.7 / ~1.7 / ~3.7** | |
| 召唤、出征两拍、出勤、私吞 | — | **0** | 全部有后果，**不在这个分母里** |

**结论（裁定 ⑮ 要解决的问题，量到了）**：

> **最坏档位从 0.8 天变成 4.3 天（×5.4），中档从 2.0 天变成 9 天（×4.5）。**
> 留档面板（杂谈）在 500 条之内**没有任何天数窗口**——远征不再挤占它。

**残余的一条收窄通道**：**配合脚注 `Note`**。它每次远征最多贡献 1 条，且本身不改任何字段（R1b 判为无后果），因此近况窗口仍随远征次数收窄。这是上表里最慢档只到 4.3 天而不是恒定 23 天的唯一原因。若要连这条一起去掉，须先在 **Q10** 里回答「一条只读不写的读数算不算后果」——**本文档不单方面把它划成有后果**，那会是给判据开后门。

**旧 F4 的结论，一半作废**：原结论「可见窗口的单位是动作，不是天」在**近况**面板上仍然成立（0.7 → 3.7 随动作变 5.3 倍），但在**留档**面板上**已经不再成立**——它的窗口由 `ArchiveCapacity` 决定，与动作数无关。

### F5 — 模板抽取与重复率

```
k = 该槽位的模板条数
idx = rand_int(0, k)
连续两次抽到同一句的概率 = 1 / k
```

| 槽 | `k` | 紧邻重复率 |
|---|---|---|
| `莽.take` / `傲.take` / `贪.take` | 2 / 2 / 2 | **50%** |
| `莽.good` / `傲.good` | 3 / 3 | 33% |
| `贪.pocket` | 3 | 33% |
| `Day*` 八类 | 各 4 | 25% |
| `SquadRival` / `SquadLeft` / `SquadBack` / `SiteOpened` / `Arrive` | 4 / 3 / 3 / 4 / 3 | 25%–33% |
| `SquadGood` / `Building` | 3 / 3 | 33% |
| `SquadGreed` | 2 | **50%** |

**诊断用途，不是规则**：`k = 2` 的槽位（三种性格的接活、队伍抢绳索）连续重复的概率是 50%。对「接活」这个每天都在发生的槽位，这意味着玩家会明显感到重复。**本 GDD 不擅自加去重逻辑**（开发者从未描述过记忆机制），仅记录，见 Q4。

**已有的一个隐性去重**：`Nick(h)` 每次重掷，所以 `{a}` 绰号位本身就有变化——同一句模板配上不同绰号，观感不完全重复。这是个副作用，不是设计，且它同时是 `design/gdd/summoning.md` Q2 里「绰号没有持久化」的那个问题的来源。

### F6 — 署名率（诊断量，非规则）

```
署名率 = (Who != null 的条目数) / (总条目数)
```

**当前生产者清单下，署名条目的来源**：`DayIdle` / `DayQuarrel` / `DayBrawl` / `DaySick` / `DayWants` / `DaySlack` / `DayHelp`（7 类日常，其中 `DayStranger` 无名）、`Summoned`、`Took`、`Refused`、`Outcome`，以及 `Main.cs` 的花名册点击回应。
**无名条目**：`SquadLeft` / `SquadBack` / `SquadRival` / `SquadGood` / `SquadGreed` / `SiteOpened` / `Building` / `DayStranger`、空村一天、最后一个人走了、配合脚注。

| 场景 | 署名率（估算） |
|---|---|
| 纯村庄日常 | 7/8 ≈ **88%** |
| 一次满员远征（4 人） | 4 / (2 + 4 + 1) ≈ **57%** |
| 混合 | **60% – 75%** |

**诊断意义**：署名率越高，村子越像「一群有名有姓的人在过日子」；越低越像「村里的传言」。当前落在偏高的区间，与「他们在被观察」的感觉吻合。**不建议主动调低**——一旦某条具体的人身上的事都不署名，玩家就失去了「追踪某个人」的能力，而这个能力是玩家理解因果的主要手段。

## UI Requirements

| 信息 | 显示位置 | 更新频率 | 条件 |
|---|---|---|---|
| 条目正文 | **近况面板**（滚动），每条一个 `Label`（自动换行，最小宽 266） | **仅在脏标记为真时重建** | 常驻 |
| 署名 `—— 名字` | 正文下一行，字号 10、颜色 `8a7f6e` | 同上 | `Who != null` |
| **留档面板**（杂谈） | **布局未定** —— 数据层的留存与淘汰规则已定（R7 / F4a），屏幕上的位置、行数、到达路径**全部归 Q10** | 同上 | 常驻（具体形态待定） |
| 天数 | **不显示**（两个面板都不显示） | — | — |

**三条 UI 层的硬约束（对两个面板同时成立）**：

1. **不显示时间戳。** 理由见 R7：一个带时间戳的面板会被玩家读成日志，而日志是要翻页、要搜索、要做检索的。两个面板一样都不是。**这一条是缺口 #1 的解法的一半——另一半由裁定 ⑮ 的双面板给出**（F4）。
2. **不显示条数、不显示「第 N 天」分组。** 分组会邀请玩家去数「今天发生了几件」，而那是一个计数游戏，村庄不是。
3. **不提供任何筛选与收藏交互**（不可点、不可筛选、不可收藏）。玩家能做的唯一操作是读。

> ⚠️ **约束 1 与裁定 ⑮ 之间有一个未决的接缝**：约束 1 与旧的「不提供滚动条与分页」一起，蕴含「玩家读不到 500 条之外的东西」；而裁定 ⑮ 给的是**永久留档**。本 GDD **不自行加滚动条**（那会让杂谈变成日志，与定位直接冲突），**也不把这条接缝悄悄抹平**——它是 **Q10**：留档面板要么获得一条到达路径，要么「留档」被正式定义为纯存档语义。**在 Q10 拍板前，AC 全部只断言数据层的留存与淘汰，不断言屏幕可见行数。**

### 容量与渲染（裁定 ⑮ 之后）

> **AC-3 / AC-4 / AC-32 是 `{x}` 占位符事故的三条守门测试，与面板改版无关，任何情况下不得删除或弱化。**

- [ ] **AC-6 留档容量。** 连续写入 **400 条有后果**条目后，留档面板数据层存活 **400** 条，淘汰计数为 **0**。再写入到 **600** 条，存活 **500** 条，且存活集合**恰为最新的 500 条**（R7 / E17）。
- [ ] **AC-7 近况容量。** 近况面板数据层条数 `== min(16, 无后果条目累计数)`；累计 ≥ 16 时**恒为 16**。
- [ ] **AC-8 顺序。** 两个面板都是 `_entries[0]` 为最新；近况面板第一行显示的是最新一条。
- [ ] **AC-9 脏标记。** 连续 600 帧内没有新条目时，`RebuildChronicle()` 的调用次数为 **0**（用计数器断言，不是靠读代码）。
- [ ] **AC-10 可见窗口可复现（近况）。** 用固定种子跑「纯被动 10 天」，断言：近况面板数据层的条数 `==` 这 10 天实际写入的**无后果**条目数（F4b 估 ≈ 7 条），且**全部可见、零淘汰**。旧口径（16 条 ÷ 每天 3 条 = 5.3 天、第 4 天及更早不可见）**作为历史对照保留，不再是断言**。
- [ ] **AC-11 有后果的条目不被挤出（裁定 ⑮ 后恒成立）。** 一次满员远征（`E = 7` 条，其中 `Note` 至多 1 条）之后：断言这批条目**全部落在留档面板**；再紧接着写入 50 条无后果条目，断言留档面板里那 7 条**一条不少**、近况面板仍是最新 16 条。

### 事件与状态一致性

- [ ] **AC-12 R1 逐条可验。** 对 F2 表的八类事件各跑一次，断言：写完条目后，对应 `HeroAgent` 字段**确实已变**（`AbsentDays` / `GrudgeWith` / `SlackDays` / `RestlessDays`）。对 `闲逛` / `陌生人` / 无仇时的 `搭手`，断言字段**未变**，并断言它们**落在近况面板**而不是留档面板（R1b）。

- [ ] **AC-28 条件模板分流（E16）。** 同一个 `DayHelp`（搭手）跑两套夹具：**(a)** 场上有仇 → 条目落**留档**面板，且 `GrudgeWith` 被清；**(b)** 场上无仇 → 条目落**近况**面板。两条断言都必须成立。
- [ ] **AC-29 分类不采信调用方声称（E19）。** 构造一次「调用方传入 `consequential: true` 但 `WatchedFields` 前后完全相等」的写入，断言条目仍然落**近况**面板。
- [ ] **AC-30 分类不重分类（E18）。** 写入一条有后果条目 → 撤销它写过的那个状态变化 → 断言该条目**仍在留档面板**且内容逐字符不变。
- [ ] **AC-31 两面板不互相挤占（裁定 ⑮ 的核心）。** 写入 30 条**远征条目**（全部有后果），断言**近况面板条数不变**；再写入 30 条**无后果**条目，断言**留档面板条数不变**。
- [ ] **AC-13 条目不可变。** 写入一条条目后，改变 `Who` 的 `Personality` 或任何状态，断言已写入的 `Entry.Text` **逐字符不变**（R10）。
- [ ] **AC-14 杂谈不改状态。** 记录写入前后的全部 `HeroAgent` 字段与村庄量，断言**完全相等**（R3）。杂谈必须是纯读数器。
- [ ] **AC-15 署名规则。** 断言 `Day*` 八类中除 `DayStranger` 外均 `Who != null`；`SquadLeft` / `SquadBack` / `SiteOpened` / `Building` / `DayStranger` 均 `Who == null`（R4）。

### 负需求（这些**必须不发生**）

- [ ] **AC-17 停工无条目。** 把全村人设为离线并跑满 3 个游戏日，断言**这期间零新增杂谈条目**（除 E5 的「村里一个人也没有」若全村缺席）。
- [ ] **AC-18 离线不补写。** 断言 `Day` 前进而条目数**不**跳变（E8）。

- [ ] **AC-19 不跨天补跑。** 单次 `Tick` 使 `Day` 跨越 3 天，断言杂谈只新增**一次**日事件的条目（继承 `time-and-schedule.md` AC-18）。

### 体验性（playtest）

- [ ] **AC-20 读数器成立。** 5 名试玩者各玩 15 分钟后，至少 **4 人**能说出「昨天/今天村里自己发生了什么」，且**没有人**说「我看不出来」或「日志里没有」。

- [ ] **AC-23 没有人要解释。** 无人要求「告诉我为什么停工」。若有人要，是村庄建造的负需求被破坏了，不是本系统的需求。

- [ ] **AC-26 写入 O(1)。** 单条写入（`Insert(0)` + 淘汰）在缓冲满时耗时 `< 0.01 ms`；**不得**每次写入都全量重建。
