## 1. M0 · 现状审计（实测）

### 1.1 R-03：抽到自己会怎样

`HeroBehaviorService.SimulateShopping`（`src/Application/HeroBehaviorService.cs`）第 4 步
从所有 Open 摊位里**随机抽一个**，抽到自己的就跳过。

**但 `15` §7 对 R-03 的描述有一处不准确**——原写「价高且村抽 > 0 时自买自卖会**损失村抽**」。
实际代码里 `StallService.TryBuy` 在**计算费用之前**就以 `SameHero` 拒了
（`src/Application/StallService.cs:242`），自买自卖**根本不会成交，也就不会损失村抽**。

真正的问题另外两个：

| 问题 | 说明 |
|---|---|
| **浪费当天的机会** | 抽到自己 → 不成交 → `LastShoppingDay` 不写 → 这天他什么也没买到 |
| **退化情况** | 村里**只有他自己开摊**时，他抽到的永远是自己的摊 → **永远买不成** |

### 1.2 R-07：未成提示在哪

未成的购物**不发事件、不进杂谈**，只在 `--econlog` / `--shop` 的调试输出里
（`ShoppingResult.Detail` 是给调试看的**长句**，例如「金币不足：有 3，需 5」）。
玩家在界面上完全看不到「谁想买没买成、为什么」。

**核心矛盾**：设计上村庄 37 人。若每天每人一条未成提示，杂谈会被彻底淹没 ——
这正是当初把它挡在杂谈外的原因。R-07 要的是「**看得见**」与「**不刷屏**」两样。

## 3. R-03：抽样时排除自己的摊

```csharp
// 5. R-03：抽样时**排除自己开的摊**。
var buyable = new List<DomainStall>(openStalls.Count);
foreach (var s in openStalls)
{
    if (s.Owner != buyerId) buyable.Add(s);
}

if (buyable.Count == 0)
{
    return … Skipped_PrecheckFailed
    {
        Detail = "村里只有自己开着的摊（同一个人不能自买自卖）",
        SkipReason = ShoppingSkipReason.OnlyOwnStall,
    };
}
```

**为什么不是「抽到就重抽」**：重抽要多一层随机，还要定重抽次数与失败后的行为；
而排除是一次性的、确定性的，且**直接消灭了退化情况**（村里只有自己的摊时，
无摊可抽 → 明确报「只有自己开着的摊」，而不是装作什么都没发生）。

**顺带删掉的死代码**：原来的「抽到自己的摊 → 跳过」分支**在新规则下永远不会命中** ——
它留着就是一条骗人的死路径（而且会让后来的人以为自摊是被抽中才发现的）。

### 3.1 顺带修的一处隐患：摊主顺序

`ListOpenStalls` 原来直接遍历 `_stall.Stalls`（一个 `Dictionary`）。
**`Dictionary` 的遍历顺序不是契约** —— 增删之后顺序会变。
而抽样下标依赖列表顺序：顺序不稳 = 同一个种子的两次运行挑到不同的摊 = **测试不可复现**。

改用 `StallService.Snapshot()`（按摊主 Id 排序），顺序稳定。

## 4. R-07：结构化原因

`Detail` 是**长句**（「金币不足：有 3，需 5」），花名册行尾放不下；
而表现层需要的是「短、可枚举、能筛」的标签。所以新增结构化原因：

```csharp
public enum ShoppingSkipReason
{
    None = 0,            // 成交了
    NotPresent = 1,      // 不在场或正在忙
    NoDesire = 2,        // 今天不想买
    AlreadyShopped = 3,  // 今天已经买过
    NoOpenStall = 4,     // 村里没有开着的摊位
    OnlyOwnStall = 5,    // 村里只有自己开着的摊   ← R-03 新增
    BagFull = 6,         // 背包里该物品已达上限
    NotEnoughGold = 7,   // 金币不够
    SettlementFailed = 8,// 结算失败
}
```

**哪些值得给玩家看**：`NotEnoughGold` / `BagFull` / `SettlementFailed` / `OnlyOwnStall` ——
这四条是「**他自己想买、却买不成**」。

**哪些不算**：`NoDesire`（他本来就不想买）、`NotPresent`（在远征，不在场）、
`AlreadyShopped`（买过了，经济摘要已经显示）、`NoOpenStall`（村里没摊，跟他无关）。
把这四条也标出来，**真正卡住的那几条就会淹没在日常噪音里**。

> 结构化原因的好处：**不靠解析 `Detail` 那种自由文本**。
> 自由文本一改，界面上的判定就跟着悄悄坏掉。

## 5. R-07 渠道一：花名册行尾

```
▸ 逍亭  金0 石料×1  想买未成·钱不够
▸ 夜阑  金130  想买未成·只有自己的摊
```

- 行尾文本 = `经济摘要` + `  ` + `RosterNote(result)`。
- **只标当天的**：`ShoppingNoteFor` 先比 `_lastShoppingDay == (int)_clock.Day` ——
  跨天了还没买成是**昨天**的事，不该继续挂在今天的花名册上。
- 标记放**最后**：经济摘要是每一行都有的「状态」，标记是偶尔才有的追加信息，
  读起来是「名字 → 状态 → 补充」。

## 6. R-07 渠道二：每天一条汇总

```
今天有 2 人想买没买成（钱不够 1 人、只有自己的摊 1 人）。
```

- **每天一条**：`RunDailyShoppingIfNeeded` 每天只跑一次，汇总也就每天只产出一条。
- **不点名**：37 个名字进杂谈就是刷屏；而名字本来就在花名册行尾上。
  汇总只回答「今天**整体**怎么样、**卡在哪儿**」。

### 6.1 这条怎么进杂谈 —— 为什么不发事件

它**没有改变任何状态** —— 它是「今天有多少人没买成」的**读数**，不是一次事件。
按反装饰规则（事件必须声明它改了什么），**不能发事件**。

所以走 `Add(new Chronicle.Entry(...))` **直接进杂谈** —— 与既有的两条先例同路：
「摆摊失败」「副本结算被拒」也都是没改状态、但值得说一声的事。

> 顺带确认：**C1 不受影响**。C1 校验的是 `_feed.Entries`（事件源），
> 直接 `Add` 的条目不进 feed，所以「每条杂谈都能匹配到事件 ID」这条仍然成立。
> 实测 `--events` 的 C1–C4 全部照旧通过。

## 8. 真机自检

`--shop` 自检末尾新增 R-07 场景：把买家的钱清零 → 他想买（欲望够）却买不成。

欲望是随机的（性格权重），所以像上面等成交那样**逐日推进直到命中** ——
买家的钱一直是 0，一旦他动了念头，就必然落在「钱不够」上。

实测输出：

```
SHOPTEST R-07 第1天命中：花名册标记=「想买未成·钱不够」→ True
SHOPTEST R-07 杂谈新增=「今天有 2 人想买没买成（钱不够 1 人、只有自己的摊 1 人）。 | 瓦林从灯香的摊上买走了石料×1，付5金币（灯香得5）。」→ True
SHOPTEST PASS
```

> 注意汇总里那个「只有自己的摊 1 人」—— 那是**摊主本人**：
> 村里只有他一个摊，R-03 排除自摊后他无摊可抽。
> 一条汇总同时证明了两件事。

## 9. 边界与未做

- **R-05**（掉落率 / 稀有度 / 正式价格）、**R-06**（背包摘要 > 2 种）—— 不在本轮。
- 每日汇总**不点名**；想知道是谁 → 看花名册行尾。
- 行尾标记只对**当天**有效；隔天消失（有意为之：昨天的 unmet 需求不该一直挂着）。
- 背包正式容量仍是无限（`Inventory.Capacity = 0`），所以 `BagFull` 在正式游戏里今天几乎不会命中
  （规则已钉死并有单测，用有容量上限的背包夹具验证）。
- 自主购物仍然**一次只看一个摊**（v1 限制），本轮未改。
- 未改**存档**：行尾标记是当天状态，读档后自然消失；不新增持久化字段。
