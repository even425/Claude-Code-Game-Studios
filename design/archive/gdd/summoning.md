## Summary

玩家在村里的英雄酒馆里「发一次召唤」，得到一个从另一个世界来的人：他有自己的名字、来处、身上的痕迹、性格、以及从地球带来的作息。系统不做数值成长、不做装备、不做抽取池经营——它只负责**源源不断地生人**，并且保证每一个都是活人而不是一串随机字符串。

**召唤不是免费的，但它也不是一场赌博——它是一笔被村庄规模卡住的支出。**
村庄能养几个人，就召几个人（R10 / F9）；每多召一个人都从村长的金库里扣一笔钱，
且这笔钱**随村庄越满越贵**（R11 / F10）。**代价在召唤之前就能算出来，且与抽到什么完全无关**——
这正是它必须与「抽卡」划清的那条线。

**它存在的理由很具体**：没有村民，后面的性格、配队、建造、任务全都没有演员。这个系统是 Foundation 层，它唯一的硬指标是**「每发个英雄都独一无二」**，以及这条要求背后那条不能违反的底线——**不能靠纯随机去满足它**，因为纯随机会 roll 出废人，玩家会认定系统坏了。

**代价的存在不改变这件事**：容量卡的是**次数**，不是**质量**。
保底（R3）仍然保证来的人永远能用，被容量挡住时玩家损失的也只是一个名额，
不是一次抽奖机会。**这个系统从头到尾没有一个「差一点就出金」的瞬间**——这是它与抽卡的分界线，见 AC14 / AC20。

> **Quick reference** — Layer: `Foundation` · Priority: `MVP` · Key deps: `时间与作息`（消费本系统产出的作息字段）

## Overview

玩家打开酒馆，付出一段等待，村里多一个人。这个人是从六个「世界原型」之一来的——剑与魔法的大陆、赛博都市、废土边境、深海港镇、妖怪小巷、星舰编队——权重不同，来的比例不同。**关键约束是「先有来处，再有人」**：名字不是从一张全局姓名表里抽的，而是由**他来自哪个世界**决定的。剑与魔法的大陆姓「塞莱瓦奥赫」、名「恩瑞汀尔萨德林」，赛博都市姓「零霓灰白夜」、名「七九绫澈阑」。同乡的人名字风格相近、性格倾向也相近，所以一个世界是活的，而不是一堆互不相干的随机字符串。

召唤同时确定这个人身上的几样东西：三项基础数值（保底，见下）、性格（该世界更容易出现的两种之一）、特征短语（他身上带着的来自那个世界的痕迹）、投入度（肝 / 随手 / 挂机）、以及**他从地球哪一带来、习惯自己那边几点上线**。最后这一项是「村庄永远不会天黑」的全部来源，因为地球一边是晚上，另一边就是早上——而这不需要任何额外设计，人本来就来自各个时区。

**「独一无二」怎么做到**：不是靠名字。名字的组合空间只有 155 个，两个人撞名的概率约 0.65%，村里有 15 个人时就有一半可能已经撞过一次（见 Formulas §F8）。独一无二靠的是**整条记录**——来处、名字、性格、痕迹、三项数值、作息——同时不同。这一点必须被验收，否则「独一无二」只是一句口号。

**村庄是这条链的下游，不是它的旁观者**：酒馆每召一个人，村庄的承载力就少一格。
容量只看**村庄等级**（F9），不看防护罩、不看村民强度、不看村长等级——
理由写在 F9 的【新增】说明里，那里有三个被排除的候选方案与各自被排除的原因。
这条耦合的形状就是裁定 ① 要的那句话：**想扩大人口，就得先让村子像个城。**

## Player Fantasy

**Aesthetic（按 MDA，主要服务 Discovery + Expression，次要 Challenge）**

- **Discovery（发现）**：这次来的会是哪一类人？村庄的「人口构成」是玩家一次次抽出来看的东西，而不是他配置出来的。他会为了「再来一个深海港镇的」而点下去。
- **Expression（表达）**：村长能通过「我召什么」间接表达自己想造什么样的村。他召到一堆莽他就有了工地队，召到一堆贪他就有了摆摊区。
- **Nostalgia / Fantasy（异世界感）**：「不同动漫、影视、游戏世界」是原话。村庄里应该同时住着废土来的独臂工、妖怪小巷来的狐相姑娘、赛博都市来的接口疤青年——**一眼看上去就不属于同一个世界，这正是要的感觉。**

**这个系统要让玩家感到的**：轻。点一下，人来了。不要有 build-up、不要有失败、不要有「差一点就出金」的紧张——**这个系统不是赌博，是发牌**。它的乐趣在「看看这次是谁」，不在「赌一把」。

**Anti-reference（明确不要）**：《明日方舟》/《FGO》的抽卡演出节奏（保底、UP、歪、定包）。那些设计的前提是「抽取结果本身要有稀缺性」，而本系统的稀缺性是**人口本身稀缺**（人就是劳动力），不是抽取概率。这里一旦往抽卡靠，村长的「经营」感就变成了「抽卡」，而项目的核心一句是村庄在长大，不是村长在抽。

## Detailed Design

### 核心规则

#### R1 — 世界先于人（最重要的一条）

召唤的**第一步**是抽世界，之后所有字段都从这个世界派生。不存在「先抽人再贴一个来源标签」的路径。

1. 按权重抽一个世界原型 `w`。
2. 性格从 `w.Personalities`（该世界的两种倾向）中均匀抽一种。
3. 名字 = `w.Surname[随机] + w.Given[随机]`，**不使用任何全局姓名表**。
4. 特征短语 = `w.Traits`（该世界的三条痕迹）中随机取一条。
5. 三项基础数值与投入度按 §R3 / §R4 生成。
6. 作息按 §R5 生成。

#### R2 — 六个世界原型

| 世界 | 权重 | 抽取概率 | 姓 | 名 | 特征短语（择一） | 该世界倾向的性格 |
|------|------|---------|----|----|------------------|------------------|
| 剑与魔法的大陆 | 5 | 22.7% | 塞 莱 瓦 奥 赫 | 恩 瑞 汀 尔 萨 德 林 | 背着一把用了很多年的剑 / 身上有股铁锈味 / 说话很响 | 傲、莽 |
| 赛博都市 | 4 | 18.2% | 零 霓 灰 白 夜 | 七 九 绫 澈 阑 | 手臂上有一道旧接口的疤 / 说话很快 / 口袋里全是没用的零件 | 贪、傲 |
| 废土边境 | 4 | 18.2% | 沙 石 铁 灰 锈 | 柯 砾 荼 砂 无 | 在沙里走得太久，嗓子哑了 / 左手少了一根指头 / 从不脱那件外套 | 莽、贪 |
| 深海港镇 | 3 | 13.6% | 潮 渡 盐 汐 鲸 | 舟 汐 锚 澜 屿 | 手永远是咸的 / 袖口有洗不掉的鱼腥味 / 走路带响 | 莽、傲 |
| 妖怪小巷 | 3 | 13.6% | 狐 灯 纸 面 | 火 影 香 伞 铃 | 笑起来露出的牙有点多 / 总带着一股檀香味 / 走路没有声音 | 贪、傲 |
| 星舰编队 | 3 | 13.6% | 星 远 澄 朔 昴 | 航 望 序 弦 域 | 还在适应重力的方向 / 口袋里有一枚旧船徽 / 很少提从前的名字 | 傲、莽 |

权重总和 22。每个世界的姓、名、特征短语**互不相同**（无跨世界重叠字符），这是「反推来处」能成立的前提（见 §R7）。

#### R3 — 三项基础数值的保底（必需，不可删）

三项：`Power`（力量）、`Speed`（速度）、`Grit`（体力）。

1. 每项独立在 `[10, 49]` 上均匀取整数。
2. **若 `Power + Speed + Grit < 60`，整组作废重掷**，直到满足为止。
3. 该循环**必然终止**（见 Edge Cases E1 的终止性证明与前置校验规则）。

**为什么必须有它**：三项都在 10 附近的组合意味着一个人干什么都慢。纯随机下这种组合占 **7.75%**，也就是每 13 次召唤就有 1 次召到一个近乎废的人。玩家不会读作「随机波动」，他会读作**系统坏了**——因为他在别的地方没听说过「保底」这个词。保底是本系统唯一允许存在的「不纯粹随机」，且它只有一个职责：保证来的人永远能用。

#### R4 — 投入度（性格第二根轴）

本系统只**产出**投入度（肝 / 随手 / 挂机），不定义它如何影响效率——那是 `性格系统` 的事。

1. 取 `r = rand ∈ [0, 1)`。
2. `liverBar = 0.28 + (Grit - 10) / 120`，`idleBar = 0.72 + (Grit - 10) / 160`。
3. `r < liverBar` → **肝**；`r < idleBar` → **随手**；否则 → **挂机**。

**体力越好越可能是肝帝，垫底的多数挂机**——体力高的人本来就是会肝的那批人。

#### R5 — 从地球带来的作息

性格只影响他在**自己那边**偏好什么时候上线，不影响他**能不能**上线。

| 性格 | 本地上线时刻 `LocalLoginAt` | 一次上多久（小时）`PlayHours` |
|------|-------------------------------|----------------------------------|
| 莽 | `[19, 23)` 本地深夜 | `[4, 8)` |
| 贪 | `[9, 15)` 本地白天 | `[4, 7)` |
| 傲 / 其他 | `[13, 22)` 什么时候都行 | `[2.5, 6.5)` |

1. `PlayHours` 乘以投入度系数：**肝 ×1.25 / 随手 ×1.0 / 挂机 ×0.70**。
2. 结果 `clamp` 到 `[1.5, 9.0]`。
3. `UtcOffset` 从 11 个离散值中均匀取一个：`{-11, -8, -5, -3, 0, 1, 3, 5, 8, 9, 13}`。
4. 村庄时钟上的上线时刻 = `wrap24(LocalLoginAt - UtcOffset)`。

> **不要分早班晚班。** 村庄不会天黑，因为地球上永远有一边是白天。人越多，24 小时越难有空档——这是免费的设计，不是要做的东西。

#### R6 — 召唤的产出物

一次召唤产出且仅产出：`HeroAgent` 实例 + `WorldName` + `Trait`。

**`WorldName` 与 `Trait` 是伴随产出，目前不挂在 `HeroAgent` 上**——它们被立即写进杂谈。这是现状，不是设计意图；它带来的后果写在 Edge Cases E3。

#### R7 — 来处的反推

给定一个名字，取其**第一个字**在世界列表中反查所属世界；反查不到时退回一个随机世界。

> 当前实现的反查是**按姓氏首字匹配**，前提是 R2 里各世界的姓氏首字**不与其他世界的姓氏首字重合**。当前数据满足这一点（6 组姓氏首字共 27 个字符，无一重复）。这条是**数据约束**，不是运行时校验——一旦有人在两个世界里加了同一个姓氏首字，反推会返回先命中的那个世界，且静默出错。

#### R8 — 开局三人由村长钉在村庄时钟上

新档开始时，村长亲手召来 3 个人，并把他们钉在村庄时钟上（`11 + i×0.9` 小时，从当前时刻起算），直到他们被解钉。

**理由（已在 `design/game-brief.md`「已知风险」中记录）**：如果开局三个人随机撞上三个都在上班的钟点，玩家第一眼看到的是一村空房加三个「…」。**开局第一眼必须是白天。** 村庄的营业时间应该随着人口慢慢亮起来，而不是开局就黑着。

> 这三个人**不代表本系统的典型产出**——他们的作息字段被覆写了。验收覆盖度曲线时必须把钉钟的三个排除掉，否则会低估自然产出的时段分散度。

#### R9 — 玩家可见文案禁令

**任何玩家能读到的文本**（按钮、花名册、杂谈、来历说明）**不得出现**以下系统词：

> 成功 · 失败 · 获得 · 消耗 · 属性 · 奖励

这是本项目的硬规则，不只适用于召唤系统。参考当前实现：按钮文案为「酒馆召唤一个人（N 人在村里）」——`N` 是当前人口，用词是「在村里」而不是「获得」，合规。

#### R10 — 村庄容量上限（硬上限）【裁定 ①，2026-10-17】

> **召唤的唯一硬性代价：村庄养得起几个人，就召几个人。**
> **（这一条回答了本 GDD 原 OQ-4「召唤有代价吗」——开发者于 2026-10-17 拍板为「村庄容量上限」。）**

1. **准入判定**：`Population < VillageCapacity(Village.Tier)` 才允许完成一次召唤。
   `Population` 是**花名册长度**（召来的 + 已入村的本土人，见 Q8）。
2. **拒绝是确定性的**：满容量时召唤**必定**不成立。这不是概率、不是性格判定、
   不是「村长心情」，也没有任何玩家能操作的重掷、贿赂、加急通道。
3. **拒绝时一切不变**：`Population` 不变、`VillageCoin` 不变、不生成任何人、
   **不清退任何已在册的人**、不降低容量、**不写杂谈**（拒绝没有改变村庄，
   依 `chronicle.md` 的 D-2，装饰性条目不得进入杂谈）。
4. **容量永不收缩**：`VillageCapacity` 是 `Village.Tier` 的纯函数，
   而 `Village.Tier` 按 `village-building.md` R2「不能跳，不能回头」单调不减。
   因此**没有任何路径能把村庄的容量降下来**——玩家不会因为扩招而把自己锁死。
5. **不排除已入场的人**：`Population ≥ Capacity` 是**常态而不是错误**。
   村庄满员时村子照常运转；缺的只是一个新名额。

**⚠️ 修订说明（R10 与原文冲突处）：**

| 原值 | 裁定值 | 出处 |
|---|---|---|
| E10：「召唤**不检查**村庄容量、不检查建筑等级」 | **必须检查村庄容量**（`Village.Tier` 是唯一读入项） | 本条与裁定 ① |
| Dependencies 反向声明：「召唤**不需要村庄有任何建筑**」 | **需要村庄的等级**（不含建筑本身，不需要造价、不需要工地在建） | 本条 |
| Dependencies：「**循环依赖：无。本系统不读村庄的任何状态。**」 | **有向依赖**：`村庄建造`（读 `Village.Tier`）、`经济与摆摊`（读/写 `VillageCoin`）、`村长升级线`（读 `ChiefLevel`，仅 L5 世界表） | 本条与 R11 |

**「需要村庄的等级」不等于「需要村庄有建筑」。**
`Village.Tier` 达到 5 时村庄必然已经盖过井、围墙、铁匠铺，但**召唤不检查任何一栋建筑是否建成、
不检查材料、不检查工地在不在施工**。读的是一个整数，不是场景状态。

#### R11 — 召唤收费（软调节）【裁定 ⑪ 出口之一，2026-10-17】

> **容量是硬上限，收费是软调节。** 两者是同一机制的两面，缺一不可。

1. 每次召唤**扣一笔钱**，扣在**抽取之前**、**生成之后之前**——即玩家点下去的那一刻，
   在任何随机数被取用之前确定金额。
2. 金额只取决于**当前人口**，见 F10：`SummonFee(P) = FeeBase + FeeStep × P`。
3. **费用与抽取结果零相关**：不乘 `Power`、不看世界、不看性格、不设保底加价、
   不给「差一点更好」补差价。**同一人口下连点 100 次，100 次费用完全相同。**
4. **钱不够就不召**：余额不足时按与满容量相同的方式处理（见下方「容量满 / 钱不够时」）。
5. 费用进项与出项：`VillageCoin.Stall + VillageCoin.Shop`（村长金库），
   `Purse[heroId]`（村民自己的钱）**不能**用于召唤。

**⚠️ 修订说明：**

| 原值 | 裁定值 | 出处 |
|---|---|---|
| Q4 原文：「当前实现**完全免费、无冷却、无上限**……这是本系统最大的设计缺口」 | **缺口已补**：上限 = R10 容量，收费 = R11。**免费这一条不再成立** | 裁定 ①⑪ |
| Dependencies 反向声明：「召唤**不需要任何材料**」 | 材料这一条**仍然成立**（召唤不收材料）；**新增**收 `¤` | 裁定 ⑪ |

#### 容量满 / 钱不够时，到底发生什么（本节是对实现最具体的一条规格）

| 问题 | 判定 |
|---|---|
| **按钮禁用还是可点？** | **可点。** 满容量时按钮**保持可点、不置灰**。 |
| **点击后** | **不扣费、不生成、不写杂谈。** 显示一句村长的话（下方文案要求），并给出容量读数。 |
| **为什么不禁用？** | `village-building.md` 的软锁教训：**一个不给解释就变灰的按钮，玩家读作「系统坏了」。** 容量满是玩家**自己村庄的状态**，属于村长有话可说的事，由村长说出来（与裁定 ②「只以村长身份出面」同一套口吻）。 |
| **村长能不能「拒绝」？** | **能，但那是口吻，不是权限。** 村长的拒绝在容量满时**是确定性的**，不掷骰、不看性格、不允许玩家用任何手段绕过。村长**没有**额外的裁量权——他也不能超发一个名额。 |
| **玩家可见文案要求** | 必须包含：(a) 现在的容量与已住人数（两个数），(b) **一句指向「村庄」的因果**，而不是指向玩家的失败。样式：「屋里住不下了 —— 6 / 6。先把村子盖大些。」 |
| **文案禁令** | 这句话**不得**含 R9 的六个系统词（成功/失败/获得/消耗/属性/奖励），**也不得**含「解锁」「升级」「等级」。 |
| **升了一级容量之后** | 按钮立刻恢复可用，无需任何额外操作；**不产生任何提示**（不弹窗、不播杂谈）——它是村庄变大这一件事的副产品，不是另一件事。 |

**这两条为什么不能只留一条（这是本节的全部设计意图）：**

| 只留哪条 | 后果 |
|---|---|
| **只留容量（无收费）** | 容量只在玩家**撞上去的那一次**才存在。撞墙前它不可见，撞墙时按钮可点但无结果——玩家得到的是一堵没有说明的墙，且**当场没有任何可执行的选项**（唯一出路是去建造系统，跨系统跳转）。容量变成「撞到才认识」的东西。 |
| **只留收费（无容量）** | 收费是钱能绕过的。村庄收入随规模成长（`economy-and-stalls.md` F3），玩家把摊子开起来就无限扩招。村庄**没有上限地膨胀**，村庄线（材料与建造）失去意义，「最终成超大城市」这句话永远兑现不了——因为没有一座城是有终点的。 |
| **两条都在（本设计）** | 收费让**每一次**召唤都变成一个能算出来的决策，于是容量变成一个**提前可见的天花板**而不是一堵墙；容量则保证这条收费线永远不会被钱绕过。 |

#### R11 的反向风险与硬约束

> **⚠️ 软调节不得退化成硬上限。** 若「单次召唤费」在任何人口下都可能超过玩家的全部可支配收入，
> 收费就变成了第二个硬上限，两条规则塌成一条，且那条更糟——因为**它会挡住玩家真正的意图**：
> 玩家想召的是人，不是钱。

**因此本 GDD 立一条可验收的不变式（见 AC22）**：

```
max_P SummonFee(P)  <  min_t UpgradeCoinCost(t)        // 单次召唤永远比单级村庄升级便宜
```

- `max_P SummonFee` 在默认参数下 = `FeeBase + FeeStep × (VillageCapacity(5) − 1) = 10 + 3 × 49 = 157`
- `min_t UpgradeCoinCost`（`chief-progression.md` F7 定义）= `CoinBase + CoinStep × 1 = 100 + 100 = 200`
- **157 < 200 ✓** —— 召唤**永远不会因为钱而成为更贵的那一件事**。

这条不变式的方向很重要：**村庄升级是重大开支，召唤是日常开销。**
若哪天调参把两者调反了，玩家的每一召都要面对一次「这个月盖房还是招人」的抉择——
那正是 R11 要避免的、也是 `chief-progression.md` R-C1 反对的「同一个决策做两遍」。

### 状态与转换

召唤系统自身**不持有状态**——它是一个无状态的生成器。它的每一次调用独立完成并返回，村庄是否接受由调用方决定。本系统定义的状态机只有一条：

| 状态 | 进入条件 | 退出条件 | 行为 |
|------|---------|---------|------|
| 等待召唤 | 酒馆空闲 | 操作者发起召唤 | 无 |
| 生成中 | 发起召唤且**已通过 R10 准入与 R11 扣费** | `HeroAgent` 构造完成（保底循环结束） | 按 R1 逐步生成字段 |
| 完成 | 生成结束 | 调用方接收 `Summoned` 记录 | 交出 `Hero + WorldName + Trait`，本系统不再持有 |

**被拒不是一个状态。** 容量满 / 钱不够时，系统**不进入「生成中」**，也不停留在任何新状态：
它什么都不做，返回一次拒绝并由 UI 说一句话。**不得为「拒绝」新增状态或进度条。**

**本系统不拥有的状态**（明确划界）：`Online` / `AbsentDays` / `SlackDays` / `RestlessDays` / `Away` / `GrudgeWith` 全部属于 `HeroAgent`，由 `性格系统` 与 `时间与作息` 写入。本系统只在生成时给它们**初值**。

## Formulas

### F1 — 世界抽取（加权）

```
total = Σ w_i                                  （当前 = 22）
r     = rand_int(0, total-1]                   // 整数，右开
w     = 第一个满足 (r -= w_i) < 0 的世界
```

| 变量 | 类型 | 范围 | 来源 | 说明 |
|------|------|------|------|------|
| `w_i` | int | 3–5 | 世界原型表 | 每个世界的权重 |
| `total` | int | — | 计算 | 所有权重之和，当前 22 |
| `r` | int | 0..21 | 随机 | 抽签值 |

**输出范围**：世界索引 ∈ [0, 6)
**示例**：`r = 7`。剑与魔法(5)：7-5=2 ≥ 0，不中；赛博(4)：2-4=-2 < 0 → **命中「赛博都市」**。

### F3 — 三项数值与保底（拒绝采样）

```
do {
    Power = 10 + rand_int(0, 39]     // 10..49
    Speed = 10 + rand_int(0, 39]
    Grit  = 10 + rand_int(0, 39]
} while (Power + Speed + Grit < 60)
```

| 变量 | 类型 | 范围 | 来源 | 说明 |
|------|------|------|------|------|
| `stat_min` | int | 10 | 调参 | 三项的下界 |
| `stat_max` | int | 49 | 调参 | 三项的上界 |
| `threshold` | int | 60 | 调参 | 三项之和的下限 |

**输出范围**：单项 [10, 49]；三项之和 [60, 147]
**不通过率**：`P(sum < 60) = C(32,3) / 40³ = 4960 / 64000 = **7.75%**`
（推导：令 `xᵢ = statᵢ − 10 ∈ [0,39]`，则 `sum < 60 ⟺ Σx < 30`，其解数为 `C(30+3−1, 3) = C(32,3) = 4960`。）
**平均迭代次数**：`E = 1 / (1 − 0.0775) = **1.084**` —— 即约 92.25% 的召唤一次就过。
**示例**：roll 出 (12, 11, 14) → 和 = 37 < 60 → 作废重掷；roll 出 (22, 19, 24) → 和 = 65 ≥ 60 → 通过。

> **⚠ 拒绝采样会让三项偏强——调参时不能按均匀分布估算。**
> 未经保底时每项均值 19.5（`= 39/2`，即 stat 值 29.5），三项之和均值 58.5。
> 条件化到 `sum ≥ 30` 之后：
> `E[x · 1{S≤29}] = Σ_{x+y+z≤29} x / 40³ = 35960 / 64000 = 0.5619`
> `E[stat | 通过] = 10 + (19.5 − 0.5619) / 0.9225 = 10 + 20.53 = **30.53**`
> 三项之和的条件均值 61.59（对比阈值 60）。
> **所以「保底线 60」实际产出的人，平均比阈值本身略强，且三项均衡地抬高了约 1.0 点。**

### F4 — 投入度分档

```
liverBar = 0.28 + (Grit - 10) / 120
idleBar  = 0.72 + (Grit - 10) / 160
r        = rand ∈ [0, 1)

Diligence = 肝   if r < liverBar
          = 随手 if r < idleBar
          = 挂机 otherwise
```

| 变量 | 类型 | 范围 | 来源 | 说明 |
|------|------|------|------|------|
| `Grit` | int | 10–49 | F3 | 体力 |
| `liverBar` | float | **0.280 – 0.658** | 计算 | 肝 / 随手 的分界 |
| `idleBar` | float | **0.720 – 0.945** | 计算 | 随手 / 挂机 的分界 |
| `r` | float | [0, 1) | 随机 | 抽签值 |

**输出范围**：`Diligence ∈ {肝, 随手, 挂机}`

**不变量（当前参数下恒成立，改参时必须保持）**

| 不变量 | 证明 |
|--------|------|
| `idleBar − liverBar > 0`（随手永远有正概率） | `= 0.44 − (Grit−10)/480 ≥ 0.44 − 39/480 = 0.3588 > 0` |
| `挂机` 概率 ≥ 5.5% | `1 − idleBar ≥ 1 − 0.945 = 0.055` |
| `肝` 概率随 `Grit` 单调递增 | `d(liverBar)/dGrit = 1/120 > 0` |

**示例**：`Grit = 49` → `liverBar = 0.658`，`idleBar = 0.945`；`r = 0.70` → **随手**。`Grit = 12` → `liverBar = 0.292`；`r = 0.20` → **肝**（低体力但这次抽到了肝帝，这是允许的）。

### F5 — 作息区间与钳制

```
LocalLoginAt = 莽 ? [19, 23) : 贪 ? [9, 15) : [13, 22)
PlayHoursRaw = 莽 ? [4, 8)   : 贪 ? [4, 7)   : [2.5, 6.5)
PlayHours    = clamp(PlayHoursRaw × 投入系数, 1.5, 9.0)
投入系数     = 肝 ? 1.25 : 挂机 ? 0.70 : 1.00
UtcOffset    = TimeZones[rand_int(0, 10]]      // 11 个离散值
```

| 变量 | 类型 | 范围 | 来源 | 说明 |
|------|------|------|------|------|
| `LocalLoginAt` | float | [9, 23) | 性格区间 | **他自己那边**的上线时刻 |
| `PlayHoursRaw` | float | [2.5, 8) | 性格区间 | 未乘系数的一次时长 |
| `投入系数` | float | 0.70 / 1.00 / 1.25 | 投入度 | 肝更久、挂机更短 |
| `PlayHours` | float | **[1.75, 9.0]** | 钳制后 | 实际时长 |
| `UtcOffset` | float | −11..+13（11 个离散值） | 时区表 | 他从地球哪一带来 |

**钳制的实际效果（当前参数下）**

| 边界 | 是否生效 |
|------|---------|
| 下界 1.5 | **从不生效**。全局最小 `2.5 × 0.70 = 1.75 > 1.5` |
| 上界 9 | **仅对「莽 + 肝」的尾部生效**。全局最大 `8 × 1.25 = 10.0 > 9` |

> 下界钳制是死代码。这不是 bug，但它意味着「把某项调小到让挂机更短」不会有效果——想缩短挂机时长必须改系数而不是改钳制值。

### F7 — 性格的边缘分布（推导值，非规则）

单个世界内两种性格各 50%，因此总体分布由权重决定：

```
P(性格) = Σ_{w 包含该性格} (weight_w / 22) × 0.5
```

| 性格 | 出现于 | 计算 | **边缘概率** |
|------|--------|------|-------------|
| 傲 | 剑与魔法5、赛博4、深海3、妖怪3、星舰3 | (5+4+3+3+3)/22 × 0.5 | **40.9%** |
| 莽 | 剑与魔法5、废土4、深海3、星舰3 | (5+4+3+3)/22 × 0.5 | **34.1%** |
| 贪 | 赛博4、废土4、妖怪3 | (4+4+3)/22 × 0.5 | **25.0%** |

> **这是推导结果，不是设计意图。** 三种性格没有一处均分——`傲` 出现在 5 个世界里，`贪` 只出现在 3 个。观察到的后果：`傲` 的人天然比另外两种多约 1.6 倍，而 `傲` 的效率乘数是最低的那个（×0.60）。**这会系统性压低村庄平均效率。** 是否要修，见 Open Questions Q3——本 GDD 不擅自改权重。

### F8 — 「独一无二」的碰撞分析（本系统的验收数学）

**两条性质必须分开看，因为它们的保证强度差了几个数量级。**

#### (a) 名字会重复

两个人撞名的概率（名字按世界分块，两块之间不重叠）：

```
p_name = Σ_w ( weight_w / 22 )² / |Surname_w| × |Given_w|
```

| 世界 | 权重 | 名字组合数 | `P(w)² / N_w` |
|------|------|-----------|----------------|
| 剑与魔法的大陆 | 5 | 35 | 0.001476 |
| 赛博都市 | 4 | 25 | 0.001322 |
| 废土边境 | 4 | 25 | 0.001322 |
| 深海港镇 | 3 | 25 | 0.000744 |
| 妖怪小巷 | 3 | 20 | 0.000930 |
| 星舰编队 | 3 | 25 | 0.000744 |
| **合计** | 22 | **155** | **0.00654（0.654%）** |

**村庄规模下的重名预期**

| 人口 n | 组合数 C(n,2) | 期望重名个数 | 至少 1 次重名的概率 |
|--------|---------------|--------------|---------------------|
| 10 | 45 | 0.29 | 26% |
| 15 | 105 | 0.69 | **50%** |
| 20 | 190 | 1.24 | **71%** |
| 40 | 780 | 5.10 | 99.4% |

**结论（可验收）**：**人口到 15 人时，重名是或然事件而不是意外事件。** 任何「保证名字唯一」的设计承诺都与这条数学冲突，因此：

> **「独一无二」必须由整条记录承担，名字不能承担。** 见 (b)。

#### (b) 整条记录不会重复

`Summoned` 的记录身份 = `(名字, 三项数值)`，其余字段（世界、性格、痕迹、投入度）由前两者派生，不增加区分度。数值空间 = 通过保底的三元组数 ≈ `40³ × 0.9225 ≈ 59,040`。

```
p_record ≈ p_name × (1 / 59040) ≈ 1.1 × 10⁻⁷
```

| 人口 n | 期望「整条记录完全相同」的碰撞数 |
|--------|-----------------------------------|
| 40 | 780 × 1.1e-7 = **8.6 × 10⁻⁵** |

**结论**：整条记录重复在数学上可以视为不可能。**「独一无二」是成立的——但成立的是记录，不是名字。**

### F9 — 村庄容量（VillageCapacity）【新增设计，裁定 ①】

> **本条是本次新增的设计，不是开发者原话。** 裁定 ① 只给了「村庄容量上限」这个结论，
> **没有说容量由什么决定**。以下是从既有 GDD 里找出依据、再据此排除三个候选的结果。
> 依据来源：`village-building.md`（tier 0–5 表 + R2 单向性）、
> `functional-buildings.md`（F4 的承载力模型）、`chief-progression.md`（人口门槛 10/20/40）。

```
VillageCapacity(t) = VillageCapacityTable[t]        // t = Village.Tier ∈ [0, 5]

VillageCapacityTable = [ 6, 12, 20, 28, 38, 50 ]
                          t: 0   1   2   3   4   5
```

| Variable | Type | Range | Source | Description |
|------|------|------|------|------|
| `t` (`Village.Tier`) | int | `0 .. 5` | **`village-building.md`** | 村庄等级。**单调不减，永不回退**（该文档 R2） |
| `VillageCapacity` | int | **`6 .. 50`** | 数据文件 | 名册上最多能有几个人 |
| `FeeBase` | int | `0 .. 50` | 数据文件 | 召唤费基线 |
| `FeeStep` | int | `0 .. 10` | 数据文件 | 召唤费的每人一档 |

| `t` | tier 名（`village-building.md`） | **`VillageCapacity`** | 差值 | 村长线门槛是否够用 |
|---|---|---|---|---|
| 0 | 破落户 | **6** | — | — |
| 1 | 冒险者旅舍 | **12** | +6 | — |
| 2 | 有井的村子 | **20** | +8 | L2 要 `Population ≥ 10` → 20 ≥ 10 ✓（2.0×） |
| 3 | 有围墙的村子 | **28** | +8 | — |
| 4 | 铁匠铺 | **38** | +10 | L4 要 `Population ≥ 20` → 38 ≥ 20 ✓（1.9×） |
| 5 | 王国第一的城 | **50** | +12 | L5 要 `Population ≥ 40` → 50 ≥ 40 ✓（1.25×） |

**推导与理由**

**为什么是 tier 的纯函数（三个候选与排除理由）：**

| 候选 | 排除理由 |
|---|---|
| **屋数（住房数量）** | `village-building.md` 的 tier 表只把 0→1 这一步写成「盖第四间屋」，tier 5 再加「一间亮墙土屋」，tier 2/3/4 **不加屋**——整条阶梯只有 3 → 4 → 5 屋。**它撑不起一条容量曲线**（6 → 12 → 20 这条线要求容量翻倍，而屋数只有 1.7 倍）。更麻烦的是 `src/VillageView.cs:455-459` 实际画出来的屋是「tier<2 三间、tier≥2 四间、tier≥5 五间」——**与 tier 表的「0→1 加第四间」本来就对不上**（那是 #5 的待修正项，本 GDD 无权修改）。若拿屋数当容量，两个口径打架。 |
| **防护罩的承载力** | `functional-buildings.md` F4 里确实有现成的承载力模型（`ShieldCapacity`），**但它是 `MeanPower` 的函数**，而 `MeanPower` 是名册上所有人的平均战力——**召到一个高 roll 的人，容量会当场变低**。这会造出一个自伤的状态：召人把人召没了。**这条排除是本公式全部设计里最重要的一条。** |
| **依赖 `ChiefLevel`** | 会把召唤和村长线绑在一起，破坏 `chief-progression.md` R-C1「两条线互不抢资源、不能互相削弱」——村长一升级，村庄突然能多召 10 个人，村长线会变成村庄线的第二个旋钮。**明确禁止**（已写入 `chief-progression.md` R-C8 禁列，由 AC-3 守护）。 |

**为什么这条曲线是加速的（+6/+8/+8/+10/+12 而不是一条直线）**

1. 裁定 ① 的原话是「想扩大人口就得先让村子像个城」，而「超大城市」在 `chief-progression.md`
   R-C4 里是**村庄的终局胜利**——若容量是直线，tier 5 与 tier 4 的差别在人口上只有 12 人，
   「王国第一的城」在容量这个最直观的量上会看不出来。**加速是那句话的字面兑现。**
2. 它必须满足一条硬约束：**每一级的容量都要盖过挂在那一级上的村长门槛**（末列），
   否则 `Population ≥ 40` 在 tier 5 会**永远不可达**，村长线被容量锁死（软锁）。
   最紧的一格是 tier 5：门槛 40、容量 50，余量 1.25×。
3. 余量不能更大。人口**可能减少**（退坑、缺席、`native-folk.md` 的入村/离开）。
   若 tier 5 容量是 60，玩家要凑 40 就几乎没有犯错的余地，而 `time-and-schedule.md`
   F4 实测「10 人起时段无空档」说明 40 人村庄的在场率必然低于 100%——
   **余量是给退坑留的，不是给设计留的。**
4. 这条曲线的**验收形式**是一条不等式，不是六个数字：**对每一级 L，
   `VillageCapacity(minTier(L)) ≥ cond[L].Population`**（见 AC19）。
   任何人调整 tier 门槛或容量表，AC19 会立刻变红。**这比逐个核对数字更抗改。**

**这条公式明确不管的事**

- **不管屋数。** 地图上画的 3 / 4 / 5 间屋是**地标**，不是每人一间。
  一个 50 人的村庄不会画出 50 间屋——那是 #5 的表现层取舍，本 GDD 不去纠正它。
- **不管在场人数。** 容量按**名册**算，与 `functional-buildings.md` R7「罩按名册、不按在场」同口径。
  半夜一个人都不在**不是**容量问题（裁定 ⑯ 不做软保底）。
- **不管本土人是否占容量**（当前**占**，见 Q8）。

### F10 — 召唤收费（SummonFee）【新增设计，裁定 ⑪ 出口之一】

```
SummonFee(P) = FeeBase + FeeStep × P
P             = 当前 Population（召唤前）
默认：FeeBase = 10，FeeStep = 3
```

| Variable | Type | Range | Source | Description |
|------|------|------|------|------|
| `P` (`Population`) | int | `0 .. 50` | 花名册长度 | 召唤**之前**的人口 |
| `FeeBase` | int | `0 .. 50` | 数据文件 | 第一次召唤的起步价 |
| `FeeStep` | int | `0 .. 10` | 数据文件 | 每多一个人，下一次召唤贵多少 |
| `SummonFee` | int | `10 .. 157` | 计算 | 单位 `¤`（`economy-and-stalls.md` 的 `¤`，符号仍是占位符，见其 OQ-E3） |

**输出范围**：`SummonFee ∈ [10, 157]`（默认参数下）。
**没有任何一项取自抽取结果**——R11 第 3 条。

**取线性、且斜率为正的三个理由：**

1. **必须是连续量。** 软调节的定义是「玩家每次都能看到一个变化的价格」；
   阶梯式或按 tier 跳变的收费会在某些区间内退化成常数，
   那一刻它就不是软调节，而是第二个硬上限。
2. **斜率必须为正。** 斜率为 0（固定价）时，收费**不调节任何东西**——
   玩家每次面对的决策完全一样，「要不要多召一个」变成一个和村庄状态无关的常数决策。
   那时候它就只剩「把钱花掉」这一个作用，等于一条没有节奏的税。
   斜率为负则出现「人越多召唤越便宜」，村庄会滚雪球到 tier 5 的 50 人上限后停住——
   **上限会被人口数自己顶满，中段（tier 2–4）会挤成一团**。禁止。

**几个读数（算例）：**

| 人口 P | 村庄 | `SummonFee` | 说明 |
|---|---|---|---|
| 0 | 开局 | **10 ¤** | 第一批几乎免费——保护 R10 落地后的第一口甜头 |
| 5 | tier 0 满员边缘 | 25 ¤ | 6 人村庄里再召要 25 |
| 19 | tier 2 满员边缘 | 67 ¤ | 有井的村子，钱开始有分量 |
| 39 | tier 4 满员边缘 | 127 ¤ | 铁匠铺 |
| 49 | tier 5 满员边缘 | **157 ¤** | 全局最高，**仍低于**单级村庄升级的 200 ¤ |

**这一栏的形状就是它的全部设计意图**：价格从 10 涨到 157，
玩家在**离墙还很远的时候**就开始感觉到「这个月该攒着点」，
而不是走到墙前才发现。**容量是天花板，收费是斜坡**——先感觉到斜坡，才不会撞到天花板。

**与村庄升级抢钱的配比（两条出口必须能共处）**

```
Σ UpgradeCoinCost(t=1..5) = 200+300+400+500+600 = 2000 ¤
Σ SummonFee              = 10×50 + 3×(0+1+…+49) = 500 + 3675 = 4175 ¤
比例 = 2000 / 4175 = 0.48
```

**要求这个比例落在 `[0.15, 0.50]`**：低于 0.15 说明村庄升级便宜到不值得为它攒钱，
两条线会挤在同一个月里打架；高于 0.50 说明升级吞掉了召唤的钱，
村庄会在「盖城」和「招人」之间反复饿肚子——**那正是 R-C1 反对的「同一个决策做两遍」。**
当前默认落在**区间上沿（0.48）**，偏保守：宁可让召唤花钱多一点，
也不要让升级变成一个每次都要重新权衡的大件。见 AC22、AC23。

#### (c) 玩家肉眼判断的唯一性

玩家在地图上看到的是**名字 + 头像颜色**（颜色按性格分：傲蓝 / 贪黄 / 莽红）。重名但不同性格的玩家**看得出是两个不同的人**；重名且同性格的玩家看不出。F7 显示同世界同性格的组合大量存在（如剑与魔法同时出傲与莽）。**这一项的处置是设计决策，不是数学结论 → Open Questions Q2。**

## Tuning Knobs

> 所有数值当前**硬编码在 `src/HeroFactory.cs` 中**。按项目编码标准（"Gameplay values must be data-driven (external config), never hardcoded"），下表每一项都应当迁移到 `assets/data/` 或等价的外部配置，并可由测试注入。**这一点记入验收标准（AC9）。**

| 参数 | 当前值 | 安全范围 | 类别 | 增大时 | 减小时 |
|------|--------|---------|------|--------|---------|
| `stat_min` | 10 | 1–20 | curve | 来的人整体更强，村长更轻松 | 底层村民变弱，村庄起步更难 |
| `stat_max` | 49 | 30–49 | curve | 顶层更强，但**必须同步校验 `threshold ≤ 3×stat_max`**（E1） | 数值空间压缩，「独一无二」的碰撞率上升 |
| `threshold`（保底线） | 60 | 50–90 | **curve** | 几乎不出现弱人，村庄节奏变顺滑，**随机性下降** | 弱人变多，但村庄「捡到宝」的感觉更强。**不建议低于 50** |
| 各世界 `weight` | 5/4/4/3/3/3 | 1–10 | curve | 改变村庄的「民族构成」。**注意 F7：改权重会直接改变三种性格的边缘分布** | 同左 |
| `liverBar` 基线 / 斜率 | 0.28 / (grt−10)/120 | 0.15–0.45 | feel | 肝帝变多，村庄营业时间变长 | 挂机变多，村子更安静但更常「没人」 |
| `idleBar` 基线 / 斜率 | 0.72 / (grt−10)/160 | 0.60–0.90 | feel | 随手变多（中间态变宽） | 挂机变多 |
| 性格作息区间 | 见 F5 | 各 ±2h | gate | 村庄时段覆盖更集中或更分散——**时区已经保证了分散**，动这里的收益低 | — |
| `PlayHours` 钳制 | [1.5, 9.0] | 下界 ≤1.75 / 上界 ≥10 时**不再生效** | feel | 下界当前无效；上界收紧会让「莽+肝」的高时长塌到 9 | 同左 |
| 投入度系数 | 1.25 / 1.00 / 0.70 | ±0.15 | curve | 投入度的分化更明显 | 村庄更平均，个体差异变小 |
| `TimeZones` 表 | 11 个离散值 | — | gate | 加值 = 更多样的时段覆盖 | **减值会直接造成时段空档**（已踩过的坑） |

## Acceptance Criteria

### 功能性

- [ ] **AC1 — 先有来处**：连续召唤 200 次，**每一次**记录都带有一个非空 `WorldName`，且该 `WorldName` 属于 R2 表中的 6 个世界之一；**没有任何一次**的名字来自全局姓名表。
- [ ] **AC2 — 世界分布符合权重**：在 10,000 次召唤的样本中，各世界的实际出现频率落在 `权重/22 ± 2 个百分点` 内（卡方检验，p > 0.01）。
- [ ] **AC3 — 保底生效**：10,000 次召唤中，`Power + Speed + Grit < 60` 的记录数为 **0**。同时统计循环总迭代次数，除以召唤次数应落在 **1.05 – 1.12**（理论 1.084）。
- [ ] **AC4 — 保底会抬高均值，必须知道抬到哪**：在 10,000 次样本中，`Power` 的均值落在 **[30.1, 31.0]**，三项之和的均值落在 **[61.0, 62.2]**。这是**拒绝采样的必然结果**，不是偏差（推导见 F3）。若实测落回 29.5 附近，说明保底没生效。若有人把期望值当成 29.5 来调参，会以为系统有 bug。
- [ ] **AC5 — 投入度不变量**：在 10,000 次样本中，三种投入度**每一种都至少出现 1,000 次**。若某一档为 0，说明 F4 的两个不变量被破坏。
- [ ] **AC6 — 作息可复算**：随机抽取任意一个已生成的 `HeroAgent`，用 `wrap24(LocalLoginAt − UtcOffset)` 复算出的 `LoginAt` 与其实际 `LoginAt` **完全一致**（容差 1e-6）。**开局的三个钉钟人排除在外。**
- [ ] **AC7 — 反推可逆**：对 200 个已生成的 `HeroAgent`，`World.OfName(h.Name)` 返回的世界**与其实际的 `WorldName` 一致**，命中率 **200/200**。
- [ ] **AC8 — 文案禁令**：全项目 grep 玩家可见字符串，**零命中** `成功 / 失败 / 获得 / 消耗 / 属性 / 奖励`。

### 「独一无二」专项（本系统的核心验收项）

- [ ] **AC9 — 名字不唯一是可接受的，但必须被设计承认**：在 30 次召唤的样本中，**允许**出现 0–1 个重名。测试用例必须**包含一个 30 人村庄**（期望重名 ≈ `C(30,2) × 0.00654 = 2.84` 个），并确认重名者**在花名册上仍可被区分**（见 Q2 的处置结果）。**若测试断言「零重名」，该断言本身是错的**——F8 已证明它不可能成立。
- [ ] **AC10 — 记录唯一**：在 5,000 次召唤的样本中，**不存在两个 `(Name, Power, Speed, Grit)` 完全相同的记录**。理论期望碰撞数 ≈ 5.1e-4，实测应为 0。
- [ ] **AC11 — 分布层面无退化**：每个世界都必须被抽到过（**6/6**，无休眠世界）；每个世界的性格倾向都出现过。
- [ ] **AC12 — 人不是字符串**：在 30 人村庄中，随机抽 5 个村民，测试者能根据「名字风格 + 特征短语」**正确判断出他们来自哪个世界**，正确率 ≥ 4/5。**这是「先有来处，再有人」是否真的成立的唯一人测标准。**

### 体验性

- [ ] **AC13 — 轻**：召唤从点击到人出现在地图上，**不超过 1.5 秒**，无 loading、无过场演出、无期待值铺垫。
- [ ] **AC14 — 不像抽卡**：5 名 playtester 连续召唤 20 次后，**无一人主动使用「抽」「卡池」「保底」「概率」描述这个功能**。若有人这么说，说明演出或文案把它推向了抽卡。
- [ ] **AC15 — 重名不刺眼**：给 playtester 看一个含重名的 30 人村庄，问「有没有两个一样的人？」——期望回答是「没有两个**看起来**一样的」，而不是「有两个叫塞恩的，很奇怪」。

### 工程

- [ ] **AC16 — 无硬编码**：F1–F8 的每一个数值常量都能从外部配置读取，且测试可在不启动 Godot 的情况下注入固定种子（当前实现使用**未播种的静态 `Random`**，不满足此条）。
- [ ] **AC17 — 配置前置校验**：加载配置时校验 `threshold ≤ 3 × stat_max`、各世界姓氏首字两两不重叠、`idleBar > liverBar` 恒成立。任一条不满足则**拒绝加载并报错**，不得进入运行时（E1 / R7 / F4）。

## Open Questions

| # | 问题 | 为什么是问题 | Owner | 截止 |
|---|------|------------|-------|------|
| **Q1** | **要不要给 `HeroAgent` 加上 `WorldName` 和 `Trait` 两个持久字段？** | 目前来处和痕迹**召完就丢了**，只能靠 `OfName` 从名字首字反推，反推失败还会静默返回随机世界（E3/E4/E5）。**花名册上无法显示「废土边境来的」**，而「来处」是这个系统最值钱的产出。 | game-designer + lead-programmer | 下一个迭代 |
| **Q2** | **重名的人怎么区分？** | F8 证明 15 人时重名是或然事件。当前头像颜色按性格分，所以**同世界同性格的重名玩家在地图上是两个长得一模一样的人**。三个选项：(a) 接受，靠杂谈和事件里累积的经历区分；(b) 给重名者分配一个持久绰号（注意：`Nicknames` 目前是**每次用就重掷**的，不是挂在人身上的，不能直接复用）；(c) 扩姓名空间（加长名 / 三字名 / 复合姓），把 155 提到 500+，代价是每个世界的姓名表要扩写一倍。 | creative-director（这是**美学决策**） | 垂直切片前 |
| **Q3** | **要不要修正 F7 的性格偏斜？** | `傲` 边缘概率 40.9%（应约 33%），而 `傲` 的效率乘数最低（×0.60）。**这会系统性压低村庄平均效率**，且原因纯粹是世界权重表的副产品而非设计意图。**本 GDD 未擅自改动**——要么承认它，要么在某个世界里加入 `贪` 来平衡。 | economy-designer + game-designer | 第一次 balance-check |
| **Q4** | **召唤有代价吗？** | 开发者原话是「系统**开局只能召几个人**」，但当前实现**完全免费、无冷却、无上限**（`_btnSummon` 从不禁用）。村长的稀缺感目前**完全不存在**——人口增长没有任何瓶颈。**这是本系统最大的设计缺口**，但**开发者从没说过代价应该长什么样**，所以这里只提问，不给方案。选项大致是：每次召唤消耗某种资源 / 有冷却 / 有并发上限 / 村庄有容量。**任何一种都需要开发者确认后才写进本 GDD。** | **creative-director**（需要开发者拍板） | **最高优先级** |
| **Q5** | **「村里第一次见这种人」的杂谈文案怎么处置？** | 当前模板无条件说「第一次见」，到 20 人时基本是假的（E12）。建议改成**以「该世界第一次来」为条件**触发，条件不满足时走另外的模板。这需要 `Chronicle` 侧支持条件模板，且依赖 Q1（要知道来处）。 | narrative-director + game-designer | 跟随 Q1 |
| **Q6** | **时区表只有 11 个值，够吗？** | 真实 UTC 偏移跨 −12..+14，当前表跳过了一部分（−12, −10, −9, −6, −4, −2, +2, +4, +6, +7, +10, +11, +12, +14）。这未必是问题（11 个值已能让 40 人村庄无空档），但**这是一张手工表、不是真实地球**，需要确认它是刻意的简化还是待补。 | game-designer | 下次覆盖度复测 |
| **Q7** | **召唤是否要与 `本土角色与本土剧情`（系统 #12）共用一个入口？** | 开发者原话里两者是分开的（「从地球召唤玩家」vs「本土角色、本土剧情」）。但从玩家视角，酒馆里同时出现「地球来的人」和「本地人」会不会更好玩，还是会破坏「村庄是异世界」的感觉？**本 GDD 当前只产出地球来的人。** | creative-director | Alpha 前 |
