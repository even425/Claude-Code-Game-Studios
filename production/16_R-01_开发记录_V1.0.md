| 摆摊 / 交易 | `StallService` / `Trade` | ✅ 复用，不重写 |

**审计发现的 4 处真实缺陷（草案未写）：**

1. **参战名单回退用错标识** —— `Main.ResolveDungeon` 里 `_mission` 为 null 时回退取
   `crew.Select(h => h.Name)`（**显示名**），主路径取 `m.Id.Value`（**英雄标识**）。
   奖励资格要按标识判定，两条路径必须一致。
2. **副本业务标识会误判「已结算过」** —— 原标识是 `d{小时}`。同一小时内第二次副本
   得到**同一个** `SettlementKey` → `_settlement.Apply` 返回 `false` →
   **奖励被静默跳过**（不发也不报错）。
3. **物品奖励不在结算路径上** —— `SettlementDelta` 只有 `ResourceDelta`。
   物品若单独发一步就破坏 I15，且要另建一套幂等（草案 §4.4 明令禁止）。
4. **战利品物品必须先在价格表登记** —— `ItemGrantService` 要求物品价格 > 0；
   `PriceBook.Default` 只有 石料 / 木料 / 布匹，而副本任务表的 `job.Res` 是「铁料」，
   **不在表内** → 直接发会被判 `UnknownItem` 拒掉。

| Q2 | 「全队平分」覆盖哪些奖励类型 | **只发物品**；金币与材料继续走现有村庄资源结算，不动 |
| Q3 | 背包装不下 | **整次奖励回滚**，谁都拿不到，记录结算异常（幂等键不落，可重试） |
| Q4 | 剩余物品的随机源 | **独立派生子流**，由副本实例标识派生子种子 |

另两项按草案原文执行：五项规则（D01–D05）原样实现；幂等标识复用
`SettlementKey(RunId, BattleResultId)`，**不新建状态记录**。

**规则细化中由本轮拍板的两项**（草案 §2.4.5 列为「交界项，需在开发前确定」）：

- **余数随机 = 逐件独立抽样**：同一英雄**可能**连拿多件余数。轮流发（谁先谁后）
  确定性强、可预测，那不是 D03 说的「随机分配」。
- **随机调用次数 = 余数份数**：可整除时**一次都不抽**。这条被单测钉死
  （`LootSplitTests.Split_DrawsFromRandomSourceExactlyOncePerRemainderItem`）——
  调用次数一变，同一个副本的分配结果就变，而分配结果是**要进背包、要存档**的。

## 4. 五个关键设计决策

### 4.1 物品进结算增量，而不是另发一次

副本成功时，**村庄资源**与**英雄个人物品**是同一笔奖励的两半。
分两次发，中间任何一步失败都会留下「村庄拿到了、英雄没拿到」的半笔账 ——
那正是 I15 要禁止的状态。放进**同一个增量**，`Settlement.Apply` 才能用
**同一把幂等锁**、在**同一次提交**里把两半一起落下去。

`Apply` 的三步顺序不可换：**先算全量 → 预检物品 → 一次性提交**。
物品预检必须在资源写入**之前**，否则顺序反了就会产生半笔账。

### 4.2 物品写入分两阶段（预检 + 提交）

`IItemGrantWriter` 拆成 `CanGrant`（只回答「行不行」）与 `Grant`（已知可行时一次性发完）。
预检通过后提交不再有失败路径 —— 因为**背包（`Inventory`）是不可变的**，
「先算出每个英雄的新背包，再一次性换上」天然是原子的。

### 4.3 奖励随调用带进来，不放会话级共享状态

`Settlement.Apply(key, heroesWon, rewardsOverride)` 新增可选参数：
本次副本的战利品**随这次调用**传进奖励委托。

**为什么不用字段**：若把战利品放进会话级字段由奖励委托去读，
任何一次**与副本无关**的结算都可能把它当成自己的奖励再发一遍。
「状态留在全局、靠调用方记得清」是本轮实施中途**实际改掉**的一版写法
（初版用 `_pendingLoot` 字段，现改为 `rewardsOverride`）。

### 4.4 随机用独立派生的子流

掉落若从全局随机源（`Main._rng`，战斗与日常共用那一条）抽，会**插队**：
一次副本掉落会改变此后所有战斗与日常的结果。而掉落结果是**要被存档的**
（它进了背包），它需要的是「**同一个副本永远得到同一份分配**」。

种子由**副本实例标识**派生（FNV-1a，**不是** `string.GetHashCode()` ——
.NET 的字符串哈希每个进程都不一样，用它派生种子，「读档重放得到同样的结果」
这条承诺当场就废了）。

### 4.5 副本实例标识加会话令牌

原标识 `d{小时}` 会在同一小时内撞车 → 结算幂等误判 → **奖励被静默跳过**。
现为 `d{小时}.{会话内序号}.{会话令牌}`：

- 会话内序号：同一局内逐个不同；
- 会话令牌（`BootSeed` 派生）：跨局也不同 —— 上一局留下的结算键不会误伤这一局。

副本实例本身**不落盘**，所以「同一个副本被结算两次」只可能发生在**一次会话内**，
由会话内序号保证唯一。

## 6. 自检增补（`--dungeon`）

`--dungeon` 自检新增 R-01 段落，输出**发放前后的背包对照**、分配明细、
入包校验、未参战者校验、开摊与他人购买、入档校验：

- 发放前快照 → 分配明细 → 逐人「石料 0 → 19（应 +19）」
- 战利品入包 / 未参战者没拿到（失败局两者都必须为 `True`）
- 战利品开摊 → 他人购买（买家背包 +1、买家金 −5）
- 战利品已入档、已结算键 1 个、存档版本 0.4

另外：**自检会自己组队**（走 `OnRosterItemActivated`，与玩家同一入口）——
因为开局**不预编**队伍，无人点击时 `--dungeon` 原本跑不起来。

## 8. 踩过的坑

1. **`using` 别名行被手滑改坏过一次** —— `ClaudeCodeGameStudios` 被写成了
   `ClaudeCodeGameGameStudios`，编译报「找不到命名空间」。
   报错的**行号指向别名行**，而真正的原因在上一行 —— 看到 CS0246 先去看那一行的原文。
2. **GdUnit4 的数字断言只有 `IsEqual` 能用于 `long` / `ulong`** ——
   `IsEqualTo` 是 `int` 专用的扩展方法。对 `long` 用 `IsEqualTo` 会报
   「`INumberAssert<long>` 未包含 `IsEqualTo` 的定义」。
3. **写文件时用 `WriteAllText` + UTF8 无 BOM** —— PowerShell 5.1 的
   `Out-File -Encoding UTF8` 会写 BOM，混进 C# 源码里虽能编译，但会让 diff 变脏。
