## Summary

村长把最多 4 名村民编成一队，一起出村做任务。系统读三样东西算出一个「配合」系数：
**这支队有几个人**（人越多越乱）、**性格搭不搭**（两个傲谁也不服谁）、
**他们彼此是什么关系**（同乡、搭子、师徒、欠人情，还是仇人）。
系数作用在每个人的办事成功率上。吵过架（有仇）的人**不能**进同一支队——
这不是打折，是**不让成行**，而且游戏会明确告诉你是为什么；搭手可以让两人和解，
之后那支队又合法了。配队是玩家**唯一能控制**的那一层，
而同一批村民不出任务时会按性格自己行动，那是玩家**控制不了**的一层。

> **Quick reference** — Layer: `Core` · Priority: `MVP` · Key deps: `性格系统`、`时间与作息`、`任务与副本`、`杂谈`

## Overview

村长把最多 4 名村民编成一队，一起出村做事。这不是「选四个最强的」——**队伍本身就是一个变量**。

三件事同时在起作用：

1. **人多未必好。** 两个人时指挥链最短、最清楚（`×1.10`）；
   三个人开始互相传话（`×1.00`）；**四个人就「人多手乱」了（`×0.90`）**。
   多带一个人确实能多带材料回来，但每个人带回来的都更少——**这是一个真实的取舍**。
2. **性格互相影响。** 两个傲挤在一起谁也不服谁；两个莽反而谁也不等谁（这是好事）。
   性格只**摩擦**，不否决——他们照样能一起干活。
3. **关系也在算。** 同一个世界来的两个人是**同乡**，零成本、出生就有，是配合的默认底子；
   一起扛过活的会变成**搭子**，老手带新人会变成**师徒**，帮过人的记着**人情**；
   反过来，看你升级比他快的会**嫉妒**，想抢同一个摊位位的会**竞争**。
   **这些关系是村庄自己长出来的，不是你摆出来的。**

有仇的两个人**不能**被塞进同一支队——**游戏会告诉你为什么**，而不是悄悄把你的系数砍一半。
唯一的解法是村庄日常里的「搭手」：和好之后那支队重新合法。

同时——**你不派他们，他们也会自己按性格行动**。配队是你手里唯一的那根杆，
日常自主行动是杆子够不着的那部分。

## Player Fantasy

**Aesthetics（目标情感）**：**Expression（表达）** + **Challenge（挑战）**，辅以 Narrative。

玩家要的感觉是「**我在挑人，不是在点数值**」。目标情绪按 MDA 反推：

| 层 | 内容 |
|---|---|
| **Aesthetics** | 我摆出一支队伍 → 我希望感到「这是我的人，我知道他们凑在一起会出什么事」 |
| **Dynamics** | 玩家反复调整队伍——**不只是挑人，还要挑人数，还要避开仇人、照顾关系的新旧**；队伍带着摩擦出门；杂谈里出现对应的一句 |
| **Mechanics** | 人数清晰度 × 性格摩擦 → 配合系数 → 乘进成功率；关系层做**合法性拦截**与**按人上浮** → 材料与杂谈文案 |

**反对的读法**：这个系统绝不能读成「打开面板 → 把四个人头拖进去 → 完成」。
如果最优队伍永远只有一种填法，这个系统提供的 Expression 就是零——那还不如
一个「派出」按钮。这是 §「已定性缺陷」存在的理由，而**该缺陷已由本次重构修复**
（见该节）。

**自主性对照（这是开发者原话里最重要的一层）**：

```
配队      —— 我控制的      我决定谁跟谁出门
日常自主  —— 我控制不了的   他按性格自己挑活儿
```

两层共用性格数据。玩家应该在杂谈里看到「他自己去干了他爱干的」，同时知道
**如果我把他换进我那一队，我就能改这件事**。这才是这个系统的份量所在。

## Detailed Design

### Core Rules

**R1 — 队伍上限。** 一支队伍最多 `SquadMax = 4` 人。超出时点击无效，不静默丢弃。

**R2 — 派出的实际成员 = 在场成员。** 系数与产出只按**此刻在村里能干活的**人计算
（在线，且不在生病 / 缺席状态）。判定顺序：`AbsentDays <= 0 && IsOnlineAt(hour)`。
不在场的人不算人数，也不触发性格冲突——他今天根本没上车。
（⚠️ `expedition.md` 与 `village-building.md` 把 `¬Away` 作为独立的第三个条件，
本文件未采纳，见 Open Questions Q9。）

**R3 — 系数是三层相乘，不是九档 if 链。**
> ⚠️ **修订说明（2026-10-17 裁定 ⑤）**：旧 R3 写的是「**命中即定，不连乘**」，
> 配一张 9 档 if 链表。**该规则已作废。**
> **为什么必须废掉它——这是可证的，不是偏好**：
> `first_match` 的顺序表里，`mang >= 2 → 1.10`（序 7）排在 `C >= 3 → 1.15`（序 8）之前，
> 而 `C >= 3` 会吞掉所有 `C == 2` 的分支；`C == 2 无冲突 → 1.05`（序 9）是 `C >= 3` 的
> **前置拦截**，所以 **1.05 永远不可达**。同理 1.15 只在「人数 ≥ 3 且不命中任何性格档」时成立，
> 而人数 ≥ 3 时必然命中 `mang>=2` 或落进 1.05 的空档，导致 **1.15 也几乎不可达**。
> **一张表里有两档是死分支，它就不是一张好表**——调参的人会照着死数字做预算。
>
> **新规则**：配合系数 = **人数清晰度 × 性格摩擦**，两层相乘。
> 性格摩擦**逐条相乘、不短路**，因此任何性格组合都产生一个确定值，**不存在死分支**。
> 完整穷举见 § Formulas F1b。

**R4 — 人数清晰度 `ClarityOf(C)`（裁定 ⑤ 的核心）。**

| 在场人数 C | 清晰度 | 面板说法 |
|---|---|---|
| 0 | ×1.00 | 没人在村里 |
| 1 | ×1.00 | 一个人，没有配合可言 |
| 2 | **×1.10** | 两个人，说清就行 |
| 3 | ×1.00 | 三个人，开始互相传话 |
| 4 | **×0.90** | 人多手乱 |

> **人多反而乱，这是刻意设计。** 两个人时指挥链最短、每人只跟一个人打交道；
> 四个人时每个人要同时对三个人负责，指令在队里传三手。
> **新增这一维不是为了惩罚玩家多派人，是为了让「派几个人」第一次成为一个需要想的问题。**
> 旧表里人数这一维是**平的**（3 人与 4 人同为 ×1.15），所以它根本不是一维。见 § 已定性缺陷。

**R5 — 性格摩擦 `FrictionOf(ao, tan, mang)`（逐条相乘，不短路）。**

| 条件 | 乘数 | 面板说法 |
|---|---|---|
| `ao >= 2` | ×0.88 | 谁也不服谁 |
| `ao >= 1 且 mang >= 1` | ×0.96 | 边吵边干 |
| `ao >= 1 且 tan >= 1` | ×0.97 | 谁也看不上谁 |
| `tan >= 2` | ×0.94 | 互相防着 |
| `mang >= 2` | **×1.06** | 谁也不等谁 |

一队同时命中多条时**全部相乘**（例：2 傲 + 2 莽 = 0.88 × 0.96 × 1.06 = 0.8955）。
**性格只摩擦，不否决**——两傲照样能一起干活，只是慢（承 `personality.md` 铁律 1）。

**R6 — 有仇：硬禁止，不是软惩罚。** ⚠️ **修订说明（2026-10-17 裁定 ⑬）**

> **旧值**：R6 原文为「有仇是**软惩罚**，可以同队，代价是全队 **×0.50**」，
> 并把它列为九档之一（序 1）。**该条已整条作废，`×0.50` 这个值在本系统中必须 0 命中。**
>
> **裁定 ⑬ 的理由**：软惩罚的真正问题是
> **「玩家不知道为什么自己的队伍变差了」**——系数凭空砍一半，面板只写「有仇」，
> 而惩罚又不足以改变他的决定。定成硬禁止以后，原因**必须**显示出来。
>
> **新规则**：
> ```
> for each 队员对 (a, b):
>     if GrudgeBlocks(a, b):        // relations.md F7，Churn >= GRUDGE_AT=40
>         该队伍标记为「不成行」，禁止发布，并显示原因
> ```
> - **不产生任何系数值。** 不是 0.50，不是 0.00，不是任何折扣——**这一队压根不成立**。
> - **游戏会说明为什么**：面板脚注 + 发布按钮禁用态 + 悬停说明，必须指向具体的两个人。
>   （裁定 ⑬ 原话：「不能同队（游戏会说明为什么）」）
> - **唯一的例外**：`relations.md` R7-b 的安全阀——凑不出 `SQUAD_MIN` 人时允许降级出发，
>   并写一条说明为什么的杂谈。**该例外属于关系系统，不属于本系统**，本文件只承接其结果。

**R6-b — 被否决的是「这一支队伍」，不是「这个人」。**
这条与 `personality.md` 铁律 1 的修订说明是同一件事的两面，两份文档必须一致：

| 问的是 | 答案 | 归属 |
|---|---|---|
| 「他能不能干活？」 | **能。** 他照常进工地、进建造、进兜底指派，效率系数一分不打折 | `personality.md` |
| 「他能不能和**别人**组队？」 | **能。** 他与任何无仇村民都是合法组合 | R6 |
| 「他能不能和**与他有仇的那个人**同车？」 | **不能。** 仅此一例被拒绝 | R6 |

**他的数值完全不受结仇影响**——`chance` 的计算路径里**不允许**出现 `GrudgeWith` / `Churn`。

**R7 — 可和解：搭手（裁定 ⑬ 的第二半）。**
`搭手` 事件把两人的敌意降下来。**降到 `GRUDGE_AT` 以下，那支队立即恢复合法**，
系数与「从未结仇」时**逐位相同**，不残留任何惩罚。

> ⚠️ **搭手需要几次 —— 与现有实现有差异，按 `relations.md` 的两次制写。**
> `relations.md` F3 取 `搭手（有仇时）ΔChurn = −25`，而 `GRUDGE_AT = 40`。
> 一场打架给 `Churn = +45`，故 `Churn = 45 → 20`，**一次搭手即解**；
> 若先吵架（+30）再打架（+45）累积到 `Churn ≥ 65`，则需要**两次**搭手。
> **现状实现是「一次搭手直接清零」（`VillageLife.cs:127`）——本文件按两次制写**，
> 理由是「动手一次不该被一顿饭抹掉」，见 `relations.md` Q2 与 AC-E2。
> **这是一条显式回归项**：实现按现状跑，本文件的 AC 会红，红了是对的。
>
> **本文件不拥有这条规则**——敌意怎么涨怎么降全部由 `relations.md` 定义。
> 本文件只承诺：**它降到门槛以下时，合法性立即恢复。**

**R8 — 系数在派出的瞬间快照。** 系数与合法性判定都在按下派出的那一刻算好并冻结，
任务期间村子里新结的仇、新病倒的人**不改变**这一次远征的结果。
面板上显示的实时系数只对**下一次**派出有效。
（承 `relations.md` E6：仇对双方若已在已冻结名单里，照常结算、不停机。）

**R9 — 系数只乘成功率，不乘倍率产出。** 见 §Formulas 的 F3。补充人手增加的是
**人数**和**人均 Power/8 项**，不是对同一份材料的多倍抽取。

**R10 — 队伍永不空手而归。** 全员未成事时，第一个人仍然带回一份材料。
**这条只适用于合法的队伍**——非法队伍在 R6 就发不出去了，谈不上空手。
（⚠️ 旧版把 R9 写成「正是 R6 值得留着的理由」，该论证随软惩罚一并作废。）

**R11 — 玩家可见文案禁用词。** 配队面板与本系统产生的任何杂谈句，
不得出现：成功 / 失败 / 获得 / 消耗 / 属性 / 奖励。现有的说法
（没人在村里、一个人没有配合可言、两个人说清就行、三个人开始互相传话、人多手乱、
谁也不服谁、互相防着、边吵边干、谁也看不上谁、谁也不等谁、他们有过节）
全部合规。

### States and Transitions

本系统本身**无持久状态**——它是一个纯函数 `CohesionOf(readySquad) -> (系数, 说法, 脚注)`。
存在的状态在协作者身上：

| 状态 | 进入条件 | 退出条件 | 行为 |
|---|---|---|---|
| 待命（In roster） | 召唤进村 | 死亡 / 退坑 | 可被点进队伍，不出勤 |
| 在队（In squad） | 点击加入且未满 4 人 | 点击移出 / 队伍解散 | 参与系数判定 |
| 在场可出勤（Ready） | 在队 且 `AbsentDays<=0` 且 `IsOnlineAt` | 离线 / 生病 / 缺席 | **只有 Ready 成员参与系数与产出** |
| 外出（Away） | 派出瞬间全体置 Away | 远征结算完成 | 期间不参与日常事件、不参与新系数 |
| 有仇（Grudge） | `relations.md` 的 `Churn >= GRUDGE_AT` | 搭手把 `Churn` 降到门槛下 | ⚠️ **修订**：原行为「同队系数 ×0.50」，现为**不可同队**（R6）。**判定读 `GrudgeBlocks(a,b)`，不读 `HeroAgent.GrudgeWith`** |

> ⚠️ **旧字段 `HeroAgent.GrudgeWith` 已不再被本系统消费。**
> 该字段存的是**名字字符串**，而 `summoning.md` F8 已证明 15 人时重名是或然事件——
> **两个人同名就会被误判成有仇**，整个村庄因此拆不开队。
> 本文件的判定改读 `relations.md` 的 `GrudgeBlocks(a, b)`，**它按 `HeroId` 存取**。
> 该字段的迁移顺序见 `relations.md` Q4，本文件不拥有它。

### 关系层接口（本系统消费 `relations.md` 的三个量）

> **本系统只读三个函数，不接触 `Bonds` 的内部结构。**
> 关系类型的定义、敌意怎么涨怎么降，全部由 `relations.md` 拥有。
> **本文件不发明任何一种关系。**

| 交给本系统的函数 | 返回 | 本系统用它做什么 | 属于哪一层 |
|---|---|---|---|
| `GrudgeBlocks(a, b) -> bool` | `Churn(a→b) >= 40 或 Churn(b→a) >= 40` | **可行性拦截**：成真则该队伍不成行（R6） | **队层**——唯一能改「可不可行」的关系 |
| `BondKind(a, b) -> Kind` | R3 顺序表命中项 | **文案与脚注**：显示「他们是同乡 / 师徒 / 搭子 / 欠人情 / 嫉妒 / 竞争」 | **只读标签**，不进系数 |
| `BondFreshness(a, b) -> days` | `Day - LastDay` | **按人扣减**：久不一起走的人今天跟队更生疏（R6-c） | **人层**——不进队表 |

#### R6-c — 为什么正向关系**不**进队表（采纳 `relations.md` R6-a 的建议）

> `relations.md` Q6 问「搭子要不要进配合系数」，并建议**不进**。**本文件采纳。**
>
> **理由（与本文件要修的病是同一个）**：旧表的系数是**按队伍整体命中即定**的。
> 若加一条「队内有 N 对搭子 → 系数上浮」，玩家就会去**经营一支固定队伍**——
> 于是最优解重新变回「永远派同样那四个人」，
> **恰好是 § 已定性缺陷 正在修的那个退化**。加它等于把病请回来。
>
> **所以正向关系走「按人」而不是「按队」**：
>
> ```
> bond_uplift(h) = min(BOND_UPLIFT_CAP, BOND_UPLIFT_PER × 队内与 h 关系为 搭子/师徒 的人数)
> freshness_penalty(h) = -min(FRESH_PENALTY_CAP,
>                             FRESH_PENALTY_STEP × max(0, BondFreshness(h, ·) - FRESH_GRACE))
> ```
>
> 两者都加在**该成员自己的 `chance` 上**，**不进 `CohesionOf()` 的队表**。三���理由：
> 1. **队表保持干净**——它的输入只有人数与性格，穷举可验（§ F1b）。
> 2. **按人上浮是可绕开的**：换一个熟人进来就行，不需要「必须带齐四个人」。
>    队级加成则相反，它奖励的是**那四个人恰好在一起**，玩家没有别的选择。
> 3. **新鲜度扣减是反固化的**：总派同样四个人，他们的 `BondFreshness` 会一路涨，
>    扣减跟着涨，**玩家被迫轮换**。这与「永远派同样那四个人」直接相反。
>
> ⚠️ **扣减的三个硬边界**：① `Bond` 不存在时**不扣**（`relations.md` E7 不建零值边）；
> ② `BondFreshness <= FRESH_GRACE` 时**不扣**（新队伍与从未同过队的人都是 0）；
> ③ **有仇的人永远不在这条路径上**——他根本进不了队（R6），没有系数可算。

### Interactions with Other Systems

| 系统 | 方向 | 契约 |
|---|---|---|

## Formulas

### F1 — 配合系数（三层：可行性 → 队表 → 按人）

```
# ── 第 0 层：可行性（不是系数，是「这支队伍成不成立」）
legal = NOT ∃(a,b) ∈ pairs(squad): GrudgeBlocks(a, b)          // relations.md F7
if not legal → 队伍不成行。不产生任何数值。                       // R6

# ── 第 1 层：队表（纯函数，输入只有人数与性格）
Clarity = ClarityOf(C)
Friction = FrictionOf(ao, tan, mang)
Cohesion = Clarity × Friction

# ── 第 2 层：按人（关系层，加在每个人的 chance 上，不进队表）
chance(h) = min(0.95, base_chance(h) × Cohesion × person_mult(h) × (1 + bond_uplift(h) + freshness_penalty(h)))
```

**`ClarityOf(C)`（人数清晰度）**

| C | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| `ClarityOf` | 1.00 | 1.00 | **1.10** | 1.00 | **0.90** |

**`FrictionOf(ao, tan, mang)`（性格摩擦，逐条相乘）**

| 条件 | 乘数 |
|---|---|
| `ao >= 2` | ×0.88 |
| `ao >= 1 且 mang >= 1` | ×0.96 |
| `ao >= 1 且 tan >= 1` | ×0.97 |
| `tan >= 2` | ×0.94 |
| `mang >= 2` | ×1.06 |
| （未命中任何一条） | ×1.00 |

| 变量 | 类型 | 范围 | 来源 | 说明 |
|---|---|---|---|---|
| `C` | int | 0 – 4 | 计算 | ReadySquad 的大小，受 `SquadMax` 限制 |
| `ao` / `tan` / `mang` | int | 0 – 4 | 计算 | 三种性格在 ReadySquad 中的计数 |
| `Clarity` | float | 0.90 – 1.10 | F1 表 | 人数清晰度 |
| `Friction` | float | 0.7634 – 1.06 | 计算 | 5 条乘数之积，见 F1b 穷举 |
| `Cohesion` | float | **0.7221 – 1.1660** | 计算 | `Clarity × Friction` |
| `person_mult` | float | 1.00 – 1.15 | `expedition.md` F2 | **远征成功率侧的性格系数由 `expedition.md` 拥有**，本文件只沿用不定义 |
| `bond_uplift(h)` | float | 0 – +0.12 | F6 | 该成员与队内熟人的人数 × 每档 |
| `freshness_penalty(h)` | float | −0.12 – 0 | F6 | 久未同队 |

**Coefficient 预期输出范围**：`0.7221` – `1.1660`。
（⚠️ **旧范围 `0.50` – `1.15` 已作废**：`0.50` 那端是软惩罚，随裁定 ⑬ 整条消失。）

**边界**：
- `C == 0` 与 `C == 1` 都是 `1.00`——没有人可以「破坏」配合，但也没有配合可言。
- 性格**永远不会**把 `Cohesion` 压到 0 或负数：最坏的 2 傲 + 2 贪 = 0.7221。
  **返回 0 等价于「这支队伍不成立」，那是 `legal` 的职责，不是 `Cohesion` 的。**
- **`Cohesion` 恒 > 0**，所以 0.95 截断是唯一的上界来源（见 F5）。

### F1c — 人数是不是甜点？可证的部分与不可证的部分

**先说清楚一件容易被糊弄过去的事：单趟材料总数里，人数永远越大越好。**
这是可证的，不是估计：

```
E[material](C) = job.Amt + C × p(C) × floor(Power/8)
p(C) = min(0.95, base_chance × Clarity(C) × Friction × person_mult)
```

`job.Amt` 是**固定的一份**（F3）。所以 `E[material]` 对 `C` 的偏导
正比于 `Clarity(C) + C · Clarity'(C)`。要让 4 人严格劣于 3 人，需要
`Clarity(4) < Clarity(3) / 4`，即 **0.90 < 0.25**——**要求人数惩罚砍到四分之一才可能**，
那时 4 人队已经完全没有存在意义，退化成另一种「不许用」。
**所以「人数甜点」不可能出现在单趟材料上，任何声称它出现了的设计都是错的。**

**甜点在哪里？出现在「每人份」与「机会成本」两个口径上。**
下面用同一批村民算三档（Power = Speed = 30，`base_chance = 0.72`，`job.Amt = 14`，
全部贪，即 `person_mult = 1.00`，关系层中性）：

| 口径 | C=2 | C=3 | C=4 | 形状 |
|---|---|---|---|---|
| `Cohesion` | 1.0340 | 0.9400 | 0.8460 | **严格递减** |
| `chance`（人均） | 0.7445 | 0.6768 | 0.6091 | **严格递减** |
| `E[material]`（总量） | **19.58** | **21.61** | **23.14** | **严格递增** |
| `E[material] / C`（每人力） | **9.79** | **7.20** | **5.78** | **严格递减** |

**两组指标方向相反，这就是折衷本身。**

| 村庄处境 | 该派几个 | 为什么 |
|---|---|---|
| **工地正缺人**（人手紧张） | **2 人** | 每人力产出最高。少占一个人，工地就多一个人干 11 小时 |
| **工地在赶工、这一趟要压产量** | **3 人** | 折衷档。总量比 2 人高 10%，每人力只比 2 人低 26% |
| **闲人很多、只冲这一趟** | **4 人** | 总量最高，但**每个人带回来的都更少** |

**折衷点的具体数字**：第 4 个人让总量多 **`23.14 − 21.61 = 1.53` 材料**，
代价是**多占一个村民 11 个村庄小时**。所以判据是可算的：

```
第 4 人值得派 ⟺ 1.53 材料 > 那一个村民在工地 11 小时内的边际产出
```

> **这个判据的右半边不属于本文件。** 工地的边际产出由 `village-building.md` 定义，
> 本文件**不去引用一个本文档没有定义过的数**。见 Open Questions Q8——
> **这是本设计唯一的外部依赖，且它决定甜点落在 2 / 3 / 4 中的哪一档。**
> 在它落地前，**默认甜点是 3 人**（`Clarity(3) = 1.00`，中性，不奖励也不惩罚）。

### F2 — 性格摩擦逐条相乘（旧表「命中即定」的陷阱已消除）

旧表的一个大坑是「2 傲 + 2 莽 = ×0.55 而不是 ×0.55 × ×1.10」——
**它让调表的人把 4 人队的期望算高 2–3 倍**，而且没有任何规则说明该按哪个口径算。
新表没有这个坑：**5 条乘数全部命中就全部相乘**，规则与代码是同一件事。

```
2 傲 + 2 莽：  Friction = 0.88 × 0.96 × 1.06 = 0.8955
               Cohesion = 0.90 × 0.8955      = 0.8059      ← F1b 第 24 行
2 傲 + 2 贪：  Friction = 0.88 × 0.97 × 0.94 = 0.8024
               Cohesion = 0.90 × 0.8024      = 0.7221      ← F1b 第 33 行（全场最低）
```

### F3 — 系数如何进入产出

```
base_chance(h)  = 0.52 + (h.Power + h.Speed) / 300
chance(h)       = min(0.95, base_chance(h) × Cohesion × person_mult(h)
                                 × (1 + bond_uplift(h) + freshness_penalty(h)))

person_mult:  莽 1.15 | 傲 1.10 | 贪 1.00

going  = 出发的成员中，没有撂挑子的
good   = going 中 chance 判定通过的人
if good 为空 → good = going[0]        // R10，永不空手
if going 为空 → going = crew[0]       // 全员撂挑子时仍派出第一个人

material = job.Amt + Σ_{h ∈ good} floor(h.Power / 8)
```

> **`job.Amt` 是按 good 人数分摊的，不是每人一份。**
> 这条是 F1c 那个「总量单调递增」结论的支点，也是为什么甜点只能落在人均口径上。

| 变量 | 类型 | 范围 | 来源 |
|---|---|---|---|
| `h.Power` / `h.Speed` | int | 10 – 49 各 | HeroFactory |
| `base_chance` | float | 0.587 – 0.847 | 计算 |
| `chance` 截断 | float | ≤ 0.95 | 硬上限 |
| `job.Amt` | int | 14 – 38 | `Jobs` 表 |
| 单人附加产出 | int | 1 – 6 | `Power / 8` |

### F6 — 关系层：按人上浮与陈旧扣减（**不进队表**）

```
bond_uplift(h)      = min(0.12, 0.06 × |{ x ∈ squad : BondKind(h, x) ∈ {搭子, 师徒} }|)
freshness_penalty(h) = -min(0.12, 0.03 × max(0, max_{x ∈ squad} BondFreshness(h, x) - 3))
```

| 变量 | 类型 | 范围 | 当前值 | 说明 |
|---|---|---|---|---|
| `bond_uplift(h)` | float | 0 – +0.12 | 每档 0.06，上限 0.12 | 与队内熟人的人数 |
| `freshness_penalty(h)` | float | −0.12 – 0 | 每步 0.03，宽限 3 天，上限 −0.12 | 久未同队 |
| `FRESH_GRACE` | int | 0 – 7 | **3 天** | 之内不扣 |

**三个硬边界（缺一不可）**：
1. `Bond` 不存在时 `freshness_penalty = 0`（`relations.md` E7 不建零值边）。
2. `Cohesion` 上界已被 F1b 锁在 1.1660，`1 + 0.12` 使实际 `chance` 上界为
   `0.847 × 1.1660 × 1.15 × 1.12 = 1.271` → **必然触及 0.95 封顶**。
   **上浮在强队上是无效的**——它只在弱队上起作用。这是刻意的（见 F5）。
3. 有仇的人走不到这里（R6 已拦），**`chance` 的计算路径里不允许出现任何关系字段的惩罚项**
   ——`freshness_penalty` 是唯一的负项，且它只由「久未同队」触发，**与仇无关**。

### F4 — 例算（三档，核对整条链）

队伍：全贪，Power 均为 30、Speed 均为 30。任务 `job.Amt = 14`。关系层中性。

```
base_chance = 0.52 + (30+30)/300 = 0.72

档 A（C=2）
  Clarity 1.10, tan≥2 → ×0.94  →  Cohesion = 1.0340
  chance = 0.72 × 1.0340 × 1.00 = 0.7445（未触及 0.95）
  E[good] = 1.4890
  E[material] = 14 + 1.4890 × 3.75 ≈ 19.58

档 B（C=3）
  Clarity 1.00, tan≥2 → ×0.94  →  Cohesion = 0.9400
  chance = 0.72 × 0.9400 × 1.00 = 0.6768
  E[good] = 2.0304
  E[material] = 14 + 2.0304 × 3.75 ≈ 21.61

档 C（C=4）
  Clarity 0.90, tan≥2 → ×0.94  →  Cohesion = 0.8460
  chance = 0.72 × 0.8460 × 1.00 = 0.6091
  E[good] = 2.4365
  E[material] = 14 + 2.4365 × 3.75 ≈ 23.14
```

**读法**：这三档**没有任何一档在另一个维度上被支配**——
总量 `19.58 < 21.61 < 23.14`（递增），每人力 `9.79 > 7.20 > 5.78`（递减）。
**第四个人不是一个免费的开关了**：他让你多拿 1.53 材料，
代价是全队每个人的成功率都掉一截（人均 −18%）。
⚠️ **旧版这里写的是「档 B 比档 A 多 ~13% 材料且没有任何代价」——那句话随裁定 ⑤ 一并作废。**

### F5 — 0.95 截断在新表下的行为（**结论反过来了**）

`chance` 在 0.95 封顶。`Power + Speed` 在 10–49 之间均匀分布（上限 98）。
把 0.95 反解成触发 `Power + Speed` 的门槛（`base_chance = 0.52 + PS/300`）：

| 性格倍率 | `Cohesion` | 对应情形 | 触顶所需 `PS` | 可达？ |
|---|---|---|---|---|
| 莽 1.15 | 1.1660 | 2 人全莽 | **≥ 57** | 是，约一半 |
| 莽 1.15 | 1.0600 | 3 人全莽 | ≥ 78 | 是，约一成 |
| 莽 1.15 | 0.9540 | 4 人全莽 | ≥ 104 | **不可能**（上限 98） |
| 傲 1.10 | 1.1660 | 2 人全莽阵容里的傲 | ≥ 66 | 是 |
| 贪 1.00 | 1.0340 | 2 人全贪 | ≥ 120 | **不可能** |
| 贪 1.00 | 0.9400 | 3 人全贪 | ≥ 146 | **不可能** |
| 贪 1.00 | 0.8460 | 4 人全贪 | ≥ 179 | **不可能** |

> **一条新发现的性质，值得写下来：人数惩罚不会被截断吃掉。**
> 4 人档的系数（≤ 0.954）对任何人**都不触顶**，
> 所以 **`Clarity(4) = 0.90` 这个扣减是老老实实生效的**，不是被 0.95 掩掉的假惩罚。
>
> 反过来，**C = 2 对强莽会触顶**——这意味着「两个人」的收益在强队上会被削平。
> 这不是 bug，它让「派几个人」这个决策**对强者和弱者给出不同的最优解**，
> 是一件好事。代价是面板可能写着「配合 ×1.17」而实际不生效——见 Q5。

## Edge Cases

| 场景 | 实际行为 | 理由 |
|---|---|---|
| 队伍空 / 全员离线 / 全员生病 | ×1.00，报「没人在村里」，任务按钮禁用 | R2 |
| 队伍 4 人，此刻 3 人离线 | 按那 1 个在场的人算（×1.00），不是按 4 人算 | R2。在场的人才是队伍 |
| ⚠️ **仇人在队但本人不在场（离线 / 病倒）** | **不构成拦截。** 合法性按 **Ready 成员**判定，他没上车 | R2 与 R6 各管一层 |

## 已定性缺陷：人数维度是退化的 —— **已修复（2026-10-17，裁定 ⑤）**

> **本节保留原文作为缺陷记录。** 判定与证明**一个字都没改**，
> 因为它当时是对的；错的是当时的设计。末尾附修复结果。

**原判定：这是缺陷，不是取舍。** 给出可证的理由，而不是观感。

**原缺陷描述**：`SquadMax = 4`，而人数档在 **C ≥ 3 就已经到顶（×1.15）**。
即：3 人和 4 人拿同一个系数。

**为什么第 4 个人永远不亏**（可证，不是估计）：

1. **材料不会重复领。** `job.Amt` 是按 `good` 人数**分摊**的（F3）。
   队伍从 3 人变 4 人，任务给的那份材料总量不变。
2. **因此第 4 人的边际产出 = `floor(Power/8) × P(他成事)` ≥ 0，恒不为负。**
3. **系数也不变。** 3 人 ×1.15，4 人还是 ×1.15。
4. **合起来：相容的 4 人队 ⊃ 相容的 3 人队，且严格更优。**

**结论**：最优策略唯一且静态——找到四个互不冲突的人，然后一直用他们。
这与开发者原话「配队不只是『选四个人』」直接矛盾。

### 修复结果（裁定 ⑤：「加成递减，人多反而乱」）

| 缺陷的哪一条 | 现状 |
|---|---|
| 「3 人与 4 人同档」 | **已消除。** `ClarityOf` = `[1.00, 1.00, 1.10, 1.00, 0.90]`，四个档全不同 |
| 「第 4 人边际产出恒 ≥ 0」 | **部分保留，且这是真的。** 材料的总量口径上 4 人恒优（§ F1c 证明这是 `job.Amt` 分摊的必然结果，**不是设计能改掉的**）。**新增了「每人力」口径，在其上 4 人严格劣于 3 人与 2 人** |
| 「最优策略唯一且静态」 | **已消除。** 人数由村庄缺不缺人手决定（§ F1c 三档表）；固定铁队被 `freshness_penalty` 反固化 |
| 死分支 ×1.15 / ×1.05 | **已消除。** 新表 35 组穷举无死分支（§ F1b） |

**采用了哪条修复方向**：原文档列了 A / B / C 三条。**采用的是 C（A + B 同时做）的变体**——
系数同时看构成（R5 摩擦）与人数（R4 清晰度），**外加第三条来自 `relations.md` 的维度**
（关系层按人上浮与陈旧扣减，见 R6-c）。
原方向 B 说「给小队伍人均加成，4 人 ×1.00/人」；本实现取了更保守的
`Clarity(4) = 0.90` 而不是 1.00——因为 1.00 等于「4 人不罚不奖」，人数维度仍是平的。

**仍然开放的部分**：「甜点到底落在 2 / 3 / 4 的哪一档」取决于
**一个村民在工地 11 小时内的边际产出**，那个数属于 `village-building.md`。
本文件不去引用没有定义过的数。见 Q8。**在它落地前默认甜点是 3 人。**

**环形依赖的断开方式**（承接 systems-index 的约定）：
配队**只读**性格的**系数**（`Personality` 字符串与三项数值），

这条链在数据上是单向的：性格系统与关系系统都不知道谁在队里。

## Game Feel

### Feel Reference

> 像《太吾绘卷》的**组队检阅**：你把几个人拖进一支队伍，面板立刻告诉你
> 他们凑在一起会出什么事——而且这个「会出什么事」是**人话**，不是一堆图标。
> 借用的是「**合不合适，扫一眼就知道**」的读法。
> **不是**《暗黑破坏神》那种纯数值 build 检阅——那套里人格只是加点来源。

### Input Responsiveness

| 操作 | 最大输入到反馈延迟 | 备注 |
|---|---|---|
| 加入 / 移出队伍 | ≤ 50ms（3 帧） | 队伍面板与系数必须同帧刷新，不等下次 tick |
| 名单行悬停 | ≤ 100ms | 显示该人的性格与是否与队内某人结仇 |
| 系数变化 | 与操作同帧 | 玩家改完队必须**立刻**看见后果，不能等到派出 |

### Feel Acceptance Criteria

- [ ] 玩家在不看说明的情况下，能说出「这支队为什么不合适」
- [ ] 玩家把一个人移出队伍后，**同一帧**看见系数变了
- [ ] 杂谈里出现「两个傲谁也不服谁」时，玩家不觉得突兀——他记得自己派的是谁

      把 `Churn(A→B)` 降到 `GRUDGE_AT = 40` **以下**（模拟若干次搭手），断言：
      ① 同一支队**立即变为合法**且可发布；
      ② 系数与「A、B 从未结仇」的同一支队**逐位相等**（不是「差不多」，是 `==`）——
      **不残留任何惩罚**；
      ③ 降到 39 时合法、降到 40 时**恰好不合法**（边界值测试，对应
      `relations.md` AC-D1 的 39/40/41）。

### 退化（这一组是本次重构的守门测试）

- [ ] **D-1 穷举表可复现。** 对全部 35 组（3 性格多重组合 × 人数 0–4）
      重算 `CohesionOf()`，断言与 **F1b 表**逐行相等；
      断言**表中不存在任何不可达值**（死分支检测——见下）。

- [ ] **D-2 死分支检测（可机检，核心）。** 断言 `ClarityOf` 的 5 个输出
      **与 `FrictionOf` 的 6 个输出全部被至少一个组合命中**。
      ⚠️ **旧表有两档死分支（`×1.15` 与 `×1.05`）——本断言是它们消失的证明。**
      特别地断言 `ClarityOf(3)` 与 `ClarityOf(4)` **不相等**
      （旧表里 `C >= 3` 一档同时覆盖两者）。

- [ ] **D-3 甜点表可复现。** 重算 § F1c 的三档表，断言：
      ① `E[material]` 随 `C` **严格递增**（19.58 < 21.61 < 23.14）；
      ② `E[material] / C` 随 `C` **严格递减**（9.79 > 7.20 > 5.78）。
      **这两条同时成立 = 存在真实折衷**——任何一个不成立都意味着人数维度又塌了。
      **这条取代旧版 D-1**（旧版要求「存在 3 人严格优于 4 人」，§ F1c 已证明
      那个断言在材料总量口径上**永远不可能成立**，写它进 AC 是错的）。

- [ ] **D-4 记录最优策略。** 用固定种子跑 1000 次派出，统计队伍人数分布。
      断言**不出现 100% 为 4 人**。若成立，说明 `ClarityOf` 被调平了，退化回归。

      上浮只能出现在**该成员自己的 `chance`** 上（R6-c）。

### 体验

- [ ] **E-1 面板数字不撒谎。** 对 `Power + Speed ≥ 60` 的莽，「配合 ×1.17」
      在他的实际成功率上必须产生**可测量**的差异（用固定 RNG 序列跑 10000 次，
      断言 ×1.1660 与 ×1.00 的成事率之差 > 3 个百分点）。若为 0，
      说明 0.95 截断吃掉了它——见 F5 与 Q5。
- [ ] **E-2 「他们有过节」读得懂（裁定 ⑬ 的验收）。** 3 名未读过本文档的试玩者，
      在被问到「这支队为什么发不出去」时，5 人中至少 4 人能答出
      「**他们有过节**」，且能指出是哪两个人。
      ⚠️ 旧版这条问的是「这支队怎么了」（针对 ×0.50 的折扣），
      **现在问的是「为什么发不出去」**（针对硬禁止）——问题改了，答案要求更高了。
- [ ] **E-3 弃用词检查。** 对全部玩家可见文案（各档说法 + 面板字段 +
      本系统写入的杂谈句）执行关键词扫描，断言 **零命中**：
      `成功`、`失败`、`获得`、`消耗`、`属性`、`奖励`。
- [ ] **E-4 自主对照读得出来。** 5 名试玩者中至少 4 人能区分
      「我派出去的」和「他自己去干的」两种行动，且不认为后者需要玩家操作。
- [ ] **E-5 人数成为真决策（裁定 ⑤ 的体验验收）。** 8 名试玩者中至少 6 人
      在被问到「你为什么这次只带两个人」时，能说出
      「人多手乱 / 少占一个人在工地」这类理由，**而不是**「忘了」。
      ⚠️ **若玩家从不因为人数而调整队伍，裁定 ⑤ 在体验层是失败的**——
      数值上存在折衷不等于玩家感受到了它。
