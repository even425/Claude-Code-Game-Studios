## 二、详细规则

### 2.1 奖励触发条件

1. 仅当副本成功完成并进入成功结算流程时，才允许生成和发放副本战利品。
2. 副本失败时，不发放副本战利品。
3. 副本成功与否以现有副本结算结果为准，不另行引入第二套成功判定逻辑。
4. 同一次副本结算不得因为重复调用而重复发放战利品。
5. 奖励发放应与副本结算的幂等机制保持一致；如果现有代码尚不具备足够保障，应在实施前明确补齐方案。

> **实施落点：** 复用 `SettlementKey(RunId, BattleResultId)` 作为幂等键；`Settlement._applied` 与存档 `AppliedSettlementKeys` 共同保证「同一次副本只发一次」，读档后重放被拒。**未新建第二套幂等状态。**

### 2.2 奖励资格

1. 奖励资格限定为实际参加本次副本的队伍成员。
2. 不参加本次副本的英雄不参与本次奖励分配。
3. 奖励资格必须依据本次副本的实际参战记录确定，而不是直接读取当前队伍名单。
4. 如果副本结算期间队伍发生变化，应优先使用本次副本开始或执行过程中保存的参战名单，具体快照时机需要结合现有代码确认。
5. 如果无法取得可靠的参战名单，不应默认为所有村庄英雄均有资格领取奖励。

> **实施落点：** 资格取自 `DungeonRun.Participants`（副本实例的参战快照），**不是**当前队伍。空名单 → 不发放并记录结算异常（E01 / E02）。

### 2.3 全队平分

1. 副本成功后，将本次生成的战利品分配给符合资格的参战英雄。
2. 每位符合资格的英雄都应获得平等的奖励分配机会。
3. 可整除的物品数量按相同数量分配。
4. 无法平均分配的剩余物品，按 R01-D03 的选择随机分配给符合资格的队员。
5. 货币奖励、可堆叠物品和不可拆分的装备是否采用完全相同的分配算法，仍需确认；本草案不擅自规定所有奖励类型必须共用一种算法。

> **实施落点：** `LootSplit.Split`（`src/Domain/Settlement/LootSplit.cs`）——纯函数，均分部分 `quantity / n`，余数部分 `quantity % n`。
> **第 5 条已决（Q2）：** 本轮**只发物品**；金币与材料走现有村庄资源结算，不参与平分。**装备 / 不可拆分物品**本轮未做 —— 当前领域模型无此类型，需扩 `ItemDefinition`，另开任务（E06）。

### 2.4 剩余物品的随机分配

1. 随机分配对象只能来自符合资格的参战英雄。
2. 随机分配不得把物品分给未参战英雄。
3. 随机选择应复用项目现有的 SeededRandom 机制，以保证测试可重复。
4. 随机结果必须在本次奖励结算中确定，并随英雄背包状态保存。
5. 如果剩余物品有多个，应明确随机过程的执行顺序及随机结果是否允许同一英雄连续获得多个剩余物品；这属于实现细节与规则细化的交界项，需在开发前确定。

> **实施落点：**
> - **第 3 条**：`DecisionFlow.SeededRandom`，种子由 `LootSplit.DeriveSeed(副本实例标识)` 派生（**FNV-1a**，不用 `string.GetHashCode()` —— 后者每进程都不同，会让「读档重放得到同样的结果」当场失效）。
> - **第 4 条**：分配结果进英雄背包（已落盘），幂等进 `AppliedSettlementKeys`（已落盘）。
> - **第 5 条已决（D-047-a / D-047-b）：** **逐件独立抽样**（不是轮流发 —— 轮流发是确定性的，那不是 D03 说的随机）；同一英雄**可能**连拿多件余数。**随机调用次数 = 余数份数**（可整除时一次都不抽）。

### 2.5 个人所有权与物品流转

1. 不设置村庄公共奖励池。
2. 奖励发放完成后，物品归获得该物品的个人英雄所有。
3. 物品进入英雄背包后，按照现有摊位和交易规则决定是否能够出售或转移。
4. 成功交易后，物品所有权由卖家转移给买家。
5. 交易失败时，不得出现物品已经转移、但货币未正确结算等部分提交状态。
6. 本规则不意味着英雄必须出售副本战利品；英雄是否保留、使用或出售物品，由现有物品系统及后续设计决定。

> **实施落点：** 物品经 `SettlementDelta.ItemGrants` 进入**同一次结算、同一把幂等锁**（不变量 I15）。写入协议为 `IItemGrantWriter` 两阶段：`CanGrant`（预检，不改状态）→ `Grant`（一次提交）。背包不可变 ⇒ 提交阶段无失败路径，杜绝「村庄拿到了、英雄没拿到」的半笔账。

### 2.6 副本失败

1. 副本失败时，不发放副本战利品。
2. 不得因为重复进入失败结算分支而发放奖励。
3. 失败后已有的关系变化、战斗记录或其他既有结算行为是否保留，继续遵循现有规则，不由本任务擅自修改。
4. 本规则只限制副本战利品，不自动否定未来可能单独设计的任务补偿、参与奖励或其他奖励机制。

> **实施落点：** `Main.ComputeLoot` 在 `!outcome.Succeeded` 时直接返回空分配；失败局的村庄材料亦不变（`D-010 Q1`）。

## 三、待确认的边界情况

以下问题目前没有足够依据认定为已确认规则，实施前需要开发者决定或批准默认行为。

| 编号 | 场景 | 建议处理方向 | 状态 |
|---|---|---|---|
| E01 | 副本成功，但没有有效参战成员名单 | 不发放奖励并记录明确的结算异常，避免奖励丢失原因不可追踪 | 【已实施】 |
| E02 | 副本成功，但参战名单为空 | 拒绝生成个人奖励，记录异常 | 【已实施】 |
| E03 | 副本成功，但部分英雄在结算前离开队伍 | 以本次副本实际参战快照为准，而不是当前队伍 | 【已实施】 |
| E04 | 某位符合资格的英雄在奖励发放时不存在或状态无效 | 明确是中止整次结算还是跳过该英雄；不得静默吞掉奖励 | 【已决 · Q3：整笔回滚 + 记录异常】 |
| E05 | 战利品数量少于参战人数 | 按逐件随机分配规则处理；部分英雄可能无法获得该种物品 | 【已实施】 |
| E06 | 装备或其他不可拆分物品无法均分 | 按物品实例逐件分配，避免拆分非法物品 | 【已决：本轮不做，领域模型无此类型，另开任务】 |
| E07 | 随机分配过程中发生异常 | 应保证奖励结算不出现重复发放或部分提交 | 【已实施】 |
| E08 | 相同副本结算请求重复执行 | 使用稳定的副本业务标识实现幂等 | 【已实施】 |
| E09 | 英雄背包容量不足或库存约束拒绝收货 | 需要明确是回滚整次奖励、重新分配还是保留待领取奖励 | 【已决 · Q3：整次回滚，幂等键不落，可重试】 |
| E10 | 副本成功后，奖励已提交但程序立即退出 | 应保证恢复后不会再次发放相同奖励 | 【已实施】 |
| E11 | 不同类型奖励同时存在 | 需要确认货币、可堆叠物品、装备等各自的分配规则 | 【已决 · Q2：只发物品，货币/材料走村庄资源结算】 |
| E12 | 参战英雄人数为一人 | 全部奖励归该唯一符合资格的英雄 | 【已实施】 |

特别说明：E05 中的“少于参战人数”指某一种物品的数量不足以让每名参战英雄都获得一件，并不意味着副本整体失败或不产生奖励。

> **已知限制：** 正式背包容量当前为「无限」（`Inventory.Capacity = 0`），所以 E09 在正式游戏里今天不会真的触发。规则已钉死并有单测（用有容量上限的背包夹具验证整次回滚），将来给背包加上限时无需改规则。

## 四、对现有代码的影响

实施前应基于当前仓库再次核对文件与方法，以下为预计影响范围，不代表已经确认这些文件中一定存在对应的可复用接口。

> **本节已按 M0 审计结论回填**（`16` §1）：下列各项**均已落地**，并额外修掉 4 处审计中发现的真实缺陷。

### 4.1 副本结算

预期涉及：
- `Main.cs` 中的副本结算入口及成功分支。
- 现有副本执行结果、队伍信息和副本业务标识。
- 现有关系合作事件的触发顺序。

修改目标：
- 在现有成功结算路径中接入战利品生成和分配。
- 失败分支不发放战利品。
- 避免新增独立的副本成功判定逻辑。
- 不破坏现有关系增长、事件记录和奖励结算行为。

> **落点：** `Main.ComputeLoot` + `Main.ResolveDungeon`；战利品经 `Settlement.Apply(key, heroesWon, rewardsOverride)` **随本次调用**带入（不放会话级共享字段，否则与副本无关的结算可能把它再发一遍）。`SquadBonded` 关系加成与既有杂谈均未变。

### 4.2 物品与背包领域

预期涉及：
- `Items` 领域中的 `ItemDefinition`、`Inventory`、`Wallet`。
- 现有背包添加物品及库存约束方法。
- 必要时新增独立的战利品分配领域服务。

修改目标：
- 复用已有物品定义和库存约束。
- 确保分配结果能够落入英雄个人背包。
- 不能绕过领域模型直接修改背包内部状态。
- 在规则确认前，不擅自加入稀有度、掉落权重或新的价格系统。

> **落点：** 新增 `src/Domain/Settlement/LootSplit.cs`（分配纯逻辑）、`src/Domain/Settlement/ILootProvider.cs`（内容注入点）；`src/Application/ItemGrantService.cs` 实现 `IItemGrantWriter`（批量发放，预检+提交）。背包经 `Inventory.TryAdd` 产出新对象再整体换上，不改内部状态。**未新增任何价格、稀有度或掉落权重。**

### 4.3 随机数

预期涉及：
- 现有 `SeededRandom` 实现。
- 现有随机数注入方式与测试辅助工具。

修改目标：
- 使用可注入、可复现的随机来源。
- 固定随机种子时，测试应能够验证剩余物品分配结果。
- 不使用无法控制的独立随机调用绕过项目既有约束。

> **落点：** 复用 `DecisionFlow.SeededRandom`；种子由 `LootSplit.DeriveSeed`（FNV-1a）从**副本实例标识**派生 —— 走**独立子流**，不插队进战斗与日常共用的全局随机源。

### 4.4 存档与幂等

预期涉及：
- 现有 `SaveGame` 模型与存档版本。
- 副本结算业务标识和奖励发放状态。
- 现有存档校验、恢复和原子写入逻辑。

修改目标：
- 同一次副本奖励只能成功发放一次。
- 保存、退出和重新加载不能导致重复发放。
- 只有在确实需要新增持久化字段时才调整存档版本，并遵循现有兼容策略。
- 不为奖励发放另建一套与现有幂等系统相互冲突的状态记录。

> **落点：** 复用 `SettlementKey`；战利品结果落在**已落盘**的英雄背包，幂等落在**已落盘**的 `AppliedSettlementKeys`。**未新增持久化字段，存档版本保持 0.4。**

### 4.5 交易和摊位

预计主要是复用现有功能，不应在 R-01 中大幅重写：
- `StallService` 的摆摊与购买。
- `Trade` 的交易结算。
- 现有摊位库存、货币与物品所有权变更。

R-01 的交付重点是让物品能够真实进入英雄背包，而不是顺便完成正式商店 UI、定价体系或完整自主经济行为。这些仍应按后续任务的依赖顺序推进。

> **落点：** 未改 `StallService` / `Trade`。真机已验：战利品开摊 → 他人购买成交（买家背包 +1、金 −5）。

### 4.6 架构约束

1. Domain 不得引用 Godot。
2. 优先复用现有 Application、Domain 和存档结构。
3. 不得为了 R-01 重构无关模块。
4. 不得把尚未确认的奖励规则写死为不可调整的技术约束。
5. 修改前记录当前 Git 状态，完成后提供文件清单、测试结果和实际运行验证证据。

> **落点：** `LootSplit` / `ILootProvider` / `ItemGrant` 全在 `src/Domain/`，不引用 Godot（`DomainLayerPurityTests` 守门）。
