## 1. M0 · 现状审计（实测）

### 1.1 能直接复用的

| 能力 | 现状 |
|---|---|
| 摊位目录 | `StallService.Snapshot()` —— 摊主 / 物品 / 库存 / 单价 / 状态，**字段齐全** |
| 购买结算 | `StallService.TryBuy(seller, buyer, itemId, qty, simTime, requestId)` —— **唯一结算入口**，11 种 `BuyOutcome`，I15 四步提交 |

### 1.2 两个绕不开的现状约束

1. **项目里没有「玩家化身」。** 玩家是村庄管理者：6 个按钮都是村庄级操作，
   摆摊按钮的逻辑是「自动挑第一个在场 + 空闲 + 有可售物品的英雄」。
   → **「谁买」这件事在 R-02 之前没有答案**，这是本轮第一个必须拍板的问题。
2. **摊位不画在地图上。** `VillageView` 没有任何摊位绘制代码 —— 摊位是纯数据。
   → 「摊位库存面板」只能是一张列表；R-04 天然随它一起完成。

### 1.3 空间账

- 左栏已排满：花名册 300 + 队伍 + 6 按钮 + 间隔 = 584，栏高 656（`UiLayout`）→ 加第 7 个按钮后 620，**仍装得下**。
- 右栏：杂谈 400 + 关系 68 = 468，栏高 656，剩约 188px —— 塞得下一个列表，但**要挤杂谈**（主体）或砍关系区。
- 结论：**弹窗**。零布局成本，且与既有摆摊弹窗同构，玩家的心智模型连贯。

## 3. 分层：三层，各管各的

```
Presentation/StallMarketText.cs    全部文案（纯函数，逐字可测）
Presentation/StallMarketPanel.cs   Godot 界面（两跳交互、列表、回执）
Application/Stall/StallMarket.cs   纯逻辑：MaxAffordable / BagRoom / Candidates
Application/Stall/StallMarketService.cs  应用服务：谁买得到 / 买多少 / 成交
Domain/Stall/StallService.cs       唯一结算入口（TryBuy）—— 本轮未新增第二条路径
```

### 3.1 为什么要有 `StallMarketService`

面板与真机自检需要的是**同一件事**：「这个摊，谁买得到、最多买几份、买下来」。
两边各写一份，就会出现「界面说能买 19 份、点下去只买到 12 份」这种对不上的局面。
所以规则只在一处，界面与自检都调它。

> 实现过程中面板里一度写了两遍候选池构造（`RefreshBuyers` 与 `CurrentOffers`），
> 抽到服务层后这个重复自然消失 —— **重复的候选池就是"两套规则"的前兆**。

### 3.2 「尽可能多」的口径

```
MaxAffordable = min(摊位库存, 余额 ÷ 单价, 背包余量)
```

三者取小，少一样就会出现「钱花光了但没买够」或「买爆背包」这种半截结果。

**单价为 0 时不看钱** —— 白送摊（单价 0 是合法值，见 `Stall` 构造期防线）下
「余额 ÷ 单价」会除以 0。实现里只在 `unitPrice > 0` 时才拿钱设上限。

**背包余量不能靠 `TryAdd` 试算** —— `Inventory` 不可变，`TryAdd` 要么返新对象要么返 null，
拿它当尺子只能试出「装不装得下 1 份」，试不出「还能装 7 份」。
余量 = `Capacity - Count(item)`（容量 0 = 无限，返回 `long.MaxValue`）。

### 3.3 候选名单的两条纪律

1. **摊主本人不在名单里。** `TryBuy` 会以 `SameHero` 拒绝，但那是**成交阶段**的拒绝 ——
   面板里摆一个「点了必然失败」的选项，等于骗玩家。所以先滤掉。
2. **买得起 0 份的不列。** 与其把「这个人买不起」列出来让玩家点一下再失败，
   不如一开始就不列 —— **名单里出现的每一个人都是点了就能买成的**。

名单按显示名排序（Ordinal）—— 稳定、可测、玩家扫读时顺序不跳。

### 3.4 「在场」的门槛

随队外出（`Away`）、在工地（`ToSite`）的人买不了。
这与自主购物的判据**完全一致**（`HeroBehaviorService` 的「不在场或正在忙」）——
两边口径不一样会让玩家看到「他能买你买不了」的怪事。

## 4. 反馈

| 情形 | 去处 | 理由 |
|---|---|---|
| 成交 | **`TradeCompleted` 事件** → 杂谈 | 真的改了钱和货（`hero.wallet` / `hero.bag`），属于基线 §7.2「该被记下来的事」 |
| 成交（手动） | **与自主购物共用同一条事件** | 两者改的是同一样东西，不该有两种记法 —— 玩家不必分辨这笔是英雄自己买的还是他点的 |
| 失败 | **面板内当场回执** | 杂谈是「村里发生了什么」，不是「玩家每次点击的回执」 |

> 这与 R-07 **不冲突**：R-07 说的是**自主购物**的「未成提示」（37 人/天会刷屏）。
> 手动购买是玩家操作，失败必须当场看得见。

失败文案（`StallMarketText.Rejected`）对 `BuyOutcome` **全覆盖** ——
`Bought` 也在表里（"买成了。"）。理由与 `ShoppingFeedback` 相同：
任何一次调用都不该掉进什么都不说的分支。

```
├── 标题    「摊位（2）」/「摊位（2）· 已选一个」

```

**售罄的摊位也占一行**（标「（已售罄）」）—— 玩家该知道「这个摊卖完了」，
而不是发现它凭空消失。已收摊（`Closed`）的不占位置。

**「可买几份」写进行里** —— 只写「星航 · 金100」的话，玩家还得在脑子里做除法。

### 5.1 截图暴露的两个真问题（已修）

第一版面板放在 `x = 860`、宽 380 → 盖住右栏（`x ≥ 992`），
而 Godot 的 `Panel` 默认样式是**半透明**的 —— 底下的杂谈文字透了上来，
两边的字叠成一片，谁也读不清。

| 问题 | 修法 |
|---|---|
| 面板压住村庄杂谈 | 移到 `x = 300`（地图区偏左），避开右栏 |
| 背景半透明，杂谈透上来 | 给 `Panel` 覆盖一个不透明 `StyleBoxFlat`（`#171d27` + 1px 边框） |
| `ItemList` 默认浅色底，在深色面板上是两块灰砖 | 覆盖 `panel` 为 `StyleBoxEmpty`，只留选中高亮 |
| 列表 `ExpandFill` 把中间撑出大片空白 | 去掉 `ExpandFill`，固定 190 / 150，面板高度收到 470 |

## 6. 顺带补掉的一处真实缺口

`StallService.BuyStallResult` 原先**只带金额、不带份数**。

份数只能拿「金额 ÷ 单价」反推 —— 而**单价可以是 0**（白送摊，合法），
除法会炸；就算不炸，那也是"从结果里猜一个数"。
已补 `Quantity` 字段：**成交结果自己带份数**，谁都不用猜。

（`BuyStallResult` 此前只被 `StallService` 构造，无其它构造点，补字段零风险。）

---

## 7. 手动购买的幂等：传空 requestId

`TryBuy` 的 `requestId` 非空时会做**业务幂等**（同一键只成交一次）。
手动购买**传空串** —— 玩家每点一次就是一次独立交易，不存在"重放"要挡。
真实需要幂等的是自动流程（自主购物、结算回放），那条路本来就走 `AppliedPurchaseKeys`。

## 9. 真机自检：`--market`

```
godot --headless --path . --quit-after 180 -- --market
```

**刻意经过面板**（`Open()` → `SelectStall(0)` → `SelectBuyer(n)`），
而不是直接调服务 —— 「玩家点下去会发生什么」正是本轮要验的东西。
面板内部最终调的就是 `StallMarketService.BuyAsMuchAsPossible` → `StallService.TryBuy`。

`SelectStall` / `SelectBuyer` 是面板上**仅供自检**的口子：它们走的是与真的点 `ItemList`
完全相同的那条路（与 `--click` 验花名册同一路数）。
