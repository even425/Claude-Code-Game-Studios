## 0. 怎么读这份文档

**【已确认】** 标记沿用基线 §0：**没有标记的句子无效。**

| 标记 | 含义 | 可以拿它做什么 |

| **【已确认】** | 来自基线或已确认技术约束 | 可以直接实现 |

### 0.1 本文的三条硬约束

**【已确认】** **本文不含任何具体数值。** 伤害、命中、掉落、经济、时间倍率、行动频率、疲劳曲线一律不写。
**【建议】** 因此本文**没有「公式」章节**——公式必须有变量表与取值范围，而第一阶段这些取值全部未定，写出来的只能是被伪装成规则的占位符。
**【建议】** 需要数值的地方，本文一律写成**【待定】+ 指向 `07` 的 T 编号**，由 `03` / `04` 在规则确定后补公式，而不是由本文先占一个位。

### 0.2 本文不做什么

**【已确认】** 本文**不设计**以下内容，且这些不是遗漏：

| 不做的事 | 依据 |
|---|---|
| 疲劳机制的任何字段、曲线、恢复途径 | 基线 §4.4 性质未定；`07` T-003「**不得实现**」 |
| 召唤卡池 / 稀有度 / 概率 / 保底 / 重复召唤处理 | 基线 §10.6 全部待定；`07` T-005 |
| 剧情、恋爱、家族、世代系统 | 基线 §17 禁止事项 |
| 摆摊经济的定价与费率响应曲线 | 基线 §5.4–§5.6；`07` T-006 |
| 本土居民与本土剧情的完整实现 | 开发计划 §六 |
| 建筑功能、消耗、依赖关系 | 基线 §12.3「不得仅凭建筑名称自行指定功能」 |

**【建议】** 摆摊、本土、大事件在本文中只以**一句话**出现在「后续阶段」，不作为任何一步的组成部分。

### 0.3 「后续阶段」一句话交代（不参与第一阶段验收）

**【建议】** 摆摊经济、本土居民与本土剧情、世界大事件、完整城市成长、完整召唤机制在基线中都是核心系统；本文**只在流程的 P4 与 P5 之间留一个扩展挂载点**，不实现、不验收、不写成第一阶段的步骤。

## 1. 流程总览

### 1.1 十个步骤

**【建议】** 最小可玩闭环 = 十个步骤的顺序执行：

```text
P0 启动与载入
      ↓
P1 观察村庄 ────────────────────┐
      ↓                          │
P2 建造与发展村庄                │
      ↓                          │
P3 获取英雄  ◄── 准入闸门 ────────┤（首个循环必经一次；此后为条件步骤）
      ↓                          │
P4 英雄自主生活                  │
      ↓                          │
P5 观察与决定是否干预 ───────────┘（回到 P1，构成村庄/英雄循环）
      ↓
P6 组队 ──► P7 副本推进与自动战斗 ──► P8 结算与结果回流
                                              ↓
                                        P9 回到村庄（进入下一轮 P1）
```

### 1.2 与核心玩法循环 §3 六阶段的对应

**【已确认】** 核心玩法循环 §3 的 A–F 六阶段是本文的骨架；本文只是把它展开成十个步骤，并补上它没有的一步。

| 核心循环阶段 | 本文步骤 | 说明 |
|---|---|---|
| A 观察村庄 | **P1** | **【建议】** 展开为两步：P1 观察 / P2 建造，对应 §3 阶段 B |
| B 创造生活条件 | **P2** | 同上 |
| C 英雄自主生活 | **P4** | 【已确认】英雄行为由自己决定 |
| D 观察并决定是否干预 | **P5** | **【建议】** 第一版的「干预」几乎全是否决，理由见 §4.3 |
| E 组队并攻略副本 | **P6 → P7** | 【已确认】自动战斗、可在地图上观察 |
| F 结果回流村庄 | **P8 → P9** | 【已确认】副本不得是与村庄无关的战斗界面 |
| —（核心循环 §2.1 **没有**这一步） | **P3 获取英雄** | 本文补入，论证见 §1.3 |

### 1.3 「获取英雄」放在 P3 的理由（本文补入的一步）

**【已确认】** 事实核对：核心玩法循环 §2.1 的主循环文本里**没有**「获取英雄」；但同一份文档 §6.3 的 MVP 演示流程**第 2 步**是「玩家通过最终确定的英雄获取入口获得英雄」；设计基线 §3.2 的主循环图里**有**「获取英雄（召唤，和村庄进度关联）」这一格。
**【已确认】** 因此三份上游文档并不矛盾：核心玩法循环 §2.1 省略它是因为那段主循环的观察重点是「观察→干预」的反复；§6.3 与基线 §3.2 都要求它在流程中占一个位置。

**【建议】** 把获取英雄定义为 **P3「准入闸门」** 而非循环内的固定一格，理由三条：

1. **【建议】** 首轮必经、后续条件触发。首个存档英雄数为 0，若不先获取英雄，P4 无对象可自主生活、P6 无对象可编队，闭环在结构上走不通（基线 §6.6 N1 的精神同样适用于此）。但基线 §10.8 的 S4/S5 说明召唤要消耗资源、可能不足，所以它在后续轮次是**条件步骤**：满足条件才可再次执行。
2. **【建议】** 它是**准入**不是**日常**。召唤有资源门槛、结果不确定（`07` T-005）。把它画成循环里与其他步骤同等的一格，会暗示玩家每个循环都要点一次；作为闸门则准确表达「没有它，后面的步骤无事可做」。
3. **【建议】** 它与 P2 建造相邻而不重叠。基线 §10.5 建议召唤与村庄进度关联，但「是否由村庄进度决定解锁」本身是**【待定】**（基线 §10.5 待确认）。因此本文规定 P3 位于 P2 之后，但**不规定** P2 的建造结果是否影响 P3 是否可执行——后者标【待定】，不由本文决定。

**【建议】** 关于 P2 与 P3 的先后：开发计划 §6.3 第 2 步把获取英雄放在「进入村庄」之后、任何建造之前；基线 §3.2 把「建造村庄」放在「获取英雄」之前。两者在首轮实际不冲突（初始村庄已是三间土屋，P2 首轮可以是无操作），本文按**基线 §3.2 的顺序**排列，并在 P2 注明首轮允许无操作。

### 1.4 本文的「三字段」约定

**【建议】** 每一个步骤都按三个字段写，缺一不可：

| 字段 | 回答 |
|---|---|
| **玩家看到什么** | 界面、提示、可读数器。**只列第一版真的要显示的**，不列理想 UI |
| **系统做什么** | 触发了哪条规则、调用哪个模块。模块名与 `05` §2.3 一致 |
| **状态怎么变** | 哪些字段变了、是否可观察。字段名与 `05` §3 一致 |

## 2. 分步规格

### P0 · 启动与载入

**【已确认】** 对应开发计划 M1、M7；这是整个流程的第零步。

#### 玩家看到什么

**【建议】**
- 45° 等距俯视的村庄画面（基线 §2.2 视角【已确认】）
- 三间土屋可见（基线 §2.2 村庄起点【已确认】）
- 基础 UI：资源读数、模拟时间读数、杂谈面板（三者均**【待定】**具体内容，见本步「待定停靠」）

**【已确认】** 新游戏与继续游戏的区分由存档是否存在决定；**【建议】** 新游戏走「创建村庄实例为三间土屋」，继续游戏走「解析 DTO → 校验 ID 与引用 → 恢复运行时状态」。

#### 系统做什么

**【已确认】**
1. 应用层会话生命周期建立（`05` §2.1 应用层）
2. 新游戏：`05` §3.3 村庄实例由新游戏流程创建为三间土屋
3. 继续游戏：**先解析 DTO、校验 ID 与引用，再恢复运行时状态**（基线 §13.7；不变量 I11）
4. 领域层七个模块各自初始化（`05` §2.3），**不建巨型 GameManager**（基线 §13.4；开发计划 M1 验收）

#### 状态怎么变

**【已确认】** 新游戏后运行时实体存在且**只有**这些：`Village`、`BuildingInstance`×3、`SimClock`。
**【已确认】** `Hero` 数量为 0——这是 P3 存在的原因。
**【已确认】** 存档边界就是 `05` §2.6 列举的十类实体，不多不少。
**【建议】** 英雄为 0 时，P1/P2 仍可正常进行（玩家在空村里建房子是合法的）。

#### 待定停靠

**【待定】** 初始资源数量（核心循环 §3 阶段 A）→ `07` 临时参数台账
**【待定】** 模拟时间与现实时间的关系、时间倍率（T-001）→ `03`
**【待定】** 新手引导方式（核心循环 §3 阶段 A）→ 第一版是否需要，`06` 判定

#### 验收挂钩

**【建议】** 开发计划 §五 ① 工程与村庄 · I9 · I10 · I11

### P1 · 观察村庄

**【已确认】** 对应核心玩法循环 §3 阶段 A；这是玩家的第一个动作，也是一切决策的输入。

#### 玩家看到什么

**【建议】**
- 村庄地图上的建筑实例（三间土屋）及其在场状态
- 英雄列表（首轮为空；P3 之后非空）及其**当前所在活动**
- 杂谈面板中的近期条目
- 资源读数与模拟时间读数

**【已确认】** 表现层通过**只读查询或订阅领域事件**刷新显示，**不回写**领域（基线 §13.5；`05` §2.4 第三条通道）。

#### 系统做什么

**【建议】**
1. 表现层向**拥有数据的模块**发起只读查询（不是拿到领域对象引用再改字段）
2. 模拟时钟推进——**推进的频率与倍率属【待定】**（T-001）

**【建议】** 本步不产生领域状态变更；它是纯观察。**【已确认】** 若观察期间有英雄正在执行行为，杂谈可能因该行为产生新条目。

#### 状态怎么变

**【已确认】** 无玩家指令进入领域层——本步**没有任何命令**。
**【建议】** 唯一可能的被动变化：`SimClock.Now` 随模拟推进而变化（I13：单调不回退）。

#### 玩家在这一步能做什么

**【建议】** 只能查询，不能指令。**【待定】** 玩家是否可暂停 / 加速 / 单步（T-001）——第一版**不**作为玩家操作提供，见 §4.1 O7。

#### 验收挂钩

**【建议】** 开发计划 §五 ① 工程与村庄（「地图显示位置与运行时状态一致」，M2 验收）· I10

### P2 · 建造与发展村庄

**【已确认】** 对应核心玩法循环 §3 阶段 B；开发计划 M2。

#### 玩家看到什么

**【建议】**
- 可建造建筑的列表及其建造结果（建成 / 建造进度，`05` §3.3）
- 村庄资源读数的变化
- 地图上新增或变化的建筑实例

**【待定】** 建筑成本、前置条件、资源种类、建筑效果、解锁规则（基线 §12.3）——**本文不写，列出即违规**。
**【已确认】** **不得由实现者自行指定每栋建筑的功能**，尤其不得仅凭名称推断它改变战斗或经济数值（基线 §12.3 / 验收项 B1）。
**【建议】** 第一版只要求三间土屋可见可用；其余建筑**定义存在但效果字段留空**，而不是填占位数值（`05` §3.3）。

#### 系统做什么

**【建议】**
1. 玩家在表现层发出**建造命令**（`05` §2.4 第一条通道：命令是唯一能改变领域状态的入口）
2. **村庄与建筑模块**校验前置条件与资源充足性
3. 通过 → 创建 `BuildingInstance`、扣减资源、发**领域事件**（建筑建成 / 升级，基线 §7.2 触发条件之一）
4. 不通过 → **拒绝命令**（`05` §4.2 三种处理方式之一），**不创建实例、不扣资源**

#### 状态怎么变

**【建议】** 通过时：`BuildingInstance` 集合 +1；村庄资源存量 −建造成本；新增一条 `DomainEvent`。
**【建议】** 该事件若被杂谈模块判定为值得记录，则新增一条 `ChronicleEntry`（I5：条目必须指向真实事件）。
**【建议】** 不通过时：**零变化**。

#### 待定停靠

**【待定】** 资源种类与数量（核心循环 §8 第 6 项）→ 临时参数
**【待定】** 建筑成本与前置条件（基线 §12.3）→ 临时参数
**【建议】** 不变量 I12（资源不会变为负数）在规则未定前**只能断言流程**（扣减前检查充足），不断言具体数值。

#### 失败路径

**【建议】** 见 §5 的 F-09（资源不足）。

#### 验收挂钩

**【建议】** 开发计划 §五 ① 工程与村庄 · I12 · 基线 §12.5 B2「建造规则一致」

### P3 · 获取英雄（准入闸门）

**【已确认】** 核心循环 §6.3 第 2 步；基线 §10.3「玩家通过村庄里的召唤设施召唤」。

> **这一整步的规则形态都是【待定】。** 本文只规定**流程位置**、**通道归属**与**必须可断言的性质**，不规定召唤怎么工作。

#### 玩家看到什么

**【建议】**
- 一个「获取英雄」的入口，且**该入口的可用性状态可见**（可用 / 条件不满足 / 资源不足）
- 召唤后的结果：一名新英雄进入村庄，并出现在 P1 的英雄列表中
- 村庄资源读数的相应变化

**【待定】** 召唤设施的具体形态：建筑名称、解锁条件、位置、是否唯一（基线 §10.3 / 待确认清单 #15）。
**【待定】** 消耗什么、消耗多少（基线 §10.6：优先游戏内资源，不预设真实货币；`07` T-005）。

#### 系统做什么

**【建议】**
1. 表现层发出**获取英雄命令**
2. **英雄模块**校验获取条件（**【待定】** 具体条件）
3. 校验通过 → 创建一个 `Hero`（唯一写者是英雄模块，`05` §3.2）；发领域事件（召唤到新英雄，基线 §7.2 点名的杂谈触发条件）
4. 资源扣减由**拥有资源的村庄与建筑模块**执行，**不由英雄模块代劳**（不变量 I10 / 基线 §13.5）

**【建议】** 首轮的最小实现只需保证「英雄能被创建、进入村庄、进入 P1 列表」。**【待定】** 该最小实现是否需要一个召唤设施，还是一个新游戏即已有初始英雄——基线未确认初始英雄人数（核心循环 §3 阶段 A）。

#### 状态怎么变

**【建议】** 通过时：`Hero` 集合 +1；村庄资源 −消耗量；新增 `DomainEvent`；可能新增 `ChronicleEntry`。
**【建议】** 英雄创建后**立即具备被 P4 观察的资格**：进入村庄 = 当前所在活动从「未进入村庄」转为某个初始活动。
**【已确认】** 新英雄**没有**任何死亡代价相关字段（基线 §4.6 / `05` §3.2 / 不变量 I6）。

#### 明确不做的

**【已确认】** 本文**不写**卡池、稀有度、概率、保底、重复召唤处理（基线 §10.6 全部待定；`07` T-005；开发计划 §六）。
**【已确认】** **不得因为采用抽卡形式就默认采用手游式保底**（基线 §10.6 / §17）。
**【已确认】** **不得在未定义经济规则前让召唤凭空改变资源**（基线 §17 最后一条）。

#### 待定停靠

**【待定】** 召唤设施形态（基线 §10.3 #15）· 消耗（基线 §10.6）· 唯一性语义（#27）· 是否为主要获取途径（#28）· 英雄是否知道自己来自虚构作品（#26）
**【建议】** 上述五项全部指向 `07`，**不由本文回答**。第一版的最小获取流程只需满足「能获得英雄 + 资源扣减可断言」（基线 §10.8 的 S4/S5）。

#### 验收挂钩

### P4 · 英雄自主生活

**【已确认】** 对应核心玩法循环 §3 阶段 C；开发计划 M3。这是本闭环的**核心验证点**。

#### 玩家看到什么

**【建议】**
- 英雄在地图上的位置与其**当前所在活动**变化
- 杂谈面板出现新条目
- 至少一种日常活动被执行（基线 §4.2：**喜欢打副本的英雄同样会休闲、会采集**，只是效率慢一点）

**【已确认】** 玩家**不下达**任何日常指令——本步的价值恰恰在于玩家什么都不做（开发计划 §五 ②「不逐条指挥英雄时」）。

#### 系统做什么

**【建议】**
1. **模拟时钟与调度模块**推进模拟步
2. **英雄模块**按规则让英雄做出行动选择（依据人物特质 / 玩法偏好 / 当前状态 / 已有关系四层，基线 §4.1）
3. 行动完成后，**拥有对应数据的模块**各自写入结果（物品 → 英雄持有物；资金 → 经济数据）
4. **领域事件与杂谈模块**在事件发生时生成条目

**【已确认】** 偏好**只改变权重与倾向，不改变可行性**（基线 §4.3）——一个偏好休闲的英雄仍然可以被派去副本（这正是 P6 能成立的前提）。
**【已确认】** 四层是正交的四件事，**不合成单一「性格」属性**（`05` §3.2）。

#### 状态怎么变

**【建议】** 随英雄实际选择而变，可观察的有：`Hero` 的当前所在活动、持有物引用、状态槽位（**槽位与取值属【待定】**）。
**【已确认】** 每次有意义的自主行动应产生**可观察的结果**（物品变化、资金变化、关系变化或一条杂谈）——核心循环 §3 阶段 C。
**【已确认】** 杂谈**根据已发生的事件生成消息**，而不是每隔几秒随机生成文本（基线 §7.2）。
**【已确认】** 杂谈**每条必须指向一个已存在的领域事件 ID**，同一事件 ID 至多一条（I5 / 基线 §7.4 C1+C2）。

#### 待定停靠

**【待定】** 行动优先级、行动频率、行动耗时、资金与疲劳规则、英雄何时主动提出冒险需求（核心循环 §3 阶段 C）→ `03`，其中频率与耗时对应 `07` **T-002**
**【待定】** 模拟时间推进方式 → `07` **T-001** → `03`
**【待定】** 人物特质条目与取值（#3）、玩法偏好品类与权重表（#4）→ `03`

#### 明确不做的

**【已确认】** **不实现疲劳**（`07` T-003「**不得实现**」；基线 §4.4 性质未定；开发计划 §二）。本文中 P4 的英雄**不携带任何疲劳字段**。
**【已确认】** 第一阶段不实现关系变化的完整行为链（欺骗 → 纠纷 → PvP → 追逐 → 复仇）（开发计划 §六；`07` T-008）。**【建议】** 关系在第一阶段**只建模方向性存储**（I8），不建模变化规则。

#### 验收挂钩

**【建议】** 开发计划 §五 ② 英雄自主行为 · 核心循环 §7.2 C1 / C2 · I5

#### 玩家看到什么

**【建议】**
- 杂谈面板：发生了什么、涉及谁
- 英雄当前状态与所在活动
- 一个**明确的下一步选择**：继续观察，或进入 P6 组队

#### 系统做什么

**【建议】** 本步**没有**新的系统调用。它是玩家的决策点。

**【建议】** 第一版的「干预」边界如下——这是本文对核心循环 §3 阶段 D【待定】问题的一个**保守回答**，不是终案：

| 干预类型 | 第一版 | 依据 |

#### 状态怎么变

**【已确认】** 本步**不改变领域状态**。

### P6 · 组队

**【已确认】** 对应核心玩法循环 §3 阶段 E 第 1–3 步；开发计划 M4。

#### 玩家看到什么

**【建议】**
- 可派遣英雄列表，**并标出谁已被占用**（在任务中的英雄）
- 当前队伍成员
- 「发起攻略」按钮；条件不满足时按钮禁用并给出**可理解的原因**

**【已确认】** 队伍成员与玩家选择一致；任务进度可观察（开发计划 M4 验收）。

#### 系统做什么

**【建议】**
1. 表现层发出**编队命令**
2. **队伍与任务模块**校验：英雄存在、未被冲突任务占用（不变量 I2）
3. 通过 → 创建 `Squad` + `Mission`，任务状态 `未开始 → 进行中`
4. 不通过 → **拒绝命令，不创建任何实体**（`05` §4.2）

**【已确认】** 英雄接受任务后，**不能在同一时刻被重复分配到冲突任务**（开发计划 M4；不变量 I2）。
**【已确认】** 玩家决定队伍组成，**不等于**直接操纵战斗中的每一步（`05` §3.4）。

#### 状态怎么变

**【建议】** 通过时：`Squad` +1；`Mission` +1 且状态为进行中；被编入英雄的**当前所在活动**由「日常活动」转为「队伍任务中」。
**【已确认】** `05` §3.4 只记录「成员 ID 列表」，**不记录任何人数常量**——编队的**具体**人数上限、职业定位、条件属【待定】。

#### 待定停靠

**【待定】** 队伍人数上限、职业定位、职业条件（核心循环 §3 阶段 E / §8 第 5 项）→ `04`
**【已确认】** `07` D-002 已裁定 `squad_max: 4` **不构成本基线的任何部分**，编码时**不得**引用。
**【待定】** 副本攻略期间村庄中其他英雄是否继续生活与交易（核心循环 §8 第 4 项）→ 影响 I2 的例外情形，第一版先按「继续生活」实现并标注为**临时参数**，或整体挂起——本文不替开发者决定，见 §5 F-10。

#### 失败路径

**【建议】** 见 §5 的 F-01（无可用英雄）、F-02（队伍不满足条件）、F-03（冲突编队）。

#### 验收挂钩

**【建议】** 开发计划 §五 ③ 玩家队伍操作 · I2 · I14

### P7 · 副本推进与自动战斗

**【已确认】** 对应核心玩法循环 §3 阶段 E 第 4–5 步；开发计划 M5。

#### 玩家看到什么

**【已确认】** 三条硬要求，全部可见：
- 战斗**全自动**——玩家不直接操控即时攻击
- 战斗**可在地图上观察**，**不是**切换到独立战斗场景
- 战斗**可读**——玩家应能看清谁为什么赢、谁为什么输

**【建议】** 具体呈现：副本当前阶段序号（`05` §3.5）、实时战斗画面、一份战斗日志（`05` §3.6）。

#### 系统做什么

**【建议】**
1. **副本与战斗模块**创建 `DungeonRun`（在任务派遣成功并通过合法性检查后创建，`05` §3.5）
2. 阶段推进：**【建议】** 阶段**不单独建实体**，是副本实例内的一段状态 `当前阶段序号`（`05` §3.5）
3. 每个阶段执行**自动战斗**
4. 战斗结束 → 创建 `BattleResult`（**每个副本实例至多一个**，不变量 I3）
5. 达到最终目标 → `DungeonRun.状态 = 已完成`；失败条件触发 → `已失败`

**【已确认】** 副本必须具备：**明确入口、多个阶段（至少两个，单场遭遇不算副本）、最终目标、结算与奖励**（基线 §8.2）。
**【已确认】** 参与英雄 ID 是**进入时快照**，不随英雄后续状态变化（`05` §3.5）——否则读档重放结算会算出与当时不同的结果。
**【已确认】** `BattleResult` **创建后不可修改**（`05` §3.6）。

#### 状态怎么变

**【建议】** 推进期间：`DungeonRun.当前阶段序号` 递增；被编入英雄的所在活动保持「队伍任务中」。
**【已确认】** `BattleResult` 记录：结果（成功 / 失败）、参与英雄 ID 快照、产出清单的**描述**（**数值属【待定】**）、战斗日志。
**【已确认】** 战斗日志要能**复现胜负判定所引用的每一个关键事件**（基线 §8.5 验收项 D5）。
**【已确认】** **副本与战斗模块不直接写村庄资源与英雄持有物**（`05` §2.3）——那属于 P8。

#### 待定停靠

**【待定】** 战斗的全部数值规则：伤害、命中、冷却、状态效果、AI 目标选择（基线 §8.3 / 待确认清单 #13）→ `07` **T-004** → `04`
**【待定】** 副本结构、阶段数量、失败条件、任务耗时（核心循环 §8 第 5 / 12 项）→ `04`

#### 失败路径

**【建议】** 见 §5 的 F-04（副本失败）、F-06（英雄在副本中死亡）。

#### 验收挂钩

**【建议】** 开发计划 §五 ④ 多阶段副本 · ⑤ 自动战斗可读性 · I3 · 基线 §8.5 D1 / D3 / D5

### P8 · 结算与结果回流

**【已确认】** 对应核心玩法循环 §3 阶段 F；开发计划 M6。**这是本闭环成立与否的判定步骤。**

#### 玩家看到什么

**【建议】**
- 结算结果：成功 / 失败、产出清单、进入村庄与英雄的分别归属
- 村庄资源读数的变化、英雄持有物的变化
- 一条与本次完成相关的杂谈条目（**首次**完成副本是基线 §7.2 点名的触发条件）

**【已确认】** **副本不应只是一个与村庄无关的战斗界面**——至少要有一条真实、可验证的结果路径回到英雄生活或村庄经营（核心玩法 §3 阶段 F；`05` §6）。

#### 系统做什么

**【建议】**
1. **结算与回流模块**检查 `DungeonRun.结算是否已应用` 标志
2. 已应用 → **立即返回，不做任何写入**（幂等）
3. 未应用 → 按 `BattleResult` 计算增量
4. **由拥有该数据的模块分别写入**：资源 → 村庄与建筑模块；持有物 / 状态 → 英雄模块；再由**结算与回流模块**只写「结算已应用」标志与结果引用（`05` §3.5 唯一写者列）
5. 发领域事件 → 杂谈条目

**【已确认】** **已结算的副本不能重复结算**（不变量 I4；基线 §13.7「重复发放奖励」）。

#### 状态怎么变

**【已确认】** 首次结算后，`DungeonRun.结算是否已应用 = 真`，**且该标志必须显式落盘**，不能靠读档后重新推算（`05` §2.6）。
**【建议】** 第二次调用结算时，村庄资源 / 英雄持有物 / 英雄状态的**增量第二次为零**。
**【已确认】** **结算要么完整应用，要么不应用**（不变量 I15）——不存在部分入账；产出引用失效时**明确报错，不发一半奖**（`05` §4.2）。

#### 待定停靠

**【待定】** 奖励内容与数值（核心循环 §8 第 13 项 / #13）→ `07` **T-004** → `04`

#### 验收挂钩

**【建议】** 开发计划 §五 ⑥ 结果回流 · ⑦ 事件与杂谈 · I4 · I5 · I15 · 基线 §8.5 D2 · 核心循环 §7.2 C7 / C8

## 5. 失败路径

**【已确认】** 以下每一条都是第一版**真的会走不通**的情况。**【建议】** 第一版对每一条都必须有**可观察的**处理，不得静默崩溃、不得静默丢弃（`05` §4.2：**没有第四种「静默丢弃」**）。

### 5.1 运行期拒绝（命令被拒，不产生副作用）

| # | 触发 | 系统行为 | 断言 |
|---|---|---|---|
| **F-01** | 无可用英雄时尝试编队或派遣 | **拒绝命令**，不创建 `Squad` / `Mission` | 创建前后实体数不变 |
| **F-02** | 队伍不满足已定义的参与条件 | **拒绝创建**任务与副本实例（`05` §4.2：任务→副本定义引用断了 → 派发时拒绝该命令） | 无任务被创建 |
| **F-03** | 把已在任务中的英雄编入冲突任务 | **拒绝命令** | 不变量 I2 |
| **F-09** | 资源不足以建造或获取英雄 | **拒绝命令**，资源不变 | 不变量 I12（流程层面）；资源**不为负** |

**【建议】** 这四条拒绝都必须给玩家一个**可理解的原因文本**，不只是禁用按钮（核心循环 §3 阶段 D「让玩家能够理解发生了什么」）。

### 5.2 结算类失败

| # | 触发 | 系统行为 | 断言 |
|---|---|---|---|
| **F-04** | 副本失败 | `DungeonRun.状态 = 已失败`；**结算照常执行一次**（结果为失败） | 不变量 I3 / I4：仍至多一个 `BattleResult`、一次结算 |
| **F-05** | 奖励产出清单为空 | **【建议】** 视为合法的零增量结算：照常写「结算已应用」标志，发事件，不产生部分入账 | 不变量 I15：总增量为 0，且标志仍为真 |
| **F-06** | 英雄在副本中死亡 | **复活，无任何代价**（基线 §4.6）：不掉装备、不掉等级、不损失时间、**关系不因死亡本身而恶化** | 不变量 I6：死亡前后**属性 / 持有物 / 可用性完全一致**；**关系若有变化，必须能追溯到基线 §9 的行为链** |
| **F-07** | 对同一 `DungeonRun` 连续调用两次结算 | 第二次**增量全为零** | 不变量 I4 |

**【已确认】** F-04 的**失败条件本身属【待定】**（`04`）；本文只规定「失败也是一次正常结算」，不规定失败时给不给奖励。
**【待定】** **失败是否给予任何奖励** → `04`。

**【已确认】** **F-06 的「不恶化关系」带一条例外**，不是「死亡后关系一定不变」：基线 §4.6 的原文是「**没有**（除非 §9 的行为链本身导致，属独立事件）」。英雄死在一条 PvP 追杀链里，关系**可以**变——但那是 §9 行为链造成的后果，不是死亡造成的。F-06 的断言因此**不能写成快照全等**，否则会因合法行为而失败（详见 `05` §5.1 的 I6 三条断言；第一阶段不建模 §9 行为链，故第一阶段可直接断言「不存在任何关系写入点」）。

### 5.5 需要开发者裁决、我停在这里的问题

**【待定】** **F-10 · 副本攻略期间，村庄中其他英雄是否继续生活与交易？**
