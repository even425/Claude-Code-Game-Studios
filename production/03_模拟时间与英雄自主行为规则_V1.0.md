## 2. 模拟时间

### 2.1 什么在推进

**【已确认】** 推进者是 **`SimClock`**（`05` §3.9），唯一写者是**模拟时钟与调度模块**。

**【已确认】** `SimClock` 持有：当前模拟时间；已处理的模拟步序号；时间倍率设置（`05` §3.9）。

**【已确认】** **所有领域模块都只读 `SimClock`**——它为事件时间戳、行动耗时提供时间基准（`05` §3.9「谁读它」列）。

**【建议】** **模拟时间是唯一的、不依赖渲染帧的时间源。** 任何领域规则都不得使用「帧」「帧间隔」「上一帧」作为时间输入。

### 2.2 模拟与画面分离（基线 §13.2 的直接落点）

**【已确认】** 基线 §13.2 要求模拟与表现分层；`02` P1 明确表现层通过只读查询或订阅领域事件刷新显示，**不回写**领域。

**【已确认】** `07` 技术债 **A4** 记录：现有 `VillageView.cs:71` 存在**表现层反向驱动领域 `Tick`（控制反转）**，这是重写领域层时**必须消除**的债。

**【建议】** 因此推进链固定为单向：

```text
[表现层] 引擎帧 dt  ──只读读取──┐
                              ▼
[应用层] 固定步长累加器  ──每累积够一步──► 发起一次「推进模拟步」命令
                              │
                              ▼
[模拟时钟与调度模块] SimClock.Advance(模拟步长)
                              │
                              ▼  按 §2.4 的顺序
[领域层] 各模块在步内依次执行 ──► 领域事件 ──► 只读快照
                              │
                              ▼
[表现层] 订阅事件 / 拉取快照刷新显示（不回写）
```

**【已确认】** **表现层不得直接调用 `SimClock.Advance` 或任何领域推进方法。** 它只能把引擎的 `dt` 作为**输入数据**交给应用层。

**【建议】** 由此得到一条可机械断言的性质（**帧率无关性**）：

> **断言 A-01**：在固定模拟步长、固定随机种子、相同的模拟总时长下，**以不同帧率驱动**（例如低帧率与高帧率各跑一遍）产生的模拟状态序列**完全一致**。
>
> 这条断言不需要任何数值，只需要「固定种子 + 固定步长 + 相同总时长」三个输入条件，因此它在 T-001 未决时**就可以先写**。

### 2.3 一个模拟步（step）是什么

**【建议】** **模拟步是模拟世界的最小时间单位**，是 `SimClock` 与所有领域模块之间的唯一同步点。

**【建议】** 一个模拟步内发生的事，按 §2.4 的顺序执行。模拟步之间不共享任何临时状态。

**【建议】** **模拟步长（每个步代表多少模拟时间）属【待定】`T-001`。** 本文只给出接口形状：

| 项 | 内容 | 状态 |
|---|---|---|
| 模拟步长 | 一个模拟步代表的模拟时间量 | **【待定】T-001** |
| 每现实秒的模拟步数 | 派生量 = 1 / 模拟步长 ÷ 时间倍率 | **【待定】T-001** |
| 时间倍率 | 玩家或系统可调的推进速度系数 | **【已确认】字段存在（`05` §3.9）；**【待定】取值范围与可调性 T-001** |
| 暂停 / 加速 / 单步 | **【已确认】** `02` O7 列为【待定】T-001，**第一版不作为玩家操作提供** | 第一版不暴露 |
| 单步追帧上限 | 现实卡顿后一次补多少个模拟步 | **【待定】T-001** |

**【建议】** **单步追帧上限**这一项容易被忽略但必须显式存在：现实卡顿（加载、断点、窗口失焦）会积累大量待补步，若无上限会一次性涌入几十个模拟步，导致英雄「瞬移式」完成大量行动。**上限的存在是【建议】的，上限的值属【待定】T-001。**

**【已确认】** 不变量 **I13**：模拟时间单调不回退。因此 `SimClock` 的取值序列非递减（`05` §5.2）。

### 2.4 一个模拟步内的模块顺序

**【已确认】** 顺序由**模拟时钟与调度模块**决定，但**它不决定任何英雄做什么**（`05` §2.3）。

**【建议】** 第一阶段的步内顺序如下，理由逐条写在最后一列：

| 序 | 步骤 | 执行模块 | 为什么在这个位置 |
|---|---|---|---|
| **1** | 推进 `SimClock`，步序号 +1 | 模拟时钟与调度 | 所有后续步骤的时间戳基准必须先更新 |
| **2** | 处理**到期**的行动：完成结算、写入结果、发领域事件 | 英雄模块 + 拥有数据的模块 | 见 §4.3「完成先于新决策」 |
| **3** | 推进副本实例与自动战斗 | 副本与战斗模块 | 与自主生活**并行但不互相冻结**（D-006） |
| **4** | 对**空闲**英雄执行决策流程（§3 七步） | 模拟时钟与调度发起，英雄模块执行 | 见 §3.1 |
| **5** | 处理到期的大事件生命周期 | （第一阶段**不实现**） | **【建议】** 挂载位保留在 3 与 4 之间，不写实现 |
| **6** | 领域事件归集 → 杂谈模块生成条目 | 领域事件与杂谈 | 见 §5 |
| **7** | 生成只读快照，交给表现层 | 各模块 | 表现层只读，不回写 |

**【建议】** 第 2 步排在第 4 步之前的理由：**刚回流到英雄手里的东西（持有物、状态）应当能立刻参与本步的候选前置校验**，否则玩家会看到「结算完成后英雄又用旧状态决策了一次」这种一帧延迟的违和。

**【已确认】** 第 3 步与第 4 步并行不冲突的依据：`07` **D-006**「副本攻略期间其他英雄继续生活，时间照常推进」——**副本不冻结村庄**。

**【已确认】** D-006 的约束：**随队英雄不执行日常行为**（他们在外）。落到本文：**随队英雄的当前所在活动为「队伍任务中」，不参与第 4 步**（见 §3.1 S1）。

**【建议】** 第 5 步的空位是刻意的：基线 §11.1 要求「新增事件不得要求重写核心世界循环」，因此调度顺序里**预留位置**比以后插入更便宜。

### 2.5 存档边界

**【已确认】** `SimClock` 在存档边界内（`05` §2.6），且「已结算」这类幂等标志必须**显式落盘**。

**【建议】** 为使读档后模拟能从同一状态继续，存档必须满足三条结构条件（**均不需要任何数值**）：

| # | 条件 | 理由 |
|---|---|---|
| **C-1** | 存档**只允许在模拟步边界**采样，不允许采样步与步之间的中间态 | 否则读档后要么重放半步（重复结算）要么丢半步 |
| **C-2** | `SimClock` 的当前时间、步序号、时间倍率三者全部落盘 | 缺任一项都无法证明「从同一时刻继续」 |
| **C-3** | **所有正在执行中的行动实例**连同其剩余时长一起落盘 | 见 §4.4 的「行动中存档」问题 |

**【已确认】** C-3 指向一个 `05` 目前**没有**的字段，见 §10.1。

**【已确认】** 随机数状态的存档方案属 **【待定】`T-007`**（基线 §13.7 / 待确认清单 #24）。本文只要求：**读档后不得重复发奖、不得重复结算、不得让同一次行动完成两次**（`05` I4 / I15 / 基线 §13.7）。**本文不要求读档后随机序列完全复现。**

### 2.6 「一天」这个单位

**【已确认】** 基线 §3.3 注明村庄循环「以『天』为单位」，英雄循环「以『次行动』为单位」，世界循环「以『事件周期』为单位」，**三者不同步才有东西可看**。

**【待定】** **第一阶段是否需要「天」这个粒度，本文不替你决定。**

**【建议】** 两种方案：

| 方案 | 内容 | 代价 |
|---|---|---|
| **(a) 只用连续时间** | `SimClock` 只持有连续模拟时间，**没有日界** | 少一个概念；但任何「一天过去」类语义无法表达 |
| **(b) 引入日界** | `SimClock` 增加「日序号 + 日内进度」，日界为模拟时间的函数 | 表达力更强；需要给 `05` §3.9 补字段 |

**【建议】** **推荐 (b) 而非 (a)**，理由：基线 §3.3 已经把「天」当作村庄循环的既有单位，而 `src/WorldClock.cs:26-31` 已有 `Day` / `_t` 的成熟表达；选 (a) 会在第二阶段做**破坏性改动**而不是**加法**。

**【已确认】** **无论选哪个方案，日长都是一个数值，属【待定】T-001，本文不填。**

**【建议】** 补充一条与 T-003 相关的边界：若将来确认「日界」与「疲劳」或「当日行动额度」相关（基线 §4.4 的选项 b/c），日界就是一个**玩法单位**而不只是显示单位。**第一阶段不因此实现任何与日界耦合的规则**——这是防止日界悄悄变成「每日重置」的前置闸门。

## 3. 决策流程

### 3.1 七步总览

**【建议】** 一个英雄在**一个模拟步内**从「空闲」走到「执行一个新行动」，经过七步：

```text
 ┌─ 每个模拟步的第 4 步，对每个「空闲且在村」的英雄执行 ─────────────────┐
 │                                                                     │
 │  S1 触发      他此刻是否轮到做决定？                                  │
 │     ↓  是                                                            │
 │  S2 候选集    哪些活动「此刻不能做」→ 剔除；其余全部保留               │
 │     ↓  候选集非空                                                    │
 │  S3 权重合成  每项候选「有多想做」——四层在这里起作用                    │
 │     ↓                                                               │
 │  S4 抽样      按权重从候选集中选出一项（固定种子可复现）                 │
 │     ↓                                                               │
 │  S5 前置校验  现在能不能真的开始？→ 失败则本项活动本步标记不可用，回 S2  │
 │     ↓  通过                                                          │
 │  S6 占用与开始 写入「当前所在活动」= 该行动实例，开始计时               │
 └─────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼  （耗时动作：等到之后的某个模拟步）
                              S7 完成、写入、发事件
```

**【建议】** **S1 的判定集合**是一个纯粹的集合表达式（不需要任何数值）：

> **O(t) = { h | h.当前所在活动 = 空闲 ∧ h.在场性 = 在村 }**

**【已确认】** 「在场性」只有两种取值（第一阶段）：**在村** / **队伍任务中**。**没有第三种。**

**【已确认】** 不存在任何其他使英雄「不在场」的状态——基线 §2.2 / `07` D-001 已作废时区作息与离线判定；`07` 技术债表列出的 `AbsentDays`（缺席）12 处、`Online`（在场）23 处全部属于**已作废设计**。

**【建议】** 因此本文中「缺席」「缺勤」「外出未归」类语义在第一阶段**不存在**。随队远征中的英雄不是「缺席」，是**在队伍任务中**（D-006）。

### 3.2 决策链里没有玩家输入点

**【已确认】** `07` **D-008**：「第一版玩家的可执行操作限于 `02` §4.2 的 O1–O8；**不允许**指定英雄日常、干预普通交易、调解纠纷、战斗即时操控。」

**【已确认】** `02` §4.3 N1：指定某个英雄今天做什么活动——第一版**不允许**，实现方式是**命令集里根本没有这条命令**，而不是加一条会返回失败的命令。

**【建议】** 因此 **S1–S7 全程没有玩家输入点**。`02` P4 的价值恰恰在于「玩家什么都不做」（开发计划 §五 ②）。

**【建议】** 唯一能**间接**影响英雄行为的两件事是**玩家建造了什么东西**（P2，改变环境，进而改变 S5 的前置校验结果）与**玩家组了队**（P6，改变 S1 的在场性集合）。**【建议】** 这是第一阶段唯一的因果杠杆，且它走的是环境而非命令，符合 D-008。

### 3.3 四层建模在七步中的作用

**【已确认】** 基线 §4.1 把「性格」拆成**四层正交**的事；`05` §3.2 复述「四层是正交的四件事，**不合成单一『性格』属性**」。

**【建议】** 四层落到七步的矩阵如下。**这张表是本文最重要的一张表**——它规定了「哪一层可以在哪一步起作用」，从而使四层无法被重新压扁成一个总评：

| 层 | S1 触发 | S2 候选集（能不能） | S3 权重（有多想） | S4 抽样 | S5 前置校验 | S6/S7 执行与产出 |
|---|---|---|---|---|---|---|
| **人物特质**（他是什么人） | 不参与 | **不参与** | **参与**：方向性修正 | 不参与 | **不参与** | **参与**：决定同一动作的表现差异 |
| **玩法偏好**（他喜欢做什么） | 不参与 | **不参与** | **参与**：基础权重 | 不参与 | **不参与** | **参与**：效率差异 |
| **当前状态**（他此刻能不能） | **参与**：状态可能使其不空闲 | **参与**：**唯一的剔除依据** | 可参与（修正权重） | 不参与 | **参与**：状态变化可使其不可开始 | **参与**：产出受状态影响 |
| **人际关系**（他跟别人怎么样） | 不参与 | **不参与**（第一阶段） | 位置已留，**第一阶段为空** | 不参与 | 位置已留，**第一阶段为空** | 位置已留，**第一阶段为空** |

**【已确认】** 上表最关键的一格：**人物特质与玩法偏好在 S2（能否）与 S5（前置校验）中一律不参与。**

**【已确认】** 这正是基线 §4.3 的直译：**偏好只改变权重与倾向，不改变可行性**；以及基线 §4.2 的直译：**人物特质影响「如何做决定」，不影响「能做什么」**。

### 3.4 为什么「人际关系」层在第一阶段是空的

**【已确认】** `05` 不变量 **I8**：关系是**有向的二元记录**（A→B 与 B→A 分别存储）；**第一阶段只建模方向性存储，不建模关系变化的触发规则**（`07` T-008）。

**【建议】** 因此本文规定：**S3/S5 中与人际关系相关的位置在第一阶段读取一个恒为空的关系视图**，对权重与前置校验**不产生任何影响**。

**【建议】** **位置先留、内容后填**的理由：留位置的成本是矩阵里的三个空格；不留位置的成本是第二阶段要**重写 S3/S5 两条主路径**。这与 `05` §3.5「升级成本远低于提前拆错的成本」是同一条原则。

**【已确认】** **本文不设计任何「什么经历导致关系变化」的规则。** 基线 §9.5 R4 要求的是「关系值的每次变化都能追溯到一个具体经历」，这是一个**可追溯性要求**，不是变化规则本身。

### 3.5 S2 · 候选集构造

**【建议】** S2 的职责是**唯一**的「剔除」环节，且剔除权**只**交给当前状态与环境。

**【建议】** S2 的输入：

| 输入 | 来源 | 可否剔除候选 |
|---|---|---|
| 英雄**当前状态槽位** | 英雄模块（`05` §3.2） | **可剔除**——这正是「此刻能不能」的定义（基线 §4.4） |
| 英雄**在场性**（在村 / 队伍任务中） | 队伍与任务模块经英雄模块 | **可剔除**——随队英雄不在候选决策中（D-006） |
| 活动**本身是否存在于注册表** | 活动定义注册表 | **可剔除**——未定义的活动不进入候选集 |
| **人物特质** | 英雄定义 | **不可剔除** |
| **玩法偏好** | 英雄定义 | **不可剔除** |
| **人际关系** | 第一阶段为空 | **不可剔除**（无可剔除的内容） |

**【已确认】** 基线 §4.4 明确当前状态包含「疲劳、受伤、资金不足、任务承诺」等；**第一阶段其中的「疲劳」不实现**（`07` T-003、`02` F-13）。

**【建议】** 因此第一阶段 S2 实际使用的状态槽位**只来自「在场性」与「已定义的活动」**；若后续加入受伤等状态，它们在 S2 的位置与权限与在场性相同，**不需要改动 S2 的规则**。

**【建议】** **候选集为空的处理**：不回退到一个「什么都不做」的伪活动，而是**该英雄本步不行动**，并在 §5 的「不生成事件」清单中登记为**合法空转**（见 §5.4）。

### 3.6 S3 · 权重合成（结构式公式）

> **【建议】** 下面是本文唯一的结构式公式。它给出**变量、运算关系与取值范围的性质**；**全部数值属【待定】**，因此本文不给出数值算例，只给出**符号算例**（§3.6.4）。

#### 3.6.1 公式

**【建议】** 候选活动 `a` 对英雄 `h` 在模拟时刻 `t` 的选择权重：

```text
W(a, h, t) = P(h, a) · M(h, a) · B(h, a, t) · S(h, t)
```

#### 3.6.2 变量表

| 符号 | 类型 | 取值范围 | 描述 |
|---|---|---|---|
| `W` | float | **(0, +∞)**，且对候选集中的每一项**恒大于 0** | 候选活动的选择权重 |
| `P(h, a)` | float | (0, +∞)；**【待定】**具体档位与权重表 = 基线 §16 #4 | **玩法偏好**基础权重：他有多想「做这一类事」 |
| `M(h, a)` | float | (0, +∞)；**【待定】**条目与取值 = 基线 §16 #3 | **人物特质**修正：他是什么人，导致他更/更不爱做这一类事 |
| `B(h, a, t)` | float | (0, +∞)；**第一阶段恒等于 1** | **人际关系**修正：他跟别人怎么样。**第一阶段为空，占位保留** |
| `S(h, t)` | float | (0, +∞)；**第一阶段恒等于 1** | **当前状态**对权重的影响（注意：当前状态**主要**作用在 S2 与 S5，此处是可选的次要修正） |
| `a` | 活动定义 ID | 活动注册表内的已定义项 | 候选活动 |
| `h` | 英雄 ID | 全部在场英雄 | 决策主体 |
| `t` | 模拟时间 | 模拟时钟当前值 | 决策时刻 |
| **结果：** 选择概率 | float | (0, 1)，**各项之和为 1** | 由 §3.7 的抽样公式给出 |

#### 3.6.3 输出范围与它的硬约束

**【建议】** `W` 的取值范围是 **(0, +∞)**，且必须满足一条**结构性约束**：

> **约束 CR-1：对候选集中的每一项 `(a, h)`，`W(a, h, t) > 0` 恒成立。**
>
> **不存在任何一项活动，其权重可以被特质、偏好、状态压到 0 或负数。**

**【建议】** **CR-1 就是开发者原话「性格不是二极管」的形式化落点。**

**【已确认】** 开发者原话（基线 §4.2）：「**性格不是二极管**——喜欢打副本的英雄同样会休闲、会采集，只是效率慢一点。」

**【建议】** 如果允许 `M` 或 `P` 取 0，系统就退化成「性格 = 允许做什么」的开关，这与基线 §4.2、§4.3 直接冲突。**CR-1 是本文对此的唯一防线，不得在实现中被「优化掉」。**

**【建议】** 由此产生一条**现在就能写的断言**（不需要任何数值）：

> **断言 A-02（反二极管）**：构造一个极端特质的英雄（该特质对活动 `a` 的修正取其允许范围的下端），运行若干模拟步，断言**该英雄至少选择过一次 `a`**。
>
> **【待定】** 「若干模拟步」与「修正下端」的具体取值待 T-001 / #3 确定后补；**但断言的形状现在就已确定**，可先以临时参数登记进 `06`。

**【建议】** **不推荐**用「权重不得低于某个下限常数」来实现 CR-1——那会引入一个无出处的魔法数。**推荐**用「所有修正因子恒正」的结构方式实现。

#### 3.6.4 符号算例（不是数值算例）

**【建议】** 设英雄 `h` 的候选集中有两项：`a_采集` 与 `a_休闲`。设某特质对 `a_休闲` 的修正 `M(h, a_休闲) = m < 1`。

| 活动 | `P` | `M` | `B` | `S` | `W` |
|---|---|---|---|---|---|
| `a_采集` | `p₁` | `n₁` | 1 | 1 | `p₁ · n₁` |
| `a_休闲` | `p₂` | `m` | 1 | 1 | `p₂ · m` |

**【建议】** 由 `m < 1` 且 `m > 0` 可知：`W(休闲) < P(休闲)` 但 `W(休闲) > 0`。

**【建议】** 这两行不等式就是「效率慢点、不是不能」的完整含义：

- **不是二极管**：`W(休闲) > 0` ⟹ `a_休闲` **仍在候选集中**，S2 不剔除它，S4 仍可能抽中它。
- **效率慢点**：`W(休闲)` 相对变小 ⟹ 它被抽中的**相对概率下降**。

**【已确认】** 数值 `p₁, p₂, n₁, m` **全部属【待定】**（基线 §16 #3、#4）。本文**不填**。

**【建议】** **「效率慢点」的另一种实现位置**：基线 §4.2 的「效率」也可以落在**产出速率**上（同样的时间产出更少）而不是权重上。**权重与效率是两个正交的调节旋钮，选哪个（或两个都用）属【待定】。** 本文不代选，但在 §7 的临时参数台账里为两者各留一个位置。

### 3.7 S4 · 抽样

**【建议】** 从候选集中按 `W` 加权抽样，得到被选中的活动 `a*`。

```text
P(a*) = W(a*, h, t) / Σ(a ∈ 候选集) W(a, h, t)
```

**【建议】** 输出范围：`P(a*) ∈ (0, 1)`，候选集上全部 `P` 之和为 1。

**【已确认】** **确定性要求**（`CLAUDE.md` 测试标准「Determinism」；`07` 技术债 **A7**：现有 4 个 `static readonly Random` 全部未播种，导致规则层无法单元测试）。

**【建议】** 因此抽样必须满足：

| # | 要求 | 说明 |
|---|---|---|
| **R-1** | 随机源**由外部注入** | 不得使用模块内的静态 `Random`（A7） |
| **R-2** | 给定**相同种子 + 相同初始状态 + 相同步数**，产生**完全相同**的模拟结果 | 这是基线 §14.2「涉及随机性的系统使用固定种子」的实现形式 |
| **R-3** | 存档往返后，**不得重复发奖、不得重复结算、不得让同一次行动完成两次** | **【已确认】** 基线 §13.7。**是否要求随机序列完全复现属【待定】T-007** |

**【建议】** R-2 与 R-3 是**两个不同强度的要求**，第一阶段只强制 R-3。**不要在实现时把二者混为一谈**——那会导致为了满足 R-3 而过度实现 T-007 尚未裁决的内容。

### 3.8 S5 · 前置校验

**【建议】** 抽中 `a*` **不等于**可以开始。S5 检查的是「现在能不能真的做」。

**【建议】** S5 的检查项（第一阶段）：

| 检查项 | 数据来源 | 失败时 |
|---|---|---|
| 活动所需的**地点/对象当前可得** | 村庄与建筑模块 / 英雄模块 | 本项活动在本步标记为**不可选**，回到 S2 重新抽样 |
| 活动所需的**资源是否充足** | 村庄与建筑模块 | 同上 |
| 活动所需的**另一名英雄**是否存在且可得（若活动需要搭档） | 英雄模块 | 同上 |
| 当前**状态**是否在抽样后发生了变化 | 英雄模块 | 同上 |

**【建议】** **S5 失败不是异常路径。** 它是「选了一个想做但现在做不了的事」的正常结果。**处理方式是重采样，不是报错、不是让英雄卡死。**

**【建议】** **S5 失败必须发出一个可观察信号**（供 `06` 断言、供未来 UI 使用），但**该信号本身不是领域事件、不生成杂谈条目**——理由见 §5.3 的反装饰规则。

**【已确认】** 「资源不足」的失败在 `02` §5.1 F-09 中已定义为**玩家命令**被拒绝的场景；**S5 是英雄自主行动，不走命令通道**，因此 F-09 的「拒绝命令」不适用于 S5。

**【建议】** S5 与 F-09 的区别必须保持清晰：**F-09 拒绝命令（不产生副作用）**；**S5 换一项行动（有副作用：状态发生了别的事）**。

## 4. 行动完成与占用

### 4.1 即时还是耗时

**【建议】** **所有活动都属于两类之一，分类是活动的静态属性，不是运行时判断。**

| 类别 | 定义 | 占用 | 所属模拟步 |
|---|---|---|---|
| **即时活动** | 在触发它的那个模拟步内完成 | **不占用**英雄（不写当前活动，或写入后可同步清空） | S7 与 S6 同一步 |
| **耗时活动** | 从 S6 开始计时，到达剩余时长为零时完成 | **占用**英雄 | S6 与 S7 发生在**不同的**模拟步 |

**【建议】** **两类都必须存在**：只有耗时活动，村庄节奏会变成「每 N 秒才有一次动作」，玩家看到的是静止的英雄；只有即时活动，英雄会在一个模拟步内连做很多事，玩家看到的是闪烁。

**【已确认】** **全部活动的耗时长短属【待定】T-002**（「英雄行动频率与耗时」，`07` §3；核心循环 §8 第 2 项）。**本文一个数字都不写。**

**【建议】** 「多久做一次决定」（S4 抽样频率）与「一次行动做多久」（耗时）**是两个独立的量**，都属于 T-002，但在结构上分开：**前者控制决策步的抽样节奏，后者控制行动的占用时长**。**不要用同一个参数控制两者**——那会让「英雄动作很快但决定很频繁」与「英雄动作很慢但决定很频繁」无法表达。

### 4.2 占用什么状态

**【已确认】** `Hero` 的「当前所在活动」是 `05` §3.2 已定义的状态字段，其取值域包含「空闲 / 日常活动 / 队伍任务中」。

**【建议】** 因此占用模型是**最小**的：占用 = 「当前所在活动」这一槽位被一个**行动实例**持有。

**【建议】** 由此得到一条新的不变量，建议补入 `05` §5：

| # | 不变量 | 来源 | 断言形式（建议） |
|---|---|---|---|
| **I16** | **同一英雄同一时刻至多处于一个行动**（含日常活动与队伍任务） | 本文 §4.2；`05` I2 的日常侧对应物 | 对每个英雄 `h`，`Count(actions where h is owner) <= 1` |

**【建议】** **I16 与 `05` I2 不重复**：I2 管的是「同一时刻至多被分配到一个**进行中的任务**」；I16 管的是「至多处于一个**行动**」，它同时覆盖日常行动与队伍任务，是 I2 在更一般的意义上成立的前提。**建议把 I16 表述为 I2 的上位不变量。**

**【已确认】** `05` §2.3：英雄模块是「当前所在活动」的唯一写者。因此占用状态的写入**只能**由英雄模块完成（不变量 I10）。

### 4.3 完成

**【建议】** 耗时活动到期时的处理：

```text
remain(a) ← remain(a) − 模拟步长
完成条件：remain(a) ≤ 0
完成后：remain(a) 被置为 0（不再为负）
```

**【建议】** 输出范围与性质：

| 量 | 范围 | 性质 |
|---|---|---|
| `remain` | **[0, +∞)** | **单调不增**；到期后**截断为 0**，**永不为负** |

**【建议】** **「永不为负」不是洁癖，是幂等性的实现方式**：它保证**同一个行动实例不可能触发两次完成**——因为第二次进入时 `remain` 已经是 0，完成条件里的 `<= 0` 会被再次满足。因此必须配合一条额外的守卫：

> **断言 A-03（行动只完成一次）**：对同一行动实例连续调用两次完成处理，断言第二次产生的领域事件数**为 0**，且村庄资源与英雄持有物的**增量第二次为 0**。

**【已确认】** 这条与 `05` I4（副本结算只做一次）、I15（结算要么全做要么不做）是同族要求，但作用对象是**行动**而非副本。第一阶段**行动完成的结果是否可能为空**属【待定】（`02` F-05 对副本的处理是「合法的零增量结算」；日常行动尚无同类规则）。

**【建议】** **完成先于新决策**（§2.4 第 2 步排在第 4 步之前）的另一条理由：**刚完成的行动产出的东西应当能立刻参与同一模拟步的 S5 前置校验。**

### 4.4 行动中的存档

**【待定】** 一个进行中的耗时行动在存档中如何表示。

**【建议】** 唯一自洽的表示是：**行动实例连同其剩余时长一起进存档**。否则读档后要么行动凭空消失（英雄的当前活动指向一个不存在的实例，触发 `05` §4.2 的「引用断了 → 校验失败」），要么行动被重算一次。

**【建议】** 因此本文向 `05` 请求为 `Hero` 增加一个字段（见 §10.1）。**在它被批准前，C-3 无法实现。**

**【已确认】** 存档不得序列化整棵场景树；字段必须经 DTO（基线 §13.7、`05` §2.6）。

## 5. 事件生成与杂谈

### 5.1 原则：事件驱动，不是随机生成文本

**【已确认】** 基线 §7.2：**杂谈根据已发生的事件生成消息，而不是每隔几秒随机生成文本。**

**【已确认】** 基线 §7.3：不记录无意义的随机文本；不记录系统内部状态变化（数值波动等）；不记录尚未发生的事。

**【已确认】** `05` I5：每条杂谈条目恰好对应一个已存在的事件 ID；同一事件 ID 至多一条。`05` §3.8：「来源事件 ID」是**必填**字段。

**【已确认】** `02` §5.4 C-01 的教训：**现有 `Chronicle.cs` 曾把「拒绝出工」记成「不但做完了，还在矿洞多待了半日」**——同一代码路径会为相反的事实生成正面描述。

### 5.2 反装饰规则

**【建议】** **领域事件只在「状态确实变了」时产生。** 一个动作如果既不改变任何运行时状态、也不构成一个已定义事件类型，**它就不产生事件，也不产生杂谈条目**。

**【建议】** 这条规则的依据有三处，且互相独立：

1. **【已确认】** `src/VillageLife.cs:11-13` 的现有注释：「事件必须改状态，不能只是写一句话……如果一个事件写进杂谈却什么都不影响，那它就是装饰，删掉。」
2. **【已确认】** `07` 技术债 **B7**：`Chronicle.cs` 的 `DayIdle` / `DayStranger` 是装饰条目，不改任何状态，违反基线 §7.3。
3. **【建议】** 反之，若一条杂谈说「他采集了」而持有物没变，那与 C-01 是同一类错误的镜像。

**【建议】** 由此得到一条**现在就能写的断言**（不需要任何数值）：

> **断言 A-04（杂谈不说谎）**：对任意一条 `ChronicleEntry`，其来源 `DomainEvent` 的发生时刻，领域状态**确实发生了**该事件所声明的变化；不存在「有条目但状态未变」的条目。
>
> 这条断言是 `07` C-01 的常态化版本，**建议写进 `06` 的事件与杂谈验收项。**

### 5.3 自主行动产生哪些事件

**【建议】** 第一阶段，**英雄自主行动**只产生下列事件类型：

| 事件类型 | 触发 | 参与者 | 状态变化（反装饰规则要求） |
|---|---|---|---|
| `HeroActionStarted` | S6 通过 | 该英雄 | 当前所在活动 = 该行动实例 |
| `HeroActionCompleted` | S7 到期 | 该英雄 | 当前所在活动 = 空闲 / 下一行动 |
| `HeroActionProduced`【建议】 | S7 且活动有产出 | 该英雄 | **由拥有该数据的模块写入**：物品 → 英雄持有物；资源 → 村庄资源 |
| `HeroActionAbandoned`【建议】【待定】 | 行动被中断 | 该英雄 | 当前所在活动改变。**触发条件属【待定】**，见 §9 Q2 |

**【已确认】** **`HeroActionProduced` 的写入方不是英雄模块单方面决定的**：物品写入由英雄模块执行，资源写入由村庄与建筑模块执行（不变量 **I10**：跨模块的状态改变只经由拥有该数据的模块；`02` P8 第 4 步同款拆分）。

**【建议】** 事件类型注册表采用**可扩展注册表**（`05` §3.7）：第一阶段只注册第一阶段会产生的类型；**新增类型不得要求重写调度顺序或决策流程**（基线 §11.1 同款要求适用于领域事件类型）。

### 5.4 明确**不**产生事件的情况

**【建议】** 以下是**合法空转**，**必须不产生事件、不产生杂谈条目**：

| 情况 | 依据 |
|---|---|
| S1 判定该英雄本步不参与决策（占用中 / 随队） | D-006；无状态变化 |
| S2 候选集为空 | 无状态变化（基线 §7.3「不记录系统内部状态变化」） |
| S4 抽签过程本身 | 随机数不是状态 |
| S5 前置校验失败并重采样 | **【建议】** 这是一次**决策过程的内部细节**，不是「发生了什么」；若记录它，杂谈会在玩家眼里变成系统自述，违反基线 §7.3 |
| 单纯的时间推进 | 无状态变化 |

**【建议】** **S5 失败不记入杂谈**是一条值得坚持的取舍：它能保证杂谈讲的是**世界里发生的事**，不是**系统内部在做什么**。若将来需要暴露它，正确做法是加一个**独立的诊断读数**，而不是塞进杂谈。

### 5.6 杂谈的其它约束

**【已确认】** 杂谈**只是一个功能，一个文字面板**，不是叙事主干，不承担剧情职责（基线 §7.1 开发者原话）。

**【建议】** 因此本文对杂谈**不提出任何文本风格、语气、叙事连贯性的要求**。杂谈的**规则**只有三条：来源事件 ID 必填、同一事件至多一条、无事件时不产生条目（I5；基线 §7.4 C1–C4）。

### 10.3 Q2 的三个选项（死亡与进行中的行动）

**【已确认】** 已定的前提：死亡后复活，**无任何代价**——没有战力损失、没有时间惩罚、没有装备或物品损失、没有关系恶化（基线 §4.6，`02` F-06，`05` I6）。

**【建议】** 前提没有回答的是：**一个正在进行中的行动，在持有它的英雄死亡时怎么办。** 这是一个**没有被任何上游文档覆盖**的问题，三个选项：

| 选项 | 内容 | 后果 |
|---|---|---|
| **(a)** | 行动**照常完成** | 最简单，无任何代价；**【建议】** 但意味着「死亡」在行动层面是**完全不可观测**的 |
| **(b)** | 行动**中断**，不产生任何产出，且**不产生任何损失**（等同提前结束） | 无代价，但产生了「免费取消行动」这个**潜在套利**（主动寻死以取消耗时行动） |
| **(c)** | 行动**中断**，且明确「中断不是无害的」 | 需要引入某种损失，与基线 §4.6 冲突 |

**【建议】** **我倾向 (a)**，理由：基线 §4.6 是一张**穷举表**（五个问题全答「没有」），(b) 与 (c) 都在表外引入了新的后果；而 (a) 在结构上最简单，且不与 I6 冲突。**但这是你的决定，本文不代选。**
