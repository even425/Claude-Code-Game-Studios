## 三类标记（本文档的规则标记，与两份实例的「原话/推导/新增」并存）

| 标记 | 含义 | 判定标准 |

| **【通用】** | **两个实例都必须满足**，且**一字不改即可继承** | 在实例①②里都能指到**同一个**约束/纪律 |

## Summary

村庄会周期性地遇到**大事**：外面的兽群压过来、一辆路过的车停在村口。
两个已做出来的大事件**在时间、空间、参与方式、后果四个维度上几乎不重叠**——
但它们用**同一张九格表**都表达得出来。

**这张九格表就是本文件。** 它的形状是固定的（九个槽位一定存在），
它的**取值每个实例自己填**，而**框架不给任何默认值**。

**两个实例给出的、最重要的一条结论**：框架不能是「九格表 + 一套默认值」，
必须是「九格表 + **每格一组可插拔的实现**」。
理由不是哲学，是可测的——**兽潮与商队在九个槽位里有五个的取值方向相反或缺省**（§ 零改动验证表）。

**第二个实例唯一不可替代的产出**：它证伪了兽潮自我复用的清单里的两条
（「两拍预警够用」「G4 = 被卷入」）。**一个框架如果没有被证伪过，它就不是框架，是一个实例。**

> **Quick reference** — Layer: `Feature` · Priority: `Vertical Slice` ·
> Key deps: `时间与作息 #1`、`杂谈 #11`、`性格系统 #3`、
> 以及两个实例各自的依赖（兽潮：#3 #6 #7；商队：#8 #4 #5）

## Overview

「一个大事件要让玩家看见什么」这个问题，两个实例各自回答了一次，答案的**槽位顺序完全一致**：
名称 → 触发 → 预警 → 参与 → 进行中读数 → 结算 → 后果 → 杂谈 → 接口。

**这九个槽位是【通用】的**（两个实例都能用同一张表表达出来，且没有一个是凑数的）。

**九个槽位的取值不是【通用】的**。本文件逐槽位给出**已被两个实例证实过的取值集合**，
以及**每个取值必须满足的可测断言**。框架**不选默认值**。

| 槽位 | 两个实例的取值 | 框架的立场 |
|---|---|---|
| G1 名称与一句话 | 都是「**带走什么 / 错过什么**」的形状 | ✅【通用】连形状一起通用 |
| G2 触发 | 变周期+筛选落点 **vs** 固定周期+锚定钟点 | 🔄 两个**已证策略**，无默认值 |
| G3 预警 | 2 拍 **vs** 3 拍 | 🔄 拍数是参数（`Beats ≥ 2`） |
| G4 参与 | 被卷入 `Present` **vs** 自愿登记+先到先得 | 🔄 同一个二元骨架，插拔点在「谁有资格」 |
| G5 进行中读数 | 战线读数 **vs** 无 | 🔶 **可选端口**（可以是「无」） |
| G6 结算 | 逐 tick×4.5h **vs** 一次性 | 🔄 粒度是参数，四条不变量通用 |
| G7 后果 | 全负（材料/磨损/停工） **vs** 正负混合（材料→钱+落败者） | ✅ 形状通用（三重封顶+不变量），方向是参数 |
| G8 杂谈 | 各 6 条，纪律一字不改 | ✅ **纪律层完全通用** |
| G9 接口 | 三个端口，末端单向 **vs** 双向 | 🔄 端口数通用，末端方向是参数 |

**本文件最重要的一节是 § 零改动验证表**：它逐槽位给出**框架给了什么、两个实例各填什么、
是否只填参数**。**那一节的判定必须全部是「是」，框架才算抽对了**——
任何一格是「否」，说明框架抽错了，回去重抽。

## § 三条不可协商的形态约束（**框架的自我约束**）

> 这三条是**防止「补丁味」的宪法**。它们不是建议，是**框架的验收标准**。

### 约束一 · **框架不为任何槽位提供默认值**

**理由**：两个实例在 9 个槽位里有 **5 个取值方向相反或缺省**。
任何一个默认值都等于**把某一个实例焊死成通用件**——那正是裁定 ⑳ 要防的第四次犯错。

- 允许的：框架提供**取值集合**（每个取值都有一个实例作证）+ **每个取值的可测断言**。
- 禁止的：框架写「默认 2 拍」「默认 4.5 小时」「默认被卷入」。

> **唯一的例外是 G8 的纪律层**（六条文案纪律）。理由：实例②**逐字声明**它是
> 「一字不改沿用兽潮」——**一个实例自己声明它是继承的，它就不是默认值，是纪律**。

### 约束二 · **每个可插拔点至少有两个被实例证过的取值，且取值空间本身不是框架的产物**

**理由**：如果框架只提供一个取值加一个 `if (eventType == ...)` 特判，
那不是插件架构，是**带分支的单体**。**框架宁可没有这个槽位，也不要一个假的槽位。**

> ⚠️ **这条把 G2 的真实状态暴露出来**：框架目前只有**两个**被证过的调度策略
> （`selected` / `anchored`），**不是一个策略空间**。见 § Open Questions 的补丁味自检。

### 约束三 · **「可选」必须是真的可选，且必须自带回落**

**理由**：G5 在商队里是「无」。若框架强制要求一个进行中读数，
商队要么被迫加一个（`caravan.md` § G3 明确说这会让它读起来像另一个游戏），
要么在框架里开一个 `if (type == caravan)` 的洞。**两个都是补丁味。**

**因此框架规则**：
1. 可选端口**允许填「无」**；
2. 每个可选端口**必须自带一条回落**（不依赖别的文档拍板就能生效）；
3. **可选端口被填「无」时，不允许任何其它槽位的取值依赖它的存在**。

## § 🔴 零改动验证表（本文件的验收标准）

> ### 验收标准原文
> **「把框架抽出来后，实例①与实例②必须都能用「只填参数、不改规则」的方式表达出来。
> 任何一份需要改规则才能套进框架，就说明框架抽错了 —— 回去重抽。」**
>
> **下表是这一条的可执行形式。每一格都必须判「只填参数」。**

**判定口径**：
- **只填参数** = 实例的该槽位取值**全部**落在框架已列出的取值集合内，且框架不需要为它加分支、加特判或加条件。
- **需改规则** = 框架必须新增一条分支/特判/新槽位才能容纳它 → **框架抽错**。

| 槽位 | 框架提供的**形状** | 框架提供的**取值集合**（每项均有实例作证） | 实例①兽潮填入 | 实例②商队填入 | 判定 |
|---|---|---|---|---|---|
| **G1** 名称与一句话 | `名称 + 一句话 + 取舍方向`（三段） | 形状唯一，取舍方向 ∈ {拿走/给/错过} | 「一段时间里从某个方向压过来的兽群；**顶住不损失，挡不住损失材料**」 | 「定期路过村口的一辆车，收材料；**卖完就走，错过不补**」 | ✅ **只填参数**（连形状都由两实例共同定义） |
| **G2** 触发 | `调度策略 ∈ {selected, anchored}` + 一个反退化断言 | `selected`：变周期 + 候选集筛选（兽潮 F2）<br>`anchored`：固定周期 + 固定钟点（商队 B1） | `selected`<br>`RAID_INTERVAL_MIN/SPAN`、`NO_REPEAT_RADIUS`、`SET_MIN_SHIFT` | `anchored`<br>`CARAVAN_PERIOD`、`CARAVAN_HOUR` | ✅ **只填参数**（策略名 + 数值，两实例各占一项） |
| **G3** 预警 | `拍数 Beats ≥ 2` + 每拍 `{提前量, 给什么, 落在哪}` | 拍数 ≥2（兽潮 2、商队 3）；落点 ∈ {杂谈, 花名册侧栏} | `Beats=2`：不安(1日) → 定更(6h) | `Beats=3`：挂榜(3日) → 定更(6h) → 开市(0h) | ✅ **只填参数** |
| **G4** 参与 | `Roster(t) = Source(t) ∩ Qualify(t)`，`Qualify` 可插拔 | `Qualify` ∈ {恒等（被卷入）, 自愿+先到先得} | 恒等：`Present(t)`，**无报名无点名** | 自愿：开市前已登记 ∧ 名额未满 | ✅ **只填参数**（`Qualify` 是一个函数接口，两实例各实现一个） |
| **G5** 进行中读数 | **可选端口**，可填「无」 | 存在（兽潮型：逐 tick 刷新） / **无**（商队型） | 存在：战线读数 6 行，`tick=0.25h` | **无**：开市后只有成交记号 | ✅ **只填参数**（可选端口填「无」是被框架明确允许的） |
| **G6** 结算 | `粒度` + 四条不变量（推进/冻结/封顶/不能靠耗时间赢） | 粒度 ∈ {逐 tick, 一次性} | 逐 tick，0.25h，4.5h/3 波 | 一次性，开市瞬间算完 | ✅ **只填参数** |
| **G7** 后果 | `三重封顶 + 不变量清单 + 无永久损失` | 方向 ∈ {纯损失, 转换, 纯收益} | 纯损失：材料被啃 / 罩磨损 / 停工 | 转换：材料 → 钱 + 摊位易主 | ✅ **只填参数**（形状两实例逐字同族） |
| **G8** 杂谈 | **纪律层**（六条，一字不改）+ 条目表（时机/文案/署名/分类） | 纪律层唯一；条目数实例自填 | 6 条 | 6 条 | ✅ **只填参数**（实例②逐字声明「一字不改沿用兽潮」） |
| **G9** 接口 | 三个端口 + `PortDirection ∈ {Out, InOut}` | `Out`（兽潮）/ `InOut`（商队） | `RaidSchedule` / `OnRaidTick` / `RaidAftermath`，`Out` | `CaravanSchedule` / `CaravanTick` / `CaravanTurnaways`，`InOut` | ✅ **只填参数** |

### 验证结论

**9 格全部「只填参数」，零「需改规则」。** 两个实例**不需要改动一个规则、一个分支、一行文本**。

**两处需要说明的「参数 vs 特判」边界**（两处都在框架内有名字，都不是分支）：

| 处 | 框架内的实现形式 | 为什么它不是特判 |
|---|---|---|
| G2 的两个策略 | 一个**枚举** `scheduling ∈ {selected, anchored}`，不是 `if` | 两实例各作证一个值；框架**不为任何一个设默认**，第三实例必须显式选一个（约束二） |
| G9 的单向/双向 | 一个**枚举** `PortDirection ∈ {Out, InOut}` | 端口**位置与数量完全相同**（三个），变的只是末端的一个布尔标记——不是另一套接口 |

### 独立验证：实例②的逐槽位判定对不对？

**裁定**：**六条判定里五条成立，一条措辞需要修正。**

| 实例②的判定 | 本文件的独立结论 |
|---|---|
| G1 / G8 ✅ 完全通用 | **成立，且低估了**。G1 不只是「名称通用」——**两实例的一句话都带同一段结构：写明「带走/错过什么」**。没有任何一个大事件的一句话是「一件好事发生了」。这条形状应当**升格为 G1 的通用内容**，否则第三个实例会写出一句「节日又到了」。 |
| G2 / G4 🔄 同槽位、取值方向相反 | **成立**。补充：G2 的真正共同点**不是「周期与钟点」这四个字**，而是一条**可测断言**——两实例都要求「村庄状态改变 ⇒ 调度输出逐项相同」（兽潮 AC-A2 / 商队 AC-A2）。**G2 的通用件是这条断言，不是任何一种调度算法。** |
| G3 🔁 通用槽位 + 实例取值 | **成立**。补充：**两拍还是三拍，不取决于事件类型，取决于「预警期有多长 + 一个下游窗口什么时候关」**。商队多一拍是因为登记窗口要提前关（`REGISTER_CLOSE_HOURS = 6`）。所以 `Beats` 是一个**派生量**，不是自由参数——见 F5。 |
| G5 🔶 必须做成可选 | **成立，但边界要写死**。商队**不是没有读数**，它是**没有「进行中」读数**——它有事前读数（侧栏四行：日子/钟点/收购清单/登记状态）。若不划这条界，第三个实例会把自己的侧栏误填进 G5。**G5 的定义必须是「从事件开始到结束之间」的读数。** |
| G6 🔁 通用槽位 + 实例取值 | **成立，且低估了**。兽潮的「逐 tick 推进」**不是** G6 的形状，G6 的形状是**四条不变量**：推进 / 名单与价格冻结 / 封顶 / 不能靠耗时间赢。**两实例四条全部满足。** 只有「粒度」是参数。 |
| G9 ⚠️ 接口形状必须换 | **成立，但「形状」这个词用得过重**。两实例的接口**数量与位置完全一致**（Schedule / Tick / Aftermath），变的只有末端的一个方向标记。若真按「形状不同」实现，会造出两套并行接口——那才是补丁。**框架只需一个枚举。** |

## Detailed Design

### § A · 九个槽位的通用契约

> 每个槽位写成三段：**是什么**（形状）· **取值集合**（已证）· **必须满足的可测断言**。
> **断言是真正通用的那部分**——形状会被改写，断言不会。

#### G1 · 名称与一句话

- **形状【通用】**：`名称 + 一句话 + 取舍方向`。
- **取值集合【实例参数】**：取舍方向 ∈ {拿走什么 / 给什么 / 错过什么}。
- **断言【通用】**：
  - **G1-a**：一句话里必须出现**一个可被村民感知的代价或损失**（顶不住 / 错过 / 卖掉）。
    **禁止一句话只描述事件本身**（「一个车队路过」不合格）。
  - **G1-b**：一句话里**不得出现** § 破坏者 #12 的六个系统词。
- **为什么**：两实例的一句话**形状完全一致**——
  兽潮「顶住不损失，挡不住损失材料」，商队「卖完就走，错过不补」。
  **它们都不是「一件好事发生了」。** 这不是巧合，是这个游戏的地基（`game-brief.md`「没有硬失败」）。

#### G2 · 触发

- **形状【通用】**：`调度策略`（枚举）+ `首次延迟` + `调度输出必须不读村庄状态`。
- **取值集合【实例参数】**（**两项，均有实例作证，框架不设默认**）：

| 策略 | 定义 | 作证 | 适用的场合 |
|---|---|---|---|
| `selected` | 周期可变 **且** 落点从候选集里筛 | 兽潮 F2 | 事件需要**换一批人**，且「换人」是设计内容 |
| `anchored` | 周期固定 **且** 钟点固定 | 商队 B1 | 事件来自外部行程，**村庄对它的时刻零影响** |

- **断言【通用】**（**这是 G2 唯一的通用件**）：
  - **G2-a（反退化 · 强）**：固定种子下，**改变村庄的强弱/等级/产出**（`VillageTier`、`ShieldLevel`、人口、材料）
    **不改变调度的输出序列**。
    兽潮 AC-A2 与商队 AC-A2 **断言的是同一条**，只是对照组不同（罩 vs 摊位容量）。
- **两条策略如何同时满足 G2-a**：
  - `selected` 读的是**名册作息**（`Roster(h)` / `TVdist`），不是村庄强度；
  - `anchored` 什么都不读。
  **目标相同，手段相反**（商队 § B1 原话）。
- **⚠️ 反例（框架禁止）**：把村庄等级接进 `RaidAt` 或 `CARAVAN_AT`。
  那会让玩家「把村庄养薄一点钓好时段」——**系统被玩家操纵，不是村庄在过日子**（兽潮 § C1）。

#### G3 · 预警

- **形状【通用】**：`拍数 Beats ≥ 2`，每拍 = `{提前量, 给玩家什么, 落在哪}`。
- **取值集合【实例参数】**：
  - `Beats ∈ ℕ⁺, Beats ≥ 2`（兽潮 2 / 商队 3）
  - 落点 ∈ {杂谈（`chronicle.md`）, 花名册侧栏}
- **断言【通用】**：
  - **G3-a**：**最后一拍必须给出一个精确到村庄小时的时间锚**，且该锚必须让玩家来得及安排自己上线。
    兽潮 § B2 对此给了取舍说明：**没有这一拍，原话 C「玩家会想办法上线」就没有抓手。**
  - **G3-b**：**时间锚不进杂谈，只进花名册侧栏**（可原样搬走 #8）。
    两实例都这么做了。
  - **G3-c**：**第一拍必然是「无后果条目」**——它只报告「要发生了」，还没改任何受监视字段。
    **因此它必然踩中 § § 一次性解法 ①**，这是结构性的，不是巧合。
  - **G3-d**：预警**不得给出玩家无法据以行动的细节**。兽潮的第一拍**刻意不给时刻**
    （给了时刻，「要不要上线」就退化成查时刻表的机械动作）。

> **「两拍够用」被实例② 证伪。** 兽潮复用清单 § 🔶-3 写的是「槽位固定，拍数可变——但需要实例② 证实」。
> **实例② 给出的答案是：拍数是派生量，不是自由参数**——见 F5。

#### G4 · 参与

- **形状【通用】**：
  ```
  Roster(t) = Source(t) ∩ Qualify(t)
  ```
  `Source` **恒定**为 `Present(t)`（`time-and-schedule.md` F5，**两实例都不重算、不缓存**）。
  框架**只**把 `Qualify` 做成可插拔。
- **取值集合【实例参数】**：

| `Qualify` | 定义 | 作证 | 性质 |
|---|---|---|---|
| `恒等` | 无额外条件，**被卷入** | 兽潮 D1/D2 | 没有人能选择不参加 |
| `自愿 ∧ 名额未满` | 开市前已登记，且登记时名额未满 | 商队 D1 | 有人能选择参加，且**先到先得** |
- **断言【通用】**：
  - **G4-a（铁律 1 守门 · 静态扫描）**：`Qualify` 的实现里
    **`EfficiencyOf` 与 `ScoreOf` 均 0 命中**。
    **两实例各自的 AC 都在扫这一条**（兽潮 AC-C1 / 商队 § Dependencies）。
    性格只能影响**结算时的出力**，绝不能影响**谁有资格**。
  - **G4-b**：有名额上限的事件（商队），**早登记不得换来更多配额**。
    商队 D3/F5 用 `PerStallQuota` 均分消灭了「永远第一个去点」——**这是一条通用反退化纪律**。
  - **G4-c**：`Roster` **允许为空**，且**系统不为它保驾**。
    兽潮 E5（允许兽潮落在空档钟点，三处全破）、商队 E2（`ActiveStalls = 0`，照常来照常停）。
    **承裁定 ⑯「不做软保底」。**
  - **G4-d**：**不得提供任何「让村民为本次事件调整上线时间」的入口。**
    **裁定 ⑰**：玩家不能改写村民作息。
    商队 § B4 把它列为「反面的诱惑（我否掉的）」，兽潮 OQ-5 是同一条理由。

#### G5 · 进行中的可读状态（**可选端口**）

- **形状【通用】**：`进行中读数 = { 若干行，每行有刷新节奏 }`，**允许为「无」**。
- **取值集合【实例参数】**：存在（逐 tick 刷新）/ **无**。
- **⚠️ 边界写死（约束三）**：G5 的定义是
  **「从事件开始到事件结束之间」**的可读状态。
  **事件之前**的读数（日子 / 钟点 / 清单 / 登记数）属于 **G3 的侧栏**，**不属于 G5**。
  兽潮的定更钟点行属 G3-b；商队的四行侧栏也属 G3。
- **断言【通用】**：
  - **G5-a**：若存在，**刷新节奏必须是一个固定 tick**，且**不得每帧重算**（承 `chronicle.md` E15 纪律）。
  - **G5-b**：若填「无」，**其余任何槽位的取值不得依赖它的存在**。
  - 商队 E 组的判法可直接搬走：
    **「没有人问『还剩多少』」是合法结果**，而「有人问『打死了给什么』」才是沟通问题（兽潮 AC-E4 同族）。
- **回落（约束三第 2 条）**：填「无」时回落 = **无**。
  **框架不提供任何替代读数**——商队 § G3 的论点是「强行加一个会让它读起来像另一个游戏」。

#### G6 · 结算

- **形状【通用】**：`粒度` + **四条不变量**。
- **取值集合【实例参数】**：`粒度 ∈ {逐 tick, 一次性}`。
- **断言【通用】（这四条才是 G6 的通用件，「逐 tick 推进」不是）**：

| # | 不变量 | 兽潮的形态 | 商队的形态 |
|---|---|---|---|
| **G6-a 推进** | 结算挂在 `AbsoluteHour` 上，**不自建时钟** | 逐 `0.25h` 推剩余兽数 | 开市瞬间一次算完 |
| **G6-b 冻结** | **每个阶段冻结参与名单 / 价格 / 规模** | 每波名单冻结（E10/E18）；兽力整潮冻结（F3） | `ActiveStalls` 在开市瞬间算完（D3）；`ArrivalMark` 一趟内恒定（F1） |
| **G6-c 封顶** | **结算结果有硬上限，与次数无关** | 破口次数 ≤ 波数；`Wear` 增量 ≤ `0.30`（H4/F8） | `Σ 成交 ≤ IntakeQuota`，**总量封顶不是次数封顶**（E11） |
| **G6-d 不能靠耗时间赢** | **延长时长不改变结果强度** | 兽力不随时间衰减（F3 / AC-D4） | 报价在一趟内冻结（AC-D3） |

- **G6-e（一次 `dt` 跨过整段）**：**按段推进，不补写中间过程的杂谈条目**。
  承 `time-and-schedule.md` E6 / `chronicle.md` E7「宁可少跑，不可刷屏」。
  两实例 E1/E11 是同一条。

#### G7 · 后果

- **形状【通用】**：`三重封顶 + 不变量清单 + 无永久损失`。
- **取值集合【实例参数】**：方向 ∈ {纯损失, 转换, 纯收益}。
- **断言【通用】**：
  - **G7-a**：**建筑集合 / `VillageTier` / `ShieldLevel` / 名册 全部恒不变**。
    **任何大事件都不许拆建筑、不许移除村民。**（`game-brief.md`「没有硬失败」是硬约束，不是氛围词）
  - **G7-b**：**资源扣除后 `≥ 0`**，且**存在贫村保底**（兽潮 `TotalMaterials ≤ 5` 时不扣）。
  - **G7-c**：**没有永久损失**——失去的东西可以再挣回来。
    兽潮：材料可再跑副本；商队：材料可再跑副本。
    **两实例的「卡住 = 材料不够」是同一条地基**。
  - **G7-d**：**单次事件的后果次数有硬上限**（兽潮 ≤3 处破口；商队 ≤1 趟）。
  - **G7-e**：**没有「认输 / 重开 / 放弃村庄」的出口**。
    兽潮 H3；商队唯一的开关是 `refuse_market`（零后果，且**二值开关没有调参空间，因此没有退化空间**）。

#### G8 · 写进杂谈的条目

- **形状【通用】**（**纪律层一字不改**）：条目表 `{时机, 文案样板, 署名, R1b 分类}`。
- **取值集合【实例参数】**：条目数（两实例各 6 条）。
- **断言【通用】**：承 § 破坏者 #2 的六条纪律，**逐条照抄，不改一个字**：
  1. 六词零命中：成功 / 失败 / 获得 / 消耗 / 属性 / 奖励
  2. 内部量名零命中
  3. 不写数字（行情只写档位词，不写倍数）
  4. 不得使用 `{l}` 槽位（`chronicle.md` R6b：地点是任务绑定的，大事件不是任务）
  5. 署名规则（`chronicle.md` R4）
  6. 模板收口到**同一个定义点**，按维度分组（R5）
- **⚠️ G8-c（结构性事实，两个实例独立出现）**：
  **每个实例的六条里，恰好有一条被判为「无后果 → 近况」，而它恰好是预警的第一拍。**
  兽潮条目 1「不安」、商队条目 1「挂榜」。
  **这不是巧合，是 G3-c 的必然结果**——第一拍在时间上还没改任何受监视字段。
  **它就是 § § 一次性解法 ① 的全部动机。**

#### G9 · 依赖的系统与新增接口

- **形状【通用】**：`恰好三个对外端口` + `末端方向`。
  ```
  <Name>Schedule()   → Pending<T> | null      // 是否有已定更的事件
  <Name>Tick(dt)     → <T>Report              // 推进，返回本帧可读状态
  <Name>Aftermath(t) → 后置状态                // Direction ∈ { Out, InOut }
  ```
- **取值集合【实例参数】**：`PortDirection ∈ {Out, InOut}`。
  - `Out`：只写自己的后置状态，**不读外部系统**（兽潮 `RaidAftermath → { Direction, ScarcityHours }`）。
  - `InOut`：**读外部系统拥有的表 + 写外部系统拥有的状态**（商队：读 #8 的 `MatWeight`，写 `VillageCoin.Stall`）。
- **断言【通用】**：
  - **G9-a**：**恰好三个对外接口**，其余字段 `private` / `internal`。
    与 `personality.md` / `relations.md` 是同一条纪律，两实例各自在 AC 里把它变成静态扫描。
  - **G9-b**：**跨系统只读既有输出，不改别人的公式。**
    兽潮不改 `ShieldLoad`；商队不改抽成公式（AC-C2 逐字校验）。
  - **G9-c（端口纪律 · 本框架对 OQ-F2 的裁决）**：
    **事件可以读一张它不拥有的价格表，也可以写一个它不拥有的计数器，
    但绝不可以定义价格。**
    兽潮 `ScarcityHours = 8`（一个**时长**，不是价格）；
    商队 `MatPrice = MatBase × MatWeight × ArrivalMark`（`MatWeight` 归 #8/#7，事件**只读**）。
    **「外部扰动 → 经济」的接口到这里为止**——它是一个**端口契约**，不是一个定价器。
  - **G9-d**：单事件被 `enabled = false` 关掉时，其它系统的回归实测值**逐字符不变**。

### § B · 🔴 一次性解法 ①：**预警条目落进滚动面板**（两个实例的同款失败）

> **问题陈述**：兽潮 OQ-2 与商队 OQ-6 是**同一个洞的两次命中**：
> 预警第一拍写进杂谈，但按 `chronicle.md` **R1b** 的判据
> （条目写入时受监视字段是否变化）**不改任何受监视字段** → 判为**无后果**
> → 落进**近况**（滚动 16 行）→ 在 `DailyEventCount` 每天 2–4 条的速度下
> **很可能在你看到之前就被挤掉**。
>
> **两个实例在同一个地方栽了同样的跟头，这就是该在框架里定义一次的信号。**
> 本节**给出解法**，不把它登记为待办。

#### B1 · 为什么会这样（结构性的，不是疏忽）

见 § G8-c：**预警第一拍必然不改受监视字段**——
它在时间上发生的时候，事件还没开始，村庄什么也没变。
`chronicle.md` R1b 的判据**忠实地执行了它**，是**事件源**选了一个必然被判无后果的时机。

> **所以这不是「某个事件的文案写错了」，是「所有大事件的预警第一拍都会这样」。**
> 第三个实例会第三次栽同一个跟头——**除非框架在这里定一次。**

#### B2 · 框架裁决：**一条字段，不是 N 条字段**

```
chronicle.md 的 WatchedFields 增加恰好一条：

    PendingEvent = { kind, at }        // kind ∈ {raid, caravan, ...}

不是 PendingRaid，不是 PendingCaravan —— 是**一条**，kind 是它的取值。
```

**为什么「一条」是这套解法的全部要点**：
- 两个实例各自要的其实就是同一条东西（兽潮要 `PendingRaid`，商队要 `PendingCaravan`），
  **形状完全相同**，只是名字不同。
- **一个事件加一条字段 = 每加一个大事件就要改一次 `chronicle.md`。**
  那是**补丁味**，而它恰好是这次要消灭的东西。
- **`kind` 是枚举不是实体**：新增事件只改 `kind` 的取值集合，**不改字段本身**。

**判定立刻翻转**：预警第一拍写入时 `PendingEvent` 发生变化 → R1b 判为**有后果**
→ 进**留档**（永久）面板 → **玩家一定看得见**。

**并且这一条同时消掉了 `chronicle.md` R1b 那个封闭清单的隐患**：
该清单本就规定「**只增不减**」，增量是它的正常用法（兽潮 OQ-2 原话）。
**框架这次做的不是破例，是用它自己的规定。**

#### B3 · 回落（约束三第 2 条：可选必须自带回落）

**若 `chronicle.md` 的 Owner（`narrative-director`）拒绝这条字段：**

| 步骤 | 动作 | 后果 |
|---|---|---|
| 1 | 框架**自动**切到回落档 | 不需要第二次拍板 |
| 2 | 预警第一拍**不写杂谈**，改写在**花名册侧栏**（与最后一拍同一个位置，G3-b） | 玩家仍然看得见，只是**发现得更晚** |
| 3 | 侧栏第一行常驻**直到事件结束** | 不会像滚动面板那样被挤掉 |

> **回落不会让任何实例改规则。** 它改的是**一条条目的落点**，而落点本来就是 G3 的参数。
> **这正是框架存在的意义**：一个上游的拒绝，不需要任何一个实例重新设计。

#### B4 · 这不是发明

| 证据 | 出处 |

| 「把 `PendingCaravan` 加进 `WatchedFields`」 | 商队 **OQ-6** 的建议原文 |

**两条形状相同的请求 → 合并成一条声明**，这是裁定 ⑳ 交给框架的工作本身，不是新机制。
**框架不发明新机制这条规则未被违反。**

### § C · 🔴 破坏者结构的兑现点：**跨事件资源归属**

> **这条是两个实例「对撞」出来的一条通用纪律，它不属于任何一个实例。**

**兽潮立**（§ G4 原文）：
> 「这是兽潮唯一给村庄经济带来的东西：**一个持续的、专用的材料去处。**
> 它不是掉落、不是奖励，是**维持**。」

**商队遵守**（§ F4）：
> 「护盾修复、罩的维护 —— **同一族材料不许被第二个事件占用**」

**框架规则【通用】**：
> **同一族资源，不得被两个大事件同时声明为「自己的后置代价」。**
> 谁先立谁拥有；后来的事件必须换一族，或者明确声明**只读不写**。

| 资源 | 拥有者 | 其它事件 |
|---|---|---|
| `Wear` / 罩的修补 | **实例①** | 只读（商队明确不碰） |
| 材料（作为**代价**被扣除） | **实例②**（材料→钱） | 实例①也扣材料——**但方向相反**（兽潮是被啃，商队是被卖）。**框架按「方向」区分，不按「资源」区分**，因为两者都满足 G7-a/b/c（三重封顶、不变量、可再挣），且**互相不叠加**（各走各的扣除路径）。 |

**⚠️ 诚实标注**：材料这一行**不是干净的所有权划分**，框架只做到「方向不同、封顶独立」。
若将来出现两个事件**同向**扣同一族材料，**规则必须重新审** → **OQ-F6**。

## Formulas

> **本节只定义「通用件」的形状与不变量。**
> **所有实例专属的数值（兽谱系 Power、`LOSS_RATE`、`CARAVAN_PERIOD`、`ArrivalMark` …）一律不在这里。**
> 框架**不提供默认值**——凡写成 `[a, b]` 的都是**取值范围**，不是建议值。

### F0 · 符号表

| 符号 | 类型 | 范围 | 含义 |
|---|---|---|---|
| `t` | float | `≥ 0` | `AbsoluteHour`，村庄小时，**两个实例与 `expedition.md` F1 同一口径** |
| `Roster(t)` | set | `⊆ 名册` | 时刻 `t` 的参与者集合 |
| `Qualify` | func | — | G4 的可插拔资格函数 |
| `Beats` | int | `≥ 2` | G3 的预警拍数 |
| `Δt` | float | `> 0` | 结算粒度（村庄小时） |
| `Cap` | int | `≥ 1` | G6-c 的封顶值（次数或总量，二者之一） |
| `PendingEvent` | struct | — | § B2 的一条受监视字段 |
| `PortDirection` | enum | `{Out, InOut}` | G9 末端的方向 |

### F1 · 参与者集合（G4 的通用式）

```
Roster(t)  =  Present(t)  ∩  Qualify(t)
```

| 符号 | 类型 | 范围 | 含义 |
|---|---|---|---|
| `Present(t)` | set | `⊆ 名册` | `time-and-schedule.md` F5 的既有函数。**框架不改写它** |
| `Qualify(t)` | set | `⊆ 名册` | 实例可插拔的资格函数 |
| `Roster(t)` | set | `⊆ 名册` | 结果 |

**输出范围**：`Roster(t)` 是名册的子集，`|Roster| ∈ [0, |名册|]`。

| 取到下界 0 的输入 | 取到上界的输入 |
|---|---|
| 全员不在场（承裁定 ⑯：不做软保底）、或全员病倒（兽潮 E7）、或无人登记（商队 E2） | 全员在场且 `Qualify = 恒等` |

> **`Roster(t) = ∅` 是合法输出，框架必须允许它，且不得为它保驾**（G4-c）。
> **这不是边界情况，是两个实例都实测过的正常状态。**

**守门（框架级静态扫描）**：
```
Qualify 的实现里  EfficiencyOf(...)  → 0 命中
Qualify 的实现里  ScoreOf(...)       → 0 命中
```
**性格只能进入结算（`Combat_i` / `EfficiencyOf`），绝不能进入资格。**
依据：`personality.md` 铁律 1 —— 唯一能让村民「不干活」的是状态，不是性格。
**两个实例各自的 AC 都在扫这一条**（兽潮 AC-C1 / 商队 AC-D1）。

**工作示例（两个实例各一）**：

```
实例①（Qualify = 恒等，t = 02:00，名册 20 人）
  Present(02:00) = { 8 人 }        ← 一字不改
  Qualify(02:00) = 全体
  Roster(02:00)  = 8 人            ← F6 场景甲

实例②（Qualify = 自愿 ∧ 名额未满，t = 10:00，名册 20 人，StallSlots = 8）
  Present(10:00) = { 9 人 }
  Qualify(10:00) = 已登记 7 人   （2 人在窗口关闭后才登记，1 人未登记）
  Roster(10:00)  = 7 人 ∩ 名额未满 = 7 人
  TurnAway       = { 1 人 + 1 个被占号位 }   ← 商队 D2 的事实
```

### F2 · 调度反退化断言（G2 的唯一通用件）

```
断言 G2-a：  ∀ 村庄状态 S, S' :
               Schedule(S,  seed)  ==  Schedule(S', seed)     （逐项相同）
```

| 符号 | 类型 | 范围 | 含义 |
|---|---|---|---|
| `S` / `S'` | struct | — | 村庄状态（人口 / `VillageTier` / `ShieldLevel` / 材料池） |
| `seed` | int | — | 固定随机种子 |
| `Schedule` | func | → 时刻序列 | 该实例的 G2 输出 |

**输出范围**：布尔。**唯一允许的取值是 `true`。**
`false` 意味着**框架被违反**，不是「这个实例平衡不好」。

**工作示例（两个实例各自的对照实验）**：

```
实例①：A 座 ShieldLevel=5，B 座 ShieldLevel=0，同种子各跑 8 场
  → 断言 8 个 RaidAt 逐个相同            ← AC-A2
实例②：A 座 tier=5（StallSlots 14），B 座 tier=0（StallSlots 4），同种子各跑 8 趟
  → 断言 8 个 CARAVAN_AT 逐个相同，
     而 ActiveStalls 与 TurnAwayCount 显著不同   ← AC-A2
```

> **实例② 的对照实验比实例① 更强**：它同时证明了「**落点不读村庄状态，但稀缺性读**」。
> 这正是「反退化」与「有内容」的分界线——**一个事件可以完全不受玩家操纵，同时仍然对村庄有影响**。
> **这条应该成为框架对所有大事件的验收形状。**

### F3 · 阶段封顶（G6-c 的通用式）

```
每阶段结算后：  OutcomeCount  ≤  Cap        （Cap = 阶段数 或 总量，二者之一）
一旦越过 Cap，后续阶段不再增加 OutcomeCount。
```

| 符号 | 类型 | 范围 | 含义 |
|---|---|---|---|
| `OutcomeCount` | int | `≥ 0` | 本次事件已产生的结果次数（破口数 / 成交次数） |
| `Cap` | int | `≥ 1` | 硬上限 |
| `Δt` | float | `> 0` | 粒度；`Δt → 0` 不改变 `Cap` |

**输出范围**：`OutcomeCount ∈ [0, Cap]`。**上界由 `min()` 保证，不是由调参保证。**

| 取到下界 0 | 取到上界 `Cap` |
|---|---|
| 全程顶住 / 村庄无材料 | 每一阶段都破（兽潮 3 波全破）或总量收满 |

> **⚠️ `Δt` 不在右侧出现 —— 这是故意的。**
> **把粒度调到 0.001 不会让破口次数变成 400。** 这就是「不能靠耗时间赢」的结构保证（G6-d）。
> 两个实例都独立地实现了这一条（兽潮 F3 / 商队 F1），**框架把它写成一条公式而不是一句原则。**

**工作示例**：

```
实例①：WAVE_COUNT = 3 → Cap = 3
  一次 dt 跨过整潮（--daylen=8）：逐波推进，WaveResistance 不足则破口 ×1
  破口 3 次后：第 4 波（不存在）不会再破。断言破口 ≤ 3、Wear 增量 ≤ 0.30   ← AC-B5
  ⚠️ 若实现出现第 4 次破口，那是实现 bug，不是设计

实例②：IntakeQuota = 80 → Cap = 80（总量，不是次数）
  一次 dt 跨过整趟：按段推进，但 Σ 成交 ≤ 80 恒成立                ← AC-A5
  次数可以很多（每摊位每次结算都成交），总量封住
```

> **两种封顶形状都合法**：次数封顶（兽潮）与总量封顶（商队）。
> **框架不选哪一种**——G6-c 只要求「**有一个与次数无关的硬上限**」。

### F4 · 无硬失败不变量（G7 的通用式）

```
∀ 一次大事件结束后：
    Δ(建筑集合)      = 0
    Δ(VillageTier)   = 0
    Δ(ShieldLevel)   = 0
    Δ(名册)           = 0          // 没有任何人被移除
    资源_after        ≥ 0
    若 资源_after ≤ POOR_FLOOR:    本次不扣该资源
    任何被扣资源                          可以再挣回来
```

| 符号 | 类型 | 范围 | 含义 |
|---|---|---|---|
| `建筑集合` | set | — | 村庄的建筑列表 |
| `VillageTier` | int | `[0, 5]` | 村庄等级 |
| `ShieldLevel` | int | `≥ 0` | 防护罩等级 |
| `名册` | set | — | 村民集合（长度 = `VillageCapacity` 的上界，裁定 ①） |
| `资源_after` | float | `≥ 0` | 事件后的资源量 |
| `POOR_FLOOR` | int | `≥ 0` | 贫村保底阈值 |

**输出范围**：五条不变量**恒为真**。**任何一条为假 = 框架被违反**，
不是「这个事件的平衡不好」。

**⚠️ 六条里最容易漏掉的是最后一条。**
前五条是「不许变坏」，最后一条是「**变坏了还能挣回来**」——
承 `game-brief.md`「**卡住 = 材料不够**」，
两实例各自的 H3 / F3 就是这一条：**没有任何一个大事件会让人「没救了」。**

**工作示例（两个实例各自的保底清单）**：

```
实例① H2：材料 ≤ 5 时不扣 · 扣后 ≥ 0 · 建筑/VillageTier/ShieldLevel/名册 全不变
        唯一长期代价：Wear（可花材料修，RepairCost = ceil(Capacity × 0.5)）
实例② F2：refuse_market 时零后果 · 材料 ≥ 0 · 建筑/VillageTier/ShieldLevel/名册 全不变
        关系只增 ΔChurn，永不清除既有 Bond
        唯一长期代价：材料（可再跑一趟副本）
```

> **两个实例的六条保底有四条逐字相同。** 这是 G7「形状通用」最硬的证据。

### F5 · 预警拍数的派生式（G3 的通用件）

```
Beats  =  1  +  ( 1  当且仅当  存在一个「必须在事件开始前关闭的下游窗口」  否则 0 )
```

| 符号 | 类型 | 范围 | 含义 |
|---|---|---|---|
| `Beats` | int | `≥ 2` | 预警拍数，**框架不设默认** |
| `下游窗口` | — | 有/无 | 一个必须在事件开始前关闭的、由其它系统拥有的时间窗 |

**输出范围**：`Beats ∈ [2, ∞)`。**没有上界**——预警可以有很多拍，
只要每一拍都满足 G3-a（给出可据以行动的信息）。

> ### ⚠️ 这里有一个框架用不了的取值，必须写死
> **`Beats = 1` 是不合法取值。**
> 只有一拍时，那一拍必然是**定更**（G3-a 要求它给出精确时间锚），
> 于是玩家**在知道有事发生之前就已经被告知了时刻**——
> 预警从「我要不要上线」退化成「查时刻表」，**决策消失**。
>
> **若第三实例算出 `Beats = 1`，有两个合法修法**：
> ① 把第一拍并入定更（降级成「无预警」，框架不禁止，但要在 AC 里明写）；
> ② 承认它需要一个下游窗口才能成立（那就先把它做出来）。
> **框架不给第三条路，也不替它选。**

**工作示例（两个实例为什么差一拍）**：

```
实例① 兽潮：不存在「必须在开始前关闭的下游窗口」
  → Beats = 2   不安(1 日前, 不给时刻) → 定更(6 小时前, 给时刻+方向)
  定更落在花名册侧栏，兽潮到点自动开始，玩家来不及也没关系「报名」

实例② 商队：存在「登记窗口」，它必须在开市前 6 小时关闭
  → Beats = 3   挂榜(3 日前, 只说日子) → 定更(6 小时前, 时刻+清单) → 开市(0)
  ⚠️ 若只有两拍，挂榜与开市之间不足 REGISTER_CLOSE_HOURS，
     村民在登记窗口关闭前根本来不及反应 —— 两拍在这个事件上【不成立】
```

> **结论：「两拍够用」不是通用件，是兽潮的实例取值。**
> 判定它的不是事件类型，是**下游窗口什么时候关**。

### F6 · 条目数与「无后果条目」的必然性（G8 的通用件）

```
Entries         ∈ ℕ⁺
其中被判为「无后果 → 近况」的条目数     ≥ 1
且该条目必然位于 预警第一拍（时机最早的那一条）
```

| 符号 | 类型 | 范围 | 含义 |
|---|---|---|---|
| `Entries` | int | `≥ 1` | 本事件写入杂谈的条目数（两实例各 6） |
| `无后果条目数` | int | `≥ 1` | 按 `chronicle.md` R1b 被判进近况的条目数 |
| `位置` | — | — | 必然是时机最早的一条 |

**输出范围**：若**只登记了 § B2 的框架裁决**（`PendingEvent` 进 `WatchedFields`），
则 `无后果条目数 = 0`。**否则 ≥ 1，且不可通过改文案消除。**

**工作示例**：

```
兽潮（未落 B2）：条目 1「东边的林子这两天不太平」—— 写入时无字段变化
              → R1b 判无后果 → 近况 → 滚动 16 行 → 很可能看不见     ← OQ-2
商队（未落 B2）：条目 1「听说有商队要过村。」—— 同上                  ← OQ-6
两者（已落 B2）：PendingEvent 变化 → R1b 判有后果 → 留档 → 永久可见
```

> **「无后果条目数 ≥ 1」是框架的一条**可测预测**：
> 若将来出现一个「预警第一拍被判有后果」的大事件实例，
> **说明 `PendingEvent` 那条字段已经生效了**（或者它没走标准预警）。
> **这条断言可以直接拿来当 B2 是否落地的验收信号。**

| **OQ-F1 事件冲突** | 🟠 **高** | 框架**完全缺失**这个槽位。它不是补丁味——它是**留白**，比补丁味更诚实，但也更不完整。 | **如实报告：一个连自己两个实例撞车都答不了的框架，现在还不能支撑第三个实例。** 这是它最大的短板 |
| **`PendingEvent` 字段** | 🟢 **低** | **这是补丁的反面**：两个实例各要一条形状相同的东西，框架合并成一条。**若做错**（做成两条），AC-B2 会当场抓住。 | 有验收守门，风险低 |
| **G4 的 `Qualify` 接口** | 🟢 **低** | 两个实例恰好落在同一个二元骨架（`Present ∩ Qualify`）上。两个就够定一个接口。 | 风险低 |
| **G9 的 `PortDirection`** | 🟢 **低** | 端口数与位置完全相同，只有一个枚举。**若「换掉形状」被误读成要造两套接口**，AC-A2 会抓到。 | 风险低 |

**自检结论（不粉饰）**：
- **没有一处是「先写死再特判」的结构。** 约束一与 AC-A2 在结构上排除了这种实现。
- **两处真实的中度补丁味**（G2 的策略空间、G5 的读数分界），**都有对应的 OQ 与复查触发点**。
- **一处高危缺口**（OQ-F1 事件冲突），**是留白而非补丁**——但它意味着
  **本框架目前只能支撑「同一时刻只有一个大事件」的世界。**
  **若第三实例上线时村庄会同时遇到两件事，本框架的答案是「还没有」。**
