> **状态：** 玩法与创作设计基线 V1.2。

## 0. 本文档的读法

核心玩法规则、具体机制与实现约束应带一个标记。解释性文字可继承所在小节的标记；若一句话会直接影响实现，但没有明确标记，应视为尚未确认，不得直接实现。

| 标记 | 含义 | 可以拿它做什么 |
|---|---|---|
| **【已确认】** | 开发者明确说过并确认过 | 可以直接实现、不可推翻 |
| **【建议】** | 本文档提出的方案，尚未经开发者确认 | 可以讨论，不可以当成定案 |
| **【待定】** | 有意留空，等结论 | **不得由实现者自行填空** |

> **为什么必须标记：** V1.0 的失败不是内容不好，是**它把「通用游戏设计常识」和「这个游戏的决定」混在一起写成同一种语气**。读者（包括以后的我）分不清哪条是拍过的板、哪条是填空的，就一定会把填空当定案，然后围绕它建一整座房子。
>
> 对会影响实现的规则，未标记的内容不得自动视为已确认。背景说明和解释性文字不需要逐句重复标记。

### 1.3 V1.0 中保留的技术原则

以下条目原样继承，不重写：

- **§11.1** 大事件不只包括兽潮；通用事件框架不应因新增事件而重写
- **§11.2** 事件通用生命周期（待触发 → 预兆 → 准备 → 进行中 → 结算 → 后续影响 → 结束）
- **§11.3** 事件模板与事件实例分离
- **§11.4** 事件系统只做触发/生命周期/协调；**同一后果不得因重复加载或重复结算而被应用多次**
- **§12.2** 分层架构（表现 / 应用 / 模拟 / 数据与存档）
- **§12.3** 不把所有领域对象做成 `Node`；场景节点负责呈现，领域对象负责规则
- **§12.5** 只保留少量真正需要全局访问的服务；**避免巨型 GameManager**
- **§12.6** 系统通过明确的命令与领域事件协作，不互相随意改数据
- **§13.3** 性能优化以测量为依据
- **§14.5** 存档可靠性（版本号、字段与引用校验、临时文件替换、保留上一份有效存档、读取失败可理解报错、版本迁移入口）
- **§15** 加载时要避免：重复发奖、重复应用事件后果、装备丢失或重复、建筑坐标冲突、任务参与者丢失、已完成事件重新进入进行中
- **§16 尾句** UI 的重点不是展示全部信息，而是在玩家需要做决定时给出足够的信息
- **§20** 规则层单元测试 / 集成测试 / 手工玩法测试三层
- **§6.2** 使用现实动漫、影视、游戏 IP 的具体角色涉及版权与授权风险（已并入 §10.7）

## 2. 项目基线

### 2.1 一句话概念 **【已确认】**

我担任异世界新手村村长，从三间土屋起步，建造村庄、吸引英雄、组织队伍攻略野外与副本，把村庄建成世界上最豪华、最繁荣的城市。

### 2.2 已确认设定清单

| 项 | 内容 |
|---|---|
| 引擎与语言 | **Godot + C#**，技术方案统一使用 C# |
| 视角 | 45° 等距俯视 |
| 参考作 | 《修仙模拟器》 |
| 穿越 | **纯故事背景**。不从 V1.0 的 A/B/C/D 方案中选，不作为设计变量 |
| 英雄来源 | 从**异世界**的不同**动漫、影视、游戏世界**召唤 |
| 英雄唯一性 | 英雄应是具有独立身份与行为的独特角色；是否允许再次召唤同一身份，见 §10.6 待定项 |
| 英雄是否知道自己来自虚构世界 | **【待定】**：是否具有自我认知、如何理解召唤，尚不能据现有基线定案 |
| 行动权 | 只能由我配队；日常行为由他们自己决定 |
| 村庄起点 | 三间土屋 |
| 建筑 | 烟囱、井、围栏、铁匠铺、**武器店、服装店、试炼塔、防护罩** |
| 摆摊 | 英雄可在防护罩内自行摆摊，**我收取摆摊费** |
| 野外 | 村庄外有怪兽，**能看到实时战斗** |
| 大事件 | 按游戏内规则周期性触发；**兽潮是举例，不是唯一**，须支持后续扩展 |
| 本土 | 这个异世界大陆**也有本土角色、本土剧情** |
| 杂谈 | 村庄杂谈**记录这些英雄做的事** |
| 死亡 | **死亡后复活，不附加死亡代价** |
| 城市终极目标 | 成为世界上最豪华、最繁荣的城市；**不以单一等级作为终局** |
| 英雄获取 | 存在**具有抽卡性质**的获取机制，但**不照搬手游付费模式** |
| 召唤消耗 | **优先使用游戏内资源，不预设真实货币付费** |

### 2.4 开发阶段 ≠ 游戏进程 **【已确认】**

**开发阶段是「我在什么时候造哪个系统」，游戏进程是「玩家在游戏里经历什么」。二者不得混用。**

V1.0 §18 把「终局目标与持续沙盒模式」写成 P4——P4 的意思是「内容扩展阶段」，那是**我**的工作阶段，玩家永远不会经历一个叫 P4 的东西。

本文档的 §15 只描述开发排期，且不承载任何游戏内的目标或结局结构。

> **玩法属于核心设计，不等于每一项都必须在第一个可玩原型中完整实现。** 分期是为了控制风险，不是为了把已经确认的玩法从整体设计中弱化或删除。分期表见 §15.2，**待定**。

## 3. 核心循环

### 3.1 核心幻想 **【已确认】**

我通过召唤获得来自异世界的独特英雄。他进入村庄后，不只是战斗单位，也会参与日常生活、交易、冒险和人际互动。

**【待定】** 英雄是否知道自己来自虚构作品、是否知道自己被召唤，以及他们如何理解玩家的角色，尚未定案。

### 3.2 主循环 **【建议】**

```text
建造村庄
   ↓
获取英雄（召唤，和村庄进度关联）
   ↓
英雄各自行动（生活 / 摆摊 / 社交 / 关系变化）
   ↓
我组建队伍、发起任务
   ↓
攻略野外 / 副本，自动战斗
   ↓
材料、装备、声望、关系发生变化
   ↓
建筑解锁新功能 / 村庄达到新的召唤条件
   └──────────────→ 世界事件定期施压 → 继续
```

### 3.3 三个子循环 **【建议】**

| 循环 | 内容 | 读数器 |
|---|---|---|
| **村庄循环** | 资源 → 建造 → 人口 → 新需求 | 建筑本身的变化 |
| **英雄循环** | 状态 → 自主行动 → 产出/关系变化 → 新状态 | 村庄杂谈（§7） |
| **世界循环** | 世界状态变化 → 预兆 → 应对 → 结算 → 后续影响 | 事件面板 + 杂谈 |

> **注：** 三个循环的**节拍不同**是刻意的。村庄循环以「天」为单位，英雄循环以「次行动」为单位，世界循环以「事件周期」为单位。三者不同步，才有东西可看。

## 4. 英雄系统

### 4.1 英雄的四层建模 **【建议】**

V1.0 §6.3 把「性格」写成一组人物特质轴，这是把四件事压成一件。拆分如下：

| 层 | 回答什么问题 | 是否可被玩家直接改变 |
|---|---|---|
| **人物特质** | 他**是什么人** | 否 |
| **玩法偏好** | 他**喜欢做什么** | 否 |
| **当前状态** | 他**此刻能不能** | 否（但会随时间变化） |
| **人际关系** | 他**跟别人怎么样** | 否（只能通过经历形成） |

> **这个拆分要解决的问题：** 同样喜欢副本的两名英雄，可以因为一个勇敢、一个谨慎而采取不同策略；两个竞争心都很强的人，也不一定天生是仇敌。
>
> 「他是什么人」和「他跟谁有仇」是**正交的**。把它们合成一个属性，系统就退化成「读属性」，而关系必须是被经历出来的。

### 4.2 人物特质 **【已确认存在，数值待定】**

影响**如何做决定**，不影响**能做什么**。

开发者提到的方向：勇敢、谨慎、贪财、好奇、固执等。

- **【已确认】** 开发者原话「性格不是二极管」：喜欢打副本的英雄**同样会休闲、会采集**，只是效率慢一点。
- **【待定】** 具体有哪几个特质、每个特质的取值范围与权重。

### 4.3 玩法偏好 **【已确认存在，取值待定】**

影响**更愿意参与哪类活动**，不构成许可或禁止。

开发者提到的方向：攻略副本、探索、休闲生活、经营、交易、PvP 等。

- **【已确认】** 偏好只改变**权重/倾向**，不改变**可行性**。一个偏好休闲的英雄，仍然可以被派去攻略副本，只是他会更不情愿、效率更低。
- **【待定】** 具体偏好品类及其权重表。

### 4.4 当前状态 **【已确认存在，性质待定】**

决定**此刻能不能做某件事**。

- **【已确认】** 疲劳、受伤、资金不足、任务承诺等属于这一层。
- **【待定】疲劳的定义** —— 是
  - (a) 一个需要**恢复的状态**（会随时间自己消解，恢复速度可被设施加速）？
  - (b) 一个**当日的行动额度**（像抽卡游戏的体力条，用完要等重置）？
  - (c) 两者兼有（短期额度 + 长期疲劳）？

  **这是一个独立的设计决定，不得套用常见游戏做法默认填入。** 它直接影响村庄每天的节拍是「休息一下就好」还是「今天不能再干活了」。

- **【待定】** 状态的具体清单、持续时间、恢复途径。

### 4.5 人际关系 **【已确认】**

见 §9。

### 4.6 死亡与复活 **【已确认】**

> **英雄死亡后复活，不附加死亡代价。**

这条规则的后果是确定的，一并写明以免以后被重新讨论：

| 问题 | 答案 |
|---|---|
| 有永久死亡吗 | **没有** |
| 有战力/等级损失吗 | **没有**（属「死亡代价」，未确认存在） |
| 有时间惩罚吗（死一次损失一天在场时间） | **没有** |
| 有装备/物品损失吗 | **没有** |
| 有关系恶化吗 | **没有**（除非 §9 的行为链本身导致，属独立事件） |

> **设计说明（建议）：** 如果死亡不产生代价，挑战仍可来自任务目标、资源消耗、时间安排、事件结算和村庄发展取舍等方面。具体挑战来源应通过玩法测试确定，不得为了制造难度而重新加入死亡惩罚。

### 4.7 英雄的获得方式

见 **§10 异世界召唤与英雄收集系统**。

> **【已确认】** 存在一个具有抽卡性质的获取机制，其形式不照搬手游付费模式。
> **【待定】** 具体形式（卡池 / 稀有度 / 概率 / 保底 / 重复处理 / 消耗）。

§4.1 的四层结构与获取方式**正交**，无论获取机制如何设计，§4.1–§4.6 都不需要重写。

## 5. 系统一 · 英雄摆摊与城市经济

### 5.1 系统目的 **【已确认】**

让村庄里的经济活动**自发产生**，我作为村长收取摊位费并因此获得发展村庄的资源。

摆摊是已确认的村庄经济玩法之一，也是玩家通过摊位费获得村庄收入的途径。其他经济来源及其优先级尚未定案。

### 5.2 系统边界 **【已确认】**

**这个系统负责：**

- 摊位分配：谁有摊位、摊位在哪儿、摊位归谁
- 摊位费：金额、收取方式、收取时机
- 商品：摆摊卖什么、货源从哪来、库存
- 定价：谁定、能不能改
- 交易结算：成交、付款、货币流转
- 英雄收益：他们赚多少、钱花在哪
- 费率反馈：费率变化如何影响摆摊意愿与村庄商业活跃度

**这个系统不负责：**

- 物品属性与战斗数值 → §8
- 关系变化 → §9（但摆摊纠纷**可以**触发关系变化，见 §9.1）
- 英雄的行为决策 → §4（摆摊只是可供选择的一类活动）
- 英雄的获取 → §10

### 5.3 摊位 **【建议】**

- 摊位是**有限的**，数量受村庄规模或防护罩范围影响
- 摊位需要一个**分配规则**（先到先得 / 抽签 / 村长指定 / 竞标 —— 【待定】）
- 摊位位置应**可见**，玩家应能看到村庄的商业面貌

### 5.4 商品与定价 **【建议】**

- 摆摊商品来源：村庄生产 / 副本带回 / 商店采购 / 系统批发（【待定】）
- **定价权归谁：这是本系统最关键的一个设计决定**
  - 若归村长 → 我可以抽成也可以定价，权力最大但村庄商业变成我的开关
  - 若归英雄 → 村庄商业更「活」，但我只能通过摊位费间接影响
  - 若由供需浮动 → 最真实，但玩家难以预测
- **【待定】** 定价权归属

### 5.5 摊位费与抽成 **【建议】**

- 摊位费有两种可能形态：**一次性摊位租金** / **按成交额抽成**
  - 二者对村庄经济的影响完全不同（见 §5.6），**【待定】**
- 费率必须**可被玩家调整**
- 费率变化必须**对村庄产生可观察的影响**（§5.6）

### 5.6 费率对村庄的影响 **【建议】**

建议让费率影响英雄租用摊位的意愿与商业活跃度，但具体因果关系、影响方向和幅度仍需设计与验证。不能在响应规则尚未确定前，把下图当成已确认的数值规律：

```text
费率低  ──────────────────────────────►  费率高
  │                                          │
  ▼                                          ▼
村庄商业活跃                          村庄商业萧条
摊位有人租、有人逛                     摊位空置、村庄冷清
我收得少                                我收得多但没生意可收
```

> **【待定】** 费率响应曲线、是否存在空置阈值，以及英雄是否会根据收益、库存、客流等因素决定是否摆摊。

### 5.7 验收标准 **【建议】**

| # | 验收项 | 方法 |
|---|---|---|
| E1 | 摊位费确实被收取并进入村庄资源 | 固定初始状态，摆摊持续 N 个时段，断言资源增量等于期内摊位费之和（±0） |
| E2 | 摊位费没有双重收取 | 断言同一时段内资源只增加一次 |
| E3 | 费率变化按已定义规则影响摆摊意愿 | 固定英雄、资金、商品、时间与随机种子，只改变费率；按已定义的决策公式检查预期结果。规则未定前，此项为待补测试 |
| E4 | 高费率情景可按规则导致部分英雄不摆摊 | 在满足拒绝摆摊条件的测试数据下，断言该英雄不会租用摊位；不得仅凭一次随机模拟推导全局单调性 |
| E5 | 极端费率输入安全 | 费率达到允许上限时，断言费用计算不溢出、货币不变负、交易系统仍可正常结算；是否必然造成空置待设计 |
| E6 | 存档后不重复收取 | 结算后存档、读档，断言摊位费总额**未改变** |

## 6. 系统二 · 本土居民与本土剧情

### 6.1 为什么需要单独设计本土角色与剧情 **【建议】**

V1.0 §1.3 提了一次「世界原本就有自己的本土居民」，然后把它排进了 P4 的「本土文明、区域势力和贸易」里。这是**把一个世界设定降级成了贸易路线**。

本土居民与本土剧情是已确认的世界内容方向。建议在系统设计上避免让它们完全依赖英雄存在；其独立模拟的深度仍需控制在可实现范围内。

### 6.2 分层 **【建议】**

设计建议：本土角色不应只是装饰 NPC。可以为其设计身份、日常目标和人物关系，并让部分本土故事与英雄、村庄建设或区域事件发生联系。具体深度和实现范围仍需按开发阶段确定。

| 层 | 内容 | 状态 |
|---|---|---|
| **本体层** | 本土居民拥有自己的身份、生活、目标、关系 | **【已确认】** |
| **剧情层** | 本土故事独立于英雄冒险而存在 | **【已确认】** |
| **接口层** | 与英雄、村庄建设、区域事件发生联系 | **【已确认】** |

### 6.3 本土居民 **【建议】**

本土角色**不是**装饰 NPC，也不是给英雄提供服务的功能接口。他们应当：

- 有**自己的身份**（来历、位置）
- 有**自己的生活与行动逻辑**，不只是等待玩家点击；其推进节奏由游戏内时间规则决定
- 有**自己的目标**（不服务于玩家的建设需求）
- 有**自己的关系**（本土人与本土人之间也有关系）
- 有**自己的故事**

**底层设计不能只服务于英雄角色。**

### 6.4 本土剧情 **【已确认】 + 部分【待定】**

- **【已确认】** 本土剧情独立于英雄冒险存在，有自身的发生地与过程
- **【待定】** 具体故事内容——**逐步制作**，本文档不预先指定
- **【待定】** 载体形式：事件？对话？区域状态？还是混合

### 6.5 与英雄系统的接口 **【已确认】存在，【待定】具体形式**

**【已确认】** 本土居民与本土剧情**能够**与下列三者发生联系：英雄、村庄建设、区域事件。

**【待定】** 联系的具体形式：

- 本土居民是否与英雄建立关系、以何种形式
- 本土剧情是否因村庄建设进度而改变
- 区域事件是否可同时包含本土主体与英雄主体
- 本土居民是否参与村庄的生产/摆摊

### 6.6 验收标准 **【建议】**

> 说明：这里的「玩家不操作」指游戏仍在运行、模拟时间继续推进；不等于关闭游戏后世界仍然运行。后者是独立的设计决定，目前未确认。

| # | 验收项 | 方法 |
|---|---|---|
| N1 | 本土居民的存在不依赖英雄数量 | 断言英雄数为 0 时，本土居民仍存在且仍执行其自身行为 |
| N2 | 本土角色可拥有自己的关系 | 若设计了本土角色关系，断言关系状态可独立保存；是否会被英雄介入影响，按最终规则测试 |
| N3 | 本土剧情有可观察的进展 | 断言在给定周期内，本土剧情状态发生了变化，并可在界面上被读到 |
| N4 | 本土内容在游戏内无人干预时仍可推进 | 在游戏运行且玩家不发出相关指令的条件下推进指定游戏时间，断言本土角色或剧情按已定义规则变化；游戏关闭后是否离线推进不在此测试范围内，除非另行确认 |

## 7. 系统三 · 村庄杂谈

### 7.1 目的 **【已确认】**

杂谈是玩家了解英雄自主行为的重要窗口之一。它应记录有意义的英雄行为，让玩家能了解没有亲自下令的事情。其他观察方式是否存在，不在此预设。

> 开发者原话：「平时村庄杂谈会记录这些英雄做的事。」
> 同时明确：「**只是一个功能，一个文字面板**」——它不是叙事主干，不承担剧情职责。

**「不是主干」不等于「不是承重」。** 杂谈是功能层，不该膨胀成剧情系统；但没有它，§3.3 的英雄循环在玩家眼里就是不存在的。

### 7.2 记什么——事件驱动 **【已确认】**

> **杂谈根据已发生的事件生成消息，而不是每隔几秒随机生成文本。**

| 事件 | 来源 |
|---|---|
| 英雄首次完成副本 | 开发者点名 |
| 某次交易发生纠纷 | §9 行为链的起点之一 |
| 两名英雄关系恶化 | §9 |
| 某位英雄获得稀有装备 | 开发者点名 |
| 英雄受伤 / 康复 | §4.4 |
| 建筑建成 / 升级 | §12 |
| 村庄日常（采集、摆摊、社交等） | §3.3 英雄循环 |
| 大事件的发生与结算 | §11 |
| 召唤到新英雄 | §10.4 |
| 本土剧情进展 | §6 |

### 7.3 不记什么 **【建议】**

- 不记录无意义的随机文本
- 不记录系统内部状态变化（数值波动等）
- 不记录尚未发生的事
- 不承担剧情叙事职责

### 7.4 验收标准 **【建议】**

| # | 验收项 | 方法 |
|---|---|---|
| C1 | 杂谈条目可追溯到具体事件 | 断言每条消息都能匹配到一个已发生的事件 ID；无法匹配的条目数为 0 |
| C2 | 同一事件不重复记两条 | 断言同一事件 ID 在杂谈中出现次数 ≤ 1 |
| C3 | 事件发生时杂谈有反应 | 触发一个已定义事件，断言该事件的杂谈条目存在 |
| C4 | 杂谈不刷屏 | 断言在给定时间内，无事件发生的时段产生的空条目数为 0 |

## 8. 系统四 · 副本与自动战斗

### 8.1 副本的定位 **【已确认】**

> 开发者原话：「通过派发任务让英雄去攻略副本」。

**副本是任务系统的核心目标类型之一，不是采集与讨伐的可选扩展。**

V1.0 §8.2 把副本排到「基本任务生命周期稳定后扩展」，这是把开发者明确的核心玩法降级了。本文档纠正。

### 8.2 副本结构 **【已确认】**

> 第一版至少要验证一个副本，且该副本必须具备：**明确入口、多个遭遇或阶段、最终目标、结算与奖励**。

| 要素 | 要求 |
|---|---|
| 入口 | 英雄队伍必须能到达，且到达方式可被玩家观察 |
| 阶段 | 至少两个（单场遭遇不算副本） |
| 最终目标 | 阶段之外还有一个明确的完成条件 |
| 结算 | 明确计算，不含歧义 |
| 奖励 | 结算产出进入村庄资源与英雄成长 |

### 8.3 自动战斗 **【已确认】**

- 战斗**全自动**。玩家不直接操控英雄进行即时攻击。
- 玩家通过**队伍配置、装备、补给、任务选择**影响结果。
- 战斗应**可在地图上观察**，而不是切换到独立战斗场景。
- **【已确认】** 战斗必须**可读**：玩家应能看清谁为什么赢、谁为什么输。

**【待定】** 战斗的全部数值规则（伤害、命中、冷却、状态效果、AI 目标选择等）。V1.0 §9.2 只列了一份 checklist（至少一种技能、至少一种状态效果），不构成设计。

### 8.4 副本与其他系统的接口 **【建议】**

| 接口 | 方向 |
|---|---|
| 副本 → 材料/装备/金币 | 结算产出（§5 货源之一） |
| 副本 → 英雄状态 | 疲劳、受伤（§4.4） |
| 副本 → 关系 | 同队协作可能改变关系（§9.2） |
| 副本 → 杂谈 | 「某位英雄首次完成副本」（§7.2） |
| 副本 → 建筑功能 | 武器店/试炼塔/铁匠铺应影响副本（§12.1） |
| 副本 → 英雄阵容 | 召唤新英雄扩大可攻略的队伍配置（§10.5） |

### 8.5 验收标准 **【建议】**

| # | 验收项 | 方法 |
|---|---|---|
| D1 | 副本可完整走通 | 从入口到结算执行一遍，断言五个要素全部到达 |
| D2 | 结算只发生一次 | 触发结算后存档、读档，断言奖励未翻倍 |
| D3 | 队伍配置按规则影响副本结果 | 选择一组具有明确机制差异的队伍配置，固定副本参数与随机种子；根据战斗规则预测并检查指定结果，不要求所有指标单调变化 |
| D4 | 建筑影响符合已定义功能 | 只有当武器店或其他建筑被明确设计为影响副本时，才进行有/无建筑对照；不能预先强制所有商店直接影响战斗结果 |
| D5 | 战斗可读 | 断言战斗日志能复现胜负判定所引用的每一个关键事件 |

## 9. 系统五 · 英雄关系与社会行为

### 9.1 关系从哪里来 **【已确认】**

> 开发者原话：「玩家间的交易也是有彩蛋的，比如有些人坏，它会交易一些不好的东西给别人，别人发现了会造成损失，然后就会出现吵架，最后 pvp 等等，上线就追着砍，被砍的只能跑野外升级，变强了再回来报仇」

这条**因果链**是本系统的骨架：

```text
交易发生 → 有人受骗/吃亏 → 发现 → 产生损失 → 争吵
   → 关系恶化（结仇） → PvP/追逐 → 一方出走野外变强 → 回来报仇
```

> **【已确认】** 这是**举例**，不是唯一的关系形态。关系应当能从**交易、社交、合作、冲突**等实际经历中发展，**不限于**这一条链。

### 9.2 关系怎么变 **【已确认】**

| 经历 | 关系变化 |
|---|---|
| 交易欺骗被发现 | 信任下降 |
| 争吵 / 冲突 | 关系恶化 |
| 长期合作 / 同队副本 | 默契或好感增加 |
| 严重冲突 | 可触发追逐与 PvP |
| 长时间无互动 | **【待定】** 是否自动淡漠，及其形式 |

### 9.3 关系的性质 **【已确认】**

- 关系是**实际经历产生的**，不是初始属性
- 关系是**双向且可不对称**的（A 恨 B，B 不一定恨 A）
- **【已确认】** 性格/人物特质**可以影响行为倾向**，但**不得**用固定的「竞争型 / 合作型」属性替代关系的发展过程

> 这一条直接作废 V1.0 §6.3 的「竞争心强 ↔ 合作倾向」。若每个人都自带竞争性立场，关系系统就退化成「读属性」，而关系必须是**被经历出来的**。

### 9.4 与 §4 四层的关系

| 关系层 | 影响关系吗 |
|---|---|
| 人物特质 | **可以影响倾向**（例：更倾向发起冲突），但不能决定 |
| 玩法偏好 | 可以（例：偏好 PvP 者更常卷入） |
| 当前状态 | 可以（例：受伤时更易产生依赖或怨恨） |
| 人际关系 | 就是关系本身 |

### 9.5 验收标准 **【建议】**

| # | 验收项 | 方法 |
|---|---|---|
| R1 | 关系由经历产生 | 断言初始状态不存在未经经历而成立的敌对关系 |
| R2 | 交易纠纷可产生关系变化 | 构造一次被骗事件，断言对应两人的关系值发生预期方向的变化 |
| R3 | 关系可双向不对称 | 断言存在 (A→B 恶化) 与 (B→A 未恶化) 的状态，且该状态可被表达与保存 |
| R4 | 关系变化可追溯 | 断言关系值的每次变化都能追溯到一个具体经历 |
| R5 | 存档后关系状态一致 | 在关系状态稳定时存档并读档，断言关系数据保持一致；若未来设计关系随时间衰减，再单独测试该规则 |

## 10. 系统六 · 异世界召唤与英雄收集系统

### 10.1 两个概念的区分 **【已确认】**

| 概念 | 性质 | 内容 |
|---|---|---|
| **异世界召唤** | **世界观设定** | 英雄来自异世界的动漫、影视、游戏世界 |
| **角色获取（抽卡性质）** | **玩法机制** | 玩家如何获得新英雄 |

> **设计说明：** 异世界召唤属于世界观层面，抽卡性质属于角色获取机制。二者可以结合，但不意味着必须采用手游式付费模式。

本文档确认的是：英雄来自异世界（§2.2），且存在一个具有抽卡性质的获取机制。**具体形式属于【待设计】。**

### 10.2 定位：角色获取与村庄经营的关系 **【建议】**

> **设计建议：** 抽卡可作为英雄获取入口，但应避免让村庄经营沦为角色收集的附属功能。

本游戏有两个核心乐趣：

| 乐趣 | 内容 |
|---|---|
| **收集英雄** | 期待召唤到心仪的角色，逐步扩充阵容 |
| **经营英雄的生活** | 看着英雄在村庄中自主生活、消费、交易、组队、攻略副本，产生冲突与关系变化 |

**本系统是获取英雄的入口，不是游戏的主轴。**

**可执行约束（两条，缺一不可）：**

| 约束 | 含义 | 检验方法 |
|---|---|---|
| **C-资源约束（建议）** | 如果召唤设计为消耗游戏内资源，则成本必须真实结算 | 固定召唤成本后，断言资源扣减与规则一致；是否必须消耗哪种资源仍待确定 |
| **C-经营独立性（建议）** | 村庄经营不应只为召唤服务 | 暂停召唤后，检查建造、交易、任务等已实现的核心循环是否仍有可进行的目标 |

> 这些是用于评估设计的建议性约束，不是已经定案的召唤规则；在召唤系统正式定案前，不应据此锁定具体资源成本或卡池结构。

### 10.3 异世界召唤 **【已确认】**

- 玩家通过**村庄里的召唤设施**召唤来自异世界的英雄
- 召唤是游戏内获取英雄的一种机制；它是否为主要途径、是否存在其他获取途径，尚待确认
- 召唤是否以及如何与村庄发展进度关联，需要在机制设计中明确；目前不预设具体解锁曲线

> **【待定】** 召唤设施的具体形态：建筑名称、解锁条件、位置、是否唯一。

### 10.4 独特英雄收集 **【已确认】**

每位英雄具有自己的：**外观、背景、人物特质、玩法偏好、装备需求、行为倾向**。

> **设计方向：** 召唤到的英雄不应只是战斗数值卡牌，也应能参与村庄生活、交易、冒险和人际互动。

**【已确认】核心方向：英雄应当是具有自身身份和行为的独特角色，而不是只有数值差异的卡牌。**

**【待定】** 「每次召唤都得到不同身份的英雄」与「同一角色可能再次出现」是两种不同规则。当前文档尚未确认唯一性具体指角色身份、角色实例还是召唤结果，因此在此问题明确前，不实现重复角色、角色碎片或重复转化机制。

**约束：** 一个英雄若只有战斗数值、无法在村庄中自主行动，则其「独特性」不成立。

### 10.5 与经营系统的联动 **【建议】**

> **设计建议：** 召唤到的新英雄应当与村庄经营产生实际联系，而不只是增加收集数量。

| 影响 | 落到哪个系统 |
|---|---|
| 队伍搭配 | §8 副本攻略能力 |
| 装备消费 | §12.1 武器店 / 服装店的商品需求 |
| 摊位交易 | §5 摆摊的货源、顾客与交易活跃度 |
| 副本机会 | §8 可攻略的队伍配置增加 |
| 住房需求 | 村庄居住容量压力 |
| 商业需求 | §5 商业活跃度变化 |
| 服务需求 | §12.1 建筑的使用需求变化 |

**双向要求：**

- **【建议】** 英雄 → 经营：新英雄最好能通过消费、交易、住房需求或其他已设计行为影响村庄
- **【待定】** 经营 → 英雄：村庄发展进度是否决定召唤解锁、召唤资源或召唤内容，需在召唤规则中明确

**设计建议：** 召唤最好与村庄经济或发展形成联系；具体资源成本和联动强度尚未确定，不应提前锁定为固定规则。

### 10.6 待验证规则

| 机制 | 处理方式 |
|---|---|
| **召唤入口与解锁条件** | **【已确认】** 纳入核心设计；**【待定】** 具体建筑名称与解锁条件 |
| **角色稀有度与概率** | 可以设计；**【待定】** 档位与概率 |
| **英雄唯一性与重复召唤** | **【已确认】** 英雄应是独特角色；**【待定】** 同一身份是否可能再次出现、重复获取如何处理 |
| **召唤消耗** | **【已确认】** 优先考虑游戏内资源；**不预设真实货币付费** |
| **保底机制** | **【待定】** —— **不得因为采用抽卡形式就默认采用手游式保底** |
| **召唤池与世界观** | 可以按不同异世界/主题划分；**【待定】** 具体规则 |

### 10.7 角色来源、原创角色与 IP 风险 **【建议 / 待确认边界】**

> **版权提醒：** 若使用现实中已有动漫、影视或游戏角色，需要评估相应 IP 的授权风险。开发早期可先使用原创英雄验证召唤与经营循环。

因此：

- **【建议】** 开发早期使用原创英雄验证召唤与经营循环，降低授权和内容依赖风险。
- **【待定】** 「英雄来自不同动漫、影视、游戏世界」究竟指使用现实作品中的既有角色，还是原创的平行世界/致敬型设定，需要在内容制作前明确。
- 若使用现实 IP 的具体角色或受保护素材，应先评估授权风险；设计与代码不应在未确认授权的情况下硬编码特定 IP 角色。

### 10.8 验收标准 **【建议】**

| # | 验收项 | 方法 |
|---|---|---|
| S1 | 召唤条件按最终确定的规则执行 | 召唤规则确定后，测试满足条件与不满足条件的边界；若最终没有进度门槛，则删除本项门槛测试 |
| S2 | 召唤产出的是独立角色，不是数值卡牌 | 断言召唤出的英雄在村庄中产生自主行为（摆摊/社交/冒险/关系），且不依赖玩家逐条指令 |
| S3 | 新英雄对经营产生可观察影响 | 在一个预先定义的场景中加入指定英雄，按该英雄的行为规则运行固定游戏时间，断言至少出现一项预期的经营事件或指标变化；不要求所有指标单调变化 |
| S4 | 消耗来自游戏内资源 | 断言召唤前后村庄资源减少量等于消耗量；不涉及任何外部支付 |
| S5 | **资源结算** | 若召唤消耗资源，连续召唤至资源不足时，断言扣费准确且不会产生负数或凭空增加资源 |
| S6 | **经营独立性（建议）** | 暂停召唤后，验证其他已实现的经营循环仍可继续；具体范围随开发阶段确定 |
| S7 | 获取规则与文档一致 | 仅在角色获取途径确定后补充测试；当前不预设必须存在非召唤获取途径 |

## 11. 世界与大事件

### 11.1 事件框架 **【已确认】**

> **已确认方向：** 大事件（例如兽潮）应按一定周期触发，并且系统应能扩展到其他类型的大事件。这里的「周期触发」指游戏内规则；是否涉及真实时间、离线期间推进或线上活动均未确认。

因此：

- 大事件按**已定义的游戏内周期或触发规则**发生；是否与现实时间绑定尚未确认
- **通用框架必须先行**，兽潮只是其中一个实例
- 新增事件**不得要求重写核心世界循环**（继承自 V1.0 §11.1）

### 11.2 生命周期 **【建议】**（沿用 V1.0 的可选技术方案）

```text
待触发 → 预兆 → 准备 → 进行中 → 结算 → 后续影响 → 结束
```

某些事件可跳过不适用阶段，但状态迁移与存档规则必须明确。

### 11.3 模板与实例分离 **【建议】**（沿用 V1.0 的可选技术方案）

- **事件模板**：触发条件、阶段规则、参与者选择规则、持续时间、结算规则、可能后果
- **事件实例**：本次事件的 ID、当前阶段、开始时间、进度、参与者、结果、已应用的后果

### 11.4 系统边界 **【建议】**（沿用 V1.0 的可选技术方案）

事件系统负责触发、生命周期与协调，**不直接承担所有业务细节**。它可以请求：

- 怪兽系统生成或调度怪兽
- 任务系统提供防御任务
- 战斗系统结算冲突
- 建筑系统计算损伤
- 经济系统扣除消耗
- 关系/声望系统处理结果影响

**幂等要求：** 事件结束后记录结果，**确保同一后果不会因重复加载或重复结算而被应用多次**。

### 11.5 已知实例 **【已确认】**

| 实例 | 状态 |
|---|---|
| 兽潮 | 开发者明确举例 |
| 其他 | **【待定】** 待补充 |

> **【待定】** 除兽潮外的第二、第三个事件实例。框架的可扩展性需要至少两个实例来验证——**用一个实例抽象出的框架，无法区分「通用」与「该实例专属」。**

### 11.6 验收标准 **【建议】**

| # | 验收项 | 方法 |
|---|---|---|
| V1 | 事件按其模板完成生命周期 | 对指定事件模板逐项验证适用阶段和合法状态迁移；不要求所有事件都必须经历全部七个阶段 |
| V2 | 后果不被重复应用 | 结算后存档、读档，断言后果只应用一次 |
| V3 | 事件可预告 | 断言「预兆」阶段在「进行中」之前，且玩家可从界面读到 |
| V4 | 事件不越权改数据 | 断言事件产生的状态变化全部经由对应系统完成，无跨模块直写 |

## 12. 村庄与建筑

### 12.1 建筑类型 **【已确认】**

只保留开发者明确提出的建筑：

| 建筑 | 开发者原话 |
|---|---|
| 土屋（起始） | 「一开始三间土屋」 |
| 烟囱 | 「招人来之后开始有烟囱」 |
| 井 | 「然后有井」 |
| 围栏 | 「有围栏」 |
| 铁匠铺 | 「有铁匠铺」 |
| **武器店** | 「比如武器店，服装店」 |
| **服装店** | 「比如武器店，服装店」 |
| 试炼塔 | 「又或者一些试炼塔，作用是让玩家快速升级」 |
| 防护罩 | 「还有防护罩，作用是保护村庄不被外面攻击」 |

**V1.0 中未确认因而删除的建筑：** 冒险者公会、训练场、诊疗设施、工坊、城墙、商业街、魔法设施、大型奇观、专属区域、特色系统。

**【待定】** 上述建筑之外是否还需要其他建筑。**新增建筑必须由开发者提出，不得由实现者补充。**

> **注意：** V1.0 §7.2 曾以「铁匠铺 + 市场/商店」替代「武器店 + 服装店」。这是错误的泛化，已纠正。

### 12.2 成长目标与衡量方式 **【已确认 / 建议】**

> **已确认方向：** 村庄最终目标是发展成世界上最豪华、最繁荣的城市，不以单一等级作为唯一终局指标。多维成长与具体解锁结构属于设计建议，维度和条件仍待定。

因此：

- **【已确认】** 终极目标不能只用单一城市等级作为判定
- **【建议】** 城市成长可采用多个维度，并通过发展解锁新玩法；具体维度和解锁规则待定
- 不预设固定的六段线性阶段，除非后续设计明确采用
- **【已确认】** 终极目标是**世界上最豪华、最繁荣的城市**，不是某个数值到达上限
- **【待定】** 多维包含哪些维度、每个维度如何度量、玩法解锁的具体条件

### 12.3 建筑与村庄的关系 **【建议】**

- **【已确认】** 建筑是村庄成长的重要组成部分，村庄变化应能在地图上被观察到
- **【待定】** 每栋建筑的具体功能、是否直接影响数值系统，以及建筑之间的依赖关系；不能仅凭建筑名称自行指定功能
- **【建议】** 建筑之间应存在相互影响（互相供给、或争夺同一份资源），使建造顺序成为一个**有取舍的决定**而非一条直线
  - **【待定】** 具体的影响关系。这是 §12.2「多维成长」能否不沦为「多条平行进度条」的关键。

### 12.4 摆摊与防护罩的关系 **【已确认】**

> 开发者原话：「有些玩家还会在村庄周边，**防护罩内**自行摆摊」

因此摆摊位置受防护罩范围约束（§5.3）。

### 12.5 验收标准 **【建议】**

| # | 验收项 | 方法 |
|---|---|---|
| B1 | 建筑功能符合已确认定义 | 为每栋建筑先明确其功能与预期效果，再分别测试；在功能定义完成前，不要求所有建筑都必须改变战斗或经济数值 |
| B2 | 建造规则一致 | 按已确定的成本、前置条件和解锁规则测试建造；只有在设计明确存在顺序依赖时，才要求不同建造顺序产生不同结果 |
| B3 | 建筑与村庄状态可见 | 建造或升级后，断言地图与建筑数据反映该变化；不假设存在固定的建筑阶段或线性等级 |
| B4 | 摆摊范围受防护罩约束 | 断言防护罩范围变化时，可用摊位数量随之变化 |

> 本节列出当前文档明确保留的技术约束。它不是 V1.0 全部技术内容的替代品；未在此列出的技术细节需要查阅并核对独立技术设计，不能仅凭「承接 V1.0」推定其仍然有效。

### 13.1 引擎 **【已确认】**

Godot + C#。技术方案统一使用 C#。

### 13.2 分层架构 **【已确认】**（继承自 V1.0 §12.2）

| 层 | 职责 |
|---|---|
| 表现层 | 地图、镜头、角色与怪兽节点、建筑、动画特效音效、UI 与输入 |
| 应用层 | 玩家指令入口、用例协调、游戏时间与速度控制、场景与会话生命周期 |

### 13.3 Node 与领域对象 **【已确认】**（继承自 V1.0 §12.3）

**不要把所有领域对象都做成 `Node`。** 场景节点负责呈现与引擎交互，领域对象负责规则与状态，两者通过明确接口、命令、事件或受控引用连接。

### 13.4 全局服务 **【已确认】**（继承自 V1.0 §12.5）

只保留少量真正需要全局访问的服务。**避免创建一个包含所有业务逻辑的巨型 `GameManager`。**

### 13.5 模块通信 **【已确认】**（继承自 V1.0 §12.6）

使用明确的命令与领域事件。事件处理者可以更新 UI、关系或日志，但**不应绕过业务服务修改其他模块的核心数据**。

### 13.6 静态定义与运行时状态分离 **【已确认】**（继承自 V1.0 §14.1）

静态定义描述「这种东西是什么」，运行时状态描述「这个实例当前怎么样」。运行时变化**不得**写回静态定义资源。

### 13.7 存档 **【已确认】**（继承自 V1.0 §14.4–§14.5、§15）

- 显式 DTO + 版本号，**不直接序列化整个场景树**
- 临时文件写入后再替换正式存档；保留上一份有效存档
- 加载时先解析 DTO、校验 ID 和引用，再恢复运行时状态
- 提供版本迁移入口
- **加载时必须避免：** 重复发放奖励、重复应用事件后果、装备丢失或重复、建筑坐标冲突、任务参与者丢失、已完成事件重新进入进行中
- **【待定】** 随机数状态的存档方案。基本要求是存档读档后不得重复发奖或重复结算；若要求模拟从读档点继续得到一致的随机序列，应保存随机数状态或采用等效的确定性方案。具体方案通过技术原型决定。

## 14. 验收标准的写法（规范）

### 14.1 为什么重写 **【已确认】**

V1.0 §19 的 12 条验收场景中，5 条不可测（"改变计划""确实改变""会影响""失控"均无定义），4 条半可测。**无法验证的验收标准等于没有。**

### 14.2 四段式 **【已确认】**

每一条验收标准必须包含：

```text
1. 输入   —— 固定的初始状态、参数、随机种子
2. 执行   —— 明确步骤，含状态恢复
3. 预期   —— 具体的状态或数值，不使用"合理""正确""更好"
4. 检查   —— 可机械执行的断言
```

**关键约束：**

- 涉及随机性的系统，使用**固定种子**；或检查**有明确边界**的结果，而不是要求每次模拟完全相同
- 需要对照的测试，必须**先记录基线、恢复初始状态、再跑对照**（见 §14.3）
- 「影响是否真实存在」是首要问题，**具体的数值平衡是次要问题**——先保证规则可验证，再通过实测确定平衡数值

### 14.3 完整示例：防御设施是否真的影响兽潮

> 这是对 V1.0 §19 第 8 条「防御建设和英雄配置会影响结果」的改写。

```text
1. 固定输入
   · 相同的初始世界状态（村庄、建筑、库存）
   · 相同的英雄队伍（成员、装备、状态）
   · 相同的兽潮参数
   · 相同的随机数种子

2. 执行 A（对照组）
   · 不建造任何防御设施
   · 执行一次完整兽潮模拟
   · 记录：建筑损伤、英雄伤亡、事件结果

3. 恢复初始状态
   · 从步骤 1 的初始状态恢复

4. 执行 B（实验组）
   · 建造指定防御设施
   · 执行一次完整兽潮模拟
   · 记录同上

5. 验证
   · 防御设施通过明确的游戏规则改变了至少一项结算指标
   · 且结果与对应规则的预测一致
   （不预先规定"防御设施减少多少伤害"——
     先保证规则可验证，再通过实测确定平衡数值）

6. 幂等检查
   · 在执行 B 之后存档，读档，断言本次兽潮不被重复结算
```

### 14.4 全局验收清单 **【建议】**

| 类别 | 要求 |
|---|---|
| 摆摊 | §5.7 的 E1–E6 |
| 本土 | §6.6 的 N1–N4 |
| 杂谈 | §7.4 的 C1–C4 |
| 副本 | §8.5 的 D1–D5 |
| 关系 | §9.5 的 R1–R5 |
| 召唤与收集 | §10.8 的 S1–S7；获取途径和重复处理规则确认后再锁定对应断言 |
| 事件 | §11.6 的 V1–V4 |
| 建筑 | §12.5 的 B1–B4 |
| 存档 | 全部涉及结算的系统都必须通过「结算后存读档，断言不重复结算」 |

## 17. 禁止事项

以下是当前的设计约束与建议性反模式；其中标记为建议的项目需要结合原型验证。

| 不做 | 原因 |
|---|---|
| 添加未经开发者提出的剧情路线、恋爱/家族/世代系统或其他玩法 | V1.0 的失败模式：通用模板内容冒充本游戏设计 |
| 用出厂属性（竞争型/合作型）替代关系的发展过程 | §9.3 |
| 给死亡附加任何代价 | §4.6 已定案 |
| 把开发阶段写成玩家的游戏进程 | §2.4 |
| 用「合理」「正确」「更好」作为验收标准 | §14.2 |
| 在本文档里给【待定】项填空 | §0 |
| **让村庄经营沦为角色收集的附属功能** | §10.2 的设计建议；需通过整体循环验证 |
| **不要在未定义经济规则前让召唤凭空改变资源** | §10.2、§10.5 的建议性约束；召唤成本与经济联动尚待确认 |
| 因为采用抽卡形式就默认采用手游式保底 | §10.6 |
| 在开发早期假定现实 IP 角色必然存在 | §10.7 |
| 新增建筑而不经开发者提出 | §12.1 |
