## 🔴 A. 会推翻既定设计的问题（需开发者拍板）

### A1 — 召唤完全没有代价
**来源**：`summoning.md` Q4
**开发者原话**：「我的系统 只能召唤几个人」
**现状**：`HeroFactory.Summon()` 免费、无冷却、无并发上限、无村庄容量。人口增长零瓶颈。
**为什么重要**：这句话原话里有「只能」，是**限制**。现在实现里没有这条限制——整个村庄的人口增长曲线因此不存在。
**候选**：消耗资源 / 冷却 / 并发上限 / 村庄容量。
**这是本轮最大的设计缺口。**

### A2 — 配队的「人数」维度是个缺陷，不是取舍
**来源**：`squad-and-cohesion.md`
**可证推理**：`job.Amt` 是按成功人数**分摊**而非累加 → 第 4 人的边际产出恒 ≥ 0；
而 C=3 就已达顶（×1.15），上限却是 4 → **任何相容的 4 人队都严格优于 3 人队**，最优解唯一且静态。
**开发者原话**：「配队不只是选四个人」
**结论**：直接违背开发者自己的注释，所以不是取舍，是缺陷。作者给了三个修法方向，**没有替开发者定**。

### A3 — 「有仇」在三处说法不一致
**来源**：`squad-and-cohesion.md` Q4
- `HeroAgent.cs` 注释 + `design/game-brief.md` L153 都写「**进不了同一支队**」（硬禁止）
- 实现是 **×0.50 软惩罚**（`CohesionOf()`）
**要定**：硬禁止还是软惩罚。

## 🟠 B. 实现缺陷（设计没错，代码错了）

### B1 — 软锁：扣了材料却没人能盖，无法取消
**来源**：`village-building.md`，**已独立复核**
```
src/Main.cs:362   if (_buildTarget >= 0) return;    // 一次只盖一样 → 再也进不去
src/Main.cs:256   if (!OnDuty(h))                  // 离线的人点花名册无效 → 撤不了队
grep 退款|取消|Cancel|refund  →  无任何结果          // 没有取消/退款路径
```
**后果**：按 Q 交了 30~130 材料 → 所有能盖的人下线 → 工地冻结 → 不能取消、不能退款、
不能换人、不能开别的。唯一出路是按 F 再召人，或等那个人上线。
**这是我（M0）自己写的代码里的洞，不是设计意图。**

### B2 — 0.95 上限吃掉顶档莽的加成
**来源**：`squad-and-cohesion.md` F5
`chance ×= 1.15`（莽）之后才 clamp 到 0.95 → 顶档约一半的莽拿不到 ×1.15。

### B3 — `GrudgeWith` 存名字字符串
**来源**：`squad-and-cohesion.md` Q6
姓名空间会撞（见 C2），两人同名时结仇判定会误判。

### B4 — 保底采样把均值抬到 30.53，不是 29.5
**来源**：`summoning.md`
拒绝采样（`do{...}while(三项<60)`）使分布偏移。**按 29.5 调参会误判为 bug。**

### B5 — 召唤后 `WorldName` / `Trait` 立即丢弃
**来源**：`summoning.md` Q1
只写进杂谈，人身上存不下来 → 花名册无法显示「废土边境来的」；
`OfName` 反推失败还会**静默返回随机世界**。

## 🟡 C. 值得知道，但不用现在决定

### C1 — 「独一无二」靠的不是名字
**来源**：`summoning.md` F8
姓名空间只有 155 种组合。2 人时撞名概率 0.654%，**15 人时重名就是或然事件（20 人时 71%）**。
撑得起「独一无二」的是**整条记录**（碰撞率 ~1e-7）。
→ 召唤 GDD 里那条「零重名」的验收标准**本身是错的**，已改写成正确断言。

### C2 — 性格分布偏斜：傲 40.9% / 莽 34.1% / 贪 25.0%
**来源**：`summoning.md`
纯属世界权重表的副产品。而**傲的效率乘数最低**（×0.60），会系统性压低村庄平均效率。

### C3 — 时区表只有 11 个离散值
跳过了 −12 / +14 等。是刻意简化还是待补？

### C4 — 杂谈模板「村里第一次见这种人」在 20 人时基本是假的
无条件触发，人多了就是谎言。

### C5 — `assets/data/` 不存在，所有系数硬编码在 `Main.cs`
Tuning Knobs 表已标为待迁移。

### C6 — 村庄建造/配队都撞上同一个问题：**铁匠铺归谁**
现在只有外形和炉火，所以两者都可声明它。趁它还没产出东西赶紧定。

## 追加 2026-10-17 · 性格系统 GDD 落地（本项目方法论最硬的一份）

### ✅ 它把「可分离性」做成了机制，而不是声明
我派活时标了这个系统**最高风险**：「效率系数」和「偏好权重」很容易退化成同一个东西的两个换皮。
作者的处理：
- 权重**只进「自主通道」**，效率**只进「执行通道」**
- 自主选中后**走与被指派完全相同的代码路径**
- 对外只暴露三个函数：`EfficiencyOf` / `ScoreOf` / `AutonomyInterval`

### ✅ 它给了三条证伪方法（不是三条断言）
- **A 冻结一轴** —— 统计口径强制按「英雄 × 类目」分组，否则分布变化会污染读数
- **B 最后一个人测试** —— 15 组全通过，**直接杀掉原型 `prototype.html:254` 那段被否决的 `return false`**
- **C 秩相关不得 = +1.0**

### ✅ 它的示例计算本身就是证据
> 傲挑副本的分数 **0.919 > 莽 0.697** ——他更想抢，却打得更慢。
> 贪为钱去接一场效率 **0.70** 的战斗。
> **如果这俩是同一个数，上面三行都不成立。**

### 🔴 A5 — 效率矩阵的取值大多不是开发者说的
**来源**：`personality.md` Q7
矩阵 0.60 / 1.00 / 1.30 里，**只有「傲 × 0.60」是开发者原话**（他自己写的注释），
其余是作者推导。**调参前应确认，否则等于在给一个没定过的数调平衡。**

### 🔴 A6 —「熟练度」被正确地挡下了
**来源**：`personality.md` Q6
长期只干一类活，效率会不会涨？——是很强的正反馈，但它是**新系统**，开发者没提过，作者没加。**这个克制是对的。**

### 🟠 B7 —「干起来了」触发条件推不出来
**来源**：`personality.md` Q3
八个村庄日常里，**唯一推不出后果的一个**。作者把它挡在上线之外了。
其余七个（病倒/吵架/磨洋工/想走/搭手/陌生人/闲逛）都有明确的状态后果。

### 🟡 C9 — 傲/贪的「摆摊」效率和偏好没有依据
**来源**：`personality.md` Q2
开发者只提过「采集跑腿、脏活细活」。**摆摊是 Batch 2 经济系统要用的，这里欠着。**
→ 已作为输入带进经济那份 GDD 的派活指令。

### 🟡 C10 — `choice_temperature = 2.0` 是作者自己选的
村庄自主行为有多「随机」。**觉得太乱/太整齐就调这一个数。**

### 🔴🔴 B8 — 远征中撤队 → 该村民永久消失　**已独立复核，严重性高于 agent 报告**
**来源**：`expedition.md` A4
```
src/Main.cs:163   OnDuty = AbsentDays<=0 && IsOnlineAt(hour)   ← 不检查 Away
src/Main.cs:302   crew   = _squad.Where(h => h.Away)
src/Main.cs:355   foreach (var h in crew) h.Away = false
```
远征中的人 `Away=true` 但仍「在岗」→ **花名册点得动** → 被移出 `_squad`
→ 第 302 行找不到他 → 第 355 行**永远不会**给他清 `Away`
→ **`Present => !Away && Online` 为假 → 从地图永久消失**，不能盖房，UI 不作解释。
**一次误点，永久损失一个村民。**

### 🔴🔴 B9 — 远征中把人全撤 → 直接崩　**已独立复核**

**两步复现：按 R，然后点名字把人全撤掉。UI 没有任何拦阻。**
这是至今最严重的 bug。

### 🟠 B10 — 配合表有两档永远不可达
**来源**：`expedition.md` A9

**九档里有两档是死代码。**

### 🔴 A11 — 推导出来的「他会去看客服」在一半情况下不成立
**来源**：`death-and-revival.md` F7，作者自己量出来的
