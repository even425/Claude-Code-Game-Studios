## 2. 阶段 1 · 税额余数与存档 v0.5

### 2.1 税额计算：`StallFee.Compute` 加余数累计

```csharp
public static (long sellerNet, long villageCut, long newCarry) Compute(
    long totalAmount, long carry = 0)
```

| 项 | 决定 |
|---|---|
| 公式 | `taxUnits = totalAmount × 5`（1/100 金）→ `accumulated = carry + taxUnits` → `villageCut = accumulated / 100` → `newCarry = accumulated % 100` → `sellerNet = totalAmount - villageCut` |
| 溢出 | `taxUnits` 用**不溢出的分解式**：`(totalAmount / 100) × 500 + (totalAmount % 100) × 5`（后半 < 500，必不溢出） |
| 边界 | `carry` 必须在 [0, 99]，否则抛 `ArgumentOutOfRangeException` |
| 兼容性 | 另留 `ComputeSplit(totalAmount)` 薄包装（2 元组）给只需要单笔拆分的调用方 |

> **实现形态的一处修正**：`27` 评审稿初版建议「给 `Compute` 加默认参数，现有 8 条用例一条都不用改」——
> **那不准确**：返回值多带 `newCarry` 就是 3 元组，`var (a, b) = ...` 的解构会**编译失败**。
> 最终采用「单一函数 + 3 元组 + 2 元组薄包装」：真相源唯一，测试零改动。

### 2.2 状态所有者：`StallService`

| 项 | 决定 |
|---|---|
| 余数存哪 | `StallService._villageCutCarry`（`long`，单位 1/100 金）—— 摊位交易只有这一条写路径，余数必须和交易在**同一次提交**里更新 |
| 提交顺序 | ① `_village.Add`（**唯一可能抛**）→ ② 写 `carry`（纯内存赋值，不会抛）→ ③ 不可失败赋值 |
| 为什么余数在金库之后 | `Village.Add` 用 `checked` 算术，金库接近上限时会抛 `OverflowException`。**先写余数再写金库**会留下「余数记了、钱没入账」的半笔账 |
| 读档入口 | `RestoreVillageCutCarry(long)` —— 带范围检查的专用入口（不设公开 setter） |
| 暴露 | `VillageCutCarry` 只读属性（供存档与测试） |

### 2.3 溢出加固

| 风险点 | 处理 |
|---|---|
| `totalAmount = UnitPrice × qty` 溢出 | 新增 `TryMultiply`（除法比较法判溢出）→ 溢出**判为 `InvalidRequest`**，不抛异常 |
| 为什么不用 `checked` | 调用链（`HeroBehaviorService` → `DailyShoppingService` → 游戏循环）**没有接住异常**，异常一路冒到 `_Process` 会把游戏打断。交易金额溢出是「这笔单子不成立」，用**返回值**表达比用异常合适 |
| `taxUnits` 溢出 | 不溢出的分解式（见 2.1） |

### 4.3 采集结果（1000 模拟天 / 1984 行流水）

| 指标 | **新基线**（0.5 / 0.65 / 累计村抽） | 旧基线（0.4 / 0.5 / 逐笔 floor） |
|---|---|---|
| 副本场次 | 1000（成功 **277** / 失败 723） | 1000（成功 136 / 失败 864） |
| **副本成功率** | **27.70%**（理论 `0.65³` = 27.46%） | 13.6%（理论 12.5%） |
| 有战利品的场次 | **277**（旧基线 136 → **样本量翻倍**） | 136 |
| 掉落出现场次 | 石料 260 / 木料 178 / 布匹 71 | 石料 131 / 木料 94 / 布匹 32 |
| ↳ 占比 | 93.9% / 64.3% / 25.6% | 96.3% / 69.1% / 23.5% |
| ↳ 理论值（3 抽，权重 60/30/10） | 93.6% / 65.7% / 27.1% | 同 |
| 成交笔数 | 707 | 1115 |
| 成交额 | 3280 金 | 5088 金 |
| **村抽合计** | **164 金** ← **D-052 的核心目标达成** | **0 金**（死规则） |
| 5% 理论值 | `floor(5% × 3280)` = 164 金 | 254 金（**收不到**） |
| **守恒** | `sum(villageCut) + 在途零头` = 164 金，**差额 0**（在途零头落在 0..0.99 金）→ **成立** | — |

**三条关键结论**

1. **胜率改动生效**：副本成功率 27.70%，与理论 27.46% 吻合（1000 场样本的标准误约 1.4%）。
2. **掉落分布仍与权重吻合**：三项占比与理论值的偏差都在 1.5 个百分点内 ——
   说明**提高胜率没有改变掉落分布本身**，只是把样本量翻了一倍。
3. **村抽从死规则变成实际收钱**：3280 金成交额抽出 **164 金** = **正好 5%**，
   且 `sum(villageCut) + 在途零头` 与 5% 理论值**分毫不差** → 累计口径的守恒成立。

> **顺带说明为什么旧基线的成交额更高（5088 vs 3280）**：
> 旧基线里副本少成功 141 场，掉落少一半，**可交易的货也就少**；
> 而旧基线的村抽是 0，等于**摊位费整段失效** —— 卖方拿全额，
> 成交更「划算」，于是同样的产出被交易掉了更多次。两件事叠加，成交额更高。
> 这不是新版本变差了，是**旧版本的村抽根本没在工作**。

### 5.2 数据暴露的两个**机制级**问题（不是数值问题，改数值解决不了）

| # | 现象 | 根因 | 性质 |
|---|---|---|---|
| **A** | 成交笔数从第 0–99 天的 **155 笔**降到之后稳定的 **47–97 笔/100 天**（↓约 60%），但**并未归零** | 自主购物「买什么」的判据是「该英雄背包里数量 < 5」（`HeroBehaviorService` 的背包上限）—— 背包装满就停买。**不是没钱**（村金库在涨、市场仍在转） | **机制**。背包上限 5 份/物品 是成交量的硬顶 |
| **B** | 村抽是**单向货币沉淀**：钱只在英雄之间循环，每笔 5% 永久进村库；村库的钱**只有玩家手动升级村庄才会花出去**。1000 天抽走 164 金 ≈ 初始货币池（3 英雄 × 100 金）的一半，而**没有反向货币来源**（采集只进村庄材料，不进钱） | 5% 税 + 封闭货币池 | **机制**。长期看货币持续收缩，直到玩家把村库花掉 |

> **这两条都不是「把掉落率调高一点」能解决的**，也**不在 R-05 的数值范围内** ——
> 它们要么改**经济机制**（背包上限 / 货币来源 / 村库出口），要么在**更长的采样**下继续观察。
> 建议**单独立项**，不要塞进 R-05 第二轮的数值定案里。
