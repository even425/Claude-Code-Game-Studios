## Summary

村庄有一个自己走的时钟；每个村民带着一个**地球时区**和**他自己那边的上线钟点**，
换算到村庄时钟之后决定他几点出现在村口。村庄因此永远有人在线，永远不会天黑，
而「营业时间」随着人口增长自己被拉长 —— 这条设计没有额外成本，因为人本来就来自各个时区。

> **Quick reference** — Layer: `Foundation` · Priority: `MVP` · Key deps: `召唤系统`（提供时区与作息字段）

---

## Overview

村民不是 NPC，是有地球作息的人。所以村庄的「人力」是波动的：
**下午开工，村里没人，工地冻一整夜**——这是 M0 已经实测到的行为，不是假设。

本系统负责三件事：
1. 一个自己走的村庄时钟（一天默认 75 秒真实时间，可压缩给测试）；
2. 每个村民的在线窗口——由**他自己在地球那边的时区与上线钟点**换算而来；
3. 「在场」的判定——村庄建造、配队、日常事件全都读这一个判定。

它明确**不做**的事：不区分早班晚班，不做排班，不让玩家调整村民的作息。

## Player Fantasy（简）

你是一个村长，你没有打卡制度。你的村子自己有作息表，而这张表不是你排的 ——
它是几十个地球人从各个时区带过来的。你要做的是看着村子亮起来。

## Detailed Design

### Core Rules

**R1 — 时钟自己走。** 村庄时间不靠玩家点击推进。每一帧 `dt` 推进 `dt / DayLength`，
越过 1.0 就进一天（`Day += 1`），一天内的进度回到余数。开局的时刻固定为
**上午 10:00**，因为玩家打开游戏时村里得有人。

**R2 — 一个「天」= `DayLength` 秒真实时间，默认 75 秒。**
测试用 `--daylen=N` 覆盖；`N` 必须 `> 0.5`，否则忽略该参数、回落到 75。

**R3 — 村民的作息登记为三个字段，不是一个钟点。**

| 字段 | 含义 | 取值来源 |
|---|---|---|
| `UtcOffset` | 他在地球哪一带，比 UTC 快几小时（可带 .5） | 从 11 个时区里随机 |
| `LocalLoginAt` | **他自己那边**几点上线（0..24） | 性格决定的偏好 |
| `PlayHours` | 一次上多久（游戏内小时） | 性格 × 投入度 |

**R4 — 村庄钟点由时区换算而来。**
`LoginAt = (LocalLoginAt − UtcOffset + 24) mod 24`，即他「那边」的上线钟点减去时区偏移。
**这是全部机制。** 地球一边是晚上，另一边就是早上——把偏移一散，24 小时就再也难有空档。

**R5 — 一次在线是一段区间，可能跨午夜。**
在线窗口 = `[LoginAt, LoginAt + PlayHours)`，右端**开区间**（下线那一刻就不在了）。
`LoginAt + PlayHours > 24` 时窗口跨午夜，判定回绕到次日。

**R6 — 缺席优先于作息。** `AbsentDays > 0` 时 `IsOnlineAt` 对任何时刻都返回 false，
先判缺席、再判窗口。

**R7 — 「在场」= 不在外勤 且 在线。** `Present = !Away && Online`。
`OnDuty`（能派活的村民）= `AbsentDays <= 0 && IsOnlineAt(村庄当前时刻)`。
**在线只决定他在不在地图上，不决定他干不干活**——干活快慢是性格系统的事。

**R8 — 离线即冻结，但时间照走。** 离线的人不移动、不进工地、不贡献任何干活速率。
`BuildRate == 0` 时工地进度**原地停住**，时钟继续走。这是 M0 的头号卖点，不是 bug。

**R9 — 不分早班晚班。**
不存在任何「班次」概念。作息是**时区 + 上线钟点**，不是岗位表。村庄不会天黑，
因为地球上永远有一边是白天。

**R10 — 三个开场村民被钉在村庄时钟上。**
开局那三人（村长亲手召来的，不随机）`PinOnlineAt(10.0, 11 + i*0.9)`，
覆盖村庄时间约 10:00–22:48。他们是村子唯一稳定的白班。
**后来召来的人一律按自己的时区**，不钉——村庄的「营业时间」由人口自己拉长。

**R11 — 调试铁律：看到「某个时段没人」，先查时区。**
最早的作息表按村庄钟点写死，导致「清晨 6–10 点」三种性格一个都不会上线，
招一百人那个洞还在。时区一散，洞自己就没了。**这个洞不是 bug，是本作的核心机制。**

**R12 — 作息表是「他自己的时间」。** 花名册上写的是 `LocalLoginAt` 和他的时区
（如 `19时（东亚）`），不是村庄钟点。那是他的作息，跟村庄无关。

### 村庄时钟的阶段划分

`Hour` 是 0..24 的浮点。七个阶段与「深夜」标记：

| 阶段 | 区间 | 说明 |
|---|---|---|
| 深夜 | `[0, 5)` | |
| 清早 | `[5, 8)` | |
| 上午 | `[8, 11)` | 开局落在这里 |
| 晌午 | `[11, 14)` | |
| 下午 | `[14, 18)` | |
| 傍晚 | `[18, 21)` | |
| 夜里 | `[21, 24)` | |

`DeepNight = Hour >= 22 || Hour < 6`——用于「最后一个也走了」的判定，避免深夜反复记账。

### States and Transitions

村民在本系统里只有「在不在村口」这一个状态维度。四个可见状态：

| 状态 | 进入条件 | 退出条件 | 行为 |
|---|---|---|---|
| **在场** | `Online && !Away` | 下线 / 出征 / 缺席 | 移动、参与日常、去工地 |
| **离线** | `IsOnlineAt(hour) == false` | 上线时刻到 | **不移动、不进工地、速率 0**，不再被日常事件抽中 |
| **外出** | `Away = true`（任务系统） | 任务结束 | 不在地图上 |
| **缺席** | `AbsentDays > 0`（生病 / 昨天打架） | 跨天递减至 0 | 即使在他的窗口里也不上线 |

上下线切换会被记成一次性事件 `JustLoggedIn` / `JustLoggedOff`，供外部消费一次后清除。

### 时区来源（已实现的抽取规则）

`HeroFactory.ScheduleFor` —— 性格只影响**偏好**，不影响**许可**：

```
时区集合 = { -11, -8, -5, -3, 0, 1, 3, 5, 8, 9, 13 }      均匀随机

LocalLoginAt（他那边几点上线）      PlayHours（一次上多久）
  莽  → 19 + rand×4   → [19, 23)      莽 → 4 + rand×4  → [4, 8)
  贪  →  9 + rand×6   → [ 9, 15)      贪 → 4 + rand×3  → [4, 7)
  傲  → 13 + rand×9   → [13, 22)      傲 → 2.5+rand×4  → [2.5, 6.5)

PlayHours ×= 肝 1.25 / 随手 1.00 / 挂机 0.70 ，最后 clamp 到 [1.5, 9]
```

`PlayHours` 的 clamp 是必需的：没有下界时 `挂机 × 傲` 会得到 1.75 小时以下的窗口，
人口少时更容易出现空档；没有上界时 肝 × 莽 的窗口可以长到吞掉整个村庄白天。

### 实测覆盖曲线（`--selftest` 打印）

> **这是当前实现的测量结果，不是设计承诺。**
> ⚠️ **口径已于 2026-10-17 修正，见下方「修订」。旧表是单次抽样，不能引用。**

**多次抽样（每档 200 次独立村庄）后的真值**：
`--selftest` 现在对每个人口规模跑 200 次，报均值 / 最坏 / 「24 小时无人的试验占比」。

| 人口 | 空档均值 | 最坏空档 | 24 小时无人的试验占比 |
|---|---|---|---|
| 3 | 11.18 | 18 | 0% |
| 6 | 5.17 | 12 | 5% |
| 10 | 2.18 | 9 | **35%** |
| 15 | 1.00 | 10 | **57%** |
| 20 | 0.39 | 6 | **78%** |
| 30 | 0.06 | 2 | 96% |
| 40 | 0.01 | 1 | 99% |

读法：**村庄的营业时间是被人口撑出来的，不是被写死的**，但**撑满需要的时间比直觉长**——
**10 个人只有 35% 的把握全天有人，要到 30 人才接近可靠。** 这就是 R9 + R4 的全部效果。

> ### ⚠ 修订记录（2026-10-17，必读）
>
> **本节原有的一张表说「10 个人时 24 小时无空档」，是错的。**
> 那张表来自 `Coverage()` 的**单次抽样**——它抽 60 个随机村民然后取前 N 个，
> 每个进程重抽一遍，**同一份代码两次跑能给出不同答案**（实测 pop3 的空档数在 7 与 12 之间跳）。
>
> **它还错在另一处**：`Coverage()` 量的是随机召来的村民，
> **不是**被 `PinOnlineAt` 钉住的开局三人。两者不可混用。
>
> **教训（与 `chronicle.md` AC 口径事故同类）**：
> **一次抽样不是测量。** 任何「跑一次看结果」得出的百分比都必须标明抽样次数；
> 覆盖率这类小概率量尤其如此——10 人时 35% 与 100% 之间的差别，
> 在单次抽样里根本看不出来。

### 时区是加权的（2026-10-17 裁定）

`HeroFactory.PickTimezone` 对三种性格**分别加权**，池子不切分：

| 性格 | 加权时区 | 权重 | 落点倾向 |
|---|---|---|---|
| 莽 | 东八 / 东九 / 新西兰 | ×8 | 村庄 **11–17** 点扎堆（他们那边正是深夜） |
| 贪 | 北美西 / 中 / 东岸 | ×8 | 村庄 **22–23** 点扎堆（他们那边正是白天） |
| 傲 | 无 | ×1 | 平的 |

**为什么是加权不是切分**（两条都量过）：
1. **切分会把时区池劈开**，早先靠「时区一散洞自己就没了」补上的清晨空档会重新裂开。
2. **覆盖代价与倾斜强度无关** —— 实测权重 2 与权重 10 的覆盖率几乎相同：
   代价在「有倾斜」这件事本身（任何非均匀分布都收窄），不在倾斜有多强。
   所以倾斜强度是免费的，取到「看得见但仍留着变化」为止：权重 8。

⚠️ **「莽是夜猫子」只在相对他自己的时区成立** —— 在村庄时钟上他们是**下午**那批。
这条曾被误写进设计文档并被两个 agent 各自独立证伪（见 `beasts-and-raids.md` **OQ-3**）。

## Formulas

### F1 · 村庄时刻推进

```
t ← (t + dt / DayLength) mod 1
Hour = t × 24
Day  += 1                       （每次 t 越过 1 时；一次 dt 内可越过多次）
AbsoluteHour = (Day − 1) × 24 + Hour
```

| 变量 | 类型 | 范围 | 来源 | 说明 |
|---|---|---|---|---|
| `t` | float | `[0, 1)` | 运行时 | 一天内的进度。开局 = `10/24` |
| `dt` | float | `≥ 0` | 引擎帧时间 | 本帧经过的真实秒数 |
| `DayLength` | float | `(0.5, ∞)` | 默认 75；`--daylen=N` | 一个游戏日的真实秒数 |
| `Hour` | float | `[0, 24)` | 计算 | 一天内的村庄钟点 |
| `Day` | int | `≥ 1` | 运行时 | 天数，跨天只增不减 |
| `AbsoluteHour` | float | `≥ 0` | 计算 | 从开局起的累计小时 |

**输出范围**：`Hour ∈ [0, 24)`，由 `mod 1` 保证；`Day ≥ 1` 且单调不减。
`Hour` 恒小于 24，所以格式化出来**永远不会出现 `24:00`**。

**边界情况**：`dt` 远大于 `DayLength`（掉帧、`--daylen=8` 配 headless）时 `while` 循环会连续翻好几天，
`Day` 一次涨好几位，但 `Rolled` 只保留最后的天数——**日事件当帧只触发一次**（见 Edge Cases E6）。

**工作示例**：`DayLength = 75`，`t = 10/24 ≈ 0.41667`。`dt = 1s` → `t ≈ 0.43`，
`Hour ≈ 10.32`，显示 `10:19`。`dt = 75s` → `t` 回到 `0.41667`，`Day = 2`，`Hour ≈ 10.0`，显示 `10:00`。

### F2 · 上线时刻换算（时区换算）

```
Wrap(h) = ((h mod 24) + 24) mod 24
LoginAt = PinnedVillageHour ≠ null ? PinnedVillageHour
                               : Wrap(LocalLoginAt − UtcOffset)
```

| 变量 | 类型 | 范围 | 来源 | 说明 |
|---|---|---|---|---|
| `LocalLoginAt` | float | `[0, 24)` | 召唤（性格偏好） | **他自己那边**几点上线 |
| `UtcOffset` | float | `-12 .. +14`，实际取值 `{−11,−8,−5,−3,0,1,3,5,8,9,13}` | 召唤（随机时区） | 比 UTC 快几小时 |
| `PinnedVillageHour` | float? | `null` 或 `[0, 24)` | 开局三人 / 调试 | 非空时直接覆盖换算结果 |
| `LoginAt` | float | `[0, 24)` | 计算 | 换算到村庄时钟，他几点上线 |

**输出范围**：恒定落在 `[0, 24)`，由 `Wrap` 的双重取模保证——`LocalLoginAt` 小于 `UtcOffset`
时中间结果为负，`Wrap` 把它拉回正区间。**不存在负的下线时刻。**

**工作示例**

| `UtcOffset` | `LocalLoginAt` | 中间值 | `LoginAt` | 读法 |
|---|---|---|---|---|
| `-11`（夏威夷） | `19.0` | 30.0 | **6.0** | 莽，夏威夷深夜上线 = 村里早上 6 点 |
| `+8`（东亚） | `19.0` | 11.0 | **11.0** | 同一个人在新西兰 = 村里晚上 11 点 |
| `+13`（新西兰） | `11.5` | −1.5 | **22.5** | 负数回绕 |
| — | — | — | `10.0`（钉住） | 开局三人，忽略时区 |

### F3 · 在线判定（含跨午夜回绕）

```
IsOnlineAt(hour) =
    false                                     若 AbsentDays > 0
    否则  e = LoginAt + PlayHours
          e ≤ 24  →  (hour ≥ LoginAt) ∧ (hour < e)
          e > 24  →  (hour ≥ LoginAt) ∨ (hour < e − 24)
```

| 变量 | 类型 | 范围 | 来源 | 说明 |
|---|---|---|---|---|
| `hour` | float | `[0, 24)` | 村庄 `Hour` 或覆盖测试的整点 | 被问的村庄钟点 |
| `LoginAt` | float | `[0, 24)` | F2 | 上线时刻 |
| `PlayHours` | float | `[1.5, 9]` | 召唤（性格 × 投入度，clamp 后） | 一次在线时长（村庄小时） |
| `e` | float | `[1.5, 33)` | 计算 | 绝对下线时刻；`> 24` 即跨午夜 |
| `AbsentDays` | int | `≥ 0` | 日常事件 / 死亡系统 | 缺席剩余天数 |

**输出范围**：`true` / `false`，无第三种结果。窗口长度恒等于 `PlayHours`（1.5–9 小时），
即使跨午夜也不变形。

**边界情况**

| 输入 | 结果 | 原因 |
|---|---|---|
| `hour == LoginAt` | `true` | 上线那一刻就在（左闭） |
| `hour == e`（不跨夜） | `false` | 下线那一刻就不在了（右开） |
| `e > 24` | 走 `∨` 分支 | 窗口尾部回绕到次日 `[0, e−24)` |
| `hour == e − 24` | `false` | 回绕区右端同样开 |
| `PlayHours == 0` | 恒 `false` | `hour ≥ L ∧ hour < L` 空集（clamp 下界 1.5 使其不可达） |
| `PlayHours == 24` | 恒 `true` | 两个分支互补覆盖全域（clamp 上界 9 使其不可达） |
| `AbsentDays > 0` | 恒 `false` | 缺席优先于一切 |

**工作示例（跨午夜的夜猫子）**：`LoginAt = 22`，`PlayHours = 4` → `e = 26 > 24`，回绕尾 `2`。
`IsOnlineAt(21.9) = false`；`(22) = true`；`(23) = true`；`(0) = true`；`(1.9) = true`；`(2) = false`。✅

**工作示例（普通窗口 + 缺席）**：`LoginAt = 10`，`PlayHours = 5` → `e = 15 ≤ 24`。
`(9.99) = false`、`(10) = true`、`(14.99) = true`、`(15) = false`。
若 `AbsentDays = 1`，则 `(10) … (14)` **全部返回 false**。✅

### F4 · 时段覆盖（诊断量）

```
Coverage(h) = Σ_i IsOnlineAt_i(h)          h = 0, 1, …, 23
EmptySlots  = |{ h ∈ [0,24) ∩ ℤ : Coverage(h) = 0 }|
Peak        = max_{h ∈ [0,24) ∩ ℤ} Coverage(h)
```

| 变量 | 类型 | 范围 | 来源 | 说明 |
|---|---|---|---|---|
| `Coverage(h)` | int | `0 .. N` | 计算 | 该整点在线的人数 |
| `EmptySlots` | int | `0 .. 24` | 计算 | **空档**——一个人都没有的整点数 |
| `Peak` | int | `0 .. N` | 计算 | 最拥挤的整点人数 |
| `N` | int | `≥ 1` | 村庄人口 | 花名册长度 |

**输出范围**：`EmptySlots ∈ [0, 24]`（`N = 0` 时为 24），`Peak ∈ [0, N]`。
三个量都是整数，可直接打印、可直接断言。

**边界情况**：抽样只取**整点** `h = 0..23`。窗口边界落在非整点时（如 `LoginAt = 22.5`）
整点 22 那一格会算作未上线——这是**抽样误差，不是缺陷**，`--selftest` 的表只保证可读。
需要精确判定时用 F3 传真实 `Hour`。

**工作示例**：开局三人（钉在 10 点，窗口 11 / 11.9 / 12.8 小时）。
`Coverage(0..9) = 0` → 10 个空档；`Coverage(10..21) = 3`；`Coverage(22) = 1`（21:54 那个还挂着）；
`Coverage(23) = 0`。`EmptySlots = 12`，`Peak = 3`。✅

### F5 · 在场 / 出工判定

```
OnDuty(h)   = (AbsentDays ≤ 0) ∧ IsOnlineAt(Hour)
Present(h)  = ¬Away(h) ∧ Online(h)
ReadySquad  = 队伍中所有满足 OnDuty 的成员
```

| 变量 | 类型 | 范围 | 来源 | 说明 |
|---|---|---|---|---|
| `Away` | bool | `true`/`false` | 任务系统 | 出发离村，回来才清 |
| `Online` | bool | `true`/`false` | `RefreshOnline` 每帧刷新 | 当前是否在窗口内 |

**输出范围**：布尔。`OnDuty` 决定**能否被派活**；`Present` 决定**是否在地图上**。
两者可以不一致：出勤远征的队员 `Away = true` 但仍在自己的窗口内，`OnDuty = true`、`Present = false`。

### F6 · 工地速率与停工（M0 的头号卖点）

```
BuildRate(t) = Σ_{h ∈ 花名册} [ ToSite(h) ∧ ¬Away(h) ∧ OnDuty(h) ] × WorkRate(h)

Progress(t + dt) = Progress(t) + BuildRate(t) × dt     若 BuildRate(t) > 0
                 = Progress(t)                        若 BuildRate(t) = 0   ← 冻结
```

| 变量 | 类型 | 范围 | 来源 | 说明 |
|---|---|---|---|---|
| `ToSite` | bool | `true`/`false` | 村庄建造 | 是否被派去工地 |
| `WorkRate` | float | `0` 或 `> 0` | **性格系统**（不在本文档定义） | 缺席时恒为 0 |
| `Progress` | float | `[0, 1)` | 建造系统 | 工地进度；到 1 即建成 |
| `dt` | float | `≥ 0` | 引擎帧时间 | 真实秒数 |

**输出范围**：`BuildRate ∈ [0, ∞)`，实测量级 `0.0000`–`0.0030`；`Progress ∈ [0, 1]`
（到 1 被消费并归零）。

**边界情况**：`BuildRate = 0` 时 `Progress` **既不前进也不倒退**——工地冻住，但时钟继续，
村民照常上线、下线、发生日常。这正是「下午开工，工地冻一整夜」。
`Progress` 永不因为无人而**倒退**，这是硬规则：一次停工不该处罚玩家。

**工作示例**：某天 15:00 开工，5 人在场，`WorkRate` 各约 `0.0012` → `BuildRate = 0.0060`。
18:00 最后一个下线 → `BuildRate` 骤降为 0，`Progress` 停在某个固定值上不再变化，
直到次日某人的窗口重新覆盖到工地（`ToSite` 仍为 true 时才恢复）。已实测：`工地上0人 速度0.0000 进度冻结9小时`。

### F7 · 期望在线人数（诊断量，非规则）

```
E[Coverage(h)] = N × mean(PlayHours) / 24
```

用于对照 F4 判断某个空档是**抽样运气**还是**结构性洞**。
`mean(PlayHours)` 由性格与投入度分布决定，当前落在 4–6 小时量级 → `E ≈ 0.17N … 0.25N`。
实测人口 40 峰值 14（`0.35N`）——峰值高于期望是对的，因为窗口不是均匀铺开的。

## Edge Cases

| # | 场景 | 期望行为 | 理由 |
|---|---|---|---|
| **E1** | 村民的窗口跨午夜（`LoginAt = 22`，`PlayHours = 4`） | `IsOnlineAt(0) = true`，走 `∨` 分支回绕 | 「夜猫子」是真实存在的一类作息，不能因为跨天就判他离线 |
| **E2** | `LocalLoginAt − UtcOffset` 为负（`-1.5`） | `Wrap` 拉回 `22.5` | C# 的 `%` 对负数返回负值，不 wrap 会得到负的下线时刻 |
| **E3** | `AbsentDays > 0`，且此刻正在他的窗口内 | 仍然 `false` | 病了就上不了线，这是本项目「事件必须改状态」的第一条 |
| **E4** | 开局三人被 `PinOnlineAt` 钉住 | `LoginAt` 直接等于村庄钟点，**忽略** `UtcOffset`；花名册显示「村里常驻」；`PlayHours` 被钉住的值覆盖原值 | 开局不能是一村空房；他们是村长亲手召来的，不是随机来的 |
| **E5** | `--daylen=0.4` / `--daylen=abc` / 无参数 | 全部回落到 `75` | 0.5 秒以下的一天在 headless 下没法读；非法输入静默忽略而不是崩溃 |
| **E6** | 一次 `dt` 内跨了多天（掉帧，或 `--daylen=8`） | `Day` 正确累加，但 `Rolled` 只保留最后一天 → **日事件当帧只触发一次** | 补跑多天的日常事件会让杂谈一次刷出几十条。当前选择是「宁可少跑，不可刷屏」 |
| **E7** | `AbsoluteHour` 跨午夜 | **单调不减**（`Hour` 会从 23.9 跳回 0.0，做差会变负） | 出征剩余时间、stall 报告的间隔全部依赖它。**踩过，别再踩**——报告要每 2 小时的间隔，负数会让它永远不再打印 |
| **E8** | 全村无人在窗口内，`BuildRate = 0` | 进度冻结，时钟继续，日事件照跑 | M0 的招牌行为。**不是 bug，不得改回「不在线也照盖」** |
| **E9** | 全村 `AbsentDays > 0`，跨天触发日常 | 杂谈记一条「村里一个人也没有。天亮了，什么也没发生。」 | 空白的一天也是信息，而且**只改状态、不许装饰**的规矩要求它有一句实话可说 |
| **E10** | 最后一个村民离场，且**不在**深夜（`DeepNight == false`） | 记一条「最后一个也走了。村里静下来。」 | 这是本系统唯一主动产出的杂谈条目。深夜不记，否则一夜刷几十条 |
| **E11** | `Hour = 23.999` 时格式化 | 显示 `23:59`，**永不出现 `24:00`** | `Hour` 由 `mod 1` 保证 `< 24`；小时位是截断不是四舍五入 |
| **E12** | 玩家在开局空档时段（0–9 点）打开游戏 | 一村空房，时钟照走 | 这是设计，不是缺陷。缓解手段只有 R10 的钉住开局三人 |
| **E13** | `PlayHours` 为 0 或 ≥ 24 | 0 → 恒离线；24 → 恒在线 | 抽取时 `clamp(1.5, 9)` 使两者都不可达，但 `IsOnlineAt` 对它们必须仍给出良定义结果 |
| **E14** | 一次多人召唤中某人 `PinnedVillageHour` 已非空 | 直接覆盖，无副作用 | `PinnedVillageHour` 的写入路径只有 `PinOnlineAt`，目前仅开局三人调用 |
| **E15** | `Coverage()` 的抽样 vs 真实窗口边界 | 整点抽样有 ±1 小时的误差；判定一律走 F3 传真实 `Hour` | 覆盖表是给人读的诊断，不是判定依据 |
| **E16** | 存档恢复（MVP 不做存档） | 无规则 | 若将来做，需决定恢复后 `AbsoluteHour` 从哪起算——见 Open Questions Q7 |

## Player-visible 文案约束

**玩家可见文案不得出现系统词：成功 / 失败 / 获得 / 消耗 / 属性 / 奖励。**
本系统产出的全部玩家可见字符串：

| 位置 | 现有文案 | 说明 |
|---|---|---|
| 状态栏 | `第 N 天 HH:MM 上午` | `Clock` + `Phase`，村庄钟点 |
| 状态栏 | `在村 3/7` | `Present` 计数 / 花名册长度 |
| 花名册（在线） | `●名字 性格 投入 3/2/4 干过12 拒过3` | 实心圆 = 在场 |
| 花名册（离线） | `○名字 性格 投入 19时（东亚）上线` | **写他自己的时间**，不是村庄时间 |
| 花名册（缺席） | `○名字 性格 投入 病了` | 缺席原因写在花名册上，村长至少知道为什么缺人 |
| 花名册（钉住） | `村里常驻` | 开局三人 |
| 花名册（外出） | `不在村口。19时（东亚）才上线。` | 点击离线村民时的回应 |
| 杂谈 | `最后一个也走了。村里静下来。` | E10 |
| 杂谈 | `村里一个人也没有。天亮了，什么也没发生。` | E9 |
| 杂谈 | `从{世界}来的{名字}今天到了村里。{特征}。` | 召唤时写入，含来处 |

**`WorkRate` / `IsOnlineAt` / `LoginAt` 等内部量名一律不得出现在文案里。**
「早班 / 晚班 / 班次 / 排班」也不得出现——它们描述的是一套**不存在的**机制。

| 系统 | 方向 | 依赖性质 |
|---|---|---|
| **召唤系统** (#2) | 本系统 → 召唤 | **数据依赖**：本系统消费 `UtcOffset` / `LocalLoginAt` / `PlayHours` 三个字段，不消费它的任何规则。`systems-index.md` 目前把 #2 标为无依赖，**需要补上这条边**（见 Open Questions Q1） |
| **性格系统** (#3) | 性格 → 本系统 | **规则依赖**：`LocalLoginAt` 与 `PlayHours` 的偏好按性格/投入度抽取。`systems-index.md` 未列此边，**需补**（Q1） |

| **死亡与复活** (#10) | 死亡 → 本系统 | **状态触发**：「停机一天」若以 `AbsentDays` 实现，会直接压掉上线判定（E3）。**「一天」以谁为准必须由该系统定义**（Q2） |

| **任务与副本** (#6) | 双向 | **规则依赖**：远征耗时以 `AbsoluteHour` 计（跨天，见 E7）；`Away` 由它设置 |

**接口约定**：本系统对外只暴露
`Hour` / `AbsoluteHour` / `Day` / `Clock` / `Phase` / `DeepNight` / `OnDuty(h)` / `Present(h)`。
其余系统**不得**自己重算在线窗口，也不得缓存 `LoginAt`（`PinOnlineAt` 可以在运行中改写它）。

### R7a — 村内居民必须有统一接口，行为不得按类型分叉

> **2026-10-17 增补。** 本条由 `native-folk.md` 提出，实现方批准。
> 起因：`OnDuty` / `Present` / `IsOnlineAt` 三个谓词原先都挂在 `HeroAgent` 上，
> **本土人插不进去**，于是每个下游都会长出一个 `is HeroAgent` 的特例分支——
> 那正是「本土人变成到处打补丁的特殊情况」的开端。

**规则**：
1. `OnDuty(h)` / `Present(h)` 的**参数类型放宽为 `IHabitable`**。
   `IHabitable` 只要求**这两个**谓词 + `AbsentDays`。
   ⚠️ **`IsOnlineAt` 不在基接口上**——它属于「地球作息」子接口，只有从地球召唤来的人
   实现。本土人的 `Presence` 必须是**恒为真且不读取 `h`**（见 `native-folk.md` AC-4）。
   这一点是 2026-10-17 复核时更正过的：最初本条把 `IsOnlineAt` 也列进了基接口，
   与 `native-folk.md` AC-4 正面冲突。
   同样**不要求** `LoginAt` / `PlayHours` / `UtcOffset` / `Diligence`
   —— 那些字段的语义是「他以为自己有份地球的工作」，本土人没有。
2. **下游一律不得用 `is HeroAgent` 之类的类型判断来决定行为规则。**
   需要区分时，走 `IHabitable` 上的**显式查询方法**（例如「他属于哪个阵营」、
   「他有没有地球作息」），不靠类型。
3. **违反本条的正确后果**：一旦某个下游写了 `if (h is HeroAgent)`，
   本土人就会被静默降级——所有需要他的规则（例如算进建造劳力）都会悄悄跳过他，
   **且不报错**。这是本条要求单独成文的原因。

**验收**：`native-folk.md` 的可测不变量 F3——**拿掉本土人，作息覆盖的空档必须上升**。
若不涨，说明本土人正在走 `IsOnlineAt` 这条旧路径，本系统没有真正承重。

## Tuning Knobs（简）

| 参数 | 当前值 | 安全区间 | 调高的影响 | 调低的影响 |
|---|---|---|---|---|
| `DayLength` | 75 s | 30 – 180 s | 一天更真实，但玩家等不到昼夜变化 | 村庄转得快，观察不到「冻一整夜」 |
| `TimeZones` 集合大小 | 11 个 | 4 – 24 | 覆盖更平，空档更早消失 | 空档更多，村子更暗，但也更像真的 |
| `PlayHours` 性格基值 | 莽 4–8 / 贪 4–7 / 傲 2.5–6.5 h | ±2 h | 空档变少，但没人会连轴转 | 空档变多，「村庄自己会过日子」的观感更强 |
| `PlayHours` 投入度乘子 | 肝 1.25 / 挂机 0.70 | 1.1 – 1.4 / 0.6 – 0.8 | 肝闲差距拉大 | 差距变小，九宫格失去意义 |
| `PlayHours` clamp | `[1.5, 9]` | 下界 ≤ 2.0，上界 ≤ 12 | — | 下界 > 2.0 会让挂机几乎填不满空档 |
| 开局钉住窗口 | `PinOnlineAt(10, 11 + i×0.9)` | 8 – 14 h | 开局更稳 | 开局可能摆一村空房 |

> **平衡上的取舍**：所有这些值都同时压两头——把空档填满，玩家就看不到村庄「自己」的呼吸；
> 把空档留大，玩家会以为卡了。`design/game-brief.md` 已把它记为**已知风险**并说明当前靠 R10 缓解。

## Acceptance Criteria

> 每条都可由一次运行或一个测试独立判定。所有测试默认**确定性**（固定随机种子 / 固定输入）。

**时钟**

- [ ] **AC-1（跨天单调性）** 对 `DayLength = 75` 的时钟连续 `Tick` 720 次 `dt = 0.5`，
      `AbsoluteHour` 在**每一次**调用后都不小于上一次——包括跨午夜的那几次。测试名称含 `AbsoluteHour`。
- [ ] **AC-2（跨天计数）** 同样 720 次 `dt = 0.5`（共 360 秒 = 5 个游戏日）后，
      `Day == 6`，`Hour` 与 `10.0` 的差在 `1e-3` 内。
- [ ] **AC-3（格式）** 对 `Hour ∈ {0.0, 0.5, 9.99, 10.0, 13.999, 23.999}` 断言 `Clock` 匹配 `^\d{2}:\d{2}$`，
      且**任何输入下都不以 `24:` 开头**。逐项期望值：`0.0→"00:00"`、`0.5→"00:30"`、`9.99→"09:59"`、
      `13.999→"13:59"`、`23.999→"23:59"`。
- [ ] **AC-4（阶段边界）** 断言 `Phase` 在 `0/4.99→深夜`、`5→清早`、`7.99→清早`、`8→上午`、

      `21→夜里`、`23.99→夜里`。
- [ ] **AC-5（深夜标记）** `DeepNight` 在 `5.9 = false`、`6.0 = false`、`21.9 = false`、
      `22.0 = true`、`23.9 = true`、`0.0 = true`、`5.99 = true`。
- [ ] **AC-6（开局时刻）** 新建时钟后 `Day == 1`、`Hour ≈ 10.0`。
- [ ] **AC-7（参数解析）** `DayLengthOverride` 对 `{ "--daylen=8" }` 返回 `8`，
      对 `{ "--daylen=0.4" }`、`{ "--daylen=abc" }`、`{ "--daylen=-5" }`、`{}` 一律返回 `75`。

**时区换算与在线判定**

- [ ] **AC-8（换算含负值回绕）** `IsOnlineAt` 的输入 `LoginAt` 经 F2 换算：
      `LocalLoginAt=19, UtcOffset=-11 → 6.0`；`19,+8 → 11.0`；`11.5,+13 → 22.5`；`0,0 → 0.0`；
      `0,-11 → 13.0`。全部落在 `[0, 24)`。
- [ ] **AC-9（跨午夜窗口）** `LoginAt=22, PlayHours=4`：`IsOnlineAt` 在
      `21.9/22/23.9/0/1.9` 为 `true`，在 `2/10/21.8` 为 `false`。
- [ ] **AC-10（窗口边界开闭）** `LoginAt=10, PlayHours=5`：`9.99 → false`、`10 → true`、
      `14.99 → true`、`15 → false`。
- [ ] **AC-11（缺席优先）** 在 AC-10 的同一个人身上把 `AbsentDays` 设为 `1`，
      `IsOnlineAt(10..14)` **全部**为 `false`；`RefreshOnline` 收到 `newDay=true` 后
      `AbsentDays` 减一，缺席归零时 `AbsentWhy` 被清空。
- [ ] **AC-12（退化窗口良定义）** 直接把 `PlayHours` 置 `0` → 任意 `hour` 为 `false`；

- [ ] **AC-13（钉住覆盖）** 对三人调用 `PinOnlineAt(10f, 11f/11.9f/12.8f)` 后，

- [ ] **AC-14（在场定义）** 断言 `Present == (!Away && Online)`，在

- [ ] **AC-15（离线即冻结，M0 核心）** 开局三人钉在 10 点，跑到村庄 22:00 之后（三人均已下线），

## Open Questions

> 以下都是**开发者没说过、也没在实现里出现**的问题。不得先当规则实现。
> 每条需要 `game-designer` 拍板，涉及跨系统时按 `systems-index.md` 的 Circular Dependencies 断法处理。

| # | 问题 | Owner | 为什么重要 |
|---|---|---|---|
| **Q1** | `systems-index.md` 里 #2（召唤）和 #3（性格）都标为无依赖，但实现中召唤写入了作息字段、性格决定了作息偏好。**是否给索引补上这两条边？** | systems-designer | 依赖表必须双向；不补的话 `/consistency-check` 会报假冲突 |
| **Q2** | **「停机一天」的「一天」以谁为准？** 是村庄日（24 游戏小时）还是他自己的地球日？跨时区时这两者差最多 22 小时——一个东八区的人「停一天」可能根本不影响他原本的窗口 | game-designer + systems-designer | 死亡与复活 (#10) 是直接消费者。**这条不定，#10 无法写** |
| **Q3** | **在线人数是否需要软保底？** 实测 3 人时有 11 格没人，brief 已确认「空村有味道」，但如果玩家恰好在开局就赶上 20 小时空档，会不会真的以为卡了？（`design/game-brief.md` 的「已知风险」节承认了这一点，目前的缓解只有 R10） | game-designer | 触及 Pillar：村庄的自主感 vs 可读性。**动了就是改设计，不是改数值** |
| **Q4** | **上线时段要不要逐日漂移？** 目前是每天同一时刻上线（可读性最好）。要不要让他逐日微移，模拟真实作息的不规律？ | game-designer | 会影响杂谈可读性和覆盖曲线的稳定性 |
| **Q5** | **玩家能不能改村民的作息**（强制他留在村里 / 延长他今天的窗口）？开发者从未提及 | game-designer | 若能，「村庄有自己的心跳」这条 Pillar 就被玩家接管了；若不能，玩家在深夜打开游戏只能干看着。**两边都有代价，不要我替他选** |
| **Q6** | **上线 / 下线要不要有表现？** 现在上下线是静默的，只有「最后一个也走了」一条。村庄要不要天黑、窗户亮灯、村民进进出出的门响？ | art-director + game-designer | 当前只有「在场 / 不在场」两个可见状态。夜间表现会直接放大或抹平空档的观感 |
| **Q7** | **存档恢复（若将来做）时 `AbsoluteHour` 从哪里起算？** 村民的窗口是按村庄钟点还是按绝对小时对齐的？ | technical-director | brief 写明 MVP 不做存档，但这条一旦漏掉会在 M4 之后变成 `propagate-design-change` 的返工项 |
| **Q8** | **时区是否只作用于「上线时刻」，还是也该影响别的？** 目前只影响 `LoginAt`；`PlayHours` 与时区无关。跨时区的人「一晚上」的自然长度是一样的吗？ | game-designer | 若将来影响 `PlayHours`，F4 的实测表全部作废 |
| **Q9** | **峰值密度是否够？** 40 人时峰值 14 人同时在村口 —— 会不会视觉上穿模、卡顿，或者反而显得太挤？ | art-director | 现有代码里村民是各自随机选点，没有碰撞。峰值只增不减的话需要实测 |
| **Q10** | **村庄钟点是否是唯一权威时间？** UI 显示的是村庄钟点，但玩家的真实时钟是另一回事。是否要在某处提示「这是村子里的时间」？ | game-designer + ux | 玩家可能在凌晨 3 点打开游戏看到一个显示「15:00」的村庄。当前设计对此完全没有交代 |
| **Q11** | **每一对上下线是否都该记一笔杂谈？** 现在只有「村口清空」才记。若每次上线都记，40 人的村庄一天就是几百条，杂谈会被淹没 | game-designer | 涉及 #11 杂谈的信息密度。当前 40 条上限会直接截断掉 village life 的内容 |
