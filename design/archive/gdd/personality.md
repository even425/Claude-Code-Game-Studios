## 开发者原话（本文档的唯一依据）

> 「有些喜欢打副本，有些是休闲玩家，有些是pvp玩家等等，这些都能通过性格来表现，
> 根据他们的性格权重，他们会自行去做一些事情」

> 「性格不是二极管。不是说这个玩家喜欢打副本，他就不会休闲了、不会采集了，
> 只是说效率会慢点。」

**第二句是对第一句的修正，也是本系统最容易做错的地方。**
它直接否决了早期实现：`prototypes/cunzhang-yu-maoxianzhe-concept/prototype.html`
第 254–258 行的

```js
if (h.p === '傲') { if (!t.hard) { h.refused++; return false; } ... }
```

那个 `return false` 就是二极管——傲对所有非难活一律不出现在候选集里，
等价于「傲不干活」。**本文档取代那段实现。** 新的验收标准里有一条专门证伪它
（§ Acceptance Criteria · B 最后一个人测试）。

## Summary

性格系统给每个村民两根独立的轴：**轴一决定他要什么**（莽 / 傲 / 贪），
**轴二决定他投入多少**（肝 / 随手 / 挂机）。这两根轴只通过**两个互不相交的
接口**影响世界：`EfficiencyOf()` 回答「他干这活有多快」，`ScoreOf()` 回答
「没人派活时他挑哪个」。前者改的是速度，后者改的是选择——**没有任何一根轴
决定他能不能干某件事**。缺人时任何性格都能顶上，只是慢。

## Overview

玩家是村庄的村长，他不直接指挥谁去干什么。每个被召唤来的村民身上带着一组
性格数据（莽 / 傲 / 贪 之一，加上 肝 / 随手 / 挂机 之一）。当村庄里有活没人
领的时候，村民自己按性格权重去挑；挑中了之后他干活的速度又按另一组数据算。
于是同一座村庄会自己长出不同的面貌：一村莽汉永远在副本和工地之间两头跑，
一村商人天天绕着集市转，一村傲气的人谁都不搭理，但真没人手的时候他也会去
搬石头——只是慢，慢到你能一眼看出来他不想干。

性格**从不否决**任何一份工作。它只改变速度，改变选择，改变村民之间的关系。
这不是一条过滤器，是一层摩擦。

> ⚠️ **一处必须读准的边界（2026-10-17 裁定 ⑬ 修订）**
> 「性格不否决」说的是**这个人能不能干活**——他照样能接活、能盖房子、能远征，只是慢。
> 它**不是**说「任何组合都合法」。**编队层面的硬约束是另一回事**：
> 有仇的两个人**不能**被派进同一支队（`squad-and-cohesion.md` R6）。
> 「不能进这一支队」≠「不能干活」。这两件事在本文件里始终分开，见 § 铁律 1。

## Player Fantasy

**主要服务的 MDA Aesthetics：Discovery（发现）+ Narrative（叙事）+ Challenge（挑战）**

玩家该有的感觉是**「我认识他们每一个人」**。不是因为游戏告诉他了每个人的数值，
而是因为他看过足够多的杂谈，能在派活之前就猜到：「今天让老李头去搬石头？他会干，
但会磨洋工」「这个副本缺人，找那个摔断过腿的莽」。

- **Discovery**：性格是可以被观察出来的规律，不是 UI 上的标签。玩家从杂谈里读出
  「这人挑难的」，再在派活时验证，验证成功的那一刻是系统的核心快感。
- **Narrative**：杂谈是自主行为的唯一读数器（`game-brief.md` 已知风险第三条）。
  没有性格就没有杂谈，性格是把数字变成故事的那一步。
- **Challenge**：不是操作挑战，是**排兵布阵**的挑战——手上的莽是好刀，但莽不肯
  采石；傲的效率在粗活上只有 0.6，村长必须知道什么时候该硬着头皮让他上。

**SDT 校验**
- **Autonomy（对村民）**：他们自己挑活，这是他们的自主性。玩家不能夺走。
  玩家的自主性体现在**排班与配队**，不在「派谁干哪件」——那一层归村庄。
- **Competence（对玩家）**：性格是可学习的知识，不是随机的骰子。
  `Acceptance Criteria · C` 给了判定「学到了没有」的可测量指标。
- **Relatedness**：性格 + 结仇 + 吵架构成村民之间的人际网，玩家是这张网的中心。

**参考气质**：《修仙模拟器》里弟子按性格自己决定修炼还是下山——决策者是 NPC，
玩家是观察者与布局者。本系统要的是这个气质里**「他今天居然去采石了」**
的那一半，不是战斗数值那一半。

## Detailed Design

### 两条轴

| 轴 | 取值 | 开发者依据 |
|---|---|---|
| 轴一 · 他要什么 | **莽** / **傲** / **贪** | 「有些喜欢打副本…有些是pvp玩家等等，这些都能通过性格来表现」 |
| 轴二 · 他投入多少 | **肝** / **随手** / **挂机** | **⚠️ 推导项，开发者未提及。** 依据是「同样是莽，有的是肝帝，一个是指一天游——这对村长的用法完全不同」 |

**轴一 = 玩家类型（副本党 / 休闲 / PvP）的机制化表达。**
- **莽** = 副本党：要强度。战斗效率最高，细活也干得了只是嫌慢；没人派时主动挑战斗活。
- **傲** = PvP 党 / 独行：要胜负。战斗高，**脏活细活低（×0.60 —— 开发者原话）**；
  没人派时挑**有对手的、难的**活。
- **贪** = 经商党：要财富。采集跑腿最高，战斗低；没人派时挑**来钱多的**活。

> ⚠️ **不要读成「莽不采集」「傲不盖房子」。** 那是硬门槛，会把队伍凑法锁死。
> `game-brief.md` 明确写了这一条。

**轴二只改一件事：自主决策的频率。** 它**不碰** `EfficiencyOf`，**不碰**
`ScoreOf` 的取值。这样第二根轴不会吃掉第一根轴——否则「肝」会变成一种速度加成，
那不是玩家类型，是数值。

| 投入度 | 自主决策间隔 | 每日自主次数上限 | 玩家的用法 |
|---|---|---|---|
| **肝** | 2 小时 | 6 | 你是他的上线时间，按专业对口用 |
| **随手** | 6 小时 | 3 | 指望不上，但填个坑可以 |
| **挂机** | 24 小时 | 1 | 一个不会跑的工位；被指派才动 |

> 全部为推导值，见 § Open Questions Q1。

### 三条铁律

**铁律 1 · 唯一能让一个村民「不干活」的，是状态，不是性格。**

病倒、想走、已死一天——这些能让他不出现。
性格不能。任何 `if (personality == X && category == Y) return;` 形式的分支，
在本系统中一律视为 bug。搜索代码时按这个模式找。

> #### 铁律 1 · 修订说明（2026-10-17 裁定 ⑬）
>
> **原文与裁定的冲突**：旧版铁律 1 写的是「性格**永不可否决**」，
> 而裁定 ⑬ 要求「有仇的人不能进同一支队」。两句直接对撞——
> 一份文档既宣称永不否决，又必须提供一条否决路径。
>
> **冲突其实在措辞，不在机制。** 旧措辞没有区分两个不同的层：
>
> | 层 | 问的问题 | 裁定后的答案 | 归属 |
> |---|---|---|---|
> | **人（能不能干活）** | 「他**能不能**接这活？」 | **能。永远能。** 没有任何性格、没有任何关系能让他「干不了」。傲照样盖房子，贪照样打架 | 本文件 · `EfficiencyOf` |
> | **队（这支队能不能这么组）** | 「这**几支队伍**能不能同车？」 | **有仇不能。** 硬禁止，且游戏明确告知原因 | `squad-and-cohesion.md` · R6 |
>
> **关键区分：被否决的是「这一支队伍」，不是「这个人」。**
>
> - 他**照常**出现在候选池里、**照常**自主挑活、**照常**被兜底指派去工地和建造。
> - 他**照常**能和其他**别的**人组成队伍——只要那些人不与他有仇。
> - 只有「把他和与他有仇的那个人放进同一支队」这一个动作被拒绝。
>   他本人仍然是一条完全可用的劳动力和一条完全可用的队伍成员。
>
> **所以铁律 1 修订后是**：「唯一能让一个村民『不干活』的，是状态，不是性格，
> **也不是他与谁有仇**。有仇否决的是**编队**这一层，不是**他**这一层。」
>
> **实现上怎么查**（验收时按这个搜）：
>
> | 搜索模式 | 期望 | 说明 |
> |---|---|---|
> | `if (personality == X && category == Y) return;` | **0 命中** | 原二极管，铁律 1 的核心 |
> | `EfficiencyOf(...) == 0` / 返回 0 或负数 | **0 命中** | `EfficiencyOf` 恒 > 0 |
> | `GrudgeWith != null` 影响 `EfficiencyOf` / `WorkRate` / `ScoreOf` | **0 命中** | 铁律 1 与裁定 ⑬ 共同禁止 |
> | `GrudgeWith != null` 影响 `CanJoinSquad` | **允许，这是唯一一条** | 编队层的硬禁止，`squad-and-cohesion.md` R6 |

**铁律 2 · 自主选完之后，执行走的是和被指派一模一样的代码路径。**

```
自主通道：没人派 → ScoreOf 决定【挑哪个】 ─┐
                                          ├→ 执行通道 → EfficiencyOf 决定【多快干完】
指派通道：有人派 ──────────────────────────┘
```

权重只影响**选择**，效率只影响**速度**。它们在代码里是两次不同的调用、
两个不同的函数、分属两个不同的模块边界。这条是整个系统成立的地基。

**铁律 3 · 事件必须改状态，不能只是写一句话。**

病倒的人真的干不了活，吵过架的人真的进不了同一支队。
（第二句在 2026-10-17 由裁定 ⑬ **确认成立**——旧实现给的是 ×0.50 软惩罚，
与这句铁律原本就对不上。详见 § 铁律 1 · 修订说明与 § 8 种日常事件。）
如果一个事件写进杂谈却什么都不影响，那它就是装饰，**删掉**。
`game-brief.md` 硬规矩，本系统继承。

### 自主行动流程

对每个村民，按其投入度的间隔触发一次自主决策：

1. **在线检查**——若当前村庄时钟该村民不在线，跳过本次 tick（不消耗次数）。
2. **状态检查**——若村民处于不可工作状态（病倒 / 想走），跳过本次 tick。
   **这是唯一允许空手离场的理由。**
3. **取候选池** `C`——所有当前存在且**尚有空位**的活：
   工地未满的槽位、副本未组满的编队、（M4）摆摊空位。
4. **若 `C` 为空**——记为「闲着」，不产生任何事件文案。
   *（空闲时长的累积由后续模块读取；本系统不为他编故事。）*
5. **打分**——对每个 `t ∈ C` 算 `w = ScoreOf(hero, t)`。
6. **抽取**——按 `w^γ` 归一化后随机抽一个 `t*`。`γ` = `choice_temperature`。
7. **占位**——若 `t*` 在抽取瞬间已被占满，重抽，最多 3 次；仍失败则落选，回到第 3 步的候选池（若已空则按第 4 步处理）。
8. **进入执行通道**——该村民按 `EfficiencyOf(hero, cat(t*))` 开始干活。
   **从此以后，代码路径与「被村长指派」完全一致。**
9. **落杂谈**——事件写入 `杂谈`。

### 兜底指派（缺人时的顶替）

一村活没有人接时，**任何在线且状态正常的村民都要接**，
按他本人的 `EfficiencyOf` 计算工期——不管那活有多不适合他的性格。

- 傲去干建造：速度 ×0.60，工期变成 1.67 倍。杂谈走「这次没挑」那一类文案。
- 这是**特性不是 bug**。「缺人时任何人能顶，只是慢」是开发者原话的直接推论。

### 权重作用于「吸引力属性」，不作用于「类目」

这是本系统第二个关键设计。如果权重只按类目配（贪=采集），那它和效率就会长得
一模一样，退化成同一个东西的两个换皮。所以：

| 维度 | 取值 | 谁提供 | 为什么在这里 |
|---|---|---|---|
| `cat` 活类别 | 战斗 / 采集 / 建造 / 跑腿 / 经商 | 任务与副本 | 莽的偏好确实是按类别说的 |
| `diff` 难度 | 1–5 | 任务与副本 | 傲「挑难的」 |
| `opp` 有无对手 | 0 / 1 | 任务与副本（PvP 是 M4/Alpha） | 傲「挑有对手的」 |
| `pay` 报酬档 | 0–3（任务池四分位） | 经济与摆摊（M4） | 贪「挑来钱多的」 |

**贪的偏好轴挂在报酬上，不挂在类目上。** 这不是修饰，这是解耦的工具：
一个报酬极高的战斗活对贪的吸引力可以超过一次中报酬的采集，
而他打这场战斗的效率只有 0.70。**他挑了个自己干不好的活**——这件事只有在
权重和效率是两套数据时才可能发生，也正是 Acceptance Criteria C 要测的东西。

## Formulas

### 1. 效率系数（本系统对外交付的唯一速度量）

```
efficiency(hero, category) = EFFICIENCY[hero.personality][category]
```

| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| `hero.personality` | enum | 莽 \| 傲 \| 贪 | `召唤系统` | 轴一 |
| `category` | enum | 战斗 \| 采集 \| 建造 \| 跑腿 \| 经商 | 任务与副本 | 活类别 |
| 返回值 | float | **0.60 – 1.30** | `assets/data/personality-efficiency.yaml` | 性格对这类活的效率 |

#### 效率矩阵（初值）

| 性格 ＼ 类目 | 战斗 | 采集 | 建造 | 跑腿 | 经商 |
|---|---|---|---|---|---|
| **莽** | **1.30** | 0.90 | 0.90 | 0.90 | 0.90 |
| **傲** | 1.20 | **0.60** | **0.60** | **0.60** | 1.00 |
| **贪** | 0.70 | **1.30** | 1.00 | **1.30** | 1.00 |

**每个数值的来源**

| 值 | 依据 |
|---|---|
| 傲 采集/建造/跑腿 = **0.60** | **开发者原话**：脏活细活低（×0.6） |
| 莽 战斗 = 1.30、贪 采集/跑腿 = 1.30 | 推导：按「最高」取矩阵上限 |
| 傲 战斗 = 1.20 | 推导：brief 写「战斗**高**」而非「最高」，故低于莽 |
| 贪 战斗 = 0.70 | 推导：brief 写「战斗**低**」，未给数值，取近下限 |
| 莽 非战斗 = 0.90 | 推导：「细活也干得了，只是嫌慢」——只表达「慢」，不表达「分档次」 |
| 傲 经商 = 1.00 | **未表态**，取中性 |
| 贪 建造 = 1.00 | **未表态**，取中性 |

> **除 0.60 外全部是推导初值。** 数值范围规则：`上限 1.30 / 中性 1.00 / 下限 0.60`。
> 这套范围本身也是推导的（见 § Open Questions Q7）。唯一的开发者原话是 0.60。

#### 系数归属（2026-10-17 修订 · 交叉一致性 §1.1）

**交叉验证报告指出**：本文件的效率矩阵战斗列（莽 `1.30` · 傲 `1.20` · **贪 `0.70`**）
与 `expedition.md:300` + `squad-and-cohesion.md` F3（莽 `1.15` · 傲 `1.10` · **贪 `1.00`**）
**对「贪」的判断完全相反**——一份说他在战斗里是惩罚，另一份说他是中性。

**修订结论：两者说的不是同一个量，本文件此前没有说清，所以看起来像矛盾。**

| 量 | 谁拥有 | 语义 | 取值 |
|---|---|---|---|
| `EfficiencyOf(hero, 战斗)` | **本文件** | 「他打起来**产出多少**」（工速 / 产量侧） | 莽 1.30 · 傲 1.20 · **贪 0.70** |
| `PersonalityMult(hero)` | **`expedition.md`** | 「他**成事**的概率高不高」（成功率侧） | 莽 1.15 · 傲 1.10 · **贪 1.00** |

- 贪**打起来产出少**（0.70，`brief` 原话「战斗低」），**同时**他成事概率**不高不低**（1.00）——
  这两句话可以同时为真：贪参与战斗，战斗打得比莽和傲吃力，但一次远征能不能带回东西，
  拼的是配合与状态，不是他个人的战斗素质。`expedition.md:314` 对此有明文解释
  （「贪的强项不是成功率，是产量」）。
- 因此**本文件的矩阵一格都不改**。要改的是**归属声明**。

> 📌 **归属声明（新增，硬约束）**
> - 本文件**只**拥有 `EfficiencyOf`，语义是**速度 / 产量**。
> - 远征成功率上的性格系数由 **`expedition.md`** 拥有，本文件**不读、不写、不复述**该系数，
>   也不得用它反向调整自己的矩阵。
> - 写代码的人若在远征成功率里乘 `EfficiencyOf(战斗)`，那是**架构违规**：
>   两个系数语义不同、量纲不同，同时相乘会让贪被罚两次。
>
> 🔁 **反向依赖**：本文件已向 `expedition.md` 对齐（采用 1.15 / 1.10 / 1.00 的口径作为
> **它那一侧**的答案）。**若 `expedition.md` 反向修改该组系数，必须回来重对本节**，
> 因为两侧的措辞必须保持「各有其量」的一致，而不是数值同步。见 Q11。

**Expected output range**: 0.60 到 1.30
**Edge case**: 恒大于 0。**本系统永远不返回 0，也不返回负数。** 返回 0 等价于
「他不能干」，违反铁律 1。

#### 下游用法（本系统不拥有这段数学，但必须签接口）

```
actual_output = base_rate(task) × hours_online × EfficiencyOf(hero, category) × Π(other_modifiers)
```

`other_modifiers` 由**别的系统**提供：属性（武/敏/韧，召唤系统）、
状态（磨洋工 ×0.40，日常事件）、熟练度（**尚未设计**，见 Q6）。
本系统只提供 `EfficiencyOf` 这一项，**不碰任何其他项**。

> ⚠️ **修订（2026-10-17 裁定 ⑬）**：上表原列「结仇 ×0.50」为 `other_modifiers` 之一。
> **该行已删除。** 结仇**不是**乘在产出上的系数——它是编队层的**硬禁止**
> （`squad-and-cohesion.md` R6），根本不进入上面这条乘法链。
> 一个有仇的村民单人干活时，`EfficiencyOf` 与状态系数**完全不受影响**：
> 他是全村最好用的劳力之一，只是不和某个人同车。
>
> **验收怎么查**：`actual_output` 的计算路径里搜索 `GrudgeWith`，**必须 0 命中**。

### 2. 偏好权重（自主选择用）

```
raw(hero, task) = BASE                                    # = 1.00
                + b_cat[hero.personality][task.cat]
                + b_diff[hero.personality][task.diff]
                + b_opp[hero.personality][task.opp]
                + b_pay[hero.personality][task.pay]

w      = max(raw, W_FLOOR)                                # W_FLOOR = 0.05
p(task)= w ^ γ  /  Σ_i ( w_i ^ γ )
```

| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| `BASE` | float | 1.00（常量） | data | 中性基线；所有维度都是相对它的偏移 |
| `b_cat` | float | −0.50 … +0.50 | data | 类目偏好 |
| `b_diff` | float | −0.15 … +0.30 | data | 难度偏好 |
| `b_opp` | float | −0.20 … +0.35 | data | 有无对手偏好 |
| `b_pay` | float | −0.45 … +0.40 | data | 报酬偏好 |
| `raw` | float | 0.17 … 2.50 | 计算 | 未截断的原始分 |
| `W_FLOOR` | float | 0.05（常量） | data | **下限，不是否决权** |
| `γ` | float | 1.0 … 6.0 | data `choice_temperature` | 犹豫程度 |

**W_FLOOR 存在的作用是：让「否决权」在数学上不可能。**
用默认参数枚举全部 3 性格 × 5 类目 × 5 难度 × 2 对手 × 4 报酬 = 600 组组合，
最坏的 `raw` 是 0.17（贪·战斗·难度1·无对手·最低报酬），**没有任何一组会触发 floor**。
它是一条**不可达的下限**——如果哪天它可达了，说明有人把权重调坏了。

#### 权重表

**莽**（要强度）

| 维度 | 取值 | | | | |
|---|---|---|---|---|---|
| `b_cat` | 战斗 **+0.50** | 采集 −0.10 | 建造 −0.15 | 跑腿 −0.10 | 经商 0.00 |
| `b_diff` | d=1 +0.04 | d=2 +0.08 | d=3 +0.12 | d=4 +0.16 | d=5 **+0.20** |
| `b_opp` | 无对手 −0.05 | 有对手 +0.10 | | | |
| `b_pay` | 0档 0.00 | 1档 0.00 | 2档 +0.05 | 3档 +0.10 | |

**傲**（要胜负 —— 注意：偏好**由 opp 和 diff 主导，不由 cat 主导**）

| 维度 | 取值 | | | | |
|---|---|---|---|---|---|
| `b_cat` | 战斗 +0.35 | 采集 −0.45 | 建造 **−0.50** | 跑腿 −0.45 | 经商 −0.20 ⚠️待定 |
| `b_diff` | d=1 +0.06 | d=2 +0.12 | d=3 +0.18 | d=4 +0.24 | d=5 **+0.30** |
| `b_opp` | 无对手 **−0.20** | 有对手 **+0.35** | | | |
| `b_pay` | 0档 0.00 | 1档 0.00 | 2档 0.00 | 3档 0.00 | |

> `b_pay` 全 0 是**有意为之**：开发者没有说傲在不在意报酬，取中性而不是编一个。
> 见 Q2。`b_cat[傲][经商] = −0.20` 同样是待定值。

**贪**（要财富 —— 偏好**由 pay 主导**）

| 维度 | 取值 | | | | |
|---|---|---|---|---|---|
| `b_cat` | 战斗 −0.20 | 采集 **+0.30** | 建造 −0.10 | 跑腿 +0.20 | 经商 +0.25 ⚠️待定 |
| `b_diff` | d=1 −0.03 | d=2 −0.06 | d=3 −0.09 | d=4 −0.12 | d=5 **−0.15** |
| `b_opp` | 无对手 −0.15 | 有对手 +0.10 | | | |
| `b_pay` | 0档 **−0.45** | 1档 −0.15 | 2档 +0.20 | 3档 **+0.40** | |

#### 报酬档的取法（`pay`）

```
pay = 0  当 task.reward < Q1(任务池)
pay = 1  当 Q1 ≤ reward ≤ median
pay = 2  当 median < reward ≤ Q3
pay = 3  当 reward > Q3
```

相对当前任务池取四分位，而不是绝对金额——这样经济整体通胀时
「贪」追的仍然是**相对更来钱**的活，权重表不需要跟着经济一起改。

**Edge case**：任务池 ≤ 3 个活时分位数退化。此时四分位退化为「唯一那个活在最高档」，
所有活同时进同一档，`b_pay` 对该次抽取不产生区分度。**这是任务池太小的输入问题，
不是本系统的 bug**（见 Edge Cases 表）。

#### 难度 `diff` 的取法

1–5 整数，由**任务与副本**系统随任务一起发布。本系统只读，不定义。

### 示例计算

村庄里贴了三个活，村长时钟 14:00：

| 活 | cat | diff | opp | reward（相对任务池） | 空位 |
|---|---|---|---|---|---|
| A 北境旧堡探查 | 战斗 | 5 | 1 | 最高档 | 2 |
| B 北坡采石 | 采集 | 2 | 0 | 最低档 | 3 |
| C 南渠挖渠 | 建造 | 1 | 0 | 最低档 | 2 |

`γ = 2.0`：

**莽**
```
A = 1.00 + 0.50 + 0.20 + 0.10 + 0.10 = 1.90
B = 1.00 − 0.10 + 0.08 − 0.05 + 0.00 = 0.93
C = 1.00 − 0.15 + 0.04 − 0.05 + 0.00 = 0.84
w^γ = 3.610 / 0.865 / 0.706  → Σ 5.181
P = 0.697 / 0.167 / 0.136
```

**傲**
```
A = 1.00 + 0.35 + 0.30 + 0.35 + 0.00 = 2.00
B = 1.00 − 0.45 + 0.12 − 0.20 + 0.00 = 0.47
C = 1.00 − 0.50 + 0.06 − 0.20 + 0.00 = 0.36
w^γ = 4.000 / 0.221 / 0.130  → Σ 4.351
P = 0.919 / 0.051 / 0.030
```

**贪**
```
A = 1.00 − 0.20 − 0.15 + 0.10 + 0.40 = 1.15
B = 1.00 + 0.30 − 0.06 − 0.15 − 0.45 = 0.64
C = 1.00 − 0.10 − 0.03 − 0.15 − 0.45 = 0.27
w^γ = 1.3225 / 0.4096 / 0.0729  → Σ 1.805
P = 0.733 / 0.227 / 0.040
```

**这张表就是分离性的证据。** 三个数字各自说明不同的事：

| 读出来的事实 | 说明什么 |
|---|---|
| 傲选 A 的概率 **0.919 > 莽的 0.697** | **傲比莽更想抢这场硬仗，尽管他打起来更慢**（E 1.20 vs 1.30）。偏好 ≠ 能力 |
| 贪选 A 的概率 **0.733 > 0.697** | 贪为了钱去接了一场战斗。**而他打这场仗的效率只有 0.70** |
| 三人抽到建造 C 的概率都 < 0.14 | 建造没人在抢——但**兜底指派**保证它照样会被人干完（傲 0.60） |

如果效率系数和偏好权重是同一个东西，上面三行**一行都不可能成立**。

## Edge Cases

| 场景 | 期望行为 | 理由 |
|---|---|---|
| 候选池为空 | 记为「闲着」。**不产生任何杂谈条目。** | 铁律 3：什么都不影响的事件就是装饰 |
| 全村只有傲在线，只贴了建造活，无人被指派 | **傲接了**，速度 ×0.60，工期 1.67 倍。杂谈走「这次没挑」类文案。**绝不允许出现「没人揭告示」** | 开发者原话：缺人时任何人都能顶 |
| 全村只有一个挂机村民在线 | 他不自主行动（`γ` 不参与），但**被指派就会干活**，按 E 计算 | 挂机是自主频率低，不是不可用 |
| 某活在抽取瞬间被抢满 | 重抽，最多 3 次；3 次后落选，重新取候选池 | 避免死循环 |
| 村民病倒中，而他是唯一能顶的人 | **他顶不了。** 病倒是不可工作状态，工期顺延 | 状态可以否决，性格不行（铁律 1） |
| 同一村民同时被指派与自主选中同一个活 | 先到先得；第二次 tick 时该活不在候选池 | |
| `γ` 被调到 ≥ 6 | 全村行为几乎完全一致，村庄显得很假 | **调参失误。** 实现必须 `clamp(γ, 1.0, 6.0)` |
| `γ` 被调到 ≤ 0 | 分布退化 / 除零 | **clamp 到 1.0** |
| 报酬档全相同（村长乱发钱） | `b_pay` 对该次抽取不产生区分度 | 经济系统的输入污染，不是本系统 bug |
| 任务池 ≤ 3 个活 | 四分位退化，`pay` 档位区分度下降 | 同上。任务池长大后自愈 |
| 全部村民同一种性格 | 村庄行为高度同质 | 抽取均匀分布下，3 人全同的概率 = 3×(1/3)³ = **1/9 ≈ 11%**。可接受，**性格不设保底**，保底留给属性（三项之和 ≥ 60） |
| `raw` 计算结果 < 0 | 触发 `W_FLOOR = 0.05` | 默认参数下不可达（最坏 0.17）；可达即为调参事故 |
| 村民离线时恰好有自主 tick | 跳过，**不消耗**每日次数上限 | 作息系统是唯一权威 |
| `EfficiencyOf` 返回值 | 恒在 [0.60, 1.30]，**恒 > 0** | 返回 0 等价于「不能干」 |

## Dependencies

| System | Direction | Nature of Dependency |
|--------|-----------|---------------------|
| **召唤系统** (#2) | 召唤系统 → 本系统 | `Data dependency`：提供 `personality`（莽/傲/贪）与 `engagement`（肝/随手/挂机）的抽取值。本系统**定义这两个枚举的取值域**，不定义抽取逻辑 |
| **时间与作息** (#1) | 作息 → 本系统 | `Data dependency`：提供「此刻是否在线」。**边界规则**：自主 tick 由投入度触发，再去查在线；**反过来不成立**——作息系统不轮询性格 |
| **配队与配合** (#4) | 本系统 → 配队 | `Data dependency`：配队**只读 `EfficiencyOf`**，不读 `ScoreOf`。这是打断「性格 ↔ 配队」循环依赖的方式（见 systems-index § Circular Dependencies） |
| **配队与配合** (#4) | 本系统 → 配队 | **规则边界（裁定 ⑬ 新增）**：配队层**不得**读 `GrudgeWith` 去改 `EfficiencyOf`；它只可用它做**编队合法性**判定。本文件保证 `EfficiencyOf` 对任何人恒 > 0 |
| **关系系统**（`relations.md`，待建） | 关系 → 本系统 | `State provider`：关系是村民之间的状态，不是性格。**本系统不生产、不修改任何关系**；「吵架 / 搭手」这两个日常事件在本文件内触发，但写入的字段语义由 `relations.md` 定义。**完整的正 / 负 / 中性关系类型见 `relations.md`**——本文件只保留「仇」与「搭手」两条，见 § 8 种日常事件 |
| **任务与副本** (#6) | 任务与副本 → 本系统 | `Data dependency`：提供候选池、`cat`、`diff`、`opp`、`reward`、`slots` |
| **村庄建造** (#5) | 村庄建造 → 本系统 | `Data dependency`：工地的槽位数就是候选池的一部分 |
| **杂谈** (#11) | 本系统 → 杂谈 | `Data dependency`：本系统是自主行为的事件源，杂谈是唯一读数器 |
| **经济与摆摊** (#8, M4) | 经济 → 本系统 | `Data dependency`：提供 `reward`，本系统据此算 `pay` 四分位。**M4 之前 `b_pay` 近乎无效**——这是有意的，见 § Acceptance Criteria C |
| **交易、背叛与 PvP** (#9, Alpha) | 本系统 → PvP | `State trigger`：`opp=1` 的任务在 M4 出现。**傲的 `b_opp=+0.35` 与他的 `E=0.60` 在粗活上，是这条因果链的引擎** |
| **死亡与复活** (#10) | 死亡 → 本系统 | `State trigger`：停机一天期间不触发任何自主 tick |

**本系统对外只交付三个函数。** 别的系统只能通过这三个函数接触性格：

```
EfficiencyOf(hero, category) -> float          // 0.60 - 1.30
ScoreOf(hero, task)          -> float          // >= 0.05
AutonomyInterval(hero)       -> hours          // 2 / 6 / 24
```

任何系统想读性格的其他部分，都是架构违规。

## Tuning Knobs

全部住在 `assets/data/`，**一律不得硬编码**。

| 参数 | 当前值 | 安全范围 | 类别 | 调高的效果 | 调低的效果 | 依据 |
|---|---|---|---|---|---|---|
| `efficiency.莽.战斗` | 1.30 | 1.10 – 1.40 | curve | 副本党更极端，但莽会垄断战斗位 | 副本需要混编 | 推导 |
| `efficiency.傲.粗活` | **0.60** | 0.50 – 0.80 | curve | 「慢」更明显，工期拖到 1.67–2.0 倍 | 兜底时村庄不至于卡死 | **开发者原话** |
| `efficiency.贪.战斗` | 0.70 | 0.60 – 0.85 | curve | 贪去打架的痛感更强 | PvP 阵容更容易凑 | 推导 |
| `b_opp.傲` | +0.35 | +0.25 – +0.45 | feel | 傲几乎只抢有对手的活 | 傲变得愿意干普通活 | 开发者「挑有对手的」 |
| `b_pay.贪` | +0.40 | +0.30 – +0.55 | curve | 贪完全由钱驱动，`E` 的作用被淹没 → **退化风险** | 贪变得像莽 | 开发者「挑来钱多的」 |
| `b_cat.傲.建造` | −0.50 | −0.40 – −0.60 | feel | 傲更明显地躲建造 | 兜底指派触发更频繁 | 推导 |
| `choice_temperature` (γ) | **2.0** | 1.0 – 6.0 | feel | 村民更「果断」，行为更可预测，**村庄更像有性格的人** | 更随机、更混乱 | **推导，见 Q8** |
| `W_FLOOR` | 0.05 | 0.01 – 0.10 | curve | 不该被触及 | 不该被触及 | 防御性 |
| `autonomy.肝.interval` | 2 h | 1 – 4 h | gate | 杂谈刷新更密 | 肝帝变懒 | 推导 |
| `autonomy.挂机.cap` | 1 /day | 0 – 2 | gate | 挂机也偶尔自己找活 | 挂机成为纯工位 | 推导 |
| `autonomy.redraw_max` | 3 | 1 – 5 | feel | 抢活更从容 | 落选更常见 | 推导 |

> ⚠️ **`b_pay.贪` 与 `choice_temperature` 是本系统最危险的两个旋钮。**
> 前者调到 +0.55 时，「贪」会退化成「纯看钱」，效率维度被完全淹没——
> 那就是权重吞掉了效率。调任何一个都要重跑 § Acceptance Criteria C。

## 8 种日常事件

| 事件 | 状态后果 | 归属 |
|---|---|---|
| **病倒** | 停工（不可工作状态） | 本系统 |
| **吵架** | 两人缺席一天 **+ 结仇** | 本系统 |
| **结仇**（吵架的结果） | **`GrudgeWith` 写入 → 编队层硬禁止**（`squad-and-cohesion.md` R6）。**修订：原为「同队效率 ×0.50」，2026-10-17 裁定 ⑬ 改为硬禁止** | 本系统写入，编队消费 |
| **磨洋工** | 干活率 ×0.40 | 本系统 |
| **想走** | 不肯出工（不可工作状态） | 本系统 |
| **闲逛** | **无后果** | 后续模块 |
| **搭手** | **`GrudgeWith` 清除 → 解仇，该组合重新合法**（2026-10-17 裁定 ⑬ 新增后果）。**修订：原写「无后果」** | 本系统写入，编队消费 |
| **陌生人** | **无后果** | 后续模块 |
| **干起来了** | **⚠️ 未确定** —— 见 Q3 | 待定 |

**本模块内只允许前五种出现在杂谈里**——加上裁定 ⑬ 之后的**搭手**，
搭手现在有真实后果了，因此**现在允许出现**。

> **「搭手」为什么从「无后果」升格成有后果（裁定 ⑬）**
> 有仇是**硬禁止**，硬禁止如果没有出口就是死路——两个有仇的人从此永远不能同队，
> 而村庄又不能把他们赶走。所以必须有唯一一条解法，且必须**写在杂谈里**，
> 玩家才能知道它存在。
> **和解路径是唯一的**：`搭手` 事件 → 清除双方 `GrudgeWith` → 组合立即恢复合法。
> 这条与 `chronicle.md` R1 一致（「搭手 → 清 `GrudgeWith`，唯一的解仇途径」）。

`game-brief.md` 把闲逛 / 搭手 / 陌生人列为「只有气氛没有后果的」，
同时又立了铁律「不改变状态就是装饰，删掉」。本文档的解法是：

> **在还没有模块接管它们之前，这三个事件不出现在杂谈里。**
> 被后续模块接管、并且真的写出状态之后，它们才回来。

这样两条规则同时成立，杂谈里也不会躺着装饰品。见 Q9。
**2026-10-17 更新**：裁定 ⑬ 已经让**搭手**具备真实后果，
所以它不再是「无后果事件」，上面的豁免对它不再适用。见 Q9。

**「干起来了」是八个事件里唯一我无法从开发者原话推导出后果的一个。**
它很可能是「想走」的反事件（被劝住、留下来），但触发条件开发者没说过。
**在触发条件确定之前，它不得上线。** 见 Q3。

| 3 | `engagement`（投入度）修改 `EFFICIENCY` 或任何 `b_*` 的取值 | 轴二会吃掉轴一，挂机变成减速 buff | 代码评审 |
| 4 | 事件只写杂谈、不写状态 | 装饰 | 逐事件 diff 存档 |
| 5 | 玩家可见文案出现「成功/失败/获得/消耗/属性/奖励」 | 见下 | 静态扫描 |

**文案约束**：`杂谈` 与所有面向玩家的文本中，
**成功 / 失败 / 获得 / 消耗 / 属性 / 奖励** 六词零命中。
原型已经做到了（「撒了一地，人没事」而不是「任务失败」），
`game-brief.md` 的判据是：**「如果你在读『铁卫 带回 44 铁』而不是在读一件事，那就是失败。」**

## Acceptance Criteria

### A. 分离测试 · 冻结一轴

> 目标是证明「效率系数」和「偏好权重」**不是同一个东西的两套皮**。
> 统计口径必须是 **按 `(英雄 × 类目)` 分组后的相对速率**——
> 先分组再比较，否则「选了什么活」的分布变化会污染速率读数。
> **这条统计口径本身就是分离性的实现要求。**

- [ ] **A.1** 将全部 `ScoreOf` 的权重置为中性（`b_* = 0`，所有性格一致），
      跑 30 天：自主选活的类目分布应**塌缩到与性格无关**；
      **同期「指派通道」上按 (英雄×类目) 分组的相对速率，分布与未冻结时一致（差异 < 5%）**。
- [ ] **A.2** 将全部 `EFFICIENCY` 置为 1.00，跑 30 天：
      **自主选活的分布与未冻结时一致（差异 < 5%）**；
      同期产出速率全部回到基础值。
- [ ] **A.3（退化判定）** 若 A.1 改变了分组后的速率分布，
      说明执行路径读了 `ScoreOf` —— **本系统已退化为一套东西，判定不通过。**
- [ ] **A.4** 对 A.1 / A.2 的「差异 < 5%」做统计检验（30 天样本下取 p > 0.05），
      而不是目测。

### B. 最后一个人测试（二极度假伪）——**本系统最重要的一条**

> 直接对应开发者否决掉的那段原型代码。

- [ ] **B.1** 场上只留**一个傲**，村庄只贴一个**建造**活，无人被指派。
      结果**必须**是：傲接了活，工期 = 基础工期 ÷ 0.60，村庄进度正常推进。
- [ ] **B.2** 同一场景下，`杂谈` 中**不得**出现「没人揭告示」这一类文案，
      必须出现「没挑 / 没说什么就去了」那一类。
- [ ] **B.3** 同样的构造对**全部 3 性格 × 5 类目 = 15 组**执行，
      **每组都必须存在一条通向「该英雄完成该活」的完整路径。**
      这是静态可查的：`EfficiencyOf` 的定义域是全集，没有 `NaN`、没有排除项。

### C. 偏好与能力必须不同向（换皮判定）

> **一句话指标**：跑 30 天，把每个村民的「自主选中率」和「单位时间产出」
> 各排一个名次，**两者的 Spearman 秩相关不得等于 +1.0**。

- [ ] **C.1** 上述秩相关 `ρ < 1.0`（例如 30 天样本下 `ρ < 0.9`）。
- [ ] **C.2** 必须能观测到**至少一例**：某村民自主选中了一个 `EfficiencyOf < 1.0` 的类目
      （他挑了个自己干不好的活——贪为钱去打仗，傲为赢去干粗活）。
- [ ] **C.3** 必须能观测到**至少一例**：傲挑中副本的概率**高于**莽
      （§ Formulas 示例计算里是 0.919 vs 0.697）。
      若此例不成立，说明 `b_opp` / `b_diff` 权重不够，需重调表而不是改效率矩阵。
- [ ] **C.4** ⚠️ **C.2 在 MVP 不一定观测得到**——`b_pay` 依赖经济系统（M4）。
      **该判据的正式验收推迟到 M4**，MVP 阶段只跑 C.1 和 C.3。

### D. 事件后果

- [ ] **D.1** 八个事件逐一验证：每个要么能给出**改状态前后的存档 diff**，
      要么按 § 8 种日常事件 的规则不出现在杂谈里。
- [ ] **D.2** `杂谈` 中**不存在**任何只出现在文案、从不改变任何状态的条目。
- [ ] **D.3** ⚠️ **修订（2026-10-17 裁定 ⑬）** 验证 `EfficiencyOf` 的返回值
      **从不参与** `磨洋工 ×0.40` 的计算路径——状态系数与性格系数是相乘的两项，
      不是同一个数。
      **旧版这条还要求验证「结仇 ×0.50」的路径，现已删除**：
      结仇不再是乘在产出上的系数（`×0.50` 这个值在本系统中**必须 0 命中**），
      它是编队层的硬禁止。
- [ ] **D.4 有仇时该组合法（裁定 ⑬）。** 构造一名村民 A 与 B，`GrudgeWith` 互指。
      断言：把 A、B 放进同一支队伍 → 该队伍**标记为非法且不能派出**，
      且面板**明确显示原因**（说「他们有过节」一类的说法，**不是**一个乘数）。
      **断言 `CohesionOf` 对这支队不返回任何数值**（不是 0.50、不是任何折扣）。
- [ ] **D.5 搭手后恢复合法（裁定 ⑬）。** 承接 D.4，触发一次 `搭手` 事件。
      断言：双方 `GrudgeWith` 被清空 → **同一支队立即变为合法**且可派出，
      系数恢复到与「从未结仇」完全相同（两者必须逐位相等，不允许残留惩罚）。
- [ ] **D.6 有仇不影响他本人（铁律 1 的正面断言）。** 承接 D.4：
      断言 A 的 `EfficiencyOf(任一类目)` **与从未结仇时逐位相同**；
      断言 A 仍出现在工地的候选池与兜底指派池中；
      断言 A 仍可与**第三名无仇村民 C** 组成合法队伍。
      **这三项合起来就是「否决的是这一支队伍，不是这个人」。**
- [ ] **D.7 关系层不被误读（裁定：配合系数读关系，不读性格表）。** 断言本系统
      **不生产**除「吵架 → 仇」「搭手 → 解仇」以外的任何关系状态；
      其余关系类型（搭子 / 师徒 / 同乡 / 欠人情 / 嫉妒 / 竞争 / 欠债 / 普通同村）
      **0 命中**于本系统的写入路径。完整关系设计见 `relations.md`。

### E. 文案

- [ ] **E.1** 对全部 `杂谈` 文案做静态扫描：
      「成功 / 失败 / 获得 / 消耗 / 属性 / 奖励」**六词零命中**。
- [ ] **E.2** 读前 10 条杂谈时，读的人**在读一件事**，不是在读一个数字。

### F. 边界

- [ ] **F.1** 没有任何一条代码路径会因性格而让活「无人可做」。
- [ ] **F.2** 本系统对外只暴露 `EfficiencyOf` / `ScoreOf` / `AutonomyInterval` 三个函数；
      任何系统读取性格的其他部分即为架构违规。
- [ ] **F.3** 所有数值来自 `assets/data/`，代码中零硬编码。
- [ ] **F.4** 性能：50 个村民 × 200 个候选活的 `ScoreOf` 计算
      在单帧预算内完成（目标 < 2 ms）。

### G. 体验（playtest，无法用测量仪器验证）

- [ ] **G.1** 玩测者在被问到「你为什么让老李头去搬石头」时，
      能说出「因为他慢但还是会干」而不是「因为他干不了」。
- [ ] **G.2** 两个村庄跑三天，各自长出**不同的劳动分布**，测试者能一眼分辨。
      （`systems-index` 给 M1 定的验收目标。）
- [ ] **G.3** 没有任何测试者说「这些人好像被设定了不会做某件事」。

## Game Feel

**Feel Reference**：《修仙模拟器》里你不下指令，弟子今天自己下山了——
那种「他们有自己的主意」的节奏感，**不是**战斗操作的手感。
本系统是**观察者与布局者**的节奏：一个 tick 落下去，一个人做了一个决定，
杂谈里多了一句话。爽点在**事后回看时发现规律**，不在当下操作。

- **Weight**：重。自主行动必须是**不可撤销**的——他今天选了采石，你就不能把他拽去副本。
  轻飘飘的自主行为会让玩家觉得没实感。
- **Player control**：低（在选择层）、高（在编排层）。
  玩家控制不了「谁接了什么活」，但完全控制「明天出什么活」。
- **Snap quality**：不适用。本系统没有输入。
- **Failure texture**：不适用。本系统**没有硬失败**。
  唯一「失败」的表现是一个傲磨洋工拖慢了工期——那是**可读的**，
  玩家能一眼看出「他不想干」，这是设计目标，不是需要掩盖的问题。
- **节奏目标**：`γ` 调高时杂谈应该读起来像**每个人各有主张**；
  `γ` 调低时读起来像**一群人在掷骰子**。当前默认 2.0 偏前者。
