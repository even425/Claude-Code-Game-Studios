# 异世界村庄经营与英雄冒险游戏 — 核心玩法循环设计 V1.0

> **文档状态：** 设计草案，待确认  
> **上游基线：** 《异世界村庄经营与英雄冒险游戏 — 设计基线 V1.2》  
> **核心体验：** 观察英雄自主生活，通过村庄经营创造条件，在关键时刻进行干预，并通过副本攻略推动村庄与英雄的后续发展。  
> **第一版目标：** 建立一个包含村庄经营、英雄自主模拟、英雄互动、摊位经济和副本攻略的最小完整闭环。

本文中：
- **【已确认】**：来自现有设计基线的明确要求。
- **【建议】**：本设计提出的方案，等待开发者确认。
- **【待定】**：目前缺少决策，不得由实现者自行补充为正式规则。

## 1. 设计目标

### 1.1 核心体验

【已确认】玩家扮演异世界新手村村长，从三间土屋开始建设村庄，吸引来自异世界的独特英雄，组织队伍攻略野外和副本，最终将村庄发展为世界上最豪华、最繁荣的城市。

【本次已选择的设计方向】玩家主要采用观察模拟型玩法：英雄自主生活和互动是重点，玩家观察故事、适时干预。

【建议】将核心体验组织为三个相互依赖的系统：

1. **村庄经营：** 提供空间、设施、经济活动和发展条件。
2. **英雄模拟：** 产生自主行动、人际互动、交易和日常故事。
3. **冒险与副本：** 提供玩家可主动选择的挑战，以及能反过来影响村庄与英雄的结果。

### 1.2 玩家应该反复体验什么

【建议】玩家的主要体验不是不断点击建筑升级按钮，而是：

- 观察英雄在村庄中自主生活，发现值得关注的行为。
- 看到英雄的个性、偏好、当前状态和既有关系影响他们的行动。
- 通过建造、调整经营规则、组队和派遣任务影响接下来可能发生的事情。
- 观察英雄完成冒险、交易或冲突后，村庄状态和人物关系如何变化。
- 根据这些变化决定下一步要建设什么、派谁冒险，以及是否介入某件事情。

**设计原则：玩家主要决定方向和条件，而不是逐条控制英雄的日常行为。**

英雄日常自主行动是已确认方向；玩家可以干预到什么程度、是否允许对某些日常行为直接下令，仍需要进一步定义。

## 2. 核心玩法循环

### 2.1 总体循环

【建议】采用以下主循环：

```text
观察村庄当前状态
        ↓
发现需求、机会或问题
        ↓
玩家进行经营决策或选择是否干预
        ↓
村庄条件发生变化
        ↓
英雄根据自身状态、偏好与环境自主行动
        ↓
产生交易、社交、关系变化或冒险机会
        ↓
玩家选择组队并派遣英雄攻略副本
        ↓
自动战斗与副本结算
        ↓
英雄、物品、资源、关系及村庄状态发生变化
        ↓
村庄出现新的需求与机会
        └──────────────→ 回到观察与决策
```

此图是建议的玩法组织方式，不代表其中所有步骤都必须依次发生，也不意味着每次循环都必须进入副本。

### 2.2 三个子循环

| 子循环 | 核心过程 | 主要观察对象 |
|---|---|---|
| 村庄经营循环 | 发现需求 → 经营决策 → 村庄状态变化 | 建筑、资源、摊位、村庄发展 |
| 英雄生活循环 | 当前状态 → 自主行动 → 行动结果 → 新状态 | 英雄日常、交易、互动、关系与杂谈 |
| 冒险攻略循环 | 选择队伍 → 派遣任务 → 自动战斗 → 副本结算 | 队伍表现、战斗过程、奖励与后续影响 |

【建议】三个子循环应通过共享状态连接，而不是各自独立运行。

例如，英雄在副本中获得的物品，若规则允许，可以成为其摆摊或消费的货源；英雄之间的交易可能改变资金和物品持有情况；人物关系则可能影响后续互动。

以上具体因果关系需要由各子系统规则确定，不能仅凭示例直接实现。

## 3. 一次典型游戏过程

以下是一段用于检验核心循环是否成立的**设计示例**，不是已经确定的剧情或数值规则。

### 阶段 A：观察村庄

村庄从三间土屋起步。

玩家能够观察到：
- 村庄当前有哪些建筑与可用空间。
- 已加入英雄的身份、当前状态和行动情况。
- 当前有哪些经营活动、交易记录和近期杂谈。
- 是否存在值得玩家处理的需求或冒险机会。

【待定】初始资源数量、初始英雄人数、初始建筑的具体功能，以及新手引导方式。

### 阶段 B：创造生活条件

玩家根据当前情况作出经营决策。

【已确认】村庄建筑包括土屋、烟囱、水井、围栏、铁匠铺、武器店、服装店、试炼塔和防护罩等已列项目。

【建议】第一版不需要一次实现全部建筑。应先挑选能够支撑最小闭环的建筑或设施，并为每个纳入原型的建筑定义明确用途。

玩家可以观察建造或经营调整之后，英雄的行动环境是否发生了变化。

【待定】建筑成本、前置条件、资源种类、建筑效果与解锁规则。

### 阶段 C：英雄自主生活

英雄进入村庄生活后，根据其人物特质、玩法偏好、当前状态和已有关系作出行动选择。

可能出现的行为包括：
- 购物或出售物品。
- 在防护罩范围内摆摊。
- 与其他英雄互动。
- 选择休闲、采集或其他可行活动。
- 表达冒险意愿，或响应已有的任务安排。

【已确认】英雄日常行为由英雄自己决定，玩家只能由自己决定队伍组成；人物关系应通过经历形成，而不是直接由出厂属性决定。

【建议】每次有意义的自主行动，都应产生可观察的结果，例如物品变化、资金变化、关系变化或一条杂谈记录。

【待定】行动优先级、行动频率、行动耗时、资金与疲劳规则，以及英雄在什么情况下会主动提出冒险需求。

### 阶段 D：玩家观察并决定是否干预

玩家通过村庄画面、英雄状态和杂谈了解正在发生的事情。

例如：
- 某位英雄开始摆摊。
- 某次交易成功或发生纠纷。
- 两名英雄的关系出现变化。
- 英雄准备参与某项冒险。

【建议】界面应提供足够信息，让玩家能够理解事件发生了什么，以及自己有哪些可选的干预方式。

【待定】玩家是否可以直接干预普通交易、指定英雄日常活动、解决纠纷或改变英雄的行为计划。

不应为了增加操作量而强制玩家处理每一次日常事件。

### 阶段 E：组队并攻略副本

【已确认】副本攻略是核心玩法，战斗采用全自动方式；玩家能够观察野外实时战斗。

【建议】第一版提供一个小型副本，形成以下完整流程：

1. 玩家查看副本入口、已知挑战信息和可派遣英雄。
2. 玩家选择队伍并发起任务。
3. 系统检查队伍是否满足已定义的参与条件。
4. 英雄进入副本，自动执行战斗规则。
5. 玩家能够观察战斗过程或查看战斗结果。
6. 副本按明确规则结算成功、失败及相关状态变化。

【待定】队伍人数、职业定位、战斗数值、技能释放、目标选择、失败条件、副本结构、奖励内容和任务耗时。

第一版应优先验证队伍选择与战斗规则之间确实存在可观察的因果关系，而不是先追求大量怪物、技能或副本地图。

### 阶段 F：结果回流村庄

副本结束后，玩家回到村庄模拟与经营循环。

【建议】副本结果通过已定义的规则影响至少一项后续玩法，例如：
- 英雄持有的物品发生变化。
- 英雄状态发生变化。
- 获得的物品进入英雄库存，后续可以参与交易。
- 某条关系或杂谈因实际发生的行为而更新。
- 村庄出现新的经营需求或后续冒险机会。

以上是候选的结果类型，不代表所有结果都必须同时发生。

**关键要求：副本不应只是一个与村庄无关的战斗界面。** 至少要有一条真实、可验证的结果路径回到英雄生活或村庄经营。

## 4. 玩家操作与自动模拟的边界

### 4.1 玩家负责什么

| 操作 | 状态 | 设计说明 |
|---|---|---|
| 建造与发展村庄 | 【已确认方向】 | 具体建造规则待定 |
| 获取来自异世界的英雄 | 【已确认方向】 | 存在抽卡性质的获取机制；入口、概率与消耗细节待定 |
| 决定队伍组成 | 【已确认】 | 不等于直接操纵战斗中的每一步 |
| 发起副本攻略 | 【建议】 | 作为连接经营与战斗的主要玩家操作 |
| 观察英雄日常和人际互动 | 【已选择方向】 | 具体观察界面待定 |
| 调整摊位费 | 【已确认方向】 | 具体收费形式和计费规则待定 |
| 直接改变英雄日常行为 | 【待定】 | 需要定义玩家干预的权限边界 |

### 4.2 系统负责什么

【建议】在没有玩家直接干预时，系统仍应能够根据已定义规则推进英雄日常生活。

| 自动行为 | 规则边界 |
|---|---|
| 英雄选择日常活动 | 由人物特质、偏好、当前状态和环境共同影响；权重待定 |
| 英雄之间发生互动 | 需要明确触发条件、参与者和结果 |
| 摊位经营与交易 | 必须遵守最终确定的商品、定价、付款与收费规则 |
| 人际关系变化 | 必须由实际经历或行为链触发 |
| 副本中的战斗 | 自动执行已定义的战斗规则 |
| 大事件推进 | 按游戏内已定义的周期或触发规则执行；具体实例与周期待定 |

英雄的自主性不意味着行为完全随机。建议让行为选择可以被解释、观察和测试。

## 5. 系统依赖关系

### 5.1 依赖图

【建议】以如下关系组织系统：

```text
                    游戏时间与模拟调度
                     /      |       \
                    ↓       ↓        ↓
                村庄系统  英雄系统   世界事件系统
                   ↕        ↕
                经济系统 ←→ 关系系统
                   ↑        ↑
                   └── 副本与战斗系统
                           ↑
                        玩家组队
```

该图表达的是建议的职责与依赖方向，不是最终技术架构图。具体调用关系、事件接口和数据所有权应在系统设计阶段另行确定。

### 5.2 各系统的职责边界

| 系统 | 应负责 | 不应独自决定 |
|---|---|---|
| 村庄系统 | 建筑、空间、村庄状态 | 英雄具体如何选择日常行为 |
| 英雄模拟系统 | 英雄行动决策与行动过程 | 自行绕过经济系统修改货币 |
| 经济系统 | 资金、物品、摊位费与交易结算 | 人物关系如何变化 |
| 关系系统 | 记录并更新英雄之间的关系 | 凭空创造没有行为依据的冲突 |
| 战斗与副本系统 | 战斗过程、胜负与奖励结算 | 绕过库存和资源规则直接发放物品 |
| 杂谈系统 | 将符合规则的已发生事件呈现给玩家 | 把没有发生过的行为伪造成事实 |
| 世界事件系统 | 事件触发、生命周期和跨系统协调 | 重复应用同一次事件的结算结果 |

【建议】关键状态变化应有明确的来源、执行规则和结果记录，避免多个系统各自修改同一份数据。

## 6. 第一版最小完整闭环（MVP）

### 6.1 MVP 的目标

【建议】第一版不以内容数量为目标，而以验证三个系统能否共同运行作为目标：

1. 玩家能够对村庄进行至少一种有意义的经营操作。
2. 英雄能够在玩家不逐条指挥的情况下自主生活，并产生可观察的互动或经济行为。
3. 玩家能够组队攻略一个小型副本，且副本结果能影响后续的村庄或英雄模拟。

### 6.2 建议纳入的最小内容

| 内容 | MVP 建议范围 | 状态 |
|---|---|---|
| 起始村庄 | 三间土屋及最小可交互场景 | 【已确认基础，具体实现待定】 |
| 英雄 | 少量具有不同身份与行为倾向的英雄 | 【建议】 |
| 英雄获取 | 能获得英雄的最小流程 | 【已确认存在抽卡性质的获取机制；具体入口待定】 |
| 自主生活 | 至少一种日常活动与一种英雄互动 | 【建议】 |
| 摆摊经济 | 至少一种商品交易与摊位费结算 | 【已确认玩法方向；具体规则待定】 |
| 杂谈 | 能记录并显示已发生的英雄行为 | 【已确认功能方向】 |
| 人际关系 | 至少一条由实际行为触发的关系变化 | 【已确认关系通过经历形成；具体规则待定】 |
| 副本 | 一个可进入、可战斗、可结算的小型副本 | 【已确认副本攻略是核心玩法；具体内容待定】 |
| 战斗 | 自动战斗并提供可观察结果 | 【已确认方向】 |
| 结果回流 | 至少一条副本结果影响后续模拟的路径 | 【建议】 |
| 存档 | 保存并恢复核心运行状态 | 【技术基线已确认；具体数据范围待定】 |

MVP 不需要一次完成所有已确认建筑、完整城市成长曲线、多个副本、复杂事件或大量英雄内容。

但这只是实现范围的缩小，不是从总体设计中删除这些玩法。

### 6.3 MVP 的完整演示流程

【建议】准备一段能够从头到尾演示的固定流程：

1. 玩家进入三间土屋构成的初始村庄。
2. 玩家通过最终确定的英雄获取入口获得英雄。
3. 英雄进入村庄，并开始自主生活。
4. 至少一名英雄发生一次可观察的日常行为。
5. 村庄中发生一次交易，按已定义规则完成结算并收取摊位费。
6. 系统记录一条真实发生的英雄行为或互动。
7. 玩家选择英雄组成队伍，进入小型副本。
8. 副本自动战斗并完成结算。
9. 至少一项已定义的副本结果进入英雄或村庄状态。
10. 玩家回到村庄，能够观察到后续变化。

这条流程用于验证玩法是否连通，不意味着每个存档、每次游戏都必须以同一顺序发生全部事件。

## 7. 状态变化与验收标准

### 7.1 核心状态

【建议】原型阶段至少明确并记录以下状态：

| 状态类别 | 最低要求 |
|---|---|
| 村庄 | 建筑及其状态、可用空间、已定义的资源 |
| 英雄 | 身份、当前状态、所在位置或活动、持有物品 |
| 经济 | 货币、商品库存、交易记录、摊位费结算记录 |
| 关系 | 参与者、关系状态、导致变化的行为依据 |
| 副本 | 副本实例、参与队伍、进行状态、结算结果 |
| 杂谈 | 事件来源、参与者、发生内容及记录时间 |
| 模拟时间 | 当前游戏时间与已经处理的模拟步骤 |

这些是建议的最小数据范围，不代表所有字段都已成为正式数据模型。

### 7.2 验收规则

每条测试应采用固定初始状态、明确执行步骤、具体预期结果和可执行断言。

| 编号 | 验收目标 | 验收方法 |
|---|---|---|
| C1 | 英雄可自主行动 | 固定英雄与初始状态，在不下达日常指令的情况下推进模拟，检查是否出现符合其行动规则的行为 |
| C2 | 行为有可观察结果 | 执行一项已定义的行为，检查对应状态变化或事件记录 |
| C3 | 交易结算正确 | 固定商品、价格、资金和收费规则，检查买卖双方库存与货币变化 |
| C4 | 摊位费不重复收取 | 结算后保存并重新加载，检查同一计费周期的费用没有重复入账 |
| C5 | 关系变化有行为依据 | 执行一条明确会影响关系的行为，检查参与者、变化和原因记录一致 |
| C6 | 队伍选择影响副本过程 | 在固定初始状态下比较符合规则的不同队伍，验证队伍差异确实通过战斗规则产生相应结果；不预设所有指标必须单调变化 |
| C7 | 副本结算不重复 | 完成副本后存档、读档，检查奖励及其他结算结果没有重复应用 |
| C8 | 副本与村庄存在真实联系 | 选择一条明确的结果路径，检查副本结算后对应的英雄或村庄状态按规则发生变化 |
| C9 | 杂谈不伪造事件 | 检查每条杂谈都能关联到已发生的行为或事件 |
| C10 | 存档恢复可靠 | 保存核心状态后重新加载，检查英雄、库存、关系、副本和已结算记录的一致性 |

### 7.3 不应采用的验收方式

不要直接规定：
- 摆摊费降低后，每次模拟的摊位数量都必须增加。
- 英雄加入后，所有经济指标都必须上升。
- 关系变化后，英雄必须立刻发生某种后续行为。
- 某支队伍必须永远比另一支队伍强。

这些要求都可能忽略随机因素、状态差异或规则条件。

应该先确定实际规则，再验证结果是否符合规则。

## 8. 当前待确认事项

以下问题会影响核心循环，建议按依赖顺序逐步决定。

### 第一优先级：决定循环如何运转

1. **【待定】模拟时间：** 游戏时间如何推进？玩家是否可以暂停、加速或单步观察？
2. **【待定】英雄行动：** 英雄多久作出一次行动决策？行动是即时完成还是需要耗时？
3. **【待定】玩家干预：** 玩家除了决定队伍和经营外，可以在多大程度上干预英雄日常生活？
4. **【待定】副本时间：** 副本攻略期间，村庄中的其他英雄是否继续生活与交易？
5. **【待定】状态影响：** 疲劳、受伤、资金不足和任务承诺等状态具体如何影响行动？

### 第二优先级：决定循环如何形成经济与社会反馈

6. **【待定】经济基础：** 使用哪些资源与货币？它们从哪里来、用于什么？
7. **【待定】摊位规则：** 摊位费采用一次性租金还是按成交额抽成？谁决定商品价格？
8. **【待定】交易结果：** 商品交易如何影响英雄资金、库存和关系？
9. **【待定】关系规则：** 哪些行为可以触发关系变化？关系状态会怎样影响后续互动？
10. **【待定】杂谈呈现：** 记录全部事件，还是筛选值得玩家关注的行为？

### 第三优先级：决定长期成长

11. **【待定】英雄获取：** 召唤入口、资源消耗、稀有度、概率与重复获取规则。
12. **【待定】副本结构：** 单场战斗、连续房间或其他形式。
13. **【待定】结果反馈：** 副本奖励如何进入英雄生活和村庄经济。
14. **【待定】村庄成长：** 哪些经营结果能够解锁新内容，以及城市繁荣如何衡量。
15. **【待定】世界事件：** 大事件如何与日常模拟、经营和副本发生联系。

## 9. 本文的结论

【建议】本项目的核心循环应围绕以下关系建立：

**村庄创造生活条件 → 英雄自主生活并产生故事 → 玩家观察并适时干预 → 队伍攻略副本 → 结果回流英雄与村庄 → 新的生活与经营状态继续产生。**

第一版不需要先完成庞大的世界、几十种建筑或大量副本。最重要的是证明：英雄确实能自主行动，玩家确实能观察到有意义的变化，副本确实能对后续生活和经营产生真实影响。

下一步应优先完成《模拟时间与英雄自主行为规则设计》，因为它决定了观察模拟型玩法的基本节奏，也会影响交易、关系、杂谈和副本能否共用一套一致的时间与状态规则。
