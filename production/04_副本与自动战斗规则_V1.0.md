## 1. 副本在第一阶段的位置

**【已确认】** 对应 `02` 的 P6（组队）→ P7（副本推进与自动战斗）→ P8（结算与结果回流）→ P9（回到村庄）；开发计划 M5 / M6 / M7。

**【已确认】** **副本是核心玩法，不是可选扩展。** 基线 §8.1 开发者原话「通过派发任务让英雄去攻略副本」；基线 §2.3 已把副本攻略从 V1.0 的推迟状态纠正为核心系统。

**【已确认】** 第一阶段必须交付**一个**副本（开发计划 M5；`05` §3.5）。

**【已确认】** 副本**不应只是一个与村庄无关的战斗界面**：至少要有一条真实、可验证的结果路径回到英雄生活或村庄经营（核心循环 §3 阶段 F；`05` §6）。本文用 `Settlement` 作为这条路径的**唯一执行者**（§6）。

## 2. 副本的静态定义与运行时实例

### 2.1 拆成两份模型

**【已确认】** 静态定义描述「这种东西是什么」，运行时状态描述「这个实例当前怎么样」，**运行时变化不得写回静态定义**（基线 §13.6；`05` §2.5）。→ 不变量 I7。

| 静态定义 `DungeonDefinition` | 运行时实例 `DungeonRun`（`05` §3.5） |
|---|---|
| 副本名、描述、入口标识 | `Id` |
| 阶段序列（见 §3） | 副本定义 ID |
| 最终目标（见 §3.4） | 进入的任务 ID |
| 失败条件（**取值属【待定】**） | 参与英雄 ID **快照** |
| 产出规则引用（**数值属【待定】**） | 当前阶段序号 |
| 预计耗时（**属【待定】**） | 状态（未进入 / 进行中 / 已完成 / 已失败） |
| — | **结算是否已应用**标志 |
| — | 关联的战斗结果 ID（至多一个） |

**【建议】** `DungeonDefinition` 是内容期产物、第一阶段只读；`DungeonRun` 是存档边界内的运行时实体。

### 2.2 五要素 → 字段映射

**【已确认】** 副本必须具备**明确入口、多个遭遇或阶段、最终目标、结算与奖励**；**至少两个阶段**（单场遭遇不算副本）（基线 §8.2）。这五项在本文的落点如下：

| 基线 §8.2 要素 | 本文的落点 | 状态 |
|---|---|---|
| **入口** | `DungeonDefinition.入口标识` + `DungeonRun` 由任务派遣成功创建（`05` §3.5） | 【已确认】落点；入口的**具体形态属【待定】** |
| **阶段** | `DungeonDefinition.阶段序列`，长度 ≥ 2 | 【已确认】不少于两个；**阶段数量属【待定】** |
| **最终目标** | `DungeonDefinition.最终目标` | 【已确认】必须存在；**判定规则属【待定】** |
| **结算** | `Settlement`（§6） | 【已确认】幂等且原子 |
| **奖励** | `Settlement` 写入的产出增量 | 【已确认】产出**描述**在 `BattleResult` 中；**数值属【待定】** |

**【已确认】** 「入口可达且到达方式可被玩家观察」（基线 §8.2）要求入口必须是**表现层可读的状态**，不能只是一个布尔值。

### 2.3 参与英雄是快照

**【已确认】** `DungeonRun` 的参与英雄 ID 是**进入时快照，不随英雄后续状态变化**（`05` §3.5）。

**【已确认】** 理由（`05` §3.5）：结算与战斗结果必须对应「谁去了」，而不是「读档瞬间谁还在队伍里」，否则读档后重放结算会算出与当时不同的结果。

**【已确认】** **不允许通过「读到当前队伍」反推成员**（`05` §4.2 引用表：队伍 → 成员英雄 行的「同上」）。

## 3. 副本实例生命周期

### 3.1 六个步骤

**【建议】** `DungeonRun` 的生命周期分六步。**每一步都有明确的进入条件与可观察结果**，以便 `06` 逐条写断言。

```text
L1 待触发   →  L2 进入   →  L3 阶段推进  →  L4 结束判定  →  L5 结算  →  L6 终态化
（可被看见）  （占用英雄）  （循环直到终态） （完成 / 失败）  （只做一次） （释放占用）
```

| 步 | 触发者 | 做什么 | 状态变化 |
|---|---|---|---|
| **L1 待触发** | 队伍与任务模块 | 玩家选择可攻略的副本入口，看到入口信息与可派遣英雄 | `Mission` 存在且状态为「进行中」；**`DungeonRun` 尚未创建** |
| **L2 进入** | 队伍与任务模块 → 副本与战斗模块 | 合法性检查通过后创建 `DungeonRun`，写入参与英雄快照 | `DungeonRun` 状态 `未进入 → 进行中`；当前阶段序号 = 首阶段；参战英雄所在活动 = 「队伍任务中」 |
| **L3 阶段推进** | 副本与战斗模块 | 按 §4 逐阶段推进，每个战斗阶段调用一次战斗规则接口 | 当前阶段序号递增；英雄所在活动**保持**「队伍任务中」 |
| **L4 结束判定** | 副本与战斗模块 | 最终目标达成 → 完成；失败条件触发 → 失败 | 状态 `进行中 → 已完成` 或 `已失败` |
| **L5 结算** | 结算与回流模块 | 按 §6 执行**一次**结算，成功与失败都执行 | 「结算是否已应用」= 真 |
| **L6 终态化** | 队伍与任务模块 + 英雄模块 | 释放占用，参战英雄归位 | `Mission` 终态化；英雄所在活动转回日常；恢复可被编队 |

**【已确认】** **L4 失败也是一次正常结算**（`02` §5.2 F-04）：仍至多一个 `BattleResult`、一次结算。

**【待定】** 副本的**失败条件**本身 → `07` **T-004**（`02` §5.2 已登记「失败条件属【待定】（`04`）」）。

**【待定】** **副本失败时是否给予任何奖励** → `07` **T-004**（`02` §5.2 明确本文只规定「失败也是一次正常结算」，不规定给不给奖励）。

### 3.2 状态迁移表

**【建议】** `DungeonRun.状态` 只有四个取值（`05` §3.5 已固定）。合法迁移如下，**表外的任何迁移都是缺陷**：

| 从 | 到 | 允许条件 |
|---|---|---|
| （不存在） | 未进入 | 创建副本实例 |
| 未进入 | 进行中 | 任务派遣成功、合法性检查通过（L2） |
| 进行中 | 进行中 | 阶段推进（L3）；**结算标志必须仍为假** |
| 进行中 | 已完成 | 最终目标达成（L4） |
| 进行中 | 已失败 | 失败条件触发（L4） |
| 已完成 | 已完成 | **终态，不可再迁移** |
| 已失败 | 已失败 | **终态，不可再迁移** |

**【已确认】** **已结束的任务不会回到「进行中」**（不变量 I14；基线 §13.7 明列「已完成事件重新进入进行中」）。

**【已确认】** 加载一份已结束任务的存档，断言加载后其状态**仍为已结束**（`05` §5.2 I14 的断言形式）。

**【建议】** 对 `进行中 → 进行中` 的迁移加一条约束：**「结算是否已应用」为真时不得再推进阶段**。理由：一个已经结算过的副本实例不应继续产生新的战斗结果（否则违反不变量 I3）。

### 3.3 非法迁移与终止条件

**【已确认】** 「引用断了」的处理方式只有三种，且必须显式选一种：**拒绝命令**（运行期）、**校验失败**（加载期）、**记录并继续**（仅限已声明可丢失的事件负载，**杂谈与战斗日志不适用**）（`05` §4.2）。**没有第四种「静默丢弃」。**

**【建议】** 副本侧的对应落点：

| 情形 | 处理方式 | 依据 |
|---|---|---|
| 对已终态的 `DungeonRun` 再次调用推进阶段 | **拒绝命令**，不改变任何字段 | `05` §4.2 拒绝命令 |
| 对「结算已应用」的实例再次结算 | **返回「已结算」且不做任何写入** | 不变量 I4；`02` P8 步骤 2 |
| 加载时状态为已结束但**没有**关联的 `BattleResult` | **校验失败并给出可理解报错**，不做部分恢复 | `05` §4.2 引用表「结束却没有结果」；不变量 I11 |
| 加载时参与英雄 ID 解析不到 | **校验失败** | `05` §4.2；基线 §13.7 明列「任务参与者丢失」 |
| 战斗中某英雄死亡 | **不终止副本**；复活，**无任何代价** | 基线 §4.6；不变量 I6；`02` F-06 |

### 3.4 最终目标

**【已确认】** 基线 §8.2 要求副本在「阶段之外还有一个明确的完成条件」。

**【建议】** `DungeonDefinition.最终目标` 是一个**判定描述**，其判定由战斗规则接口的胜负判定插件给出（§5.4 插件 1）。

**【待定】** 最终目标的**具体形式**（清空某目标 / 存活到达 / 达成某条件）与判定规则 → `07` **T-004**。

**【待定】** 核心循环 §8 第 12 项「副本结构：单场战斗、连续房间或其他形式」**仍未定**；本文按基线 §8.2 的硬约束（≥2 阶段 + 最终目标）给出结构，但**不指定**结构是「连续房间」还是其他形态。

## 4. 阶段模型

### 4.1 阶段不单独建实体

**【已确认】** **阶段不单独建实体**（`05` §3.5）。第一阶段的阶段是副本实例内的一段状态（`当前阶段序号`），不是被别的实体引用的对象。

**【建议】** 升级触发条件（写下来是为了让后来者知道什么时候该改）：若阶段将来需要被**单独引用**（例如「关卡图鉴」「试炼塔的阶段记录」），再升级为独立实体。理由：升级成本远低于提前拆错的成本（`05` §3.5）。

### 4.2 阶段定义的字段

**【建议】** `DungeonDefinition.阶段序列` 的每一项（一个 `PhaseSpec`）包含以下**结构**字段。**所有取值一律【待定】**；本文只固定**字段的存在与类型**，不填内容。

| 字段 | 类型 | 含义 | 取值状态 |
|---|---|---|---|
| `PhaseId` | string | 阶段标识（稳定，被存档引用） | 【建议】必填 |
| `序号` | int | 在序列中的位置，从 0 起 | 【建议】必填 |
| `进入条件` | 判定表达式 | 上一阶段完成后是否可进入 | 【待定】结构与取值 |
| `敌方构成` | 引用列表 | 本阶段的敌方定义引用 | 【待定】 |
| `战斗规则覆盖` | 插件覆盖集合 | 本阶段对默认战斗规则的覆盖项（§5.4） | 【建议】可为空 |
| `完成条件` | 判定表达式 | 本阶段何时算打完 | 【待定】 |
| `非战斗耗时` | 时间量 | 本阶段不战斗的部分占用多少模拟时间 | 【待定】T-001 / T-002 |

**【已确认】** `非战斗耗时` 的**取值**属 `07` T-001（模拟时间推进）与 T-002（行动耗时）；本文只固定「阶段可能包含不战斗的耗时」这一结构位。

### 4.3 阶段之间英雄做什么

**【已确认】** 副本进行期间，**参战英雄的「当前所在活动」保持「队伍任务中」**（`02` P7 状态怎么变；`05` §3.2）。

**【已确认】** **参战英雄不执行日常行为**（D-006 约束）。

**【已确认】** 副本进行期间，**未随队的英雄照常执行自主行为，模拟时间继续推进**（D-006；`02` P9「未参与副本的英雄仍在继续生活」）。

**【建议】** 因此副本期间村庄循环不冻结，且**参战英雄不可被编入第二个任务**（`02` §5.5 选项 (a)，D-006 已采纳）。这与不变量 I2 直接兼容。

**【已确认】** 「副本期间随队英雄是否推进疲劳」属 `07` **T-003**，**第一阶段不实现**（`07` T-003「不得实现」）。本文因此**不出现任何疲劳字段**。

### 4.4 阶段间的状态流转

**【建议】** 一次阶段推进（`进行中 → 进行中`）的字段变化固定为三条：

| 字段 | 变化 | 说明 |
|---|---|---|
| `当前阶段序号` | +1（进入首阶段时置为首阶段序号） | 唯一写者是副本与战斗模块（`05` §3.5） |
| `BattleResult` | **不变** | 不变量 I3：一个副本实例**至多一个**战斗结果（`05` §5.1 I3） |
| 参战英雄快照 | **不变** | §2.3：进入时快照 |

**【已确认】** **每个副本实例至多一个 `BattleResult`**（`05` §3.6；不变量 I3）。

**【建议】** 因此 `BattleResult` 的创建时机是 **L4 结束判定**（一次），而不是每个阶段一次。**中间阶段的过程记录进入战斗日志**（§7），不进入 `BattleResult`。

**【建议】** 这一条是为了满足不变量 I3 而做的结构性选择：若要「每阶段一个 `BattleResult`」，就必须同步修改 `05` §3.6 与不变量 I3——**本文不擅自做这个修改**。

## 5. 战斗规则接口

### 5.1 契约

**【建议】** 战斗规则是一个**接口**，不是一个方法集。理由：战斗公式整体属 `07` **T-004**，尚未定案；但**接口形状必须先定死**，否则 M5 会把接口长成某个具体公式的形状，T-004 定案时就要改调用方。

**【建议】** 契约（伪签名，非实现代码）：

```text
战斗规则.Resolve(战斗输入) -> 战斗结果

输入 BattleInput =
    副本实例 Id
    阶段 Id                       ← 当前推进的阶段
    参与英雄 ID 快照               ← 快照，不是「当前队伍」（§2.3）
    队伍配置快照                   ← 成员、装备引用、补给引用
    敌方构成引用                   ← 来自 PhaseSpec
    随机种子                       ← 由调用方注入（§5.5）
    规则覆盖集合                   ← 来自 PhaseSpec，可为空

输出 BattleResult =              ← 05 §3.6，创建后不可修改
    结果（成功 / 失败）
    参与英雄 ID 快照
    产出清单的描述（种类引用；数值【待定】）
    战斗日志（§7）
```

**【已确认】** 输出即 `BattleResult`，由副本与战斗模块创建，**每个副本实例至多一个**，**创建后不可修改**（`05` §3.6）。

**【已确认】** 任何修正通过**创建新结果 + 显式替换并记录原因**（`05` §3.6）。

### 5.2 玩家影响结果的四个通道

**【已确认】** 战斗**全自动**，玩家不直接操控英雄进行即时攻击；玩家通过**队伍配置、装备、补给、任务选择**影响结果（基线 §8.3）。

**【建议】** 这四项在输入里的落点：

| 基线 §8.3 通道 | 输入字段 | 第一阶段状态 |
|---|---|---|
| 队伍配置 | 参与英雄 ID 快照 + 队伍配置快照 | 【已确认】可用；**人数上限、职业定位、职业条件属【待定】**（核心循环 §3 阶段 E；`07` D-002 已裁定 `squad_max: 4` 不构成本基线的任何部分） |
| 装备 | 队伍配置快照中的装备引用 | 【待定】**第一阶段不实现装备数值体系**（开发计划 §六）。字段位保留、取值列表为空 |
| 补给 | 队伍配置快照中的补给引用 | 【待定】同上 |
| 任务选择 | 副本定义 ID + 阶段序列 | 【已确认】可用 |

**【已确认】** **玩家决定队伍组成，不等于直接操纵战斗中的每一步**（`05` §3.4）。

### 5.3 战斗期间村庄侧发生什么

**【已确认】** **副本与战斗模块不直接写村庄资源与英雄持有物**（`05` §2.3；`02` P7）。那属于结算与回流模块（§6）。

**【已确认】** 战斗应**可在地图上观察**，而不是切换到独立战斗场景（基线 §8.3）。

**【已确认】** 表现层通过**只读查询或订阅领域事件**刷新显示，**不回写**领域（基线 §13.5；`05` §2.4 第三条通道）。

### 5.4 可插拔点

**【建议】** 战斗规则内部拆成**七个可插拔点**。每个点的默认实现与替换条件如下。**每一个点的取值当前全部【待定】（T-004）**；本文只固定「它是一个可以被替换的接口，不是一个写死的分支」。

| # | 插拔点 | 回答什么 | 替换它的后果 | 当前状态 |
|---|---|---|---|---|
| **1** | **胜负判定** | 这一场是赢是输 | 换掉「全歼 / 达成目标 / 到达上限」三者的优先级 | 【待定】T-004 |
| **2** | **伤害结算** | 一次攻击造成多少 | 整个战斗的数值基座 | 【待定】T-004 |
| **3** | **命中判定** | 这次攻击是否生效 | 决定「伤害公式的输出」是否被应用 | 【待定】T-004 |
| **4** | **冷却与行动选择** | 谁在什么时候行动 | 决定战斗节奏与 AI 目标选择 | 【待定】T-004 |
| **5** | **状态效果** | 状态如何施加与结算 | 引入减益 / 增益 / 控制类规则 | 【待定】T-004 |
| **6** | **产出与掉落** | 产出清单怎么得到 | 唯一能改 `BattleResult` 产出描述的插件 | 【待定】T-004 |
| **7** | **阶段耗时** | 一次战斗 / 一个阶段占用多少模拟时间 | 与 `03` 的模拟时间规则对接 | 【待定】T-001 / T-002 |

**【建议】** **插件 1–6 的组合就是「战斗公式」**，因此它们**一起**由 `07` T-004 裁决；不允许只定其中一两个就开工，因为缺一个会让其余的取值失去参照系。

**【建议】** **插件 7 不属于 T-004**，它属于时间规则。T-004 定案不应被它阻塞。

**【建议】** **阶段覆盖**（`PhaseSpec.战斗规则覆盖`）让不同阶段可以替换插件而不必整份副本换一套规则。这是本文唯一建议的「按阶段差异化」机制，**具体可覆盖哪些插件属【待定】**。

### 5.5 随机数注入

**【已确认】** **随机种子由调用方注入**，不由战斗规则内部自建随机源。

**【已确认】** 理由一：`05` §5.1 I9 要求领域层可脱离 Godot 编译并运行全部规则层测试；自建 `static Random` 会破坏确定性（`07` 架构债 A7 已点名 4 个未播种的 `static readonly Random`）。

**【已确认】** 理由二：基线 §14.2 要求涉及随机性的系统**使用固定种子**；基线 §8.5 D3 要求「固定副本参数与随机种子」。

**【待定】** **存档是否保存随机数状态** → `07` **T-007**（基线 §13.7 / 待确认清单 #24）。

**【已确认】** 第一版对 T-007 的**最低要求**：存档读档后**不得重复发奖或重复结算**（基线 §13.7 原文）。

**【建议】** 因此 §6 的幂等**不依赖** RNG 状态能否恢复——它依赖 `DungeonRun.结算是否已应用` 这个显式落盘标志（§6.3）。这两件事是解耦的，**不要把幂等的正确性押在 T-007 上**。

### 5.6 公式的形状（取值全部【待定】）

**【已确认】** **以下不是规则，是给 T-004 预留的填空骨架。** 变量名与变量之间的关系是【建议】；**所有取值范围一律【待定】，由 `07` T-004 填写。本文不填。**

**F-1 伤害**

```text
damage = f(attacker_stats, defender_stats, attack_input, rule_params)
```

| 符号 | 类型 | 范围 | 描述 |
|---|---|---|---|
| `attacker_stats` | 集合 | 【待定】 | 攻击方的战斗属性集合 |
| `defender_stats` | 集合 | 【待定】 | 防守方的战斗属性集合 |
| `attack_input` | 集合 | 【待定】 | 攻击动作的输入（招式、目标、附加状态） |
| `rule_params` | 集合 | 【待定】T-004 | 规则参数 |
| `damage` | float | 【待定】；**下限建议不小于 0**，否则出现「负伤害」这类系统无法使用的取值 | 本次攻击造成的伤害 |

**【建议】** 输出范围的边界是**必须由 T-004 显式裁决**的一项：`damage` 的下限是否为 0、上限是否封顶、溢出如何处理。

**F-2 命中**

```text
hit = HitCheck(attacker_stats, defender_stats, rule_params) -> bool
```

| 符号 | 类型 | 范围 | 描述 |
|---|---|---|---|
| `hit` | bool | {true, false} | 本次攻击是否生效 |

**【建议】** `hit` 与 `damage` **必须是两个独立插件**（插拔点 2 与 3），不得合成一个函数——基线 §8.3 把「命中」与「伤害」并列为两项待定规则。

**F-3 冷却与行动**

```text
next_action_time(actor) = current_time + Cooldown(actor_stats, action_input, rule_params)
```

| 符号 | 类型 | 范围 | 描述 |
|---|---|---|---|
| `next_action_time` | 时间量 | ≥ `current_time`（单调不回退） | 下一次行动的时刻 |
| `current_time` | 时间量 | 单调不回退 | 引用自 `SimClock`（`05` §3.9） |

**F-4 产出**

```text
loot = LootResolve(stage_spec, battle_outcome, loot_params)
```

| 符号 | 类型 | 范围 | 描述 |
|---|---|---|---|
| `loot` | 清单 | 长度 ≥ 0；**允许为空** | 产出清单（种类引用；数值【待定】） |
| `battle_outcome` | 枚举 | {成功, 失败} | 本次战斗结果 |

**【已确认】** **产出清单允许为空**，此时是**合法的零增量结算**（`02` §5.2 F-05）：照常写「结算已应用」标志，发事件，不产生部分入账。

**【已确认】** 「奖励内容与数值」（核心循环 §8 第 13 项）→ `07` **T-004**。

### 5.7 死亡在战斗中的处理

**【已确认】** **英雄死亡后复活，不附加死亡代价**（基线 §4.6）。逐条落实：

| 问题 | 答案 | 依据 |
|---|---|---|
| 有永久死亡吗 | **没有** | 基线 §4.6 |
| 有战力 / 等级损失吗 | **没有** | 基线 §4.6 |
| 有时间惩罚吗 | **没有** | 基线 §4.6 |
| 有装备 / 物品损失吗 | **没有** | 基线 §4.6 |
| 有关系恶化吗 | **没有**（除非 §9 行为链本身导致，属独立事件） | 基线 §4.6 |

**【已确认】** 断言形式（不变量 I6，`05` §5.1）：死亡前后英雄的**属性、持有物、关系、可用性完全一致**；**不存在**表示永久损失的状态字段。

**【已确认】** 因此 `Hero` 实体**没有**「永久死亡」「不可用」「装备损毁」这类状态（`05` §3.2）。

**【已确认】** `05` §7 把「死亡代价相关的任何字段」列为**永不建模**——「**建模它本身就是违规**」。

**【建议】** 因此战斗规则接口的输出里**不得**出现「英雄永久失效」「英雄损毁」这类字段；死亡在战斗过程内的表现属表现层演出，领域侧只发一条领域事件。

**【已确认】** **不得为制造难度而重新加入死亡惩罚**（基线 §4.6 设计说明）。

## 6. 结算（`Settlement`）

### 6.1 定位与唯一执行者

**【已确认】** `Settlement` 是**副本结果回到村庄与英雄的唯一执行者**（`05` §6）。

**【已确认】** **副本与战斗模块不直接写村庄资源与英雄持有物**（`05` §2.3）。

**【建议】** 因此在模型上，**绕过 `Settlement` 无法改变村庄资源或英雄持有物**——这不是纪律要求，而是模块边界带来的结果（不变量 I10）。

### 6.2 两条性质：幂等 + 原子

**【已确认】** **不变量 I4 · 结算只能被应用一次。**

> 断言形式（`05` §5.1）：对同一 `DungeonRun` 连续调用两次结算，断言资源 / 持有物 / 英雄状态的**增量第二次为零**；结算前后存读档再断言一次。

**【已确认】** **不变量 I15 · 结算要么完整应用，要么不应用。**

> 断言形式（`05` §5.2）：断言结算中途失败时，村庄资源与英雄持有物的**总增量要么全为 0，要么等于结算结果给出的完整增量**，**不存在部分入账**。

**【已确认】** **产出引用失效时明确报错，不发一半奖**（`05` §4.2 引用表）。

### 6.3 幂等标志：存在哪、怎么落盘

**【已确认】** 幂等标志**内含在 `DungeonRun` 上**，字段名沿用 `05` §3.5 的**「结算是否已应用」**（`05` §2.6 的存档边界列举中，它属于必须显式落盘的一类）。

**【已确认】** **该标志必须显式落盘，不能靠读档后重新推算**（`02` P8；`05` §2.6；基线 §13.7「重复发放奖励」）。

**【已确认】** **副本实例 → 「结算已应用」标志** 的引用类型是**内含**；「引用断了」的后果是：**读档后该标志必须恢复为真，否则会重复发奖**（`05` §4.2 引用表）。

**【已确认】** 因此 `02` §5.3 的 **F-11（读档后结算标志丢失）** 属于「**此情形不应发生；若发生即为缺陷**」。

**【建议】** 落盘位置与时序：

| 项 | 内容 |
|---|---|
| 存什么 | `DungeonRun` 的「结算是否已应用」布尔值 + 关联的 `BattleResult` ID |
| 存哪 | 数据与存档层的 `DungeonRun` DTO（显式 DTO + 版本号，**不直接序列化场景树**；基线 §13.7） |
| 何时写 | **在结算的全部写入完成之后**写（§6.4 的顺序） |
| 写盘方式 | 临时文件写入后再替换正式存档；保留上一份有效存档（基线 §13.7） |
| 加载时 | 先解析 DTO、校验 ID 与引用，再恢复运行时状态（不变量 I11） |

**【建议】** **标志与 `BattleResult` ID 必须一起落盘**。只存布尔值会在「结果已应用但结果引用丢失」时无法追溯；只存 ID 会在零增量结算（F-05）下无法区分「已结算」与「尚未结算」。

### 6.4 执行顺序：先算 → 全量应用 → 最后落标志

**【建议】** 结算分四步，**顺序不可调换**：

```text
① 检查「结算是否已应用」
      ├─ 真  → 立即返回「已结算」，不做任何写入（幂等）
      └─ 假  → ②
② 读取 BattleResult（不可变），算出**完整的增量清单**
      └─ 产出引用失效 → 明确报错并中止，**零写入**（不发一半奖）
③ 由各模块**分别写入**：资源 → 村庄与建筑模块；持有物 / 状态 → 英雄模块
      └─ 写「结算是否已应用」标志与结果引用（结算与回流模块是这两项的唯一写者，05 §3.5）
④ 发领域事件 → 杂谈模块生成条目
```

**【已确认】** 第 ③ 步中「由拥有该数据的模块分别写入」，结算与回流模块**只写「结算已应用」标志与结果引用**（`02` P8 步骤 4；`05` §3.5 唯一写者列）。

**【已确认】** 这满足不变量 I10：**跨模块的状态改变只经由拥有该数据的模块**（`05` §5.1）。

**【建议】** **「先算全量、再应用」是 I15 的实现方式**：只要增量清单在写入之前已经完整算好，任何一步失败都还没有产生任何入账；反之若边算边写，失败就会留下部分入账。

**【待定】** 「应用」本身**如何做到中途失败不留部分入账**（先算后写已排除大部分，但若单次写入内部失败仍需策略）→ 建议作为 `06` 的一个实现级待确认点登记，本文只给约束不给方案。

### 6.5 失败与边界情形

| # | 情形 | 系统行为 | 依据 |
|---|---|---|---|
| **F-04** | 副本失败 | `DungeonRun.状态 = 已失败`；**结算照常执行一次**（结果为失败）；仍至多一个 `BattleResult` | `02` §5.2；不变量 I3 / I4 |
| **F-05** | 产出清单为空 | 视为**合法的零增量结算**：照常写标志、发事件，不产生部分入账 | `02` §5.2；不变量 I15 |
| **F-06** | 英雄在副本中死亡 | **复活，无任何代价**；**不终止副本** | 基线 §4.6；不变量 I6 |
| **F-07** | 对同一 `DungeonRun` 连续调用两次结算 | 第二次**增量全为零** | 不变量 I4 |
| — | 产出引用失效 | **明确报错并中止，零写入**；**不发一半奖** | `05` §4.2；不变量 I15 |
| — | 加载时已结束但无 `BattleResult` | **校验失败**，不做部分恢复 | `05` §4.2；不变量 I11 |
| — | 加载时参与英雄解析不到 | **校验失败** | 基线 §13.7「任务参与者丢失」 |

**【待定】** **失败是否给予任何奖励** → `07` **T-004**（`02` §5.2 明确此项属 `04`，本文不代答）。

### 6.6 结算产生的领域事件与杂谈

**【已确认】** 结算完成后发领域事件（`02` P8 步骤 5），由杂谈模块生成条目（`02` P8；`05` §3.8）。

**【已确认】** **每条杂谈条目必须指向一个已存在的事件 ID**，同一事件 ID 至多一条（不变量 I5；基线 §7.4 C1 + C2）。

**【已确认】** 「英雄**首次**完成副本」是基线 §7.2 点名的杂谈触发条件之一。

**【已确认】** `05` §3.2 的 `Hero` 持有「首次完成副本的标记」，它是这条触发条件的状态载体。

**【已确认】** 杂谈**根据已发生的事件生成消息**，而不是每隔几秒随机生成文本（基线 §7.2）。

**【已确认】** 杂谈**只是一个功能，一个文字面板**，不是叙事主干（基线 §7.1）。

**【建议】** 结算失败（F-04）**是否**产生一条杂谈条目属**杂谈模块的判定**，本文不规定——但**领域事件必须发**，否则 C1 无法满足。

## 7. 战斗日志（基线 §8.5 · D5）

### 7.1 要求

**【已确认】** **战斗日志要能复现胜负判定所引用的每一个关键事件**（基线 §8.5 验收项 D5；`05` §3.6）。

**【已确认】** 战斗**必须可读**——玩家应能看清**谁为什么赢、谁为什么输**（基线 §8.3）。

**【建议】** D5 是**可机械执行的断言**，不是观感条目。它的可执行形式是：把日志里被胜负判定引用的每一条关键事件取出来，断言每一条都能对应到日志中的一条记录，且**没有**胜负判定引用了日志中不存在的记录。

### 7.2 日志条目结构

**【建议】** `BattleLogEntry` 的字段（**结构为【建议】，取值为【待定】**）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `序号` | int | 在本次战斗内的单调序号 |
| `模拟时间` | 时间量 | 发生时刻，引用 `SimClock` |
| `阶段Id` | string | 发生在哪个阶段 |
| `类型` | 枚举 | 可扩展注册表（§7.4） |
| `参与者` | 实体 ID 列表 | 谁参与了这次事件 |
| `目标` | 实体 ID | 事件的对象 |
| `输入` | 载荷 | **该次判定实际使用的输入快照** |
| `输出` | 载荷 | **该次判定实际给出的结果** |
| `是否为胜负判定所引用` | bool | **D5 的机器可读依据** |

**【建议】** `输入` / `输出` 两栏是 D5 能成立的关键：只记「发生了什么」不足以复现判定，必须记**判定当时的输入与输出**。

**【待定】** 日志条目的**容量上限 / 保留条数 / 体积** → 建议登记为 `06` 的实现级待确认点（本文不预设）。

### 7.3 日志不可修改、随存档走

**【已确认】** 战斗日志**不适用**「记录并继续」这种引用断了的处理方式（`05` §4.2 明确「杂谈与战斗日志不适用」）。

**【已确认】** 战斗日志**不可修改**（`05` §3.6 的 `BattleResult` 创建后不可修改，日志是 `BattleResult` 的组成部分）。

**【已确认】** 战斗日志属于**存档边界内**（`05` §2.6 列举了「战斗结果」）。

**【建议】** 因此日志条目与 `BattleResult` 一同落盘；读档后仍可用于展示与复现。

### 7.4 日志类型是可扩展注册表

**【已确认】** 领域事件类型是一个**可扩展的注册表**：第一阶段只注册第一阶段会产生的类型（`05` §3.7）。

**【已确认】** 基线 §11.1 的要求「**新增事件不得要求重写核心世界循环**」适用于战斗日志类型（`05` §3.7 已按此推导）。

**【建议】** 第一版日志类型**至少**覆盖：阶段开始 / 阶段结束 / 单次攻击 / 状态施加 / 状态结算 / 单位死亡 / 单位复活 / 胜负判定。**类型清单属【待定】**，取决于 T-004 引入哪些状态效果。

**【已确认】** **不记录系统内部状态变化**（基线 §7.3 杂谈的「不记什么」；战斗日志同理——它记判定依据，不是数值波动流水账）。

### 7.5 与杂谈的分工

**【已确认】** 战斗日志与杂谈是**两件不同的事**：

| | 战斗日志 | 杂谈条目 |
|---|---|---|
| 目的 | **复现胜负判定**（D5） | 让玩家了解英雄做了什么 |
| 读者 | 玩家（战斗可读性）+ 开发者（复现与测试） | 玩家（文字面板） |
| 来源 | `BattleResult` 的组成部分 | 领域事件（`05` §3.8） |
| 触发 | 战斗中每一个被判定引用的关键事件 | 杂谈模块判定「值得记」的事件 |

**【建议】** **战斗日志不直接生成杂谈条目**。杂谈的来源**必须**是领域事件（不变量 I5 要求每条杂谈指向一个已存在的事件 ID）。战斗产生领域事件 → 杂谈模块判定 → 条目。
